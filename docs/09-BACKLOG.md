## 1-2. ★ UI 다듬기 (Phase 7)

> ★ 분류 기준은 [07-DECISIONS.md](07-DECISIONS.md) D-031 이다.

## 1-3. ★★ 스크롤 없이 한 화면 (Phase 7)

> ★ 건우 지시 (R015, **접수만**): "**스크롤 없이 한 화면에 모든 요소가 다 보여야 한다.
> 스크롤 있으면 굉장히 조잡하다.**" / "**일단은 웹 UI 가 우선이다. 모바일은 천천히 생각해보자.**"
>
> ★★ **지금 구현하지 않는다.** 다만 요소 목록과 우선순위를 지금 정리해 두고,
> ★ **Phase 5·6 에서 화면 요소가 늘어날 때마다 이 표를 갱신한다.**

### ★ 현재 실측 (R015 / ui-check 자동 측정)

| 폭 | 문서 높이 | 뷰포트 | 초과 |
|----|----------|--------|------|
| 320px | 1,708px | 1,165px | ★ **1.47배** |
| 720px | 1,498px | 900px | ★ **1.66배** |

★ 즉 게임 화면이 한 화면에 들어오지 않는다. 목표는 이 비율을 1.0 이하로 만드는 것이다.
★ 이 값은 ui-check 가 매 실행마다 콘솔에 남긴다 (`문제 화면 높이`). 갱신할 때 근거로 쓴다.

### ★★ 게임 화면 요소와 우선순위

★ 분류 기준: **30초 안에 승부가 갈리는 동안 눈이 반드시 가야 하는 것**이 최우선이다.

| 순위 | 요소 | 지금 어디 | 판단 |
|------|------|----------|------|
| **1** | 문제 지문 | 상단 | ★★ 절대 접거나 줄이지 않는다 |
| **1** | 남은 시간 | 지문 아래 | ★★ 정수 초 (Q-83). 항상 보인다 |
| **1** | 채팅 입력창 | 하단 | ★★ **답안 입력창이다.** 항상 보이고 포커스가 있어야 한다 |
| **2** | 채팅 로그 | 입력창 위 | ★ 최근 몇 줄만 보이면 된다. 높이를 고정하고 내부 스크롤로 |
| **2** | 힌트 / 정답 공개 | 지문 아래 | ★ 나타났다 사라지는 영역. 자리를 미리 비워 두면 흔들리지 않는다 |
| **3** | 점수판 | 중단 | ★ 접기 후보. 10명이면 길다. "상위 3명 + 나" 로 줄이는 안 |
| **3** | 스킵 카드 | 중단 | ★ 투표 수만 한 줄로 줄이는 안. 버튼은 단축키(`Alt+S`)로 대체 가능 |
| **3** | 방장 카드 | 중단 | ★ 단축키(`Alt+K` / `Alt+Q`)가 있으므로 접어도 조작 가능 |
| **4** | 단축키 바 | 입력창 아래 | ★ 접힌 상태는 한 줄. `Alt+G` 로 펼침 (이미 이렇게 만들었다) |
| **4** | 상단 방 정보 (제목·인원·상태·나가기) | 최상단 | ★ 한 줄로 줄이는 안. 나가기는 `Alt+X` 가 있다 |
| **5** | 도배 억제 안내 | 입력창 위 | ★ 조건부. 나타날 때만 자리를 차지한다 (D-032 로 위치를 정했다) |
| **5** | 문제 출처(라이선스) 안내 | 최하단 | ★★ **게임 중에는 접어도 된다.** 라이선스 고지 의무는 로비·결과 화면에서 충족된다 |
| **5** | 서버 시각 오프셋 / 로그아웃 | 최하단 | ★ 개발 정보다. 게임 중에는 숨기는 안 |

### ★ 일시정지 화면 (R015 추가)

| 순위 | 요소 | 판단 |
|------|------|------|
| **1** | 왜 멈췄는가 / N·M 복귀 | ★ 한 화면 안 |
| **1** | 재개 버튼 (방장) | ★ 한 화면 안 |
| **2** | 멈춘 시점의 남은 시간 | ★ 한 줄 |
| **2** | 방이 사라지기까지 남은 시간 | ★ 한 줄. 돌아올 사람에게 가장 필요한 정보다 |
| **3** | 자동 재개가 없는 이유 설명 | ★ Phase 7 에서 접기 후보 (D-030 때문에 지금은 펼쳐 둔다) |

### ★ 아직 판단하지 않은 것

- **어떻게 줄일 것인가** (접기 / 탭 / 고정 높이 + 내부 스크롤 / 화면 분할) — Phase 7 에서 결정한다
- 결과 화면은 Phase 4 에서 다시 만들므로 그때 이 목록에 추가한다
- ★ 모바일은 뒤로 미룬다 (건우: "웹 UI 가 우선")

## 2. 향후 확장 후보

구조를 지나치게 하드코딩하지 않되, 미래 기능을 위해 지금을 복잡하게 만들지도 않는다. (guide 52절)

| 후보 | 준비된 것 | 추가로 필요한 것 |
|------|----------|-----------------|
| 객관식 | `questions.question_type` 컬럼 | `question_choices` 테이블, 판정 분기, UI |
| 이미지 퀴즈 | — | `media_url` 컬럼(ALTER로 충분), 저장소, UI |
| 초성 퀴즈 | `question_type`, 초성 변환 로직(힌트에 있음) | 판정 규칙, UI |
| 순서 맞히기 | `question_type` | 판정 규칙, UI |
| 팀전 | — | `game_players` 에 팀 컬럼, 점수 집계 변경, UI |
| 카테고리 선택·제외 | `categories` 테이블, `questions.category_id` | 설정 UI, 문제 선정에 필터 추가 |
| 난이도 선택 | `questions.difficulty` | 설정 UI, 선정 필터 |
| 개인 통계 화면 | **원천 데이터 전부 기록 중** | 집계 쿼리와 UI만 |
| 랭킹 | `game_players` | 집계와 UI |
| 힌트 추가 단계 | `generateHint()` | 규칙 확장 |
| 연속 정답 보너스 | `answer_events` | 점수 규칙 변경 |

**통계가 가장 준비가 잘 되어 있다.** guide 40절이 요구한 9종 지표가 현재 스키마로
전부 계산 가능함을 검증했다([03-DATA-MODEL.md](03-DATA-MODEL.md) 5장).
UI만 만들면 된다.

## 4. Track D — 문제 데이터 확보

| 단계 | 소스 | 예상 확보량 | 라이선스 | 상태 |
|------|------|------------|---------|------|
| D1 | OpenTDB | 약 1,100건 | CC BY-SA 4.0 | 조사 완료 |
| D2 | 위키데이터 템플릿 생성 | 수천 건 | CC0 | 미착수 |
| D3 | ETRI 엑소브레인 QA | 약 569건 | 확인 필요 (승인 절차 있음) | 미착수 |
| D4 | 직접 작성 + AI 보조 | 상시 | CC BY-SA 4.0 | 시드 53건 완료 |

**OpenTDB는 유한 코퍼스다.** API 제공분 5,298건(그중 주관식 전환 가능한 multiple 타입 4,500건)이
전부이고 전량 수확을 이미 완료했다. 생존율이 약 25%라 최종 1,100건 정도다.
**더 긁어도 나오지 않는다.**

**위키데이터가 규모 면에서 유일한 해답으로 보인다.** CC0라 라이선스 제약이 없고
구조화 트리플이라 "정답이 유일하게 결정되는" 문제를 우리가 직접 설계할 수 있다.
단조로워지지 않도록 전체의 일부로만 쓴다.
