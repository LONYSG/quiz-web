### 0. 무엇이 바뀌었는가

(2) 다음 소스를 붙일 때의 참조 구현. → 실행만 막았다(`if: inputs.confirm == 'revive-opentdb'`).

### 1. 카테고리 체계 (작업 C)

건우 초안 **대분류 7 / 중분류 48** → 최종 **대분류 7 / 중분류 63 / 소분류 294**.
전부 `pipeline/src/categories.ts` 한 파일에 있고 `enabled: false` 로 끌 수 있다.

★★ **설계 과정에서 나온 가장 중요한 발견** — 건우가 든 반례가 계층 문제가 아니었다.

```
"훈민정음을 만든 왕?"  (한국사 > 조선 전기)
"한글을 창제한 왕?"    (한국 문화유산 > 기록유산)   → 중복인데 검사를 빠져나간다
```

★ 이것은 중분류 검사의 결함이 아니라 **카테고리 목록의 결함**이다.
"한국 문화유산" 이라는 중분류가 있으면 조선 시대 유물 문제는 두 곳에 **합법적으로** 들어간다.
어느 계층에서 검사해도 막을 수 없다.

→ 규칙: **중분류는 하나의 주제 축으로만 나눈다.**
같은 대상을 다른 축(인물 / 유물 / 명작 / 기록)으로 다시 묶는 중분류를 만들지 않는다.

이 규칙으로 초안에서 뺀 것 / 쪼갠 것 / 합친 것 (전체 내역은 R011.txt 3-3)

| 조정 | 대상 | 근거 |
|------|------|------|
| 삭제 | 인물(위인·현대 유명인) | ★ 정답이 인물인 문제는 거의 모든 중분류에서 나온다 |
| 축소 | 건축·유적 → 건축 | 유적 문제는 해당 시대 역사로 보낸다 |
| 분할 | 세계사 → 서양사 / 동양사 / 전쟁·군사사 | 하나로는 소분류가 15개 넘게 필요하다 |
| 분할 | 생물·인체 → 생물학 / 인체·해부 | |
| 분할 | 격투기·기타 종목 → 농구·배구·기타 구기 / 격투기·육상·수영 | ★ "기타" 는 중복 검사 단위로 쓸 수 없다 |
| 흡수 | 단위·측정 → 수학·수 상식의 소분류 | 중복 없이 낼 수 있는 문제가 금방 고갈된다 |
| 병합 | 색·기호·상징 + 교통 표지·생활 규칙 → 기호·상징·표지 | 같은 지식 유형이고 각각 너무 좁았다 |
| 추가 | ★ 세계 문학 | **초안의 가장 큰 누락.** 한국 문학만 있었다 |
| 추가 | 만화·웹툰 / 음악 이론·악기 / 공연·연극·뮤지컬 / 에너지·환경 / 재료·건설 / 의복·패션 / 반려동물·원예 | "넓을수록 좋다" 지시 |

### 2. 중복 판정 — ★ 실측이 내 설계의 한 부분을 반박했다

3단계 설계: 정답으로 후보 추리기 → 카테고리로 의심 강도 → 질문 유사도로 최종 구분.

★ 1단계는 압도적으로 효과가 있었다. **전수 32,896쌍 → 후보 12쌍.**

★★ 그런데 3단계(유사도)는 **의도한 일을 하지 못했다.**

| 실제 중복인 쌍 | 유사도 |
|---|---|
| 토이 스토리 / 베토벤 / 스우시 / 기생충 / 버버리 / 플레밍 | 0.13 ~ 0.50 |
| **실제로 다른 문제** (빵의 어원 / 브라질 공용어 → 포르투갈어) | **0.00** |

모델이 문장을 완전히 바꿔 쓰기 때문에 같은 문제여도 유사도가 0.13까지 내려간다.
★ 0.13과 0.00 사이에 선을 그으면 이 표본(8쌍)에서는 갈리지만 **과적합이다.** 임계값을 손대지 않았다.

★★ 더 중요한 관측 — **정답이 겹치면 카테고리와 무관하게 12쌍 중 11쌍이 진짜 중복이었다.**
그리고 건우 원칙("다른 카테고리 + 같은 정답 → 문제없음")의 반례가 나왔다.

```
world-geo > 대륙·바다  "가장 넓은 대양은?"   → 태평양
earth     > 해양       "가장 넓은 바다는?"   → 태평양     ★ 대분류가 다른데 같은 문제다
theatre   > 연극 고전  vs  world-lit > 시·희곡          ★ 둘 다 햄릿
```

★ 유일한 무해 사례는 오히려 **같은 중분류 안**에 있었다.
→ 결론: 카테고리는 자동 폐기 판단에 쓰지 않는다. **의심 강도(정렬)** 에만 쓴다.
→ 위 반례는 다시 카테고리 목록의 문제다. 경계를 더 좁혀야 한다(건우 판단 항목).

### 4. ★ 프롬프트를 실측으로 한 번 고쳤다 (g1 → g2)

첫 실측에서 탈락 10건 중 **5건이 한 가지 원인**이었다 — `answer_in_question`.

```
"국왕의 권력을 제한한 대헌장의 라틴어 명칭은?" → 마그나 카르타 (answers 에 "대헌장")
"샹파뉴 지역에서 생산되는 발포성 와인은?"     → 샴페인       (answers 에 "샹파뉴")
"방바닥 밑의 구들장을 덥히는 난방 방식은?"     → 온돌         (answers 에 "구들장")
"'목폴라'라고도 불리는 스웨터 형태는?"        → 터틀넥       (answers 에 "목폴라")
```

★ 규칙 검사가 옳았다. 이 게임은 채팅으로 답을 받으므로,
**질문에 적힌 낱말을 그대로 옮겨 치면 아무것도 모르는 사람이 이긴다.**
★ 결함은 규칙이 아니라 생성 쪽에 있었다 → 프롬프트에 실패 예시 4개와 자기 점검 목록을 넣었다.

**결과**: g2 로 다시 돌린 18건에서 `answer_in_question` **0건 / 생존율 100%.**

### 5. ★ 표기 변형 하나 때문에 문제를 버리지 않는다

`answer_shape` 탈락 3건의 원인은 질문도 정답도 아니었다.

```
"애플"          변형에 "Apple Inc."              → 마침표로 끝나 서술형 판정
"오페라의 유령"  변형에 "The Phantom of the Opera" → 단어 5개로 서술형 판정
```

→ `sanitizeVariants()` 를 만들어 **그 변형만 떼어내고 문제는 살린다.**
떼어낸 것은 검수 메모에 남긴다. ★ `displayAnswer` 가 형식에 안 맞으면 걸러내지 않는다 —
그것은 규칙 검사가 잡아야 하고, 여기서 조용히 고치면 검사를 우회하는 셈이 된다.

### 6. 단계별 게이트 (작업 D-5) — ★ 목표를 못 맞췄고, 그대로 적는다

건우의 "모델 여러 개 동시 검수" 대신 **단계별 게이트**를 택했다.
싼 모델로 전량 역검증하고, 애매한 것만 상위 모델로 올린다.

| 지표 | 값 |
|------|-----|
| 1단계에서 끝난 것 | 260/270 (96.3%) |
| 상위 모델 승급 | 10건 (3.7%) |
| 역검증 토큰 | 45,897 (건당 170) |
| ★ 역검증 **호출 수** | **18회.** 게이트 없이 전량 상위 모델이면 11회 → **1.64배** |

★ 목표는 1.2~1.5배였다. **넘겼다.** 원인은 승급 대상이 그룹당 1~2건인데
그것 때문에 호출 하나를 통째로 쓴 것이다.
→ 코드를 고쳤다. 승급을 **실행 끝에 한 번만** 부른다 → 11 + 1 = 12회(1.09배).
★ 이번 샘플은 고치기 전 방식으로 생성되었다.

★ 게이트가 잡아낸 것 — `"'가장자리'를 뜻하는 순우리말은?" → 언저리`
역검증이 "변두리" 라 답하고 "테두리" 를 대안으로 냈다. **진짜 애매한 문제였다.**
★ 이것이 "생성에도 역검증을 유지한다"(건우 지시)의 실증이다.
생성은 원본이 없으므로 모델이 애매한 문제를 **지어낼** 수 있다.

### 7. ★★ 429 가 한 번도 나지 않았다 — 그리고 R010 수치가 왜 틀렸는지 찾았다

**R011 실측 (2026-09-09 UTC 01:08 ~ 01:32)**

| 지표 | 값 |
|------|-----|
| 슬롯 요청 = LLM 도달 | **270** |
| 최종 통과 | **257건 (95.2%)** |
| 중분류 커버 | ★ **63/63 전부** (중분류당 3~5건) |
| API 호출 | 29회 |
| 토큰 | 164,338 (사고 21.0%) |
| 통과 1건당 토큰 | **639** |
| **429** | ★ **0회** |
| 15분 재개 | 0회 (발동하지 않았다) |

★★ R010은 "호출 4회 / 18,236토큰에서 429" 였다. 오늘은 29회 / 164,338토큰에 아무 일도 없었다.
그 차이를 조사해 **내 도구의 결함**을 찾았다.

```
pipeline-models.mjs   생 fetch 를 쓴다        → 상태 파일에 전혀 기록되지 않았다
pipeline-compare.mjs  GeminiClient 를 쓰지만  → saveState 를 부르지 않았다
```

★ R010 때 그날 먼저 `pipeline:models`(후보 5개 × 프로브 2종 × 재시도 최대 3회)와
`pipeline:compare` 를 돌렸다. **그 호출들이 하나도 세어지지 않았다.**
→ "4회 호출에 429" 라는 관측은 실제 소비보다 훨씬 작은 수치였다.
그 수치를 근거로 "한도가 매우 좁다" 고 추정했는데 그 추정의 근거가 부실했다.
→ 둘 다 고쳤다. 이제 프로브 호출도 예산에 센다.

★ 다만 R010의 429 자체는 실재했다. 어제 일을 다시 측정할 수는 없으므로
"프로브 호출이 세어지지 않아 관측치가 작았다" 까지가 **확인된 것**이고,
"그것이 429의 원인이었다" 는 **추정**이다.

### 9. 429 → 15분 대기 → 1회 재개 (작업 A / Q-62 확정 이행)

구현했다. 상태 파일에 **구간(segment)** 을 나눠 기록한다 — 429 사이 각 구간의 건수·토큰·호출.
★ 하루에 몇 번 재개했고 각 구간에서 몇 건을 처리했는지 알 수 있다.

★ **이번에 429 가 나지 않아 재개 경로는 실행되지 않았다.** 코드는 있고 실측은 없다.
그대로 보고한다. 15분이 적절한지도 **판단 근거가 없다** — 그대로 둔다.

★ Actions 시간 제한: 걸리지 않는다. GitHub 호스팅 러너의 작업 최대 실행 시간은 6시간이고
최악의 경우(429 + 15분 대기 + 재개)도 1시간 미만이다. `timeout-minutes: 90` 을 명시했다.
★ 확인 필요: 공개 저장소 표준 러너의 과금 정책. 정책이 바뀌면 대기 방식을 재검토해야 한다.

## 2026-09-08 — 브라우저 확인에서 나온 결함 수정 + 사람 경로 검증 체계 (R008)

### 1. 결함: "게임 시작" 을 눌러도 아무 반응이 없다

**★ 원인은 지시받은 추정과 달랐다.**
지시에는 "클라이언트가 버튼을 disabled 로 만들었을 가능성이 높다" 고 되어 있었다.
코드를 확인한 결과 `disabled` 는 `만들기` / `입장` / 회원가입 제출 버튼에만 있고
**"게임 시작" 에는 없었다.**

실제로는 전부 정상이었다. 버튼이 활성이었고, 클릭이 전달되었고,
서버가 `NOT_ENOUGH_QUESTIONS` 로 옳게 거부했고, 클라이언트가 그 에러를 상태에 저장까지 했다.

**★ 없던 것은 표시 경로 하나다.**
`App.tsx` 가 안내 문구를 화면마다 각자 그리고 있었고,
`{notice && …}` 가 **방이 없는 화면의 return 안에만** 있었다.
로비 화면의 return 에는 없었다.
→ 로비에서 발생하는 **모든** 서버 에러가 보이지 않았다. `NOT_ENOUGH_QUESTIONS` 만의 문제가 아니었다.

**고친 방법 — 개별 수정이 아니라 구조 (D-027)**

1. **셸을 하나만 둔다.** 화면별 `return` 을 없애고 `view` 를 계산해 한 곳에서 렌더한다.
   `<Notice>` 는 화면 종류와 무관하게 항상 같은 자리에 있다.
   ★ Phase 3의 문제 화면을 만들어도 표시를 빼먹을 수 없다
2. **`detail` 을 함께 보여준다.** 실제 숫자와 해야 할 일이 거기 있다
3. **조용히 반환하는 코드를 없앤다.** 빈 방 ID 로 "입장" 을 누르면 무반응이었다
4. **핸들러 예외도 사람에게 알린다.** `guard.ts` 는 로그만 남기고 끝냈다.
   ★ `INTERNAL` 은 그때까지 한 번도 전송되지 않는 코드였다
5. **`BAD_REQUEST` 에 어느 요청인지 담는다.** 받은 값은 담지 않는다

**전수 점검 결과**: 서버 에러 코드 11종 전부에 대해 사람 경로 도달 가능성을 표로 확인했다.
수정 전에는 로비 화면에서 6종이 도달 불가였고 `INTERNAL` 은 전송 자체가 없었다.
표는 D-027 에 있다.

★ 도달할 수 없는 경로가 하나 남아 있고 그것은 의도적이다 —
설정값 범위 위반은 클라이언트가 서버로 보내지 않는다(숫자 한 글자마다 에러가 왕복하면
화면이 에러로 도배된다). 그 경로의 안전장치는 에러 전파가 아니라 `validateRoomSettings`
**코드 공유**다(D-026). 서버 쪽 거부는 봇 테스트가 따로 검증한다.

### 2. "내보내기" 버튼 — 구현되어 있고 동작한다

건우가 접속 종료 상태를 만들었으나 버튼을 찾지 못했다고 보고했다.

**확인 결과**: Q-15 확정 기능이 Phase 1에 구현되어 있고 정상 동작한다.
자동 확인으로 렌더와 동작(목록에서 사라지는 것, 시스템 메시지)까지 검증했다.

**★ 재현하지 못했다.** 가장 유력한 설명은 **방장이 아닌 창에서 봤을 가능성**이다.
이 버튼은 조건 세 개가 모두 맞아야 나타난다 — 내가 방장 / 상대가 접속 종료 표시 / 5초 경과.

★ 확인 불가다. 건우의 화면을 직접 보지 못했다.

**★ 그러나 문서에 실제 결함이 있었다.**
`05-STATUS.md` 의 Phase 1 표에 **이 기능 행이 아예 없었다.**
구현은 되어 있는데 문서에 없었으므로 "구현되었는지" 를 문서로 확인할 수 없었다.
→ 행을 추가하고 표시 조건까지 적었다. ★ 문서가 사실과 다른 것이 결함보다 나쁘다.

방장에게는 "내보내기로 자리를 비울 수 있습니다(방장만 가능)",

★ 조건부로 나타나는 UI 는 **왜 안 보이는지도** 알려줘야 한다.

## 2026-09-07 — `npm run dev` 실행 불가 사고 수정 (R006)

### 무엇이 일어났는가

`npm run dev` 가 서버를 띄우지 못했다.

```
Error [ERR_MODULE_NOT_FOUND]: Cannot find module 'server\src\config.js'
imported from server\src\index.ts
```

Phase 1 코드는 정상이었다. **깨진 것은 dev 실행 경로 하나였다.**

### 원인

tsconfig 의 `moduleResolution: NodeNext` 는 상대 import 에 컴파일 결과물의 확장자(`.js`)를
쓰도록 요구한다. 반면 `node --experimental-strip-types` 는 import 문자열을 재작성하지 않고
문자 그대로 파일을 찾는다. 두 규칙이 각각 옳고 조합이 불가능하다.

실측 확인: `--experimental-strip-types` 로 `'./dep.js'` 는 실패, `'./dep.ts'` 는 성공.
Node 22.18 에는 `.js` → `.ts` 재매핑이 없다.

★ 저장소 전체 상대 import 57건을 감사했다. 전부 `.js` 확장자로 **일관**되어 있었다.
즉 소스가 틀린 것이 아니라 **실행기 선택이 틀렸다.**

### ★ 왜 R005에서 발견되지 않았는가

정직하게 적는다. 세 검증이 각각 다른 이유로 못 잡았다.

| 검증 | 왜 못 잡았는가 |
|------|--------------|
| typecheck | `tsc` 는 `./config.js` 를 컴파일 후 파일로 해석한다. TS 관점에서 이 코드는 옳다 |
| build | 같은 이유. 컴파일이 성공하고 `dist/config.js` 가 실제로 만들어진다 |
| 봇 테스트 21항목 | ★ **서버를 `node server/dist/index.js` 로 띄웠다.** 컴파일 산출물이라 정상 동작했다. `npm run dev` 는 한 번도 실행하지 않았다 |

**★ 세 번째가 이번 사건의 본질이다.** 테스트가 사람이 쓰는 실행 경로와 다른 경로를 썼다.
그래서 "테스트 전부 통과"와 "실행 불가"가 동시에 성립했다.

typecheck·build 통과는 컴파일 가능성만 보장한다. **실행 가능성은 보장하지 않는다.**

### 어떻게 고쳤는가

세 선택지를 비교하고 **"dev 도 컴파일 산출물을 실행한다"** 를 택했다.
근거는 [07-DECISIONS.md](07-DECISIONS.md) D-020.

핵심 이유: 다른 선택지는 깨진 경로를 *고치지만*, 이것은 그 경로를 *없앤다*.
이제 `npm run dev` / `npm start` / `smoke` / `bot` 이 전부 같은 파일을 실행한다.
소스를 한 줄도 고치지 않았고 의존성도 늘리지 않았다.

### 재발 방지

1. `npm run smoke` — 빌드 → 기동 → `/healthz` → 클라이언트 서빙 → 소켓 핸드셰이크 →
   종료 → 포트 해제. 9항목
2. `npm run verify` = typecheck + test + smoke. **라운드 종료 게이트**
3. `npm run bot` 이 서버가 없으면 사람과 같은 경로로 직접 띄운다
4. `server/package.json` 의 깨진 `dev` 스크립트를 **제거**했다. 남겨 두면 다시 밟는다
5. dist 부재 시 `--force` 빌드 (tsbuildinfo 만 남아 빌드가 no-op 되는 함정)
6. [10-TESTING.md](10-TESTING.md) 0장에 "매 라운드 마지막에 `npm run verify`" 를 절차로 넣었다
7. 같은 문서 7장에 **브라우저 수동 확인 절차**를 넣었다.
   한글 IME 조합 중 Enter 와 모바일 화면은 봇으로 검증할 수 없다

### 작업 중 발견한 것

**smoke 스크립트 자체의 오탐 1건.**
종료 판정을 `exit` 콜백의 `code` 만으로 했는데, Windows 에서 `child.kill()` 은 즉시 종료라
`code=null, signal='SIGTERM'` 이 온다. `code` 만 보면 "신호로 종료됨"과 "아직 안 죽음"이
둘 다 `null` 이라 구분되지 않았다. 첫 실행에서 실제로 이 오탐이 났다.
→ `signal` 을 함께 추적하고 판정 기준을 "프로세스 소멸 + 포트 해제" 로 바꿨다.

**클라이언트는 문제가 없었다.** Vite 는 `'./api.js'` 를 `/src/api.ts` 로 정상 해석한다.
실측으로 확인했다(`/src/App.tsx` 응답에 `from "/src/api.ts"` 가 보인다).

프롬프트 1,481 / 출력 1,291 인 요청의 `totalTokenCount` 가 5,403이었다.

**3. 로컬 `.env` 키와 GitHub Secrets 키가 서로 다른 값이다**

양쪽을 각각 검증했더니 둘 다 유효하지만 값이 다르다(길이 39자 / 53자).

**4. PowerShell 5.1이 BOM 없는 `.ps1` 을 ANSI로 읽어 한글이 깨졌다**

**5. 봇 클라이언트가 부분 갱신 이벤트를 반영하지 않아 검증이 무의미했다**

처음 작성한 봇은 `room.state` 스냅샷만 받고 `room.playerJoined` /
`room.connectionChanged` 를 무시했다. 그래서 "참가자 1명", "활성 인원 2명" 처럼
서버가 옳게 동작하는데도 틀린 값을 보고했다.
→ 부분 갱신 핸들러를 넣고, **표시 유예 5초와 활성 인원 즉시 반영을 실제로 단정하도록** 고쳤다.
로그만 찍고 검증하지 않는 테스트는 없는 것보다 나쁘다.

**6. `RULES.HEARTBEAT_INTERVAL_MS` 가 30초로 잘못 들어가 있었다** (지시받은 수정)

Q-02 확정값은 4분인데 상수는 30,000이었다. 240,000으로 고쳤다.
클라이언트가 아직 heartbeat 를 보내지 않아 동작에는 영향이 없었으나,
RULES 상수의 존재 이유가 "규칙 수치를 한 곳에 모아 놓치지 않게 하는 것"이므로
그 안에 틀린 값이 있으면 목적 자체가 무너진다.
→ 전체 대조 결과 다른 불일치는 없었고, 누락된 상수 6개를 보강했다(R005 3장).

### 발견한 문제와 해결

**1. 부팅 시 정리 절차가 없으면 방을 다시 만들 수 없게 된다** (설계 결함)

`rooms` 에 "1인당 열린 방 1개" 부분 UNIQUE 인덱스가 있는데, 방 삭제는 메모리에서 일어난다.
프로세스가 죽으면 `closed_at` 이 NULL인 방이 DB에 남고, 메모리에는 없으므로 영원히 닫히지 않는다.
그 사람은 다시는 방을 만들 수 없다. **로컬 PC 서버는 껐다 켜는 것이 일상이라 반드시 발생한다.**

→ `server/src/db/bootCleanup.ts` 를 만들어 부팅 시 잔여 게임(`server_restart`)과 방을 닫는다.
`question_experiences` 는 삭제하지 않는다(guide 25절).

**2. `buildNormalizedIndex` 의 인덱스 매핑이 이모지에서 어긋났다** (실제 버그)

정규화 결과 문자열과 원문 인덱스 대응표를 만들 때 **코드 포인트 단위로 세고 있었다.**
이모지처럼 서로게이트 페어(코드 유닛 2개)인 문자에서 `norm.length` 와 `map.length` 가 어긋나
이후 인덱스가 전부 밀렸다. 테스트가 잡았다.

→ 코드 유닛마다 map 항목을 하나씩 넣도록 고쳤다.
이 함수는 Phase 6 마스킹의 기반이므로 여기서 잡은 것이 다행이다.

**3. `g` 플래그 정규식으로 `.test()` 를 호출하고 있었다** (잠재 버그)

`ZERO_WIDTH_RE` 에 `g` 플래그가 있는데 `.test()` 를 호출하면 `lastIndex` 가 전진해
같은 입력에 대해 호출마다 다른 결과가 나온다.

→ 판정용 비-global 정규식을 분리했다. 회귀 테스트를 추가했다.
