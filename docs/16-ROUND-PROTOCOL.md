# 라운드 운영 규약 — 세 세션(GEN · VERIFY · MAIN)과 설계 에이전트의 고정 규칙

> ★ 이 문서는 **매 브리핑에 되풀이해 적던 고정 지시**를 한 곳에 모은 정본이다. 브리핑은 "16 그대로" 한 줄로 이 문서를 가리킨다.
> 라운드마다 달라지는 것(할 일 · 대상 파일 · 찬종의 말 · 보고 항목)만 브리핑에 적는다.

마지막 갱신: **2026-10-13** (신설 — 번호 체계 분리 · 끝 점검 방식 · 모델 배정 · 브리핑 틀)

## 0. 조직 · 역할 · 모델

```
찬종 (사용자 · 운영/기획 결정권자 — 옛 문서의 "건우" 와 같은 사람)
```

## 1. 번호 체계 (2026-10-13 분리 — 찬종 결정)

옛 방식은 라운드 번호 `Rnnn` 을 GEN·MAIN 이 같이 쓰고 결정 번호 `D-nnn` 도 같이 써서 **D-174 · D-175 가 두 개씩** 생겼다(MAIN R038 · GEN R047). 앞으로는 세션마다 접두어를 나눈다.

| 무엇 | MAIN | GEN | VERIFY |
|---|---|---|---|
| 라운드 · 보고서 | `Rnnn` 그대로 — 다음 **R048** | **`Gnnn`** — **G001** 부터 (`ai-out/G001.txt`) | `Vnnn` 그대로 — 다음 **V005** |
| 결정 (07-DECISIONS) | `D-nnn` 그대로 — 다음 **D-228** | **`DG-nnn`** — **DG-001** 부터 | 결정을 쓰지 않는다 (6절 "반복 오류 유형" 으로 제안만) |
| 13-PENDING | `A` (사람이 직접 볼 것) — 다음 **A54** | `C` 그대로 — 다음 **C61** | **`CV-nn`** — **CV-01** 부터 (판정 못 한 것 · 판단 대기) |
| 미결 (08) | `Q-nnn` 공용 — 쓰기 전에 08 의 마지막 번호 확인 (지금 Q-107) | 같음 | 올리지 않는다 (CV 로) |

- ★ 겹친 R047 의 D-174 · D-175 는 GEN 이 다음 라운드(G001)에서 **DG-001 · DG-002** 로 옮긴다 (07 본문 · 05 · 13 · 15 의 참조도 함께). MAIN 의 D-174 · D-175(R038)는 그대로.
- `ai-out/README.md` 색인은 세션별 표 셋(MAIN R · GEN G · VERIFY V)으로 둔다. 옛 GEN 라운드(R011~R013 · R017~R024 · R026~R032 · R036 · R037 · R047)는 R 표에 그대로 두고 "GEN" 표시만 한다. V001~V004 행은 V005 에서 VERIFY 가 넣는다.
- 어떤 번호든 **쓰기 전에 그 문서의 마지막 번호를 확인**한다. 동시 라운드면 브리핑이 번호 범위를 미리 나눠 준다.

## 2. 브리핑 틀 (설계 에이전트가 쓴다)

브리핑 파일은 **세션마다 고정 경로 하나**다 — `ai-out/briefs/gen.md` · `ai-out/briefs/verify.md` · `ai-out/briefs/main.md`. 설계 에이전트가 라운드마다 그 파일을 새 브리핑으로 **덮어쓰고**, 직전 브리핑은 `ai-out/briefs/archive/<라운드 번호>.md` 로 옮긴다.
찬종은 세션 창에 **"ai-out/briefs/verify.md 읽고 진행"** 처럼 한 줄만 친다. 세션은 그 파일을 읽고 시작한다 — **파일 전체가 곧 지시**다 (붙여 넣기 없음 — 2026-10-13 찬종 결정).
라운드는 **한 번에 한 세션만** 돌린다 (찬종 결정). 동시 라운드가 필요해지면 "문서 분담" 줄을 쓴다.

```
[<세션> <라운드>]
TASK: 한 줄
먼저 읽기: (docs/16 그대로) + 이 라운드에 필요한 문서·보고서·파일
확정 결정 / 찬종의 말: 원문 인용 (있을 때만)
할 일: A · B · C … — 항목마다 "다 됐다" 의 기준 · 산출 파일 이름
DB 쓰기: 허용(백업 뒤) / 불허          ← GEN · MAIN
웹·토큰 예산: 숫자로 (WebSearch N회 · 하위 에이전트 N개 이내 · 생성 M건)   ← GEN · VERIFY
하지 말 것: 이 라운드에만 해당하는 것
문서 분담: 동시 라운드일 때 어느 세션이 05 · 06 · 07 · 13 의 어느 부분을 고치는지
확인할 것: 브리핑이 사실로 전제한 것 (세션이 검증한다 — 원칙 7)
끝 점검: (MAIN) 5-1 그대로 / (GEN) 게이트 / (VERIFY) 7절 자기 점검
보고 항목: 보고서 목차 (번호)
커밋: 허용 범위 · push
지난 피드백: 직전 라운드에서 잘한 것 · 틀린 것 (있을 때만)
```

- 한 라운드 **3~5 항목**. 경우의 수 표 같은 큰 검사는 따로 뗀다.
- 브리핑의 사실은 확인하고 쓴다. 확인하지 못한 것은 "(확인 대상)" 으로 표시한다.
- 운영·기획 판단은 찬종의 말을 **그대로 인용**해 넣는다. 설계 에이전트의 해석은 "설계 판단" 으로 구분한다.

## 3. 절대 원칙 (세 세션 공통 — 매 브리핑 "16 그대로")

1. 게임 규칙을 임의로 단순화·변경하지 않는다. 애매하면 Q 로 올린다.
2. 운영적·기획적 판단은 혼자 결정하지 않는다. 기술적이고 되돌리기 쉬운 것만 자체 판단하고 기록한다.
3. 모든 응답은 한국어.
4. 추측을 확정처럼 쓰지 않는다 ("추정" · "확인 필요").
5. 비밀값을 커밋하지 않는다 (문서에도 .env 값 금지 — 이름만). 저장소는 public 이다.
6. 중단·재개가 가능하게 일하고 상태를 남긴다. MAIN 은 라운드 종료 전 끝 점검(5-1).
7. ★★ 브리핑에 사실처럼 적힌 것은 검증 대상이다 — 다르면 보고서에 명시한다.
8. git 에러가 나면 먼저 VPN 을 의심한다 ("VPN 확인 필요" 로 보고).

공통 추가: 찬종에게 확인을 요청하지 않는다 (판단 못 한 것은 13-PENDING 또는 Q 로) · 찬종 PC 의 `npm run dev` · `dev:tunnel` · 브라우저는 건드리지 않는다 · 찬종은 라운드 중에도 플레이할 수 있다.

## 4. 응답 · 보고 형식 (세 세션 공통)

- **[cmd 창]** 요약만, 최대 5줄.
- **[정식 응답]** `ai-out/<번호>.txt` (UTF-8 + LF), append-only. 헤더:
  ```
  ===========================================
  ROUND: R048 / G001 / V005
  DATE: (작성 시각)
  TASK: …
  STATUS: 완료 / 부분완료 / 결정대기
  ===========================================
  ```
- 본문 순서: cmd 창 요약 → `0. 찬종이 볼 것`(짧게 — 판단 · 확인 못 한 것 · 실기기로 볼 것) → 원칙 메모(7번 검증 결과 포함) → 브리핑이 정한 목차 → 새로 생긴 결정 필요 항목 → 고친 문서 목록.
- "통과" 는 끝까지 돈 것만. 멈춘 것 · 못 돌린 것 · 표본으로만 본 것은 **이름과 숫자**로 적는다.
- 보고서를 쓰면 `ai-out/README.md` 해당 표에 한 줄.
- 커밋 메시지 끝줄 `Co-Authored-By: Claude <실행 모델 이름> <noreply@anthropic.com>`. 라운드 끝에 push (`git fetch` 뒤 충돌이면 강제하지 않고 보고).

## 5. 세션별 고정 규칙

### 5-1. MAIN

- **먼저 직전 보고서 → 브리핑 → 코드** 순으로 읽는다. 브리핑 속 사실은 코드·실측으로 확인한다.
- **문제 데이터를 건드리지 않는다** (questions · question_answers · 힌트 · 분류 · `pipeline/` · `scripts/pipeline-*.mjs` · `docs/*-review.md`). DB 구조 변경은 MAIN 몫 — 고치기 전 `npm run db:backup`.
- A → B → C 순서 · **단계마다 커밋** + 06-WORKLOG 체크박스.
- **화면은 "그림으로 확인한 것만 됐다"** — `npm run build` → ui-check 로 찍기 → 이미지를 직접 본다 → 고침 → 다시 찍기. 그림은 `docs/design/rNNN/`.
  크기: PC 1280×720 · 1536×864 · 1536×730 · 1920×1080 · 2560×1440 / 모바일 360 · 390 · 430. 방장 · 게스트 둘 다. 테마 파스텔 · 밤.
- 사람 동작은 **진짜 클릭**(CDP `realClick` · `realType`). `element.click()` 은 덮인 버튼 · 바깥 누르기 · 순서 결함을 못 본다.
- 결함은 **먼저 재현하고 고친다.** 새 검사는 고치기 전 빌드로 먼저 돌려 잡히는지 확인한다. 재현 못 하면 잰 값과 함께 "재현 안 됨 · 확인 필요".
- 검사가 왜 못 잡았나를 보고서에 적고 그 구멍을 메우는 검사를 더한다 (10-TESTING 라운드별 장).
- 디자인 원칙 · 팝업 규칙 · 한 화면 게이트는 01-GAME-RULES 16장이 정본이다.
- ★ **끝 점검 (2026-10-13 찬종 결정)**: 봇 전체(`scripts/bot.mjs` SCENARIOS) + `npm run verify`. **단계별로 나눠 끝까지 돌면 통과로 친다** (찬종 PC 메모리 사정 — 백그라운드 한 번에 돌리기는 멈춘다).
  보고서에 "한 번에 돌았는지 / 단계별이었는지" 와 단계마다 건수를 적는다. 건너뛴 단계(Chrome 없음 등)는 통과가 아니다.
  ui-check:social 이 10분을 넘으면 `UICHECK_NO_CHAIN=1` 로 `--social` · `--profile` · `--emoji` 를 나눈다. 봇이 도는 동안 `npm run build` 하지 않는다.
- 운영·기획 판단은 Q 로 올리거나 보고서 0장에 적는다. 기술 판단은 보고서 "판단" 목록 + 07 D-nnn (결정 · 원인 · 되돌리는 법).

### 5-2. GEN

- **DB 는 브리핑이 "DB 쓰기 허용" 이라고 적었을 때만** 쓴다. 쓰기 전 반드시 `node scripts/backup.mjs`. 반영 스크립트는 `scripts/gNNN-apply*.mjs` 로 멱등하게.
- 서버 기동 · ui-check · `server/ client/ shared/` 수정 금지.
- 규칙이 바뀌면 기준서(15) → `node scripts/criteria-sync.mjs` → `--check` 통과 → 새 프롬프트 버전. 옛 프롬프트는 SYNC 표시를 빼서 얼린다.
- 생성 흐름: 생성(서브에이전트 분할) → 중앙 기계 검사 → 사실 확인(웹 출처 · 못 한 것은 "지식 근거" 표시) → 채점 → 힌트(hint-v3 · checkHint) → `pipeline-load` 게이트를 파일 단계에서 미리 → VERIFY 묶음(`data/pipeline/audit/gNNN-verify-targets.json` — `questionBefore` · `sources` · `hintBasis` · `check[]` · 가능하면 `criteria`) → (허용 시) 적재.
- 서브에이전트가 429 · ENOTFOUND 로 죽으면 결과 파일이 없는 묶음만 다시.
- **자기 블라인드 테스트 · 자기 검토를 판정으로 쓰지 않는다** (R036 실측 — 떠먹여 주기를 구분 못 한다).
- 혼자 정한 것은 보고서에 **"GEN 판단 (되돌리기 쉽다)"** 로 따로.
- 사용자 검토는 `docs/*-review.md` 체크박스 문서로. 그 파일의 커밋은 GEN 라운드에서.
- VERIFY 결과 반영: keep 은 제안으로(신규가 더 가르칠 때만 교체 · 엇갈리면 기존 유지), fix 는 읽고 판단해 반영, 안 받은 것은 사유를 보고서에. VERIFY 제안 속 새 사실은 한 번 더 웹 확인.

### 5-3. VERIFY

- **판정만 한다.** DB 쓰기 · 적재 · 생성 · 규칙/프롬프트/코드 수정 · 서버 기동 · `npm run verify` · `npm run build` · Gemini 호출 금지. 목록 밖 문항은 "참고" 로만.
- 쓰는 파일: `ai-out/Vnnn.txt` · `data/pipeline/audit/vnnn-results.json` · `data/pipeline/audit/vnnn-raw/`(판정자 조각 출력 — 재감사용, 허용) · 13-PENDING 의 해당 행 + CV 항목 · README 의 V 표. **커밋·push 는 이 파일들만 `git add`** (기본 허용 — 브리핑이 달리 적지 않는 한).
- 결과 JSON: 대상 목록의 **모든 항목이 키로 한 번씩**(누락 0 — GEN 이 기계로 읽는다). 항목마다 verdict · category · proposal(전체 문구) · reason · sources. 사실은 주장마다 `true / false / unverified` + 출처 + `basis`(`web` / `knowledge`).
- 보고서 절: 0 웹 가능 여부(맨 앞) · 1 실제 판정 건수·빠진 것 · 2 종류별 결과 · 3 fix·drop 전부(현재/제안/사유/출처) · 4 unsure·경계선·미확인 주장 · 5 같은 정답 누적 분포 · 6 반복 오류 유형(생성 규칙에 넣을 것) · 7 자기 점검(표본으로만 본 것 · 못 한 것을 숫자로).
- 방식: 큰 JSON 은 `node -e` 로 필터해 본다 · 100건 안팎 조각으로 나눠 하위 에이전트에(**한 번에 3~6개**) · 판정 기준은 **한 파일**로 모두에게 같게 · 결과 개수·키를 기계로 대조 · **같은 정답이 여러 항목에 걸리면 한꺼번에** · 힌트 전수 · fix/drop 전부 · 경계선은 직접 읽는다 · 힌트와 제안 문구는 `scripts/hint-check.mjs` `checkHint` 로 기계 검사 · GEN 이 단 `sources` 는 WebFetch 로 대조(검색 예산 절약) · DB 는 읽기 전용(누적 집계).
- **교훈 (V001~V004 — 그대로 유지)**
  - A. 판정 근거에 "질문에 무엇이 적혀 있는가" 를 쓸 때는 **원문에서 확인한 것만**. 인용은 기계로 대조한다.
  - B. 힌트는 **세기만으로 고치지 않는다** (R030 기준 — 15 §4-1 H9). 세기와 상관없이 늘 fix: 정답 글자·조각 · 다른 이름(H10) · 사실 아님 · 해설과 같은 사실.
  - C. 같은 항목이 여러 쌍에 걸치면 묶어서 판정한다.
  - D. 버린 것 · 못 한 것을 **숫자로** 보여 준다.
  - E. 판정자 ok 를 그대로 받은 영역은 표본이라도 다시 읽거나, 안 읽었으면 7절에 적는다 (판정자 ok 는 느슨하다 — R031 표본 11% same).
  - F. 새 기준은 **보정 표본(5~10건)으로 먼저 맞춰 보고** 전체를 돌린다.
  - G. `blind`(힌트만 본 모델의 추측)는 떠먹여 주기의 신호로 쓰지 않는다.
- 기준이 바뀐 라운드는 브리핑 맨 위에 "폐기 기준 / 새 기준 / 적용 시점" 이 있다. 없으면 15 의 현재 문구가 기준이다.

## 6. 문서 동시 편집 · 사람 확인

- GEN · MAIN · VERIFY 가 05 · 06 · 07 · 13 · README 를 같이 고친다. **동시 라운드**면 브리핑 "문서 분담" 을 따른다. 분담이 없으면 자기 세션 행·절만 고친다.
- 13-PENDING A 항목(실기기·실사용)은 쌓이기만 하지 않게 — 설계 에이전트가 몇 라운드마다 찬종에게 "이번 판에서 봐 줄 것 3개" 로 묶어 전달하고, 결과를 받아 끝난 것을 내린다.
- 환경: 찬종 PC(16GB · 남는 메모리 1~3GB) 에 dev 서버 · 터널 · 브라우저가 늘 떠 있다. Git Bash heredoc 안 따옴표가 깨진다 → 긴 스크립트는 파일로. 파이썬은 `PYTHONIOENCODING=utf-8`. 봇은 3000 번 감시 서버를 쓰며 `server/dist` 가 바뀌면 몇 초 연결 실패한다.
