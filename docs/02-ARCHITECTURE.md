# 아키텍처와 실행 방법

## 1. 인프라 구조

```
  친구들의 브라우저 (PC / 모바일)
            │  https + wss
            ▼
  Cloudflare quick tunnel (trycloudflare.com)   ← 계정·도메인 불필요, 무료, URL은 실행마다 바뀜
            │
            ▼
  건우 PC (Windows 11)
   ├─ Node.js 서버 (Express + Socket.IO)        ← 게임 상태는 이 프로세스의 메모리에 있다
   │    └─ 클라이언트 정적 파일도 이 서버가 서빙 (★ 오리진 1개)
   └─ Docker: PostgreSQL 17 (localhost:5434)    ← 영속 데이터
```

**월 비용 $0. 가입해야 할 외부 서비스가 없다.**

### 왜 클라우드를 쓰지 않는가

건우가 방장으로 게임을 대부분 진행하고, 서버가 건우 없이 돌아갈 필요가 없다.
필요할 때만 PC에서 켠다. 고정 URL도 필요 없다 — 어차피 할 때마다 링크를 만들어 뿌린다.

이 판단으로 다음 문제들이 **사라졌다.**

- 무료 호스팅의 슬립과 콜드 스타트
- 서버리스 DB의 컴퓨트 시간 한도
- 512MB RAM 제약 (봇 동시성 테스트가 자유로워졌다)

이용자가 늘면 나중에 클라우드로 옮긴다. 그때를 위한 규칙이 아래 3장이다.

### 왜 프론트엔드를 별도 호스팅하지 않는가

프론트엔드를 다른 도메인(GitHub Pages 등)에 두면 오리진이 둘이 되어

- 세션 쿠키가 cross-origin이 되고 `SameSite=None; Secure` 가 필요해진다
- 그 쿠키는 서드파티 쿠키로 분류되어 **모바일 사파리에서 로그인 유지가 깨질 수 있다**
- CORS 설정이 필요해지고, 배포 단위가 둘로 늘어 버전 불일치가 생긴다

Node 서버가 빌드 산출물을 직접 서빙하면 이 문제들이 전부 존재하지 않는다.
그래서 **서버에 CORS 설정을 두지 않는다.** 필요해졌다면 설계가 잘못된 것이다.

## 2. ★ 네트워크 단절과 프로세스 종료의 차이

이 구분이 일시정지(PAUSED) 설계의 근거다. **혼동하면 안 된다.**

| | 서버 PC 네트워크 단절 | 서버 프로세스 종료 |
|---|---|---|
| 예시 | Wi-Fi 끊김, 공유기 재부팅, 터널 재시작 | PC 재부팅, Ctrl+C, 크래시 |
| 서버 프로세스 | **살아 있다** | 죽는다 |
| 메모리의 방·게임 | **그대로 있다** | 소실 |
| 이어하기 | **가능.** 활성 0명 → `PAUSED` → 방장이 재개 | 불가 |
| 타이머 | 남은 시간으로 멈춘다. 문제가 소모되지 않는다 | 해당 없음 |
| 경험 기록 | PAUSED 중엔 정답 공개가 없으므로 기록되지 않는다 | 이미 기록된 것은 **삭제하지 않는다** |
| 복구 절차 | 터널 재기동 → 새 링크 공유 → 방장이 "재개" | 부팅 시 정리 절차가 방과 게임을 닫는다 |
| DB 흔적 | 없음 | 게임 `end_reason='server_restart'`, 방 `closed_at` 설정 |

**검증 결과 (R004 1장)**: cloudflared 프로세스를 강제 종료해도 서버의 `bootedAt` 이 그대로였다.
즉 터널이 죽어도 서버 프로세스와 메모리는 전혀 영향을 받지 않는다.
이것이 PAUSED로 이어하기가 가능한 이유의 실증이다.

### 부팅 시 정리 절차 (`server/src/db/bootCleanup.ts`)

**왜 필요한가.** `rooms` 테이블에는 "1인당 열린 방 1개" 를 강제하는 부분 UNIQUE 인덱스가 있다.
방 삭제는 메모리에서 일어나고 그때 `closed_at` 을 기록한다.
프로세스가 죽으면 그 절차가 실행되지 않아 `closed_at` 이 NULL인 방이 DB에 남고,
메모리에는 없으므로 영원히 닫히지 않는다. **그 사람은 다시는 방을 만들 수 없게 된다.**

로컬 PC 서버는 껐다 켜는 것이 일상이므로 이 문제는 반드시, 자주 발생한다.

**처리**: 서버 부팅 시
1. `ended_at IS NULL` 인 게임을 전부 종료 (`end_reason = 'server_restart'`)
2. `closed_at IS NULL` 인 방을 전부 닫는다

**`question_experiences` 는 절대 삭제하지 않는다.** 그 문제들은 실제로 정답이 공개되어
사람들이 화면에서 본 것이므로 기록이 옳다.

## 3. ★ DB 접근 규칙 (클라우드 전환 대비)

현재 DB는 로컬 PostgreSQL이라 유휴 연결을 붙들어도 비용이 들지 않는다.
그러나 **Neon 같은 서버리스 PostgreSQL로 옮기면 사정이 완전히 달라진다.**
Neon은 5분간 쿼리가 없으면 컴퓨트를 정지시켜 요금을 0으로 만드는데,
커넥션 풀이 유휴 연결을 계속 열어 두면 그 정지가 영원히 발동하지 않는다.
Free 플랜에서는 월 한도를 초과해 DB가 멈추고, 종량제에서는 요금이 20배가 된다.

**그래서 다음 규칙을 지금부터 지킨다.**

1. 유휴 연결을 오래 붙들지 않는다 — `idleTimeoutMillis: 60_000`
2. 풀을 작게 유지한다 — `max: 5`
3. 지연 연결 — 서버 기동만으로 DB에 붙지 않는다
4. **DB를 주기적으로 건드리는 코드를 만들지 않는다**
   - `GET /healthz` 는 DB에 접근하지 않는다
   - `heartbeat` 핸들러는 DB에 접근하지 않는다
   - 만료 세션 정리 크론을 두지 않는다 (로그인 시 기회주의적으로 정리한다)
   - 세션 슬라이딩 갱신은 남은 기간이 절반(15일) 미만일 때만 한다
   - 로비 경험률은 진입·인원 변동 시에만 조회하고 주기 갱신하지 않는다
     (Phase 2 구현: `server/src/lobby/info.ts` 의 `refreshLobbyInfo()` 가 유일한 호출 지점이다.
     ★ 출제 가능 수도 같이 캐시한다 — 설정값과 무관하고 참가자 집합에만 의존하므로,
     방장이 문제 수를 한 글자 고칠 때마다 쿼리가 나가지 않게 한다.
     ★ 단 게임 시작 직전에는 캐시를 믿지 않고 반드시 다시 조회한다(Q-21))
   - 게임 진행 중 점수를 `game_players` 에 UPDATE하지 않는다 (`answer_events` 로 계산한다)

**검증 결과 (R004)**: 서버를 켜 두고 관찰했을 때 `dbActiveMs` 가 약 60초에서 멈췄다.
부팅 정리 후 유휴 연결이 60초 뒤 닫혔다는 뜻이고, (1)이 실제로 동작함을 확인한 것이다.
`GET /healthz` 의 `dbActiveMs` 로 언제든 확인할 수 있다.

### 플랫폼 중립 규칙

- 접속 정보는 전부 환경 변수로만 받는다 (`DATABASE_URL` `PORT` `SESSION_SECRET` `NODE_ENV`)
- 포트는 반드시 `process.env.PORT` 를 쓴다
- 플랫폼 고유 SDK를 쓰지 않는다. 표준 `pg` 드라이버와 표준 HTTP/WebSocket만 쓴다
- 파일 시스템에 영속 데이터를 쓰지 않는다. 모든 영속 데이터는 PostgreSQL로만 간다
- 로그는 표준 출력으로만 낸다
- 배포 설정 파일이 생기더라도 애플리케이션 코드가 그것을 읽지 않게 한다

## 4. 기술 스택

| 영역 | 선택 | 이유 |
|------|------|------|
| 런타임 | Node.js 22 + TypeScript | 단일 스레드 이벤트 루프가 "한 문제의 정답자는 정확히 한 명" 을 락 없이 보장한다 |
| 실시간 | Socket.IO 4 | 자동 재연결·room·하트비트가 기본 제공되어 재접속/동기화 구현량이 크게 준다 |
| 웹 프레임워크 | Express 4 | 정적 서빙과 헬스체크만 필요하다 |
| 프론트엔드 | React 18 + Vite 6 | |
| DB | PostgreSQL 17 (Docker) | |
| DB 접근 | **ORM 없음.** 순수 SQL 마이그레이션 + `pg` 드라이버 직접 | 스키마와 쿼리가 그 자리에 SQL로 그대로 보이는 것이 인수인계에 가장 유리하다. 커넥션 풀도 직접 통제할 수 있다 |
| 테스트 | Vitest | |
| 패키지 | npm workspaces | 새 도구 설치 없이 시작할 수 있다 |
| 외부 공개 | Cloudflare quick tunnel | 계정·도메인 불필요, 무료, WebSocket 통과 확인됨 |

### 왜 서버가 단일 인스턴스인가

`guide` 18절이 "동시에 여러 정답 요청이 들어와도 한 문제에서 두 명이 정답자가 되는 일이 없어야 한다"
를 요구한다. Node의 단일 스레드 이벤트 루프에서는 **하나의 이벤트 핸들러가 `await` 없이 끝까지
실행되는 동안 다른 이벤트가 끼어들 수 없다.** 그래서 별도의 락 없이 원자성이 보장된다.

인스턴스를 늘리면 Redis pub/sub과 분산 락이 필요해진다. 10명 규모에서는 불필요한 복잡도다.

> **★ 이 성질은 판정 블록에 `await` 를 넣는 순간 무너진다.**
> 자세한 규칙은 [04-PROTOCOL.md](04-PROTOCOL.md) 의 "동시성 설계 원칙" 을 반드시 읽는다.

## 5. 디렉터리 구조

```
quiz-web/
├─ guide.md                최초 요구사항 원본 (수정하지 않는다)
├─ docs/                   ★ 현재 유효한 규칙과 상태의 정본
├─ ai-out/                 라운드별 설계 기록 (append-only, 정본 아님)
├─ shared/                 서버·클라이언트 공유 순수 함수와 타입
│   └─ src/
│       ├─ normalize.ts    정답 정규화  ★ 서버와 파이프라인이 반드시 같은 함수를 쓴다
│       ├─ hint.ts         힌트 생성
│       ├─ ranking.ts      순위 계산 / 스킵 임계값
│       ├─ mask.ts         정답 마스킹 (Phase 6에서 구현)
│       ├─ settings.ts     게임 설정 검증 / 경험률 표기  ★ 서버·클라이언트 공용 (D-026)
│       └─ protocol.ts     Socket 이벤트 타입과 게임 규칙 상수
├─ server/                 게임 서버
│   └─ src/
│       ├─ index.ts        진입점
│       ├─ tick.ts         ★ 전역 100ms tick. 방마다 타이머를 두지 않는다
│       ├─ socket/         인바운드 이벤트 (guard.ts 가 검사 순서를 강제한다)
│       ├─ rooms/          메모리 방 모델 / 레지스트리 / 스냅샷 / 브로드캐스트 / 생명주기
│       ├─ lobby/          로비 정보 갱신 (경험률·출제 가능 수). ★ DB 조회 지점이 여기 하나다
│       ├─ game/           게임 시작·카운트다운 (T01~T04). Phase 3의 문제 진행이 여기 붙는다
│       ├─ auth/           비밀번호 / 세션
│       ├─ http/           인증 REST 라우트
│       └─ db/
│           ├─ pool.ts        커넥션 풀 (3장 규칙)
│           ├─ bootCleanup.ts 부팅 시 정리 (2장)
│           ├─ questions.ts   ★ 출제 대상 조건을 이 파일 한 곳에만 둔다
│           └─ games.ts       games / game_players
├─ client/                 React 클라이언트
├─ pipeline/               문제 수집·가공 파이프라인 (Track D, 게임 서버와 분리)
├─ migrations/             순수 SQL 마이그레이션
├─ scripts/                migrate / seed / backup / restore / dev-tunnel
├─ data/seed/              시드 문제 JSON
└─ backups/                DB 백업 (git에 넣지 않는다)
```

**단방향 관계**: 게임 서버는 `questions` / `question_answers` / `categories` 를 **읽기만** 한다.
파이프라인은 그 테이블에 **쓰기만** 한다. 유일한 접점은 DB 스키마다.

## 6. 실행 방법

### 처음 한 번

```bash
npm install
cp .env.example .env      # 값을 채운다. ★ .env 는 절대 커밋하지 않는다
npm run db:up             # Docker로 PostgreSQL 기동
npm run db:migrate        # 스키마 적용
npm run db:seed           # 개발용 시드 문제 53개
```

### 개발 중

```bash
# 터미널 A — 서버 (3000)
npm run dev

# 터미널 B — 클라이언트 개발 서버 (5173, /api 와 /socket.io 를 3000으로 프록시)
npm run dev:client
```

> ★ `npm run dev` 는 **컴파일 산출물(`server/dist/index.js`)을 실행한다.**
> `npm start` / `npm run smoke` / `npm run bot` 과 완전히 같은 파일이다.
>
> 소스(`.ts`)를 직접 실행하지 않는 이유가 있다.
> `moduleResolution: NodeNext` 는 상대 import 에 `.js` 확장자를 요구하는데
> Node 의 타입 스트리핑은 그 문자열을 재작성하지 않아 조합이 불가능하다.
> 그리고 더 중요하게는, **dev 만 다른 코드 경로를 쓰면 아무도 그 경로를 검증하지 않는다.**
> 실제로 그 때문에 서버가 뜨지 않는 사고가 있었다.
> 경위와 판단은 [07-DECISIONS.md](07-DECISIONS.md) D-020 / D-021.
>
> ★ 실행 진입점은 루트 `npm run dev` **하나**다.
> `npm run dev -w server` 는 존재하지 않는다(같은 함정을 막기 위해 제거했다).

Vite 개발 서버가 `/socket.io` 와 `/healthz` 를 서버로 프록시하므로,
**개발 중에도 "오리진이 하나"인 상태가 유지된다.** 개발 환경과 배포 환경의 동작이 달라지지 않는다.

### 친구들과 플레이할 때

```bash
npm run build             # 클라이언트 빌드
npm run dev               # 터미널 A: 서버
npm run dev:tunnel        # 터미널 B: 터널. 출력된 https 주소를 공유한다
```

자세한 절차와 네트워크 단절 시 복구는 [11-DEPLOY.md](11-DEPLOY.md) 를 본다.

### 그 밖의 명령

```bash
npm run verify            # ★ 라운드 종료 게이트: typecheck + test + smoke + ui-check
npm run smoke             # 실행 확인 (빌드 → 기동 → 응답 → 종료 → 포트 해제)
npm run ui-check          # ★ 브라우저 확인 (실제 Chrome 조작. 없으면 건너뛴다)
npm test                  # Vitest
npm run typecheck         # 전체 타입 검사
npm run bot -- <시나리오>  # 봇 테스트 (서버가 없으면 직접 띄운다)
npm run build:force       # tsbuildinfo 무시하고 강제 재빌드
npm run db:backup         # DB 백업 (★ 로컬 DB이므로 유일한 안전장치)
npm run db:restore -- <파일>
npm run db:reset          # ★ 모든 데이터 삭제 후 재적용. 개발용
```

> ★ **typecheck 와 build 통과는 실행 가능성을 보장하지 않는다.**
> 반드시 `npm run verify` 로 실제 기동까지 확인한다.

## 7. 환경 변수

**실제 값은 `.env` 에만 둔다. 문서와 저장소에는 이름만 적는다.**
저장소가 Public이므로 값이 한 번이라도 커밋되면 히스토리에 영구히 남는다.

| 이름 | 필수 | 설명 |
|------|------|------|
| `DATABASE_URL` | O | PostgreSQL 접속 문자열 |
| `PORT` | | 서버 포트. 없으면 3000 |
| `SESSION_SECRET` | O | 세션 쿠키 서명용 비밀 문자열 |
| `NODE_ENV` | | `development` / `production` |
| `PUBLIC_BASE_URL` | | **선택.** 서버가 직접 링크를 만들어야 할 때만. 없어도 정상 동작한다 |
| `GEMINI_API_KEY` | | 파이프라인 전용. 게임 서버는 쓰지 않는다 |

> 초대 링크는 기본적으로 **방장 브라우저의 `window.location.origin`** 으로 만든다.
> 터널 URL이 바뀌어도 방장 브라우저는 이미 새 URL에 있으므로 항상 올바른 값을 얻는다.
> 서버 환경 변수로 만들면 URL이 바뀔 때마다 서버를 재시작해야 하고,
> 그러면 메모리의 게임이 날아가 일시정지 기능이 무의미해진다.

## 7-1. 비밀값 관리 ★

저장소가 Public이므로 이 항목이 가장 중요하다.
값이 한 번이라도 커밋되면 히스토리에 영구히 남고, 공개 저장소는 봇이 자동으로 스캔한다.

### 키를 두는 곳과 역할

| 위치 | 역할 | 비고 |
|------|------|------|
| 로컬 `.env` | **개발·실험용.** 프롬프트 튜닝, 소량 배치 시험 | 커밋되지 않는다 |
| GitHub Secrets | **정기 배치(Actions)용** | 워크플로에서 env 로만 주입한다 |

두 곳을 모두 유지한다. 한 곳으로 줄이는 것이 이론적으로는 안전하지만,
프롬프트를 고쳐가며 반복 실행해야 하는데 Actions 만으로는 피드백 루프가 너무 느리다.
대신 **역할을 나누고 규칙을 지킨다.**

### 반드시 지키는 세 가지

1. **`.env` 를 절대 커밋하지 않는다.** `.gitignore` 로 차단되어 있고 매 라운드 재검증한다
2. **키 값을 로그·에러 메시지·응답에 출력하지 않는다.** 앞 4자리도 찍지 않는다.
   존재 여부와 길이만 보고한다
3. **파이프라인 코드는 키를 환경변수에서만 읽는다.** 하드코딩과 기본값을 두지 않는다

### 구현에 반영된 것

- `server/src/config.ts` — 값이 없을 때 **이름만** 알린다
- `scripts/verify-gemini.mjs` — 길이만 출력한다. 에러 본문에서 키 문자열을 무조건 치환하는
  `scrub()` 을 통과시킨다 (Google API 에러 본문에 요청 URL이 포함되는 경우가 있다).
  키를 쿼리스트링이 아니라 `x-goog-api-key` 헤더로 보낸다(프록시·서버 로그 노출 방지)
- `.github/workflows/verify-gemini.yml` — 키를 env 로만 주입한다.
  커맨드라인 인자로 넘기지 않는다(프로세스 목록 노출 방지).
  GitHub의 자동 마스킹에 의존하지 않는다
- 세션 토큰은 DB에 해시만 저장한다. `SESSION_SECRET` 을 HMAC 키로 쓴다 (D-017)

### 매 라운드 검증 절차

```bash
git check-ignore -v .env          # 무시되는지
git log --all -- .env             # 과거에 커밋된 적이 없는지
git diff --cached | grep -iE "AIza|API_KEY *="   # 커밋 직전 스테이지 확인
```
