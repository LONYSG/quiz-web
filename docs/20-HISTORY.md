# 프로젝트 히스토리 — 결정과 고민의 흐름 (읽는 순서로)

> **무엇**: 이 프로젝트가 어떤 고민을 거쳐 지금 모습이 됐는지를 **시간순 이야기**로 적는 문서. 07-DECISIONS 가 결정 하나하나의 정본(결정 · 원인 · 되돌리기)이라면, 이 문서는 "왜 그 방향으로 갔나 · 어떤 대안을 두고 저울질했나 · 그 뒤 어떻게 됐나" 를 몇 줄로 잇는다. 세부는 D-nnn · 라운드 보고서 · 문서 번호로 가리킨다.
> **누가 · 언제**: 설계 에이전트가 **설계 턴마다** 방향성 결정이나 큰 고민이 있었으면 항목 하나를 더한다(찬종 2026-11-08 "우리가 이 프로젝트를 진행하면서 했던 결정과 고민사항 등의 히스토리성 내역을 정리 · 계속 그 문서는 관리하자"). GEN · VERIFY · MAIN 세션은 이 문서를 쓰지 않는다. 항목 꼴: **날짜 — 제목** / 상황 · 고민(대안) · 결정과 이유 · 그 뒤 / 참고.
> **최신이 아래**(이야기 순서). 보류 중인 고민은 맨 끝 "열려 있는 고민" 에.

## 10. 플레이 서버와 개발 환경을 나누다 — 브랜치가 아니라 태그 + worktree (2026-11-08)

**상황**: 찬종 "이번 작업은 굉장히 큰 변화 … 배포용(친구들과 플레이) 서버와 개발 서버를 두는 게 효율적일까 · 여기서 브랜치를 나누자는 건데". 실측된 사고는 두 가지 — 이 폴더에서 `npm run build` 하면 플레이 중인 3000 의 클라이언트가 즉시 바뀐다(R073) · 검사 서버가 실 DB 에 붙은 10-21 사고(R060 은 DB 만 분리).
**고민(대안)**: (가) `main` 개발 · `play` 운영 브랜치 둘 (나) 같은 폴더 · 태그만 (다) **태그 + 별도 worktree 폴더** (라) 다른 PC/클라우드에 운영.
**결정**: (다) — D-331 · 구현 R078(D-332~334). 플레이 3000 은 `C:\work\quiz-web-play` worktree 에서 로컬 태그 `play/YYYYMMDD-HHmm` 커밋으로 뜨고, ops 메뉴 1 이 "main 최신 / 지금 그대로 / 태그 입력" 을 묻는다. 개발은 이 트리 3001 · quizweb_dev. 빌드 빗장은 "3000 이 이 폴더에서 떴나"(play.json).
**왜 브랜치가 아닌가**(찬종 질문 2026-11-08): ① 네 세션이 전부 `main` 한 줄기에 push 하는데 운영 브랜치를 두면 라운드마다 merge 가 하나 더 생기고, 운영 쪽에 자기 커밋이 생길 일은 거의 없다(제보 고침도 main 의 MAIN 라운드로) — 커밋이 안 생길 브랜치는 태그와 같다 ② 진짜 문제는 "같은 폴더" 였지 "같은 브랜치" 가 아니다 — 브랜치를 나눠도 한 폴더면 빌드가 플레이를 덮는다 ③ 운영은 "어떤 커밋이 떠 있나" 만 알면 되고 태그 목록이 곧 배포 기록 · 되돌리기 = 옛 태그 고르기.
**확장되면?**(찬종 질문): 태그 방식은 보통 서비스의 릴리스 태그와 같은 꼴이라 그대로 간다. 전제는 **"main 의 모든 커밋은 켤 수 있는 상태"** — 라운드 단위 완결 커밋 + 끝 점검 뒤 push 로 지금 성립. 깨질 수 있는 지점 셋과 대처: (1) 여러 라운드에 걸치는 기능 → **기능 깃발**(tuning 값으로 꺼 둔 채 올림 · 기본) 또는 짧은 **기능 브랜치**(끝나면 합침 — 운영 브랜치가 아님) (2) 운영 급수정 → 옛 태그에서 고쳐 새 태그 · main 에도 같은 고침(브랜치여도 두 번) · 필요해지면 ops "핫픽스" 메뉴 (3) 마이그레이션과 되돌리기 → **더하기만, 지우기·바꾸기는 두 라운드 뒤**(지금까지 29개 전부 더하기). 브랜치로 바꿔야 할 때는 **사람 개발자 여럿이 미완성 커밋을 main 에 올리기 시작할 때** 뿐. 클라우드 이전(11 §7)도 "태그 찍고 그 태그를 배포" 그대로.
**그 뒤**: 문항 데이터(quizweb)는 분리하지 않았다 — GEN 이 고친 문항은 플레이에 바로 나온다(의도 — 문항은 코드와 독립). 플레이 트리 첫 생성은 R078 이 해 둠 · 다음 플레이는 메뉴 1 [1] 만.

## 11. 미니게임 1차 — "전부 샘플로" 와 "한 라운드에 끝까지" 사이 (2026-11-08 저녁)

## 15. 테스트 10시간 전 — "점검을 몰아서" 가 아니라 "처음 켜기를 리허설" (2026-11-09 새벽)

## 16. 주제 세트를 라이어 · 캐치마인드에 그대로 써도 되나 (2026-11-09 새벽 · 찬종 질문)

**상황**: 찬종이 "라이어 · 캐치마인드용 주제 잘 모아 놨어? 주제 뭐뭐 있고 단어 몇 개씩?" → 실측: open 6(동물 81 · 음식 81 · 직업 72 · 장소 71 · 스포츠 68 · 악기 63 = 라이어 430 · 캐치마인드 401) + closed 세트에서 liar 494 · draw 225. 이어서 "주제 선정이 많이 말하기에서 출발한 건데 연관이 큰가, 게임마다 따로 수집하는 게 낫나 — 주제가 한정되고 태그를 일일이 달아야 하며 퀄리티가 나쁘다면".

**설계 판단**: 연관은 **"주제 단위로 모은다" 는 틀**뿐이고 실제 단어는 게임 성격이 다르다 — 열거 게임은 닫힌 목록 전부가 필요하고, 라이어·캐치마인드는 유명하고 설명·그림이 되는 것만 필요하다. §9 가 이미 그래서 open(제시어 전용)과 closed(열거용)를 나눠 놨는데, **closed 항목에 liar/draw 를 일괄로 달아 둔 것**이 잘못이었다: 라이어 풀이 세트를 균등 추첨하니 성경 13 이 음식 81 과 같은 확률로 주제가 되고 "룻기" 가 키워드로 나온다. 그러나 **형식을 게임별로 쪼갤 이유는 없다** — 주제 · 변형(채팅 정답 판정) · qid · 경험 기록이 그대로 쓰이고 다른 것은 플래그뿐이다. **결정**: 데이터로 고친다 — open 8 추가(주제 6 → 14) + closed 태그를 유명한 것만 남기고 끔(태그 0 세트는 풀에서 빠짐) · 코드는 R087 에서 추첨을 항목 수 가중으로. 밤 체인에 끼워 넣어(G043 → **G044 제시어** → G045 생성 · V043 → **V044 적정성**) 아침 메뉴 1 에 들어가게 했다.

## 19. "그리기 어렵다" 는 빼는 사유가 아니다 · 특수문자로 틀리면 안 된다 (2026-11-10)

**상황**: R087 · R088 · R089 · G046~G048 · V044 · V045 가 모두 끝났다. V045 는 캐치마인드 1,651 단어 가운데 302(18%)를 빼자고 했다 — 239 는 "한 장면 그림으로 정답이 하나로 안 보인다"(감기 · 여행 · 주차 · 셔츠/티셔츠), 63 은 같은 그림(태극기/국기). 설계는 "판정을 다시 하지 않는다" 원칙대로 전부 적용을 권했다.

**교훈**: G048 브리프의 "60~90초 선 그림으로 알아볼 수 있나 · 추상어 X" 는 설계가 넣은 기준이었고, GEN(8,122 → 1,651)과 VERIFY(→ 1,349)가 그 기준으로 두 번 깎았다. 찬종이 원한 것은 "아는 단어인가" 였다 — **거르는 기준을 브리프에 쓰기 전에, 그 기준이 재미를 깎는 쪽인지 지키는 쪽인지 찬종에게 한 줄로 먼저 묻는다.** "빼자" 는 제안이 두 번 이어지면 기준부터 의심한다. 그리고 권장안이 원칙(재판정 안 함)에서 나왔더라도, 판정 기준 자체가 찬종 뜻과 다르면 그 원칙은 적용 대상이 아니다.
