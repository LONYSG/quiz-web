## 1. 한눈에 (찬종이 읽는 곳)

1. **방을 만들면 전부 공방 목록에 뜬다.** 친구끼리만 하려면 방을 잠그고(비밀번호) 초대 링크를 보낸다 — 링크로 온 사람은 비밀번호를 안 친다.
2. **방 종류가 셋으로 나뉜다** — 퀴즈 · 캐치마인드 · 라이어. 목록도 탭 셋, 색과 아이콘도 다르다. 방 안에서 방장이 "모드 바꾸기"를 누르면 같은 사람 그대로 종류만 바뀐다.
3. **정원은 방장이 2~10명**으로 정한다. 목록 한 줄에 제목 · 인원 · 잠금 · 대기/진행 · 몇 번째 문제인지 · 미니게임 · 방장 띠 색이 보인다. 목록 위에 "빠른 입장".
4. **솔로 "승급 심사"가 생긴다** — 목숨 3개, 맞힐수록 어려워지고, 기록은 맞힌 개수. 힌트 · 세리머니 없이 빠르게, 한 문제 **문제 길이에 따라 8~13초**(모바일이라고 더 주지 않는다).
5. **어른 띠 다섯 — 화이트 · 블루 · 퍼플 · 브라운 · 블랙벨트, 띠마다 그랄 0~4**("블루벨트 2그랄")는 솔로 최고 기록으로 받는다. 공방에서 닉네임 곁에 띠가 보이고, **솔로를 한 번도 안 한 사람은 "띠 없음" 아이콘**이 보인다. 한 번 받은 띠는 내려가지 않는다. **띠 · 그랄이 오를 때만 포인트**를 준다(5-5).
6. **그대로인 것**: 판 진행 · 정답 판정 · 힌트 · 소리 · 포인트 · 업적 · 친구 초대 · 6자리 방 코드 · 두 주소(공개 · 베타). 노래 · 치이카와 · 상품 그림은 지금처럼 베타에서만.
7. **지금 코드가 이미 절반쯤 준비돼 있다** — 방 "방식"(퀴즈 · 라이어 · 캐치마인드)이 방 설정 한 칸으로 이미 있고, 강퇴 · 차단 · 중간 입장 · 라이어 구경도 있다. 없는 것은 목록 · 잠금 · 정원 · 솔로 · 띠다.
8. **모바일 화면을 먼저 그린다.** 로비 · 목록 · 방 만들기 · 솔로는 휴대폰 한 손으로 쓰는 화면을 기준으로 하고 PC는 넓힌 판.
9. **모르는 사람이 들어오는 순간부터 꼭 있어야 하는 것**(처리방침 · 약관 · 가입 동의 · 신고 · 탈퇴)을 공개 직전 라운드에 묶었다(9절).
10. **라운드 다섯 개**로 나눴다 — 시안 → 공방 → 솔로 · 띠 → 공개 준비 → 다듬기. 라운드마다 스위치로 켜고 끌 수 있다. **찬종이 고른 것은 11절**(2026-11-24 — 비밀번호 숫자 4자리 · 목록은 들어갈 수 있는 방 먼저 · 본 문제 30일 · 정원 8 · 미니게임 기본 꺼짐) · 남은 것 = 띠 기준 숫자(5-1 표 안) · 띠 포인트 표(5-5 표 안 둘).

## 3. 새 구조

### 3-1. 방 종류 — 지금의 "방식"을 키운다 (새 갈래를 만들지 않는다)

**고른 안**: 방 종류를 따로 만들지 않고 `settings.mode` 에서 계산한다.

```
방 종류(kind)   ← mode
퀴즈   quiz     ← 'quiz' · 'minigame'(미니게임만) · 'song'(베타만)
캐치   draw     ← 'draw'
라이어 liar     ← 'liar'
```

- 순수 함수 하나 `roomKindOf(mode)` 를 `shared` 에 둔다. 목록 탭 · 색 · 아이콘 · 빠른 입장이 이것만 본다.
- 근거: ① 판 엔진 셋이 이미 `mode` 로 갈려 시작한다(`start.ts`). ② 사람 · 자리 · 채팅 · 강퇴 · 방장 넘기기 · 끊김 처리는 종류와 무관하게 한 벌이다(`registry.ts` · `ejectPlayer`). ③ 방을 종류별 클래스로 쪼개면 "모드 바꾸기"가 **방 이사**(사람 옮기기 · 소켓 방 바꾸기 · DB `rooms` 새 줄 · 초대 링크 바뀜)가 된다. 지금 구조에서는 `lobby.updateSettings({ mode })` 한 번이고 링크 · 코드 · 사람 · 채팅이 그대로다.
- 바뀌는 것은 **화면의 자리**다 — 방식 고르기가 설정 창 안쪽에서 "방 만들 때 고르는 종류 + 방 안 [모드 바꾸기] 버튼"으로 올라온다.
- "미니게임만"(`mode: 'minigame'`)은 퀴즈 방의 한 선택으로 남긴다(목록에는 퀴즈 탭 · "미니게임" 표시). 노래(`song`)는 베타 자리의 퀴즈 탭에만.
- 미니게임 포함(`settings.minigames`)은 `kind === 'quiz'` 일 때만 뜻이 있다 — 지금도 캐치 · 라이어 판에는 미니게임 자리가 없다(자리 계산이 문제 번호 기준).

### 3-2. 방에 더하는 칸 (메모리 `Room` — DB 열 추가 없음)

| 칸 | 뜻 | 기본 |
|---|---|---|
| `maxPlayers` | 정원 2~10 | **8**(찬종 2026-11-24 · 11절 ⑦) |
| `password` | 잠금 비밀번호(없으면 `null` = 열린 방) | `null` |
| `passwordFails` | 계정 → 틀린 횟수 · 잠긴 때 | 빈 Map |
| `listedAt` | 목록 정렬용(만든 때 = 이미 있는 `createdAt` 을 쓴다 — 새 칸 불필요) | — |

- 방은 메모리에만 살고 서버가 다시 뜨면 전부 닫히므로 **비밀번호를 DB에 두지 않는다**. 해시도 하지 않는다(4자리 숫자는 해시해도 뜻이 없고, 방과 같이 사라지는 값이다). 대신 로그 · 스냅샷 · 목록 · `/debug/room` 에 싣지 않는다 — 방장 화면에만 보낸다(방장이 보고 친구에게 알려 줘야 한다).
- 견줄 때는 이미 있는 `safeEqual`(`auth/session.ts`)을 쓴다.

### 3-3. 방 만들기 · 입장

**만들기** `room.create { title, kind, maxPlayers?, password? }`
- `kind` → 처음 `mode`(퀴즈 `quiz` · 캐치 `draw` · 라이어 `liar`). 공개 자리에서 숨긴 방식은 지금처럼 `validateRoomSettings(…, { hidden })` 가 막는다.
- 정원 범위: 퀴즈 · 캐치 2~10, 라이어 3~10(라이어는 3명부터 시작할 수 있다 — `LIAR.MIN_PLAYERS`).
- 퀴즈 방의 `minigameKeys` 기본 = 7절 표의 "공방 기본 켜짐" 목록.
- 옛 화면(제목만 보냄)도 받는다 — 없는 칸은 기본값(퀴즈 · 열린 방).

**입장** `room.join { roomId, password? }` — 들어오는 길이 셋이고 비밀번호 규칙이 다르다.

| 길 | 보내는 것 | 잠긴 방에서 |
|---|---|---|
| 초대 링크 · 친구 초대 · 친구 [들어가기] | **긴 id**(16자 · 못 맞힘) | **비밀번호 없이 통과** — 링크를 가진 것이 곧 초대다 |
| 6자리 코드 · 공방 목록 · 빠른 입장 | 6자리 코드 | 비밀번호가 맞아야 한다 |
| 다시 붙기(이미 그 방 사람) | 무엇이든 | 통과 |

- 그래서 **목록에는 긴 id를 싣지 않는다 — 6자리 코드만.** 이것 하나로 "초대는 통과"가 새 장치 없이 된다.
- 틀린 횟수 막기: 한 방에 한 계정이 **5번 틀리면 10분** 그 방에 비밀번호를 못 넣는다(`passwordFails`). 여러 방을 돌며 찍는 것은 계정당 1분 10번 한도(`security/limits` 의 `WindowCounter` 를 그대로 쓴다). 4자리면 1만 가지라 10분에 5번은 사실상 못 뚫는다.
- 새 오류 코드 둘: `ROOM_LOCKED`(비밀번호 필요 — 화면이 입력 창을 띄운다) · `WRONG_PASSWORD`(남은 횟수와 함께). `ROOM_FULL` 의 글은 "(최대 10명)" 고정 문구를 뺀다.
- 한계(적어 둔다): 방 안 사람은 누구나 긴 링크를 볼 수 있어 밖에 퍼뜨릴 수 있다. 막는 길은 방장의 강퇴 · 차단뿐이다 — 지금과 같다.
- 순서: 차단 검사 → 자리 검사 → **잠금 검사** → 닉네임 검사 → `attachToRoom`(정원 검사는 `addPlayer` 안 — 동기라 두 사람이 동시에 마지막 자리를 못 차지한다).

### 3-4. 정원 · 잠금 바꾸기

- 새 이벤트 `room.updateAccess { maxPlayers?, password? }` — 방장 · **어느 상태에서나**(입장 검사에만 쓰이는 값이라 판 도중에 바꿔도 판이 안 흔들린다). 판 설정(`lobby.updateSettings`)과 섞지 않는다.
- **지금 인원보다 작게는 거절**한다("지금 6명이에요 — 6명부터 고를 수 있어요"). 사람을 내보내는 일은 강퇴로만 한다.
- 끊겨서 자리만 남은 사람(60초 유예)도 인원에 센다 — 지금 `room.players.size` 기준 그대로.
- 잠금을 걸거나 풀어도 안에 있는 사람은 그대로다. 바뀌면 목록에 바로 반영.

### 3-5. 모드 바꾸기

- 방장 · **대기실(LOBBY)에서만.** 이미 `lobby.updateSettings` 가 로비에서만 받는다. 판 도중과 결과 화면에서는 버튼이 "이 판이 끝나면 바꿀 수 있어요"로 흐려진다.
- **판 도중에는 안 바꾼다** — 판을 강제로 끝내고 바꾸는 길을 따로 만들지 않는다(방장에게는 이미 "강제 종료 → 대기실"이 있다).
- 점수: 판 점수는 판을 시작할 때마다 0이 된다(`start.ts` 398줄). 옮길 것이 없다. 포인트 · 업적 · 띠는 계정에 붙어 있어 그대로.
- 바뀌는 순간: 시스템 채팅 한 줄("캐치마인드 방으로 바뀌었어요") · 목록에서 탭 이동 · 화면 색 · 아이콘 바뀜 · 정원이 새 종류의 아래 한계보다 작으면(라이어 3) 정원을 3으로 올린다.
- 인원이 모자라도 바꾸는 것은 된다 — 시작이 막힐 뿐이다(지금 `LIAR_START_BLOCK` · `DRAW_START_BLOCK` 그대로).
- 팀전은 지금처럼 라이어 · 캐치에서 못 켠다(`LIAR_TEAM_BLOCK` · `DRAW_TEAM_BLOCK`).

### 3-6. 공방 목록

**어디서 오나**: 서버 메모리의 방 Map(`allRooms()`)에서 만든다. **DB를 읽지 않는다** — "타이머로 DB를 깨우지 않는다"(`02` 3장)를 지킨다.

**목록 한 줄**(`RoomListItem`) — 화면에 필요한 것만, 개인 정보 없음:

```
code        6자리 (입장 열쇠 — 긴 id 는 싣지 않는다)
title       방 제목
kind        quiz | draw | liar          tag   null | 'minigame' | 'song'
players     지금 인원                    max   정원
locked      잠금 여부
phase       waiting | playing
progress    { done, total } | null      (퀴즈 = 몇 번째 문제/문제 수 · 미니게임만 = 끝난 수/전체 · 캐치 · 라이어 = 몇 판/전체)
minigames   미니게임 포함 여부(퀴즈 방)
level       초급 | 중급 | 고급 (퀴즈 방)
host        { nickname, belt }           (방장 닉네임 · 띠 단계 — 5절)
```

- `phase`: `LOBBY` = waiting · 나머지(카운트다운~결과)는 playing. `PAUSED` 도 playing 으로 보이되 빠른 입장 대상에서는 뺀다.
- 자리(site)가 같은 방만 준다 — 공개 목록에 베타 방이 안 보인다(지금 입장 규칙과 같다).
- 차단당한 방은 그 사람 목록에서 뺀다(들어가 봐야 막힌다).

**어떻게 새로 고쳐지나**
- 화면이 목록에 있는 동안만 구독한다 — `directory.watch { kind }` / `directory.unwatch`. 서버는 소켓을 `dir:<site>:<kind>` 묶음에 넣고 바로 한 번 통째로 보낸다(`directory.list`).
- 방에 변화가 생기는 자리(만들기 · 삭제 · 입장 · 퇴장 · 판 시작 · 다음 문제 · 판 끝 · 잠금 · 정원 · 제목 · 모드 바꾸기)마다 `markDirectoryDirty(room)` 한 줄 — 표시만 한다.
- 이미 도는 100ms tick 이 **1초에 한 번** 더러워진 탭만 다시 만들어 그 묶음에 보낸다. 변화가 없으면 아무것도 안 보낸다. 구독자가 없는 탭은 만들지도 않는다.
- 방을 고르는 순간 목록이 낡았을 수 있다 — 입장은 언제나 서버가 다시 검사한다(꽉 참 · 잠김 · 사라짐 → 알림 + 목록 다시 받기).

**방이 많아질 때**
- 한 줄은 150바이트 안팎(어림). 탭 하나에 **100줄까지** 통째로 보낸다(≈ 15KB · 1초에 한 번 · 보는 사람에게만).
- 100줄을 넘으면 정렬 뒤 위 100줄만 보내고 `more: true` — 화면은 "방 코드로 찾기 · 빠른 입장"을 권한다. 페이지 넘기기는 실제로 100방을 넘는 날 만든다(R108 기준 이 PC 한계가 약 1,000명 = 8명 방 125개 — 한 탭이 100을 넘기 전에 서버가 먼저 찬다).
- 변화분만 보내는 방식(diff)은 만들지 않는다 — 통째 + 1초 묶음이 더 단순하고 위 크기에서는 충분하다.

**정렬**(찬종 2026-11-24 · 11절 ④ — 추천 그대로): ① 들어갈 수 있는 방(안 잠김 · 자리 남음) 먼저 ② 대기 중 먼저 ③ 사람 많은 순 ④ 새 방 순. 잠긴 방 · 꽉 찬 방 · 진행이 거의 끝난 방은 아래로.

### 3-7. 빠른 입장

`directory.quickJoin { kind }` — 서버가 고르고 바로 넣는다.

1. 후보 = 같은 자리 · 그 종류 · 안 잠김 · 자리 남음 · 내가 차단 안 됨 · 일시정지 아님.
2. 차례: **대기 중이고 2명 이상**(곧 시작) → **대기 중 1명** → **진행 중인 퀴즈 · 캐치**(남은 진행이 30% 넘는 방) → 진행 중 라이어(구경부터라 맨 뒤).
3. 같은 차례 안에서는 사람이 많은 방(정원의 80%를 넘지 않는 선에서) — 꽉 찬 방 하나보다 적당히 찬 방이 낫다.
4. 고른 방이 그 사이 꽉 찼으면 다음 후보로 2번까지 더 본다.
5. 하나도 없으면 방을 대신 만들지 않는다 — "지금 열린 방이 없어요" + [방 만들기] 버튼.

### 3-8. 모르는 사람과 놀 때 — 강퇴 · 신고 · 차단

- **강퇴 · 차단(방장)**: `KickFlow` · `host.kick` 이 공방에서도 그대로 된다 — 고칠 것이 없다. 차단은 지금 "그 방이 있는 동안"이다(방이 사라지면 풀림) — 그대로 둔다.
- **빈틈 하나**: 방장이 나가면 가장 먼저 들어온 사람이 방장이 된다. 공방에서는 모르는 사람이 방장을 물려받아 잠금 · 강퇴를 쓸 수 있다 → 그대로 둔다(방이 살아남는 쪽이 낫다). 다만 **잠긴 방의 비밀번호는 새 방장에게 보인다**는 것을 화면 글로 알린다.
- **사람 신고**(새로): 사람 카드(`PersonCard`)에 [신고] — 사유 고르기(욕설 · 도배 · 부적절한 닉네임/사진/그림 · 기타) + 서버가 그 방의 **최근 채팅 30줄**을 같이 붙여 저장한다(채팅 원문은 평소 DB에 안 남긴다 — 신고 때만, `01` 9장에 한 줄 더함). 표는 `app_reports` 에 `kind: 'user'` 로 얹는다(이미 `reports:report` 흐름이 있다) — 열 추가만.
- **개인 차단**(새로): 내가 차단한 사람의 채팅 · 이모티콘을 **내 화면에서만** 가린다. 표 `account_blocks(account_id, blocked_id)` · 로그인 때 한 번 읽어 화면이 거른다(서버는 방송을 그대로 한다 — 판정 경로를 안 건드린다). 정답은 가리지 않는다(누가 맞혔는지는 보여야 한다).
- **욕설 거르기**: 방 제목 · 닉네임(목록에 그대로 드러난다)에만 금칙어 목록을 건다. 채팅은 거르지 않고 신고 · 차단으로 푼다(찬종의 "도배도 재미" 방침 유지).
- 도배 한도는 지금 값(5초 5번 → 5초 잠금) 그대로.

### 3-9. 스위치 — 나눠 켜기

| 스위치(서버 환경 변수) | 켜면 | 끄면 |
|---|---|---|
| `GONGBANG=1` | 목록 · 빠른 입장 · 방 만들기의 종류 · 정원 · 잠금 | 오늘과 같다(제목만 · 목록 없음) — 목록 이벤트는 거절 |
| `SOLO=1` | 솔로 "승급 심사" | 메뉴에 안 보임 · 이벤트 거절 |
| `SOLO_GUEST=1` | 로그인 안 한 사람의 연습(기록 없음) | 로그인한 사람만 |
| `BELT=1` | 띠 표시(방 · 목록 · 프로필) | 기록은 쌓이되 표시 안 함 |
| `EXPERIENCE_DAYS=30` | 본 문제 유효 기간(6절) | 0 = 지금처럼 영원히 |

- 화면은 `/api/site` 에 실린 값으로 메뉴를 그린다(지금 `siteHidden` 을 받는 길 그대로).
- **옛 방과 새 방이 같이 사는 문제는 없다** — 방은 메모리뿐이고, 새 코드를 올리려면 서버를 다시 띄워야 하며 그때 방은 전부 닫힌다(부팅 정리).
- 베타 자리에서 먼저 켜 보고(지인끼리 목록 · 솔로 · 띠를 써 봄) 공개 자리는 `PUBLIC_OPEN` 으로 따로 연다.

## 4. 솔로 — "승급 심사"

### 4-1. 방을 쓰지 않는다 (가벼운 판을 따로 둔다)

`server/src/solo/engine.ts`(새) — 계정 하나에 `SoloRun` 하나(메모리 `Map<accountId, SoloRun>`).

- 방(`Room`)을 재활용하면 목록 · 채팅 · 건너뛰기 투표 · 힌트 · 정답 공개 8초 · 일시정지 · 본 문제 기록 · `answer_events`(= 포인트)가 전부 딸려 와 하나씩 꺼야 한다. 솔로는 사람 하나 · 채팅 없음 · 경험 안 씀이라 따로 두는 편이 훨씬 작다.
- **그대로 쓰는 것**: 문항 풀(`ensureSharedPool` — 한 벌) · 판정(`normalizeAnswer` · `flexMatch` · 문항의 `answersNorm` · `answersFlex`) · 100ms tick · 소켓 검사(`guard`) · 화면의 `QuestionText` · `noCopy` · 타이머 막대 · 소리.
- 방에 있는 사람은 솔로를 시작할 수 없고, 솔로 중에는 방에 들어갈 수 없다(끝내고 가기 확인).

### 4-2. 흐름 (서버가 한 문제씩 낸다)

```
화면  solo.start                       → 서버: 판 만들기 · 풀 준비 · solo_runs 줄 하나
서버  solo.question { n, text, category, grade, endsAt, lives, correct }   ← 정답 · 힌트는 보내지 않는다
화면  solo.answer { n, text }          (시간 안에는 여러 번 쳐도 된다 — 오타 구제 · 지금 퀴즈와 같다)
서버  맞음 → solo.result { ok: true,  answer, correct } → 0.8초 뒤 다음 문제
      시간 끝 → solo.result { ok: false, answer, lives } → 1.5초 뒤 다음 문제(정답은 보여 준다 — 공부)
      목숨 0 → solo.end { correct, best, belt, newBelt, wrongs[] }
화면  solo.quit                        → 그때까지 기록으로 끝
```

- 판정은 동기 블록에서(await 없음) — 방 판정과 같은 규칙. DB 쓰기는 판정 뒤에 기다리지 않고.
- `n` 이 지금 문제 번호와 다르면 버린다(방의 epoch 와 같은 구실 — 앞 문제에 친 답이 늦게 와서 다음 문제에 맞는 일을 막는다).
- 틀린 답에는 아무 반응도 보내지 않는다(지금 퀴즈와 같다). 시간 끝만 "틀림"이다.
- 끝 화면: 기록 · 최고 기록 · 띠 · **틀린 세 문제의 정답과 해설**(목숨 3이라 틀린 문제는 3개뿐이다 — 여기서 해설이 제 몫을 한다).

### 4-3. 어려움이 오르는 규칙

맞힌 개수에 따라 등급(`difficulty_score` 1~5 · `19`)을 올린다. 표는 `shared` 의 상수 한 곳(`SOLO_RAMP`) — 버전 번호를 기록에 같이 남긴다.

| 지금까지 맞힌 개수 | 나오는 등급 |
|---|---|
| 0~4 | 1 |
| 5~9 | 1과 2 반반 |
| 10~14 | 2 |
| 15~19 | 2와 3 반반 |
| 20~29 | 3 |
| 30~39 | 3과 4 반반 |
| 40~49 | 4 |
| 50~59 | 4가 70% · 5가 30% |
| 60~ | 4와 5 반반 |

- 뽑기: 그 등급에서 · 이번 판에 안 나온 것 · 이번 판에 나온 정답과 안 겹치는 것(지금 `usedAnswerNorms` 규칙) · **알가치 1은 뺀다**(예비 문항 — `19` §5) · 분야는 전부.
- 같은 문제가 다시 나와도 된다(찬종). 다만 **내가 최근 솔로에서 본 200문항은 뒤로 미룬다** — 판을 시작할 때 `solo_answers` 에서 한 번 읽는다(같은 문제가 판마다 첫머리에 나오면 재미가 없다 · 등급 1은 746개라 여유가 있다).
- 등급 5는 알가치 1을 빼면 78개뿐이다 → 60개를 넘기는 사람은 같은 문제를 자주 본다. 찬종 방침("공부해서 맞힌 셈")대로 둔다. 등급 5 문항이 늘면 저절로 풀린다(GEN 우선순위 — `19` §5).
- 그 등급에 낼 문제가 없으면 아래 등급에서 채운다(지금 `gradeOrder` 와 같은 "아래 먼저").

### 4-4. 시간

실측(사람 판 · 힌트가 나오기 전에 맞힌 것만 — 등급이 기록된 637문항 가운데): 정답까지 가운데 **3.9~5.8초** · 느린 쪽 10%가 **6.8~9.1초**. 질문은 가운데 54자, 정답은 3~5자.

**고른 식**(찬종 2026-11-24 · 11절 ② — "모바일이라고 시간을 더 주지는 마"): `8초 + 질문이 30자를 넘는 10자마다 0.5초 + 정답이 5자를 넘는 글자마다 0.4초` · **8~13초 사이** · **기기에 따라 바꾸지 않는다**(R113 추천의 모바일 +2초는 뺐다).
- 보통 문제(54자 · 4자) ≈ 9초 · 긴 문제(69자 · 9자) ≈ 11.5초.
- 읽고 → 떠올리고 → 치기에는 되지만, 검색 창을 열어 질문을 옮겨 치고 결과를 읽기에는 모자란다.
- 기기는 시간에 쓰지 않는다(속일 거리가 없다). 기록에는 기기를 남겨 "모바일에서 시간 끝으로 틀린 비율"을 나중에 본다 — 모바일이 눈에 띄게 불리하면 다듬기 라운드에서 찬종에게 다시 묻는다.
- 식의 숫자는 `shared` 상수 · 서버 환경 변수로 덮을 수 있게(지금 `config.tuning` 꼴) — 베타에서 "시간 끝으로 틀린 비율"을 보고 맞춘다.

### 4-5. 부정행위 — 막는 법 · 뚫리는 법 · 남는 위험

| 항목 | 막는 법 | 뚫리는 법 | 남는 위험 |
|---|---|---|---|
| 문제 글 복사 → 검색 | `.no-copy`(선택 · 복사 · 꾹 누르기 · 끌기 막기 — 이미 있다) | 개발자 도구 · 화면 글자 인식 | 낮음 — 시간이 더 큰 벽이다 |
| 시간 늘리기 | 마감(`endsAt`)은 서버 시계. 도착이 마감 + 0.3초(통신 여유)를 넘으면 무효. 화면 시계는 보여 주기만 | 못 뚫는다 | 통신이 느린 사람이 0.3초 안팎 손해 |
| 다른 탭 · 앱으로 나가기 | 화면이 가려지거나(`visibilitychange`) 창이 초점을 잃으면(`blur`) `solo.away` → **그 문제는 실패**(목숨 −1). 시작 화면에 미리 알린다 | 화면 코드를 고쳐 신호를 안 보내기 · 옆에 둔 다른 기기 | 중간 — 고친 화면은 못 막는다. 전화 · 알림으로 억울한 실패가 생긴다(판마다 몇 번인지 기록해 본다) |
| 옆 기기로 검색 · 옆 사람이 알려 주기 | 못 막는다 — 시간만이 벽 | 그대로 | **남는다** — 9초 안에 검색해 치는 것은 어렵지만 음성 검색 · AI는 된다 |
| 화면을 찍어 AI에게 묻기 · 자동 풀이 | 못 막는다. 대신 **흔적을 남긴다** — 문제마다 걸린 시간 · 나감 여부 · 기기. 사람보다 빠른 답(0.6초 안)이 잦거나 등급 4~5를 늘 같은 속도로 맞히면 그 판에 표시(`flags`) | 사람 속도로 흉내 내면 안 걸린다 | **남는다** — 띠는 자동으로 뺏지 않고 운영자가 보고 정한다. 높은 띠가 이상하면 여기부터 본다 |
| 틀려서 본 정답을 모으기(문제 은행 만들기) | 판 시작 한도(계정당 1시간 30판) | 여러 계정 · 오래 모으기 | 남는다 — 공방도 정답을 공개하므로 솔로만의 문제가 아니다. 찬종 방침상 "외워서 맞히는 것"은 허용이다 |
| 여러 계정으로 연습하고 본 계정으로 기록 | 가입 한도(R107) | 그대로 | 낮음 — 같은 문제를 다시 봐도 되는 놀이라 얻는 것이 적다 |
| 끊어서 시간 벌기 | 끊겨도 **문제 시계는 간다.** 30초 안에 돌아오면 이어서, 넘으면 그때까지 기록으로 끝 | 못 뚫는다 | 진짜 끊긴 사람이 문제 하나를 잃는다 |

### 4-6. 기록 저장 (모양만 — 마이그레이션은 솔로 라운드가 쓴다)

```
solo_runs
  id bigserial PK · account_id → accounts ON DELETE CASCADE
  started_at · ended_at
  correct smallint          맞힌 개수(= 기록)
  asked smallint            낸 문제 수
  end_reason text           lives | quit | away | server_restart
  device text · site text
  ramp_version smallint     어려움 표 버전(표를 바꿔도 옛 기록을 가를 수 있게)
  flags jsonb               의심 표시(빠른 답 수 · 나간 횟수 …)

solo_answers
  run_id → solo_runs ON DELETE CASCADE · n smallint · PK (run_id, n)
  question_id → questions · grade smallint
  correct boolean · ms int(걸린 시간) · limit_ms int · away boolean

accounts 에 열 셋
  solo_best smallint DEFAULT 0      최고 기록
  belt_step smallint                지금 띠 단계(0~24 · 없으면 NULL = 띠 없음 — 5절) · 내려가지 않는다(운영자 무효만 예외 — 5-3)
  belt_at timestamptz               그 띠를 받은 때
```

- 답 하나마다 `solo_answers` 에 쓴다(기다리지 않고) — 서버가 꺼져도 그때까지의 기록이 남는다. 부팅 정리(`bootCleanup`)에 "열린 솔로 판 닫기" 한 줄.
- **덤**: `solo_answers` 는 "한 사람이 혼자, 힌트 없이, 짧은 시간에" 푼 깨끗한 정답률이다 — 방 기록보다 난이도 보정(`19`)에 훨씬 좋다. 지금 방 기록은 누가 먼저 맞히면 나머지가 가려져 개인 정답률을 못 잰다.
- 포인트: 솔로는 `answer_events` 를 쓰지 않으므로 판에서는 **포인트가 안 생긴다**. 대신 **띠 · 그랄이 오를 때만** 차액을 `point_grants`(reason `'belt'`)로 준다(찬종 2026-11-24 · 11절 ⑤ — 5-5). 지금 포인트 식(`POINTS_SQL`)이 이미 `point_grants` 를 더하므로 식은 안 바뀐다.
- 본 문제: `question_experiences` 를 **읽지도 쓰지도 않는다** — 솔로에서 본 문제가 공방의 "이미 본 문제"가 되지 않는다(찬종).
- 업적: 1차에는 솔로 업적을 만들지 않는다(띠가 그 구실을 한다).

### 4-7. 여러 탭 · 끊김 · 손님

- 한 계정은 연결이 하나다 — 새 탭을 열면 옛 탭이 끊기고 새 탭이 **같은 판을 이어받는다**(서버가 지금 문제를 다시 보낸다 · 시계는 그대로). 탭 둘로 두 판을 돌릴 수 없다.
- 끊김은 4-5 표대로(시계는 가고 30초 뒤 끝).
- **손님 연습**(`SOLO_GUEST`): 지금은 로그인 안 한 소켓이 10초쯤 뒤 끊기고 방 이벤트를 못 쓴다. 손님에게는 `solo.*` 만 열어 주고(끊는 타이머는 솔로 중에 멈춤) 기록은 저장하지 않는다 — 끝 화면에 "가입하면 이 기록으로 띠를 받아요". IP당 한도를 건다. 솔로 라운드의 뒤쪽 항목으로 두고, 시간이 모자라면 다듬기 라운드로 넘긴다.

## 5. 띠

> ★ R114 고침(찬종 2026-11-24 · 11절 ③): **어른 띠 다섯 — 화이트 · 블루 · 퍼플 · 브라운 · 블랙벨트**(영어 이름 그대로 — 찬종: "무조건 현직자들이 쓰는 말이어야 해") · 띠마다 **그랄 0~4**(줄 대신 "그랄" — "블루벨트 2그랄"). R113 의 9띠 × 줄 4 는 걷었다.

### 5-0. 실제 주짓수 띠의 생김새 (그림의 근거 — R114 가 연 문서)

- 어른 띠는 화이트 → 블루 → 퍼플 → 브라운 → 블랙(위키백과 "Brazilian jiu-jitsu ranking system"의 어른 띠 표 · 노랑 · 주황 · 초록은 "일부 도장"으로만 적힘).
- 띠마다 그랄(스트라이프)은 **보통 4개까지** — "students have the opportunity to earn up to generally 4 stripes on their belt"(같은 문서) · 그랄은 **띠 끝의 검은 칸(랭크 바)에 감는 운동용 테이프**("small pieces of athletic tape wrapped around the black bar at the end of your belt" — BJJ More "How BJJ Belts Work" · 2026-11 갱신본).
- **블랙벨트는 그 칸이 빨강**이고 단(degree)을 빨간 칸에 감는다("On a black belt the bar is red" — 같은 문서 · Elite Sports "What Do the Stripes on a BJJ Belt Actually Mean?" 2026-09-03: "marked with a red bar near the end of the belt"). 위키백과는 "흰 칸 블랙벨트 = 일반 수련자 · 빨간 칸 = 표준 블랙벨트"라고도 적는다.
- 테이프 색은 문서마다 "흰 테이프"를 못 박지 않는다(Elite Sports: "colored athletic … tape") — 그림은 지시서대로 **흰 테이프**로 그렸다(가장 흔한 꼴 · 확인 못 한 것은 이 한 줄).
- 우리 게임의 "블랙벨트 0~4그랄"은 실제의 블랙벨트 단(1~6단)과 다르다 — 이름은 "블랙벨트 2그랄"로 같은 꼴을 쓴다(찬종이 고른 이름 규칙 그대로 · 실제 단과 헷갈림이 걱정되면 다듬기 라운드에서 다시).

### 5-1. 처음 기준 (솔로 최고 기록 → 띠 · 그랄) — ⑨ 아직 안 정함 · 표 안 둘

단계 = 띠 5 × 그랄 0~4 = **25칸**(`belt_step` 0~24 · 띠 = 5로 나눈 몫 · 그랄 = 나머지). 칸마다 "그 칸이 시작되는 기록".

**안 A (추천) — 블랙 50 그대로 · 블루는 "퀴즈 좋아하는 사람"부터**

| 띠 | 0그랄 | 1그랄 | 2그랄 | 3그랄 | 4그랄 |
|---|---|---|---|---|---|
| 화이트 | 첫 판을 끝냄(0개여도) | 3 | 6 | 9 | 12 |
| 블루 | 15 | 18 | 21 | 24 | 27 |
| 퍼플 | 30 | 32 | 34 | 36 | 38 |
| 브라운 | 40 | 42 | 44 | 46 | 48 |
| 블랙 | 50 | 55 | 60 | 70 | 80 |

**안 B — 블루를 빨리**(가볍게 하는 사람도 블루에 닿는다 · 블랙 50 그대로)

| 띠 | 0그랄 | 1그랄 | 2그랄 | 3그랄 | 4그랄 |
|---|---|---|---|---|---|
| 화이트 | 첫 판 | 2 | 4 | 6 | 8 |
| 블루 | 10 | 13 | 16 | 19 | 22 |
| 퍼플 | 25 | 28 | 31 | 34 | 37 |
| 브라운 | 40 | 42 | 44 | 46 | 48 |
| 블랙 | 50 | 55 | 60 | 70 | 80 |

**사람 넷이 닿는 곳** — R113 의 어려움 표(4-3)와 사람 넷의 맞힐 확률을 그대로 두고 R114 가 다시 돌린 모의 계산(한 판 2만 번 · "20판 해 본 최고"는 4천 사람). 스크립트는 `ai-out/R114.txt` 3절.

| 사람 | 등급 1~5 확률 | 한 판(아래 10% · 가운데 · 위 10%) | 20판 최고(아래 10% · **가운데** · 위 10%) | 안 A | 안 B |
|---|---|---|---|---|---|
| 가볍게 하는 사람 | 80 · 40 · 17 · 7 · 3% | 4 · 7 · 11 | 11 · **12** · 14 | **화이트 4그랄** | **블루 0그랄** |
| 퀴즈 좋아하는 사람 | 93 · 75 · 50 · 25 · 10% (가정) | 8 · 14 · 19 | 19 · **22** · 26 | **블루 2그랄** | 블루 4그랄 |
| 고수 | 98 · 92 · 78 · 55 · 30% (가정) | 16 · 23 · 31 | 30 · **35** · 41 | **퍼플 2그랄** | 퍼플 3그랄 |
| 최상위 | 99 · 97 · 90 · 75 · 50% (가정) | 21 · 32 · 45 | 44 · **50** · 52 | **블랙 0그랄** | 블랙 0그랄 |

- 추천 A 의 까닭: 실제 도장에서도 블루벨트는 "제대로 한다"는 표시다 — 가볍게 몇 판 해 본 사람은 화이트에 그랄을 쌓고, 퀴즈를 즐기는 사람부터 블루. 블랙은 R113 처럼 최상위가 20판쯤 해서 닿는 자리(50)에 둔다. B 는 처음 며칠 블루가 흔해진다.
- 첫 줄(가볍게)만 실측(사람 1~2명 판에서 8초 안에 맞힌 비율 — 등급 1: 80% · 2: 33% · 3: 14%)에 닻을 내렸고 나머지 셋은 **가정**이다(R113 그대로). 그래서 이 표는 "처음 값"이고 5-2 로 다시 맞춘다.
- 같은 문제가 다시 나오고 외울 수 있어 기록은 시간이 갈수록 오른다 — 표는 조금 짜게 잡았다.

### 5-2. 나중에 분포로 다시 맞추기

- 때: 로그인한 솔로 참가자 **200명** 또는 솔로를 연 지 **4주** 중 먼저 오는 때, 그 뒤로는 분기에 한 번.
- 방법: 사람마다 최고 기록의 분포를 뽑아(`solo_runs` 한 번 세기 — 스크립트 `npm run belt:report`) 띠가 시작되는 기록을 **위에서부터의 비율**로 다시 정한다.

| 띠 | 목표(그 띠 이상인 사람) |
|---|---|
| 블랙 | 위 1% 안팎 |
| 브라운 | 위 5% |
| 퍼플 | 위 15% |
| 블루 | 위 40% |
| 화이트 | 첫 판(고정) |

- 그랄은 띠와 다음 띠 사이를 다섯으로 나눈다(5-1 표와 같은 셈 · 블랙의 그랄만 위 0.5% · 0.2% … 처럼 따로).
- 기준 표는 `shared` 상수 + 버전 번호. 바꿀 때 07에 결정 한 줄.

### 5-3. 기준이 바뀌면

- **받은 띠는 내려가지 않는다.** `belt_step` 은 "지금까지 닿은 가장 높은 칸"이다 — 새 기준으로 다시 셈한 값이 더 높을 때만 올린다.
- 기준이 올라가서 내 최고 기록이 새 표에서는 낮은 띠여도 띠는 그대로다. 다음 그랄 · 띠는 새 기준을 넘어야 받는다.
- 의심 표시가 붙은 판(4-5)은 띠 셈에서 자동으로 빼지 않는다 — 운영자가 판을 무효로 돌리면(`solo_runs.flags.void`) 그때 다시 센다. 이때만 내려갈 수 있다(이미 준 포인트는 거두지 않는다 — 5-5).

### 5-4. 표시

아이콘 · 그랄 표시 · "띠 없음" 아이콘은 **R114 시안(`ai-out/R114-시안.html` 맨 위 표)에서 찬종이 고른다.** 자리는 셋이다.

| 자리 | 크기 | 보이는 것 |
|---|---|---|
| **공방 목록** 방 줄의 방장 닉네임 앞 | 작게 16~20px | 띠 색 아이콘(그랄은 고른 표시 꼴대로 — 작은 자리에서 줄 넷이 안 읽히면 숫자 또는 생략) |
| **방 안** 참여자 칸 닉네임 곁 | 24~28px | 띠 + 그랄. 채팅 줄에는 넣지 않는다(이미 색 · 사진이 있다 — 붐빈다) |
| **프로필 카드**(`PersonCard`) | 크게 64px 이상 | 띠 + 그랄(테이프 줄) · "블루벨트 2그랄" 글 · 최고 기록 · 받은 날 |

- **솔로 끝 화면**: 띠 + "다음 그랄까지 2개".
- **띠 받는 순간**: 솔로 끝 화면에서만 연출(새 띠가 묶이는 짧은 그림 + 소리 하나 + 받은 포인트 "+40P"). 방에 있을 때 받는 일은 없다(솔로는 방 밖).
- ★ **띠가 없는 사람(솔로를 한 번도 안 함 · 손님)은 띠 자리에 "띠 없음" 아이콘**(찬종 2026-11-24 — "벨트 말고 다른 아이콘 · 약간 귀엽지만 허접해 보이는 것"). 누르면 "아직 띠가 없어요 — 승급 심사 한 판이면 화이트벨트". R113 의 "아무 표시도 없다"를 바꿨다.

## 6. 중복 문제 (공방)

### 6-1. 지금 규칙을 다시 읽으면

- 2단계가 이미 **"안 본 사람이 많은 문제일수록 잘 뽑힌다"**(안 본 사람 수 가중 무작위)이다. 찬종이 걱정한 "모르는 사람 10명이 모이면 누구도 안 본 문제가 빨리 준다"는 1단계 얘기이고, 1단계가 비어도 판은 2단계로 계속 간다.
- 정말 막히는 것은 둘이다. ① **방 전원이 본 문제는 영원히 못 낸다** ② **본 사람은 그 문제에서 구경만 한다**(판정 제외) — 오래 한 사람일수록 공방에서 구경이 늘어난다.
- 얼마나 빨리 주나(셈 — 서로 상관없이 봤다고 가정): 10명이 각자 풀의 5%(381문항)를 봤으면 "누구도 안 본" 것이 60% · 14%(지금 가장 많이 본 사람 수준)면 22% · 30%면 3% · 40%면 0.6%. 지금 실측은 1단계 8,598번 · 2단계 132번 · 3단계 0번이라 아직 먼 얘기지만, 공방이 열리면 많이 하는 사람부터 닿는다.

### 6-2. 새 규칙

**(가) 2단계를 "가장 많은 사람이 안 본 문제부터"로** — 기술 결정 · 이 문서가 정한다.
- 지금은 9명이 안 본 문제와 1명만 안 본 문제가 9:1로 섞여 뽑힌다. 이것을 **안 본 사람 수가 가장 많은 묶음에서만** 뽑게 한다(그 묶음 안에서는 지금처럼 등급 · 알가치 규칙).
- `select.ts` 는 순수 함수라 옵션 하나(`strictUnseen`)와 단위 테스트로 끝난다. 2명 방에서는 지금과 결과가 같다(안 본 사람 수가 1뿐).
- 찬종의 "가장 적은 사람이 본 문제 차례로"가 바로 이것이다.

**(나) 본 문제에 유효 기간** — 게임 규칙(`01` 12장)이 바뀐다 — **찬종 2026-11-24 채택: 30일**(11절 ⑥ · `EXPERIENCE_DAYS=30`).
- 마지막으로 본 지 N일이 지난 문제는 **안 본 것으로 친다** → 다시 나올 수 있고, 그 사람도 다시 정답자가 될 수 있다. 단계 규칙(1 → 2 → 3)은 그대로 두고 "봤다"의 뜻만 바꾼다 — 그래서 ①과 ②가 한꺼번에 풀린다.
- 고칠 곳: `question_experiences` 에 **`last_experienced_at` 열 추가**(지금은 처음 본 때만 있고 덮어쓰지 않는다 — 그대로 두면 한 번 기간이 지난 문제가 그 뒤로 영원히 "안 본 것"이 된다) · 기록할 때 이 열을 갱신 · 읽는 SQL 셋(`loadExperienced` · `countExperiencedByAccount` · `countAvailableQuestions`)에 기간 조건 한 줄.
- "경험률"(로비에 보이는 %)은 기간과 상관없이 지금까지 본 것 전부로 둔다(그 사람이 얼마나 했는가의 표시).
- 숫자 정하는 법: 기간은 환경 변수(`EXPERIENCE_DAYS`). 베타에서 두 가지를 본다 — "기간이 지나 다시 나온 문제를 그 사람이 10초 안에 맞힌 비율"(높으면 기억하고 있다는 뜻 → 기간을 늘린다) · "판에서 구경한 문제의 비율"(높으면 줄인다).
- 걱정: 30일 전에 본 문제는 기억날 수 있다 — 처음 보는 사람보다 유리하다. 공방에서는 "아는 문제가 가끔 나온다"가 "구경만 한다 · 판이 일찍 끝난다"보다 낫다고 본다. 친구 방도 같은 규칙을 쓴다(방 종류로 가르지 않는다 — 규칙이 둘이면 설명이 안 된다).

**(다) 솔로와 공방은 섞지 않는다** — 솔로는 `solo_answers` 만 쓰고 `question_experiences` 를 건드리지 않는다(4-6).

**그대로 두는 것**: 같은 판 같은 정답 금지 · 정답 흘림 미루기 · 등급 계획 · 알가치 가중 · 중간 입장자의 경험 합치기 · 문제가 정말 없으면 일찍 끝내기.

## 9. 공개 전에 같이 가야 하는 것 (`23` 4절에서 "꼭"인 것)

모르는 사람이 들어오는 순간 = **공개 주소를 여는 순간**(`PUBLIC_OPEN=1`)이다. 베타(지인)에서 공방 · 솔로를 켜 보는 동안에는 필요 없다.
