### Q-63. ★ Gemini 유료 전환 여부 — 무료 한도로는 목표에 도달하지 못한다

**상태**: 결정 필요 (운영·비용 판단이므로 혼자 결정하지 않는다)

**배경 — R010 실측**

무료 한도로 100건 배치를 하루에 끝내지 못했다.

| 관측 | 값 |
|------|-----|
| 429 를 맞기까지 성공한 가공 호출 | 2~4회 |
| 그날 실제로 LLM 을 지난 문제 수 | **20건** (목표 100건) |
| 그날 누적 토큰 | 약 3만~4만 (추정. 일부는 클라이언트 밖 호출) |

★ 이 속도로는 1,000건 확보에 **수십 일**이 걸린다.
Q-46은 "친구들과의 실플레이는 1,000건 이상 확보 후" 로 정했다.

**선택지**

| 안 | 내용 | 대가 |
|----|------|------|
| (A) 무료 유지 | 매일 Actions 로 조금씩. 30~50일 | ★ 게임을 실제로 시작하는 시점이 크게 밀린다 |
| (B) 유료 전환 (종량제) | 한도가 크게 올라간다 | ★ 실제 비용 **확인 불가**. 아래 추산 참조 |
| (C) 절충 | 초기 1,000건만 유료로 확보하고 이후 무료 | 한 번의 비용으로 시작 시점을 당긴다 |

**비용 추산** (★ 추정이다. 실제 단가는 확인하지 않았다)

R010 실측: LLM 도달 1건당 약 912토큰(사고 포함, 가공+역검증 합계).
1,000건 확보에 생존율 29.4% 를 적용하면 약 3,400건을 가공해야 하고
→ 약 310만 토큰. ★ Flash 급 모델의 통상 단가라면 몇 달러 수준으로 **추정**되나,
정확한 단가와 과금 방식(사고 토큰이 출력으로 과금되는지 등)은 **확인 필요**다.

**권장안**: (C). 건우가 "월 5달러 미만이면 지불 가능" 이라고 했고,
초기 확보만 유료로 하면 그 범위에 들어갈 가능성이 있다(추정).
★ 다만 정확한 단가 확인이 먼저다.

**영향**: 높음. 게임을 실제로 플레이하기 시작하는 시점을 결정한다.

### Q-62. ★ 429 의 종류를 구분해 처리할 것인가

**상태**: 결정 필요 (Q-54의 확정 규칙을 조정하는 문제다)

**Q-54 확정 규칙**: 429 가 나오면 그날 중단한다.

**R010 실측에서 드러난 것**

그 규칙은 **일일 한도**를 전제한다. 그런데 실측된 429 는 그렇지 않았을 수 있다.

- 429 직후 최소 호출(`1+1=?`)은 5개 모델 전부 **200** 이었다 → 창이 하루보다 짧다
- 그런데 실제 크기 호출은 몇 분 뒤에도 **429** 였다 → 단순 분당 한도도 아니다
- ★ 어느 차원인지는 **확인 불가**다. 에러 본문과 헤더에 정보가 없다

**문제**: 짧은 창의 한도로 하루를 버리면 진행이 극단적으로 느려진다.
반대로 일일 한도인데 재시도하면 무의미하게 요청만 늘린다.

**선택지**

| 안 | 내용 |
|----|------|
| (A) 현행 유지 | 429 → 그날 중단. 사람이 `npm run pipeline:reset-limit` 로 판단해 해제 |
| (B) 대기 후 1회 재개 | 429 후 N분 기다렸다가 한 번 더 시도하고, 또 429 면 그날 중단 |
| (C) 429 본문 파싱 | `quotaId` 등으로 종류를 판별해 분기. ★ 그 필드가 항상 오는지 확인 필요 |

**현재 구현**: (A). ★ 코드가 스스로 규칙을 바꾸지 않았다.
기본 동작은 확정 규칙 그대로이고, 사람이 실행하는 해제 명령만 추가했다.

**권장안**: (B). 대기 시간을 넉넉히(예: 10분) 잡으면 짧은 창이면 회복되고,
일일 한도면 한 번 더 실패하고 정상적으로 중단된다. 낭비는 요청 1회다.
★ 다만 "몇 분을 기다릴 것인가" 는 운영 판단이므로 건우가 정한다.

**영향**: 중간. 하루 처리량을 좌우한다.

### Q-60. 로컬 `.env` 키와 GitHub Secrets 키가 서로 다른 값이다

**상태**: 확인 필요

**배경**: R005에서 양쪽을 각각 검증했더니 **둘 다 유효하지만 값이 다르다.**
(길이가 각각 39자와 53자였다. ★ 값은 어디에도 기록하지 않았다)

의도한 것이라면 문제가 없다. 다만 다음 상황에서 혼동이 생긴다.

- 한쪽 키를 폐기했을 때 다른 쪽이 계속 동작해 "폐기했는데 왜 되지" 가 된다
- 한쪽에만 할당량이 소진되면 원인을 찾기 어렵다

**확인 필요**: 두 값이 같은 프로젝트의 다른 키인가, 아니면 서로 다른 Google 프로젝트인가.
같은 키로 통일할 것인가.

**영향**: 낮음. 다만 키 폐기·회전 시 혼동을 막기 위해 알고 있어야 한다.

### Q-56. 키보드 단축키 실제 배정

**시점**: Phase 7 (스킵 투표가 나오는 Phase 4에는 임시 키가 필요하다)

제약이 강하다. 이 게임은 **채팅 입력창에 포커스가 있는 상태가 기본**이므로
일반 문자 키를 쓸 수 없다. 사실상 조합키 또는 기능키만 가능하다.

제안 (실측 후 확정)

| 기능 | 키 |
|------|-----|
| 메시지·답안 전송 | Enter |
| 스킵 투표 토글 | Ctrl+Space 또는 F2 |
| 방장 강제 스킵 | Ctrl+Shift+S 또는 F3 |
| 방장 강제 종료 | Ctrl+Shift+E 또는 F4 |
| 확인창 확인 / 취소 | Enter / Esc |

조합키와 F키를 모두 받아들이고 화면에는 조합키를 표기한다.
Chrome / Edge / Safari에서 충돌 실측이 필요하다.
