# 의사결정 기록 (ADR)

> 게임 규칙이나 기술적으로 중요한 사항을 **왜** 그렇게 정했는지 남긴다.
> 이 기록이 없으면 미래의 개발자(또는 AI)가 오래된 문서를 보고 과거 규칙으로 되돌리는 실수를 한다.
>
> **현재 적용되는 규칙은 [01-GAME-RULES.md](01-GAME-RULES.md) 가 정본이다.**
> 이 문서는 그 규칙에 이르게 된 이유를 추적하기 위한 것이다.

최신이 위에 온다.

## D-026. 설정값 검증을 shared 의 순수 함수 하나로 공유한다

**시점**: R007 (Phase 2)

문제 수(1~200) / 카운트다운(3~60) / 시작 방식의 범위 검증을 클라이언트와 서버가
각각 따로 쓰면 반드시 어긋난다. 어긋나면 두 방향의 버그가 생긴다.

- 화면은 통과시키는데 서버가 거부한다 → 사용자는 이유를 모른다
- 화면이 막는데 서버는 허용한다 → 봇이나 조작된 클라이언트가 규칙을 넘는다

`shared/src/settings.ts` 의 `validateRoomSettings()` 하나만 쓴다.
`server/src/socket/index.ts` 와 `client/src/GameSettings.tsx` 가 같은 함수를 부른다.

**★ 공유하는 것은 "형식과 범위" 뿐이다.** 판정 권한은 서버에만 있다(guide 44절).
출제 가능 문제 수 검증(Q-21)은 DB를 봐야 하므로 shared 에 두지 않았다. 서버 전용이다.

경험률 표기(`formatExperienceRate`)도 같은 이유로 shared 에 뒀다.
"1,234문제 중 153문제 (12.4%)" 는 규칙으로 확정된 형식이고(guide 6절),
★ 분모가 0일 때 0으로 나누지 않는 처리를 한 곳에만 두어야 한다.

## D-025. 카운트다운 만료 시점에 출제 가능 수가 부족해지면 로비로 되돌린다

**시점**: R007 (Phase 2)

**명세에 없는 경로다.** 전이표(04-PROTOCOL.md)의 T04 조건은 "활성 ≥ 1" 뿐이다.

그런데 Q-11이 **카운트다운 중 신규 입장을 허용**하므로 참가자 집합이 바뀔 수 있고,
Q-21의 출제 가능 수는 참가자 집합의 함수다("한 명 이상이 미경험인 문제 수").

- 사람이 **들어오면** 가능 수는 줄지 않는다. "전원 경험" 조건이 더 어려워지기 때문이다
- 사람이 **나가면** 가능 수가 줄어들 수 있다

즉 T01에서 통과한 검증이 T04 시점에는 거짓일 수 있다.

**결정**: T04 에서 출제 가능 수를 다시 조회하고, 부족하면 **로비로 되돌리고 이유를 알린다.**

근거: 대안은 (a) 그냥 시작한다 (b) 문제 수를 자동으로 줄인다 였다.
(a)는 Q-21("부족하면 시작을 거부하고 안내")을 정면으로 위반한다.
(b)는 방장이 설정한 값과 실제 진행되는 값이 조용히 달라지므로
"게임 규칙을 임의로 바꾸지 않는다" 는 원칙에 걸린다.
되돌리는 것이 규칙을 지키면서 사용자가 다음 행동을 고를 수 있는 유일한 선택지다.

## D-024. 문제 선정·경험률의 참가자 집합에 접속 종료자도 포함한다

**시점**: R007 (Phase 2)

**자체 판단이다.** 규칙 문서가 "참가자" 의 범위를 명시하지 않았다.

로비에서 접속이 끊긴 사람은 여전히 목록에 보이고 슬롯을 갖고 있으며,
방장이 명시적으로 내보내지 않으면 그 게임에 참가한다(Q-15).
따라서 문제 선정 대상에서 빼면 **돌아온 사람이 이미 경험한 문제를 받는** 상황이 생긴다.
그것은 Q-20(경험 기반 선정)의 취지에 정면으로 반한다.

★ 반대 방향의 부작용도 있다. 다시 돌아오지 않을 사람 때문에 출제 가능 수가
실제보다 크게 잡힐 수 있다. 그러나 그 경우 게임 중 조기 종료(Q-22)로 흡수되고,
Q-22는 이미 그 동작을 허용하고 있다. 반대 실수(경험한 문제를 다시 내는 것)는
흡수할 장치가 없다.

★ 활성 인원(activeCount) 과는 다른 축이다.
스킵 투표 분모와 PAUSED 판정은 끊김을 즉시 반영한다(Q-29). 이 결정은 그것과 무관하다.

## D-023. PAUSED 를 Phase 2에서 구현하지 않는다 — 카운트다운 만료를 보류하는 방식으로 대신한다

**시점**: R007 (Phase 2)

**확정 규칙**은 T20 "COUNTDOWN 중 활성 0명이면 즉시 PAUSED,
remainingMs = countdownEndsAt − now" 다 (Q-30 개정).

Phase 2에서 이것을 부분 구현하면 **막다른 길이 생긴다.**

| 필요한 것 | Phase 2에 있는가 |
|----------|-----------------|
| PAUSED 30분 초과 → GAME_RESULT (T14) | ✗ GAME_RESULT 가 없다 |
| 방장 `game.resume` → 원래 상태 복귀 (T23) | ✗ |
| ★ PAUSED 중 방 삭제 타이머 정지 | 이미 구현되어 있다 (tick) |

★ 세 번째가 결정적이다. PAUSED 에 들어가면 방 삭제 타이머가 멈추는데,
나오는 경로(resume / 30분 포기)가 없으면 **그 방이 프로세스 수명 동안 영구히 남는다.**
메모리 누수이자, 그 방을 만든 사람은 다시 방을 만들 수 없게 된다(1인 1방 제약).

**결정**: Phase 2에서는 T04 의 확정 조건("활성 ≥ 1")만 지켜 **만료를 보류**한다.
활성 0명이면 카운트다운이 만료되어도 게임을 시작하지 않고, 사람이 돌아오면 시작한다.
그 사이 방 삭제 타이머는 정상 동작한다(활성 0명 10분).

**최종 규칙과 다른 점 하나**: 남은 시간을 재계산하지 않는다.
30초 카운트다운 중 1초 만에 전원이 끊기고 5분 뒤에 돌아오면,
PAUSED 규칙에서는 29초가 남아야 하지만 지금은 즉시 시작된다.

★ `tick.ts` 의 `checkCountdown()` 안에 이 자리를 주석으로 표시했다.
Phase 5에서 그 자리를 PAUSED 전이로 교체한다.
★ 봇 시나리오 `empty` 가 지금의 동작을 단정하고 있으므로, Phase 5에서 규칙을 바꾸면
그 테스트가 실패해 교체를 빼먹을 수 없다.

## D-022. 짧은 라벨의 줄바꿈을 개별 요소가 아니라 규칙으로 막는다

**시점**: R007 (건우가 "전송 버튼 글자가 세로로 쪼개진다" 를 지적)

**증상**: 채팅 전송 버튼의 "전송" 이 "전" / "송" 두 줄로 나왔다.

**원인 (헤드리스 Chrome 으로 실측)**

버튼이 flex 행의 항목이고, flex 항목의 기본값은 `flex-shrink: 1` / `min-width: auto` 다.
같은 행의 입력창이 `width: 100%` 여서 남는 폭이 없으므로 버튼이
min-content(한 글자 폭)까지 눌렸고, `white-space` 기본값이 `normal` 이라
한글 두 글자 사이에서 줄이 바뀌었다.

★ 실측값: 720px 화면에서도 버튼 폭이 56.9px(내용 폭 약 27px)로 눌려 있었다.
좁은 화면만의 문제가 아니었다.

★ **"복사" 버튼만 멀쩡했던 이유**: 그 하나에만 `white-space: nowrap` 이 붙어 있었다.
즉 규칙이 아니라 우연이었다.

**결정 — 개별 수정으로 끝내지 않는다**

1. 라벨성 요소 전체에 `white-space: nowrap` 을 건다 (`button`, `.badge`, `.seat`, `.preset`)
2. 모든 버튼에 `flex: 0 0 auto` 를 건다. 늘어나야 하는 `.tab` 은 클래스가 덮어쓴다
3. "입력 + 버튼 한 줄" 배치를 `.field-row` 하나로 통일한다.
   `.invite-row` / `.chat-input` 처럼 전용 클래스를 여러 개 두면 그중 하나에
   규칙을 빼먹는 일이 반복된다. 실제로 그렇게 해서 이 버그가 생겼다
4. 제목(`h1`)과 본문은 규칙에서 제외한다. 방 제목은 30자까지 허용되므로
   좁은 화면에서 여러 줄이 되는 것이 정상이고, 줄바꿈을 막으면 화면을 넘친다

**부수 발견**: 같은 원인으로 "방 나가기" 버튼도 390px 이하에서 두 줄로 쪼개져 있었다.
지적받은 곳만 고쳤다면 그것은 그대로 남았을 것이다.

**대가**: 아주 좁은 화면에서 긴 라벨이 들어오면 줄바꿈 대신 넘친다.
버튼 라벨은 설계상 2~6자이고, 각 라벨을 320px 에서 실측해 확인한다.

## D-021. 실행 확인(smoke)을 게이트에 넣는다 — typecheck·build 는 실행을 보장하지 않는다

**시점**: R006 (npm run dev 실행 불가 사고를 고치며)

**무엇이 드러났는가**

R005에서 다음을 모두 통과라고 보고했다.

- `npm run typecheck` 통과
- `npm run build` 통과 (shared / server / client)
- 봇 테스트 21항목 통과

**그런데 `npm run dev` 가 아예 실행되지 않았다.**

세 검증이 이 문제를 못 잡은 이유는 각각 다르다.

| 검증 | 왜 못 잡았는가 |
|------|--------------|
| typecheck | `tsc` 는 `./config.js` 를 **컴파일 후 파일**로 해석한다. 소스 시점에 그 파일이 없어도 정상이다. TS 관점에서 이 코드는 완전히 옳다 |
| build | 같은 이유. 컴파일이 성공하고 `dist/config.js` 가 실제로 만들어진다 |
| 봇 테스트 | ★ 서버를 `node server/dist/index.js` 로 띄웠다. **컴파일 산출물이라 정상 동작했다.** `npm run dev` 는 한 번도 실행하지 않았다 |

**★ 핵심은 세 번째다.** 테스트가 사람이 쓰는 실행 경로와 다른 경로를 썼다.
그래서 "테스트 전부 통과"와 "실행 불가"가 동시에 성립할 수 있었다.

**결정**

1. `npm run smoke` 를 만든다 — 빌드 → 기동 → `/healthz` 200 → 클라이언트 서빙 →
   Socket.IO 핸드셰이크 → 프로세스 종료 → 포트 해제까지 검증한다
2. `npm run verify` = `typecheck` + `test` + `smoke` 를 라운드 종료 게이트로 삼는다
3. `npm run bot` 이 서버가 없으면 **사람과 같은 경로**로 직접 띄운다.
   테스트가 다른 경로를 쓰면 이 사고가 반복된다

**smoke 를 처음 돌렸을 때 이 스크립트 자체의 오탐도 하나 잡혔다.**
종료 판정을 `exit` 콜백의 `code` 만으로 하고 있었는데,
Windows 에서 `child.kill()` 은 즉시 종료(TerminateProcess)라 `code=null, signal='SIGTERM'` 이 온다.
`code` 만 보면 "신호로 종료됨"과 "아직 안 죽음"이 둘 다 `null` 이라 구분되지 않았다.
→ `signal` 을 함께 추적하고, 판정 기준을 "프로세스가 사라지고 포트가 해제되는가" 로 바꿨다.

★ 부수 확인: Windows 에서 `child.kill()` 로는 자식의 SIGTERM 핸들러가 실행되지 않는다(실측).
사람이 터미널에서 Ctrl+C 를 누르는 경로는 이 스크립트로 재현할 수 없어 확인하지 못했다(확인 필요).
포트 해제와 프로세스 소멸은 어느 경로든 동일하므로 그것만 검증한다.

## D-020. 개발 서버도 컴파일 산출물을 실행한다 — 실행 경로를 하나로 유지

**시점**: R006. `npm run dev` 가 `ERR_MODULE_NOT_FOUND` 로 실행되지 않는 사고를 고치며.

**증상**

```
Error [ERR_MODULE_NOT_FOUND]: Cannot find module 'server\src\config.js'
imported from server\src\index.ts
```

**원인** — 두 규칙이 각각 옳고 조합이 불가능했다

| | 내용 |
|---|---|
| tsconfig | `module`/`moduleResolution` = **NodeNext**. 상대 import 에 **컴파일 결과물의 확장자(`.js`)** 를 쓰도록 요구한다. 그래서 소스는 `'./config.js'` 다 (저장소 전체 57건이 이렇게 일관되어 있었다) |
| 실행기 | 이전 dev 스크립트는 `node --experimental-strip-types --watch src/index.ts` 였다. **Node 의 타입 스트리핑은 import 문자열을 재작성하지 않는다.** `'./config.js'` 를 문자 그대로 찾고, 거기에는 `config.ts` 만 있으므로 실패한다 |

실측으로 확인했다. `--experimental-strip-types` 로 `'./dep.js'` import 는 실패하고
`'./dep.ts'` 는 성공한다. Node 22.18 에는 `.js` → `.ts` 재매핑이 없다.

**검토한 선택지**

| 안 | 내용 | 판단 |
|----|------|------|
| A | dev 도 컴파일 산출물(`server/dist/index.js`)을 실행한다 | **채택** |
| B | `tsx` 같은 실행기로 바꾼다 | 의존성이 늘고, **dev 만 소스를 실행하는 divergence 가 그대로 남는다** |
| C | 모든 상대 import 를 `.ts` 로 바꾸고 TS 5.7 의 `rewriteRelativeImportExtensions` 로 emit 시 재작성 | 의존성은 안 늘지만 57건을 고쳐야 하고, `.ts` 확장자 import 는 읽는 사람에게 낯설다. 역시 dev 만 소스를 실행한다 |

**A를 택한 이유**

1. ★ **근본 원인이 "dev 만 다른 코드 경로를 쓴 것"이다.**
   `npm start` 와 테스트는 컴파일 산출물을 실행했고 dev 만 소스를 직접 실행했다.
   그래서 아무도 그 경로를 검증하지 않았다.
   B와 C는 그 경로를 **고칠** 뿐이고, A는 그 경로를 **없앤다.**
   이제 `npm run dev` / `npm start` / `smoke` / `bot` 이 전부 같은 파일을 실행한다.
2. **소스를 한 줄도 고치지 않았다.** 57건의 `.js` 확장자는 NodeNext 기준으로 이미 옳다.
3. **의존성을 늘리지 않았다.**
4. 서버는 어차피 `@quiz/shared` 를 `shared/dist` 에서 가져오므로 **dev 에도 빌드 단계가
   이미 필요했다.** server 까지 함께 빌드하는 비용은 사실상 없다.

**구현**: `scripts/dev.mjs` — 한 번 빌드 → `tsc -b --watch` + `node --watch server/dist/index.js`.

**함께 고친 것**

- ★ `server/package.json` 의 깨진 `dev` 스크립트를 **제거했다.**
  남겨 두면 같은 함정을 다시 밟는다. 실행 진입점은 루트 `npm run dev` 하나다
- `dist` 가 없는데 `tsconfig.tsbuildinfo` 가 남아 있으면 `tsc` 가 "최신"이라 판단해
  아무것도 만들지 않는다. dev 와 smoke 가 산출물 부재를 감지해 `--force` 로 빌드한다.
  `npm run build:force` 도 추가했다

**클라이언트는 문제가 없었다.** Vite 는 `'./api.js'` 를 `/src/api.ts` 로 정상 해석한다(실측).
그래서 `vite build` 가 성공했고 문제가 서버 dev 경로에만 있었다.

## D-019. 로그인 실패 메시지는 구분하지 않되, 회원가입은 구분한다

**시점**: Phase 1 (R005)

**결정**

- **회원가입**: 아이디 중복인지 닉네임 중복인지 알려준다
- **로그인**: "아이디 또는 비밀번호가 올바르지 않습니다" 하나로 통일한다

**왜 비대칭인가**

회원가입에서 구분하지 않으면 사용자가 무엇을 고쳐야 할지 알 수 없어 **가입 자체가 불가능해진다.**
아이디를 바꿔야 하는지 닉네임을 바꿔야 하는지 모르는 채로 시행착오를 반복하게 된다.
그래서 여기서는 구분한다. "그 아이디가 존재한다"는 정보가 새지만, 친구들끼리 쓰는 서비스에서
그것을 감출 실익이 없다.

로그인에서 구분하지 않는 이유는 보안 관행 때문이 아니다. 회원가입에서 이미 알려주므로
그 논리만으로는 일관성이 없다. **실제 이유는 자동화 난이도의 차이다.**
이 서비스는 아이디가 짧고 비밀번호가 4자여서(Q-04), 로그인 응답으로 유효한 아이디 목록을
자동 수집할 수 있게 만들면 대입 공격의 표적 범위가 그대로 좁혀진다.
회원가입은 사람이 하나씩 하는 반면 로그인은 자동화하기 쉽다.

## D-017. 세션 쿠키의 Secure 속성을 요청 프로토콜에 따라 분기한다

**시점**: Phase 1 (R005)

**문제**: 이 프로젝트는 두 방식으로 접속된다.

- 개발: `http://localhost:5173` 또는 `http://localhost:3000`
- 플레이: `https://xxxx.trycloudflare.com` (터널)

`Secure` 쿠키는 http 에서 저장되지 않는다. 고정으로 붙이면 **localhost 개발 중 로그인이 아예 안 된다.**
반대로 터널(https)에서는 붙이는 것이 옳다.

**결정**: 요청이 https 로 들어왔는지 보고 결정한다. 고정값을 쓰지 않는다.
터널은 프록시이므로 `x-forwarded-proto` 를 함께 본다.

`SameSite` 는 **Lax** 로 고정한다. 오리진이 하나이므로(서버가 클라이언트를 직접 서빙)
`None` 이 필요 없고, `None` 은 서드파티 쿠키로 분류되어 모바일 사파리에서 차단될 수 있다.
`Lax` 면 초대 링크 클릭(top-level navigation)에도 쿠키가 붙는다.

**부수 결정**: `SESSION_SECRET` 을 세션 토큰 해시의 HMAC 키로 쓴다.
토큰이 256비트 랜덤이라 단순 해시로도 역산은 불가능하지만, DB만 유출되고 시크릿은 유출되지
않은 경우에 한 겹 더 막아 준다. 비용이 없고, 이것이 `SESSION_SECRET` 의 실제 용도가 된다.

## D-015. cloudflared 네트워크 단절 시 터널 URL은 유지된다 (Q-53 확정)

**시점**: Phase 1 (R005). **실측 검증 완료.**

**검증 방식**: 관리자 권한으로 방화벽 아웃바운드 규칙을 만들어 `cloudflared.exe` 의 네트워크만
100초간 차단한 뒤 규칙을 제거했다.
★ PC 전체 네트워크를 끊지 않았다. 작업 환경을 해치지 않기 위함이다.
재현 스크립트: `scripts/verify-tunnel-resilience.ps1`

**결과**

| 확인 항목 | 결과 |
|----------|------|
| 차단 중 cloudflared 프로세스 | 살아 있음 |
| 차단 중 터널 URL | 502 |
| **복구 후 같은 URL** | **200 — 유지되었다** |
| WebSocket 자동 재연결 | 성공 (`transport=websocket`) |
| 서버 프로세스 `bootedAt` | 동일 (무영향) |
| 로그의 `Requesting new quick Tunnel` | **1회만** (프로세스 시작 시) |
| 로그에 등장한 고유 URL | **1개** |
| 차단 중 로그 | `Retrying connection` 반복 → `Registered tunnel connection` 재등록 |

**해석**: URL은 **프로세스 시작 시 1회 발급**되고 그 뒤에 개별 엣지 연결이 등록된다.
즉 호스트명은 "터널(프로세스)"에 속하고 "개별 연결"에 속하지 않는다.
따라서 연결만 끊겼다 재등록되는 동안 URL이 유지된다.

**★ 부수 발견: 재연결 백오프가 지수적으로 늘어난다.**
`8s → 16s → 32s → 1m4s` 로 증가했고, 차단이 100초였는데 복구 후 재등록은
차단 해제 시점으로부터 약 30초 뒤에 일어났다.
→ **단절이 길수록 복구 후 재연결까지 최대 1분 이상 더 기다려야 할 수 있다.**
운영 문서에 이 사실을 넣었다.

**한계 (과장하지 않기 위해 명시)**: 방화벽 차단은 Wi-Fi를 실제로 끄는 것과 완전히 같지 않다.
인터페이스가 살아 있고 라우팅 테이블도 그대로다. OS 네트워크 스택 상태가 다르다.
여기서 URL이 유지되었으므로 **실제 상황에서도 유지될 가능성이 높다** 는 정도로 해석한다.

**운영 절차에 반영**: [11-DEPLOY.md](11-DEPLOY.md) 3장의 복구 절차에서
"URL 유지" 를 주 경로로, "URL 변경" 을 예외로 내렸다.

## D-014. 인프라를 클라우드에서 로컬 PC + 터널로 전면 변경

**시점**: Phase 0 (R004)

**변경 전**: Render Free(서버) + Neon Free(DB). 클라우드 상시 가동, 고정 URL.

**변경 후**: 건우 PC를 서버로 쓰고 필요할 때만 켠다. 외부 노출은 Cloudflare quick tunnel,
DB는 로컬 PostgreSQL(Docker). 클라우드 서비스를 전혀 쓰지 않는다.

**이유**: 건우가 방장으로 게임을 대부분 진행하고, 서버가 건우 없이 돌아갈 필요가 없다.
고정 URL도 필요 없다 — 어차피 플레이할 때마다 링크를 만들어 뿌린다.

**효과**

- 무료 호스팅의 슬립·콜드 스타트 문제가 사라졌다
- 서버리스 DB의 컴퓨트 시간 한도 문제가 사라졌다
- 512MB RAM 제약이 사라져 봇 동시성 테스트가 자유로워졌다
- 월 비용 $0, 가입할 서비스 없음

**남긴 것**: 커넥션 풀 설정(최대 5 / 유휴 60초 / 지연 연결)과 "DB를 건드리는 주기 쿼리를
만들지 않는다"는 규칙은 그대로 유지한다. **이유가 "Neon 한도"에서 "클라우드 전환 대비"로 바뀐 것이다.**

**영향**: `ai-out/R001~R003` 의 Render/Neon 전제 서술은 더 이상 유효하지 않다.
`docs/` 에는 새 구조만 쓴다.

## D-013. PAUSED(일시정지) 상태 도입 — guide 9절 규칙 변경

**시점**: Phase 0 (R004). 건우 명시적 승인.

**변경 전**: 활성 플레이어가 0명이 되면 30초 유예 후 게임을 종료한다.

**변경 후**: 활성 0명이 되는 **즉시** `PAUSED` 로 전이한다. 타이머를 남은 시간으로 멈추고,
**방장이 눌러야 재개한다.** 30분이 지나면 그때 게임을 종료한다(`abandoned`).

**이유** — 이것이 이 프로젝트의 인프라와 직결된 결정이다.

D-014로 서버가 건우 PC가 되고 매번 새 터널 URL을 뿌리게 되면서,
**터널 재시작이 예외가 아니라 일상**이 되었다. 또 서버 PC의 네트워크가 드물게 1~2분 끊긴다.

**핵심은 서버 PC의 네트워크 단절이 서버 프로세스가 죽는 것이 아니라는 점이다.**
통로만 끊기고 메모리의 방과 게임은 그대로 살아 있다. 따라서 이어하기가 원리적으로 가능하다.
이것이 PC를 껐다 켜는 것과 완전히 다른 상황이다.

기존 규칙으로는 그때마다 판이 날아갔고, 더 나쁜 것은 **타이머가 계속 흘러 아무도 보지 못한 문제가
타임아웃 처리되며 경험 기록으로 소모되는 것**이었다. 경험 기록은 영구 자산이라 되돌릴 수 없다.

**설계상 중요한 세부**

- **자동 재개하지 않는다.** 친구 한 명이 먼저 접속한 순간 게임이 돌아가면,
  나머지가 새 URL을 입력하는 동안 문제가 소모된다
- 타이머는 절대 시각이 아니라 **남은 시간(remainingMs)** 으로 보존한다
- 재개 시 **epoch를 증가시키지 않는다.** 같은 문제를 이어서 하기 때문이다
- **방 삭제 타이머와 방장 이전 타이머도 PAUSED 중에는 정지한다.**
  이것을 빼먹으면 10분 뒤 방이 삭제되어 일시정지가 무의미해진다
- **경험 기록은 자동으로 충족된다.** PAUSED 중에는 정답 공개가 일어나지 않고,
  경험 기준이 "정답 공개 순간 그 자리에 있던 사람"(D-010)이므로 별도 예외 처리가 필요 없다

**검증**: cloudflared 프로세스를 강제 종료해도 서버의 `bootedAt` 이 그대로였다.
터널이 죽어도 서버 프로세스와 메모리는 전혀 영향을 받지 않는다는 실증이다. (R004 1장)

## D-011. 경험자 정보 공개 + 정답 마스킹 — guide 28절 규칙 폐기

**시점**: R002 (Q-35). 건우 명시적 승인.

**변경 전** (guide 28절): "다른 플레이어는 해당 사용자가 그 문제를 과거에 풀었는지 알 수 없어야 한다."

**변경 후**

1. 경험자가 1명 이상이면 **문제 하단에 경험자 닉네임을 전원에게 표시한다**
2. **경험자가 보낸 채팅에 정답이 포함되면 서버가 마스킹한다**

**이유**: guide 28절(경험자 채팅 허용)과 15절(오답도 전부 공개)의 조합에 구조적 유출 경로가 있었다.
정답을 아는 사람이 채팅에 정답을 그대로 치면, 그 사람은 점수를 못 받지만
**다른 사람이 그것을 보고 그대로 따라 쳐서 점수를 가져간다.**
경험률이 높은 사람이 많아질수록 확실하게 발생한다.

마스킹으로 유출을 차단하되, **마스킹이 왜 걸렸는지 모두가 이해할 수 있도록** 경험자를 공개하는
방향으로 규칙을 바꿨다. 가려진 이유를 알 수 없으면 더 혼란스럽다.

**설계상 중요한 세부**

- **마스크 길이는 고정이다.** `*****` 처럼 길이에 비례하는 마스크는 금지한다.
  정답 길이는 힌트보다 강한 정보이며 문제 시작 직후부터 노출되면 게임이 망가진다
- 사용자가 입력할 수 없는 **센티널 문자**(사설 사용 영역)로 치환한다.
  이모지나 특수기호를 쓰면 사용자가 직접 입력했을 때 구분되지 않는다
- **정규화 후 길이 2 이하인 정답은 메시지 전체가 정답과 같을 때만 마스킹한다.**
  그러지 않으면 정답 "달" 때문에 "달라졌네"가 마스킹되어 경험자가 정상적인 대화를 할 수 없게 되고,
  guide 28절이 보장한 "경험자도 채팅은 자유롭게 가능"이 무너진다
- **마스킹은 서버에서 한다.** 클라이언트에 원문을 보내고 CSS로 가리면 개발자 도구로 즉시 뚫린다

**알려진 한계**: `고무-줄` 처럼 기호를 끼우거나 `ㄱㅁㅈ` 처럼 초성으로 쓰면 막을 수 없다.
완벽한 차단은 fuzzy matching을 요구하는데 그것은 정답 판정 규칙(D-006)이 금지한 기술이고,
판정과 마스킹에 서로 다른 매칭 기준을 쓰면 규칙이 혼란스러워진다.
친구들끼리 하는 게임이므로 "무심코 흘리는 것"을 막는 수준으로 설계했다.

## D-010. 경험의 정의 변경 — guide 27절 개정

**시점**: R002 (Q-23/Q-24) → R003 (재검토) → **R004에서 최종 확정**

**변경 전** (guide 27절): "실제로 해당 문제를 접한 시점" 기준.

**최종 규칙**: **정답이 공개되는 순간 그 자리에 있었던 사람 전원**

- 정답자 발생 / 시간 종료 / 스킵 — 세 경로 모두 정답 공개이며 기록을 남긴다
- **`QUESTION_RESOLVED` 구간(5초)에 입장한 사람도 기록을 남긴다**
- **마지막 문제도 기록을 남긴다** (5초 대기만 생략한다)
- 강제 종료 / `abandoned` / `server_restart` 에서는 정답을 공개하지 않으므로 기록이 없다
- 문제 진행 중 연결이 끊긴 사람은 기록하지 않는다

**변경 이유 (1차, R002)**: 원래 기준으로는 잠깐 끊긴 사이 지나간 문제가 영구히 "경험함"으로
기록되어, 정답을 보지도 못한 문제에서 나중에 정답 판정이 제외되는 손해가 발생한다.

**변경 이유 (2차, R004)** — ★ R003의 판단을 뒤집은 부분이다.

R003은 "RESOLVED 구간 입장자에게 경험 기록을 남기지 않는 것이 사용자에게 유리하다"고 판단했다.
**이 판단은 방향이 반대였다.**

그 사람은 정답을 봤다. 기록을 남기지 않으면 다음 게임에서 그 문제가 나왔을 때 즉시 맞힌다.
**다른 참가자가 손도 쓸 수 없게 되는데, 그것이 바로 경험 시스템이 막으려던 상황이다.**
경험 시스템은 "그 사람을 배려하는 장치"가 아니라 "게임의 공정성을 지키는 장치"다.

**효과**: 기준이 하나로 단순해졌다. "정답 공개 순간 그 자리에 있었는가" 하나만 보면 된다.
그리고 PAUSED(D-013)에서도 별도 예외 없이 자동으로 옳게 동작한다.

## D-008. 방은 DB에, 참가자와 게임 상태는 메모리에

**시점**: R003

**결정**: `rooms` 레코드만 DB에 두고, 참가자 목록과 진행 중 게임 상태는 서버 메모리에만 둔다.
guide 48절이 이 조합을 명시적으로 허용한다.

**방을 DB에 두는 이유**

1. guide 49절이 "존재하지 않는 방"과 "이미 종료된 방"을 다르게 안내하라고 요구한다.
   메모리만 쓰면 서버 재시작 후 모든 링크가 "존재하지 않는 방"이 된다
2. "1인당 동시 보유 방 1개"를 부분 UNIQUE 인덱스로 DB가 강제할 수 있다
3. `games` 가 `room_id` 를 참조해야 게임 이력이 방과 연결된다
4. 쓰기 빈도가 극히 낮다 (생성 시 1회, 삭제 시 1회)

**참가자·게임 상태를 메모리에만 두는 이유**

1. 참가자 접속 상태는 초 단위로 바뀐다. DB에 반영하면 DB를 계속 깨워 둔다
2. 서버가 재시작되면 소켓이 전부 끊기므로 참가자 목록을 복원해도 의미가 없다

**"게임 상태 스냅샷" 요구의 해석**: 지키려는 것은 "프로세스가 죽어도 친구들의 점수와
경험 기록이 날아가지 않는 것"이다. 이는 방/참가자 상태를 통째로 저장해서가 아니라
**`answer_events` 와 `question_experiences` 를 문제 단위로 즉시 기록해서** 달성한다.
즉 "되돌릴 수 없는 사실만 즉시 기록"한다.

**부수 효과**: 프로세스 종료 시 `closed_at` 이 NULL인 방이 DB에 남아 UNIQUE 제약에 걸린다.
→ 부팅 시 정리 절차(D-007)가 필요해졌다.

## D-007. 서버 부팅 시 정리 절차 도입

**시점**: R004 (설계 결함 발견 후 수정)

**문제**: D-008의 부분 UNIQUE 인덱스와 "방 삭제는 메모리에서" 라는 설계가 만나
**프로세스가 죽으면 그 사람은 다시는 방을 만들 수 없게 되는** 결함이 있었다.
로컬 PC 서버(D-014)는 껐다 켜는 것이 일상이므로 이 문제가 반드시, 자주 발생한다.

**처리**: 서버 부팅 시 (1) `ended_at IS NULL` 인 게임을 `server_restart` 로 종료하고,
(2) `closed_at IS NULL` 인 방을 전부 닫는다.

**★ `question_experiences` 는 삭제하지 않는다.** guide 25절이 강하게 금지하고,
그 문제들은 실제로 정답이 공개되어 사람들이 화면에서 본 것이므로 기록이 옳다.

**검증**: 잔여 방 1개와 진행 중 게임 1개를 만들어 두고 서버를 재기동하자
방 0개 / 게임 0개(`end_reason='server_restart'`)가 되었고,
제약에 걸려 실패하던 방 생성이 성공했다. (R004 3장)

## D-006. 정답 판정 정규화 규칙 확정

**시점**: R002 (Q-16) + R002 (Q-36)

**결정**: NFC → 제로폭 제거 → 전각/반각 → 아포스트로피·하이픈 통일 → 공백 제거 → 소문자화.

**왜 NFC이고 NFKC가 아닌가**: NFKC는 `①` → `1`, `㈜` → `(주)`, `Ⅳ` → `IV` 처럼
**의미를 바꾸는 변환**까지 수행한다. guide 16절이 "특수문자·기호는 무시하지 않는다"고 했으므로
NFKC는 규칙을 넘어선다. NFC + 명시적 전각 변환만 한다.

**왜 NFC가 반드시 필요한가**: macOS/iOS 사파리는 한글을 NFD(자모 분리)로 보내는 경우가 있다.
NFC가 없으면 **아이폰 사용자가 눈에 똑같은 답을 쳐도 오답 처리된다.**
게임을 망치는 수준의 버그이며, 눈으로는 원인을 알 수 없다.

**왜 제로폭 문자를 따로 지우는가**: JavaScript의 `\s` 에 포함되지 않아 공백 제거로 걸러지지 않는다.
복사·붙여넣기로 흔히 섞여 들어오며 눈에 보이지 않아 디버깅이 매우 어렵다.

**왜 아포스트로피·하이픈을 통일하는가 (Q-36)**: 모바일 키보드가 `'` 를 자동으로 `’`(U+2019)로 바꾼다.
이것은 "같은 글자의 다른 표현"이지 "다른 글자"가 아니므로,
`A+B ≠ AB` 라는 규칙의 취지를 위반하지 않는다.

**바꿀 때 주의**: `NORMALIZE_VERSION` 이 바뀌면 `question_answers.answer_norm` 전체를
재계산해야 한다. **서버의 판정과 파이프라인의 저장이 반드시 같은 함수를 써야 한다.**
다르면 DB 값과 런타임 판정이 어긋나 정답이 조용히 오답 처리된다.

## D-005. 영문 힌트는 단어마다 첫 글자를 노출한다

**시점**: R004 (Q-38). ★ R002의 권장안을 뒤집었다.

**R002 권장안 (채택 안 됨)**: 전체에서 첫 글자 하나만. `New York` → `N______`

**최종 결정**: **단어마다 첫 글자, 공백 유지.** `New York` → `N__ Y___`

**이유**: 한글은 음절마다 초성을 준다(`훈민정음` → `ㅎㅁㅈㅇ`, 정보 4개).
영문만 전체에서 한 글자를 주면 **정보량이 크게 비대칭이 되어 영문 정답만 불리해진다.**
"같은 규칙의 일관된 적용"이 아니라 한쪽만 불리해지는 것이다.
단어별 첫 글자가 한글 규칙의 정보량에 더 가깝다.

**부수 결정**: 이 결정에 따라 **영문 정답은 공백을 제거하지 않고 단어 경계를 유지한다.**
한글 정답은 guide 11절대로 공백을 제거한다. 한글이 섞인 혼합 정답은 한글 규칙을 따른다.

## D-003. 스킵 임계값에 하한 2표를 둔다

**시점**: R002 (Q-28)

**문제**: guide 22절의 "활성 플레이어의 80%, 전원 동의가 되면 한 명 적은 수" 규칙을
소인원에 그대로 적용하면 **2명일 때 1표, 1명일 때 0표로 스킵된다.**
guide 22절 자신이 "0표만으로 스킵되는 등의 문제가 발생하지 않도록" 별도 처리를 요구했다.

**결정**: 하한 2표. 활성 1명이면 스킵 투표 자체가 불가능하다(방장 강제 스킵만 가능).

**분모에 경험자를 포함하는 이유**: 경험자를 분모에서 빼면 **투표 수로 경험자 수가 역산되어
정보가 샌다.** 그래서 해당 문제의 경험 여부와 무관하게 전체 활성 플레이어를 분모로 쓴다.
(D-011로 경험자가 공개되었으므로 이 우려는 약해졌지만, 규칙을 단순하게 유지하기 위해 그대로 둔다.)

## D-002. epoch(문제 세대 번호) 도입

**시점**: R003

**문제**: guide 20절이 "결과 화면에서 입력한 메시지가 다음 문제의 정답과 우연히 일치해도

**PAUSED와의 관계 (D-013)**: 재개 시 epoch를 **증가시키지 않는다.** 같은 문제를 이어서 하기 때문이다.

## D-001. 판정 블록에 await를 넣지 않는다

**시점**: R001 → R003에서 명문화

**결정**: 정답 판정과 상태 전환은 하나의 동기 실행 블록에서 수행하고,
그 블록 안에 `await` 를 절대 넣지 않는다. 판정에 필요한 데이터는 문제 시작 시점에
메모리로 미리 로드한다. DB 기록은 상태 전환이 끝난 뒤 비동기로 한다.

**이유**: Node의 단일 스레드 이벤트 루프에서는 핸들러가 `await` 없이 끝까지 실행되는 동안
다른 이벤트가 끼어들 수 없다. 이 성질 덕분에 별도의 락 없이
"한 문제의 정답자는 정확히 한 명"(guide 18절)이 보장된다.

**★ 이 규칙이 이 프로젝트에서 가장 깨지기 쉽다.** 누군가 판정 블록에 `await` 한 줄을 추가하면

- 에러가 나지 않는다
- 평소에는 정상 동작한다
- 동시 입력이 정확히 겹치는 순간에만 두 명이 정답자가 된다
- 재현이 매우 어렵다

**대응**: 판정 함수 이름에 규칙을 박아 넣고(`resolveQuestionSync`), 함수 상단에 이유를 주석으로 남기고,
동시 정답 100회 반복 테스트를 CI에 넣는다.
