# 의사결정 기록 (ADR)

> 게임 규칙이나 기술적으로 중요한 사항을 **왜** 그렇게 정했는지 남긴다.
> 이 기록이 없으면 미래의 개발자(또는 AI)가 오래된 문서를 보고 과거 규칙으로 되돌리는 실수를 한다.
>
> **현재 적용되는 규칙은 [01-GAME-RULES.md](01-GAME-RULES.md) 가 정본이다.**
> 이 문서는 그 규칙에 이르게 된 이유를 추적하기 위한 것이다.

최신이 위에 온다.

## D-092. 가운뎃점이 든 정답은 **마침표 표기를 복수 정답에 넣는다**

**시점**: R019 (작업 D)

`4·19 혁명` / `5·18 민주화운동` / `6·29 선언` / `7·4 남북공동성명` 처럼
한국어 표준 표기가 가운뎃점(`·`)을 쓰는 정답이 있다.

**문제**: ★★ 가운뎃점은 **두벌식 자판에 없다.** 플레이어는 `4.19 혁명` 이나 `419 혁명` 을 친다.
★ 정규화는 공백만 지우고 구두점은 그대로 둔다 — 실측:

```
normalizeAnswer('4·19 혁명') → '4·19혁명'
normalizeAnswer('4.19 혁명') → '4.19혁명'     ★ 다르다. 오답이 된다
```

**결정**: 대표 정답은 표준 표기(`4·19 혁명`)로 두되,
**가운뎃점을 마침표로 바꾼 표기를 `acceptedAnswers` 에 넣는다.**

★ 근거: 복수 정답의 기준은 "이 표현을 인정하지 않으면 플레이어가 합리적으로 억울한가" 다(프롬프트 B).
자판에 없는 글자를 요구하는 것은 명백히 억울하다.

★ **프롬프트 B 의 "특수문자를 쓰지 않습니다" 와 부딪히지 않는다.** 그 조항은 `W.H.O` 같은
약어의 구두점을 겨눈 것이고, 날짜의 가운뎃점은 한국어 표준 표기다.

★ 숫자만 친 `419혁명` 까지는 넣지 않았다. 셋으로 늘리면 기준이 무너진다.

## D-091. 정답이 같아도 **지식이 다르면 중복이 아니다** — 동음이의 사례를 확인했다

**시점**: R019 (작업 D)

R017 의 "우루과이"(1950 마라카낭 / 1930 1회 개최국)에 이어 두 번째 사례가 나왔다.

```
aerospace/4#009   소련·러시아의 우주정거장, 이름이 러시아말로 '평화'      → 미르
kr-language/2#007 한자어 이전에 용을 가리키던 옛 우리말                  → 미르
```

★★ Gemini 판정도 `different` (확신 1.0) 였다 — **"동음이의어일 뿐 묻는 지식이 다르다."**

**결정**: 정규화한 정답이 겹친다는 것만으로 격리하지 않는다. **판정을 거친다.**

★ 이 사례가 Q-91 의 경계를 하나 더 채운다 —
**대상이 같으면 `same`, 대상이 우연히 이름만 같으면 `different`.**
★ 우루과이(같은 나라·다른 사건)는 경계 위, 미르(다른 대상·같은 소리)는 경계 아래다.

## D-090. 라운드 안에서 같은 답이 나오면 **생성 단계에서 거절한다**

**시점**: R019 (작업 D — 60개 소분류를 한 라운드에 돌리며 드러났다)

R017·R018 은 20개 소분류씩이라 한 라운드 안에서 답이 겹치는 일이 드물었다.
★ R019 는 60개를 돌렸고, **서로 다른 대분류의 소분류가 같은 답에 이르는 일이 실제로 생겼다.**

```
생활·상식 > 재난·안전 수칙  vs  기술·의학 > 응급처치     심폐소생술 / 자동심장충격기 / 골든타임
생활·상식 > 의류 명칭        vs  한국 > 전통 의식주        고름
생활·상식 > 의류 명칭        vs  생활·상식 > 상표가 된 상품명   지퍼
생활·상식 > 별자리·십이지    vs  자연과학 > 별·별자리      황도 12궁
```

**결정**: 문제 세션이 **먼저 만든 쪽을 살리고 뒤쪽을 `ok:false` 로 거절한다.**
★ `rejectReason` 에 어느 소분류와 겹치는지 적는다.

★ 근거: 판정 단계로 넘기면 Gemini 호출이 늘고, 어차피 하나는 버린다.
**같은 세션이 둘 다 보고 있을 때 거르는 것이 가장 싸다.**

★ 실측: R019 에서 이렇게 거절한 것이 **6건**이다.
★★ 그리고 이 6건은 **판정 단계까지 갔더라도 전부 잡혔을 것**이다 —
`신규 안쪽` 후보 추출이 정규화한 정답 충돌을 보기 때문이다.
→ ★ 즉 이 규칙은 품질을 바꾸지 않고 **비용만 줄인다.**

**★★ 반대로, 생성 세션이 잡을 수 없는 것이 있다.**
라운드 간 대조와 DB 대조다. 생성할 때 그것들을 보지 않기 때문이다.
★ R019 에서 격리된 15건은 **전부** 그쪽이었다. 라운드 안 중복은 `미르` 한 쌍뿐이었고 그것은 중복이 아니었다.
→ ★ 생성 세션의 자기 검열과 판정 단계는 **겹치지 않는 영역을 맡는다.** 둘 다 필요하다.

## D-089. 중복 판정 호출을 **묶음으로 나눈다**

**시점**: R019 (작업 D)

**증상**: 후보 35쌍을 한 호출에 묶어 물었더니 **세 모델 모두** 응답이 중간에서 잘렸다.

```
[호출] gemini-3.7-flash → 응답이 JSON 이 아니다: { "items": [ { ... },
[호출] gemini-3.6-flash → 같은 증상
[호출] gemini-3.5-flash → 같은 증상
★ 판정하지 못했다. 다음 라운드로 미룬다.
```

★★ **모델 문제가 아니라 한도 문제였다.** `maxOutputTokens: 4096` 을 넘겨 JSON 이 닫히지 않은 것이다.
★ 모델 체인은 이럴 때 아무 도움이 되지 않는다 — 셋 다 같은 한도에 걸린다.

★ 이것은 D-082(요청 타임아웃)와 같은 종류의 잠복 결함이다.
**R017·R018 은 후보가 5~11쌍이라 한도에 닿지 않았을 뿐이다.**

**결정**: `JUDGE_CHUNK`(기본 12)쌍씩 나누어 부르고 결과를 합친다.

- ★ 쌍당 응답이 100~150 토큰이므로 12쌍이면 4096 안에 넉넉히 들어간다
- ★ 한 묶음이 실패하면 **그 묶음만 버리고 나머지는 살린다.** 전부 날리지 않는다
- ★ 429·예산 초과는 그 자리에서 멈춘다. 이 부분은 그대로다
- ★ 환경변수 `PIPELINE_JUDGE_CHUNK` 로 바꿀 수 있다

★ 실측: 35쌍 → 3묶음, 전부 성공. 모델은 3.6-flash 와 3.7-flash 가 섞였다.

## D-088. 적재 경로를 `generated/<round>/` 로 넓히고 새 `source_id` 를 둔다

**시점**: R018 (작업 D — ★ 코드만 고쳤다. 실행하지 않았다)

`pipeline-load.mjs` 에 `--round` 를 더했다. 주면 `approved/` 대신 `data/pipeline/generated/<round>/` 를 읽는다.

**★ 두 경로를 섞지 않는다.** `--round` 를 주면 `approved/` 는 아예 읽지 않는다.
★ 근거: `(source_id, source_ref)` UNIQUE 가 이중 적재는 막지만,
**의도하지 않은 것이 함께 들어가는 사고**는 막지 못한다. 한 번에 한 경로만 다룬다.

**★ 사람의 승인을 무엇으로 볼 것인가**
옛 경로는 `review.status === 'approved'` 로 확인했다. 새 경로에는 그 필드가 없다.
→ **`--round` 를 직접 치는 행위 자체**를 승인으로 본다. 그래서 `--round` 에 기본값을 두지 않았다.
★ 대신 코드가 강제하는 것은 남겼다 — `question.ok === true` / `discarded` 가 없다 / 정답이 있다 / 소분류 리프를 찾았다.

**★ 새 `source_id` 를 만든 이유는 라이선스가 아니라 추적이다** (`migrations/0005_seed_gen_source.sql`).
`gemini-gen` 과 `seed-gen` 은 중복률·난이도·알 가치가 크게 다르다(R017/R018 실측).
★ 문제 단위로 방식을 알 수 없으면 "어느 방식이 잘 나갔는가" 를 물을 수 없고, 적재 뒤 소급은 매우 비싸다.

★★ 0005 는 **아직 적용하지 않았다.** 그래서 지금 `--round` 로 돌리면 로더가
"sources 에 seed-gen 이 없다" 며 **거부한다.** 확인했다 — 그것이 의도한 동작이다.

★ `difficulty` 1~5 를 컬럼의 세 단계로 옮기는 경계는 임의가 아니다 —
실측 분포(평균 3.0~3.2, 4 이상이 29~40%)를 보고 2 이하=easy / 3=medium / 4 이상=hard 로 잡았다.

## D-087. Q-86 해소 — 소재가 그대로 정답이 되는 것을 문제로 보지 않는다

**시점**: R018 (건우 확정)

R017 실측에서 소재의 `subject` 가 곧 정답인 문항이 **79.5%** 였다.
프롬프트 A 는 "소재는 정답이 아니다" 를 세 번 강조하므로 설계 위반으로 보일 수 있었다.

**결정**: 문제로 보지 않는다. Q-86 을 닫는다.

**근거 (건우)**: `subject` 나 `aspect` 중 하나가 정답이 되는 것은 자연스럽고,
**실제로 같은 소분류 안 중복이 0이었다.** 각도가 갈리고 있다는 뜻이다.

★ R018 에서 이 비율은 **88.3%** 로 더 올랐다. 그런데도 같은 소분류 안 중복은 다시 **0건**이었다.
→ ★ 두 라운드 모두 "소재=정답 비율" 과 "중복" 사이에 관계가 나타나지 않았다.
**이 지표는 다양성의 대리 지표가 아니다.** 앞으로 측정은 계속하되 판단 근거로 쓰지 않는다.

## D-086. 중복 대조를 **3방향**으로 넓힌다 (라운드 간 대조 추가)

**시점**: R018 (자체 판단 — 기술적이고 되돌리기 쉽다)

R017 은 두 방향만 쟀다 — 라운드 안쪽, 기존 DB.
★★ 그래서 **소분류 사이 중복을 잴 수 없었다.** R017 스스로 그 한계를 보고에 적었다:
"200건이 소분류 20개에만 들어 있고 그 20개는 서로 겹치지 않게 일부러 골랐다."

**결정**: `seeds-check.mjs --against <round>[,<round>]` 로 **다른 라운드와도 대조**한다.

**★ 실측이 바로 값을 했다 (R018)**

| 방향 | 전체 쌍 | 후보 | 실제 중복 |
|------|---------|------|-----------|
| 라운드 안쪽 | 18,528 | 1 | 0 |
| ★ r017 대조 | 38,407 | **4** | **★ 1** |
| 기존 DB | 60,988 | 6 | 4 |

★ r017 대조에서 나온 중복 1건(`olympic/4#002` ↔ `olympic/1#001`, 쿠베르탱)은
**두 방향만 쟀다면 영영 발견되지 않았을 것이다.**

★ 후보 추리기 방식은 그대로다 — 정규화한 정답(+표기 변형)이 겹치는 쌍만 LLM 에 넘긴다.
전수 비교를 하지 않는다. 세 방향을 합쳐도 117,923쌍 중 11쌍(0.009%)만 호출에 들어갔다.

## D-085. 소재 생성과 문제 생성을 **두 단계로 나눈다**

**시점**: R018 (작업 C)

**문제**: R017 에서 프롬프트 B 의 **거절 경로가 한 번도 시험되지 않았다** (`ok:false` 0건).
★ 소재를 만든 주체와 문제를 만든 주체가 같은 세션이었기 때문이다.
내가 만든 소재를 내가 받았으니 카테고리 불일치가 날 수 없었다.

**결정**: 파이프라인을 두 단계로 쪼갠다.

```
1단계  seeds-ingest.mjs   소재만 넣는다 (question.status = "pending")
2단계  seeds-attach.mjs   그 소재에 문제를 붙인다 (seedId 로 짝을 맞춘다)
```

★ **`seedId` 로 맞추고 순서에 기대지 않는다.** 문제 세션이 일부만 돌려주거나 순서를 바꿔
돌려줄 수 있기 때문이다. 이미 문제가 붙은 소재에는 **예외를 던진다.** 덮어쓰지 않는다.

★ 옛 형식(`items` 에 `seed` 와 `question` 이 함께 있는 것)도 그대로 받는다. R017 배치를 위해서다.

**★ 순서를 나눈 것만으로 효과가 있었다 (R018 실측)**
R018 은 세션을 실제로 나누지는 않았지만 **소분류 20개의 소재를 전부 만든 뒤** 문제로 넘어갔다.
그러자 거절이 처음으로 나왔다 —

```
energy/4#010  소재 "그린워싱 + 실제보다 친환경으로 보이게 하는 행위"  → ok:false
  사유: 소분류 '환경 협약·오염' 은 협약과 오염 현상을 다루는 자리인데
        그린워싱은 기업의 광고·마케팅 행태다
```

★★ 다만 **1건은 표본이 너무 작다.** 실제 거절률은 세션을 나눠 돌려 봐야 안다.
절차는 [docs/14-GEN-SESSION.md](14-GEN-SESSION.md) 에 적었다.

## D-084. 인명 대표 정답은 **한국에서 실제로 부르는 형태**로 한다 (Q-85 확정)

**시점**: R018 (건우 확정) → 프롬프트 `question-v2`

**문제**: 프롬프트 B v1 이 두 기준을 **함께** 적었고 그것이 서로 어긋났다.

```
(가) "한국인이 이 답을 칠 때 가장 자연스럽게 치는 표현"
(나) "한국인이 아는 유명인은 풀네임으로 씁니다" + 예시 목록
```

R017 은 예시 목록을 근거로 (나)를 택해 풀네임으로 만들었다.
★ 그 결과 "라부아지에" / "바흐" 를 친 사람이 오답이 되는 위험이 생겼다.

**건우 확정**: *"내 고집을 부리는 것보다 AI 가 가진 대규모 데이터베이스를 믿어 보겠다.
한국인이 일반적으로 많이 알고 있는 걸로 가자."*

**결정**
- 인명은 **한국에서 그 인물을 부를 때 실제로 쓰는 형태**를 대표로 한다
- **풀네임이냐 성만이냐를 일률로 정하지 않는다. 인물마다 다르다**
- ★★ **판단이 갈리면 짧은 쪽을 고른다.**
  근거: 짧은 쪽이 대표이면 긴 쪽을 치는 사람이 없어 억울한 경우가 생기지 않는다.
  반대로 긴 쪽이 대표이면 **성만 치는 사람이 전부 틀린다.**
- ★ 단 **줄이면 누구인지 갈리는 경우에는 줄이지 않는다** (마리 퀴리 — 남편 피에르와 갈린다)
- ★ **인명이라는 이유로 `acceptedAnswers` 를 넣지 않는다.** 최소화 원칙은 그대로다

**★ R017 200건 재작업 결과**: 인명이 정답인 40건 중 **21건을 바꾸고 19건을 그대로 두었다.**
표기만 바꾸지 않고 **질문 노출과 힌트를 다시 검사했다** — 문제 0건.

★ v1 을 지우지 않았다. R017 의 200건은 v1 으로 만들어졌고, 어느 버전으로 만든 것인지

## D-083. **인물은 장르·분야 소분류가 맡는다. 시대 소분류가 맡지 않는다** (Q-87 확정)

**계기**: R017 에서 유일한 중복 1건이 **소분류를 넘어서** 났다.

- ★ 김홍도 건은 **신규를 버리고 기존을 유지**했다. 품질 차이가 없으니 서비스 중인 것을 건드릴 이유가 없다

**★ 경계 설명에 반영했다** (`pipeline/src/categories.ts`)
- `kr-history` 의 boundary 를 고쳤다 — "인물·유물·문화유산·사건을 **모두** 시대 소분류에" 였던 것을
  "사건·제도·정책·유물을" 로 바꾸고 인물 규칙을 넣었다. ★ 이 문장이 바로 중복의 원인이었다
- `world-history-west` / `world-history-east` 에도 같은 규칙을 넣었다
- `art` 의 `한국·동양 미술` 에 subNote 를 달았다 — "조선 시대 화가도 여기다"

**★ R017 200건 전수 점검 결과** (`data/pipeline/generated/r017/_assignment-review.json`)

| 갈래 | 건수 | 내용 |
|------|------|------|
| 위반 | **1** | 김홍도 (격리함) |
| 예외로 허용 | 7 | 아우구스투스·그라쿠스 형제·손기정·황영조·벤 존슨·히딩크·마라도나 — 전부 **사건의 주체**다 |

★★ 경계가 애매한 4건은 **규칙을 작품까지 넓힐지**를 묻는다. 특히 세한도가 그렇다 —

## D-082. Gemini 요청에 제한 시간을 건다 (`requestTimeoutMs`)

**문제 (실측)**: R017 중복 판정 호출이 **20분 넘게 돌아오지 않았다.**
`fetch` 에 제한 시간이 없어서 응답이 오지 않는 요청 하나가 파이프라인 전체를 멈췄다.

★★ 더 나쁜 것은 **재시도 사다리가 무의미해진다**는 점이다.
3+6+12+24초 백오프를 정성껏 만들어 두었는데, 첫 시도에서 영영 기다리면 그 사다리에 도달하지 못한다.

  ★ 정상 응답을 잘라내지 않을 만큼은 길어야 한다
- 그러면서도 재시도 4회가 8분 안에 끝나 사람이 기다릴 수 있다
- ★ `PIPELINE_REQUEST_TIMEOUT_MS` 로 조정할 수 있게 뒀다 (D-071 과 같은 취지)

★ 실측 확인: 재실행에서 `gemini-3.7-flash` 가 TimeoutError → 503 → 503 으로 4회 만에 포기하고
`gemini-3.6-flash` 로 내려가 1회에 성공했다. **체인이 의도대로 동작했다.**

| `exposeSuspect` | 문자열로는 들어 있으나 낱말 경계가 아니다 | ★★ **탈락시키지 않고 격리**한다. 사람이 본다 |

## D-078. Q-72 해소 — 금지 목록의 범위를 "같은 소분류 전체 이력" 으로 한다

**시점**: R017 (건우 확정 방침을 구현)

**결정**: 소재 생성 요청에 **그 소분류의 전체 이력**을 넣는다.

| 항목 | 내용 |
|------|------|
| `usedSeeds` | `subject` + `aspect` + `knowledgePoint` 전부 |
| `usedAnswers` | 대표 정답 전부 (기존 DB 문제 + 파이프라인 생성분) |

1번째에 "세종대왕 + 측우기" 를 만들고 40번째에 "장영실 + 측우기" 가 나올 때,
1번째가 보이지 않으면 막을 수 없다.

**★ 다른 소분류의 이력은 넣지 않는다.** 전역 중복은 4차 단계(LLM 판정)에서 처리한다.

한 인물이 역사적으로도 과학적으로도 중요할 수 있다.

**★★ `usedAnswers` 는 자동 금지 목록이 아니다.**
같은 답이라도 `knowledgePoint` 가 다르면 그 소재를 만들어도 된다.
"이 답이 이미 있으니 `knowledgePoint` 를 특히 주의해서 비교하라" 는 **신호**일 뿐이다.
→ 그래서 코드는 `usedAnswers` 로 아무것도 걸러내지 않는다. **목록을 건네줄 뿐이다.**

★ 실측으로 확인했다 — `football/2` 의 "1950년 마라카낭의 비극" 은 정답이 기존 문제와 같은

**같은 답이라는 이유로 잘랐다면 좋은 문제를 잃었을 것이다.**

**★ 비용 실측**: 소분류당 이력 10건을 넣었을 때 입력 블록이 30줄 안팎이었다.

실측상 문제가 되지 않았다.

## D-077. 생성 단위를 "카테고리 → 문제" 에서 "소분류 → 소재 → 소재당 문제 1개" 로 바꾼다

**정답이 겹치는 쌍이 38%** 나왔다 (R012). 겹친 것은 전부 그 분야의 대표 소재였다 —

소분류를 600~1,000개로 쪼개지 않는다. ★ 근거: 실측에서 소분류가 서로 포함 관계이면
그 둘에서 뽑은 것이 4/4 중복이었다. 잘게 쪼개면 겹치는 소분류가 늘어 **중복이 오히려 증가한다.**

**★ 실측 결과 (R017 파일럿, 소분류 20개 × 소재 10개 = 200건)**

|------|-----------|----------|
| 생성분 안에서 정답이 겹친 쌍 | R012 비교 실험 40쌍 (약 38%) | **★ 0쌍 (0.000%)** |
| 같은 소분류 안 정답 중복 | R011 에서 소분류당 1~2건에 12쌍 | **★ 0건** |
| 기존 문제와의 후보 | 32,896쌍 → 12쌍 (0.036%) | 63,200쌍 → **5쌍 (0.008%)** |
| 그중 실제 중복 | 11쌍 | **★ 1쌍** |

★★ **다만 이 비교에는 한계가 있다. 그대로 적는다.**
R017 의 200건은 소분류 20개에만 들어 있고, 그 20개는 서로 겹치지 않게 **일부러 골랐다.**
★ 소분류 사이 중복을 재는 시험으로는 약하다. 297개 전체로 넓혔을 때 다시 재야 한다.

★ 기존 g3 경로는 지우지 않고 비활성화했다 —

★ 근거: 기존 253건이 그 경로로 만들어졌고, 새 구조가 더 나쁘다는 결과가 나오면 되돌아와야 한다.

## D-073. 마스킹은 출력 변환이고 정답 판정은 입력 처리다 — 코드 구조로 분리한다

**시점**: R016 (Phase 6 구현. R003 3-3 이 예고한 위험)

**★★★ 무엇이 위험한가**

마스킹 조건은 "발신자가 이 문제의 경험자인가" 다. ★ 그 판정이 틀리면 두 가지가 동시에 망가질 수 있다 —
★ 가려지지 않아야 할 메시지가 가려지고, ★★ **그 잘못된 판단이 정답 판정까지 오염시키는 것**이다.
★ 후자가 치명적이다. 마스킹 실수 하나가 **승패를 바꾼다.**

**결정: 두 경로를 코드에서 분리하고, 그 사실을 주석으로 못 박는다.**

```
단계 2  판정   judgeAnswer(room, player, { rawText: rawNfc, ... })   ← 원문만 본다
단계 3  마스킹  maskForBroadcast(room, senderId, rawNfc)              ← 결과를 바꾸지 않는다
```

- ★★ **순서가 규칙이다.** 판정이 먼저 끝나고, 마스킹은 그 뒤의 출력 변환이다.
  ★ 마스킹을 위로 올리면 분리가 깨진다. 그래서 주석에 "순서를 바꾸지 말 것" 을 적었다.
- ★ `maskForBroadcast` 는 `outcome` 을 인자로 받지도, 돌려주지도 않는다.
  ★ 두 경로가 만나는 유일한 지점은 **같은 원문을 읽는다** 는 것뿐이다.
- ★★ 봇 시나리오가 이것을 단정한다 — 경험자의 정답이 가려지는 **같은 문제**에서
  미경험자가 같은 정답을 쳐서 정상 정답 처리되는 것을 확인한다 (테스트 케이스 #14).

★ 대가: 같은 문자열을 두 번 정규화한다(판정 1회 + 마스킹 1회).
★ 측정값으로 보면 무시할 수 있다 — 도배 부하 실측에서 판정 지연이 2ms 로 변하지 않았다(R015).
★★ 성능보다 **분리가 훨씬 중요하다.**

## D-070. 타이머는 정수 초만 표시한다 (Q-83 확정)

**시점**: R015 (건우 확정)

건우: "시간 줄어드는 게 **소수점 단위는 안 보여줘도 된다. 눈만 아프다.**"

**결정**: 화면에 보이는 모든 남은 시간은 `Math.ceil(ms / 1000)` 로 **정수 초**만 표시한다.
문제 타이머 / 카운트다운 / PAUSED 만료 카운트다운 모두 같다.

**★ 내부 계산은 ms 를 그대로 쓴다.** 표시만 바꾼다.

  **0.1초 차이로 갈리는 선착순 판정이 망가진다.**
- ★ `ceil` 을 쓰는 이유: 남은 시간이 0.4초일 때 "0초" 라고 쓰면 이미 끝난 것처럼 보인다.
  ★ 1초로 올려 보여 주고, 실제 종료는 서버 이벤트로 알린다 (클라이언트 타이머는 상태를 바꾸지 않는다).

## D-068. COUNTDOWN 에서 멈춘 방의 막다른 길을 연다

## D-067. PAUSED 는 `endsAt` 을 밀지 않고 `remainingMs` 를 저장한다

**시점**: R015 (설계 판단)

같은 목적을 두 방식으로 만들 수 있었다.

| 방식 | 내용 |
|------|------|
| (가) `endsAt` 밀기 | 멈춘 동안 매 tick 마다 `endsAt` 을 +100ms 한다 (R014 근사 구현 D-061 이 이 방식) |
| ★ (나) `remainingMs` 저장 | 멈출 때 남은 시간을 저장하고, 재개할 때 `now + remainingMs` 로 다시 잡는다 |

**결정: (나)**

**근거 넷**

1. ★★ (가)는 **"지금 멈춰 있다" 를 표현하는 값이 없다.** 상태가 `QUESTION_ACTIVE` 인 채로
   시간만 안 흐르므로, 재접속자는 멈춘 것인지 진행 중인지 구분할 수 없다.
2. ★★ (가)는 **멈춘 동안에도 tick 이 그 방을 건드린다.** PAUSED 방을 건너뛴다는 원칙과 어긋나고,
   tick 이 한 번 밀리면 그만큼 남은 시간이 줄어든다.

## D-058. 역검증을 Sonnet 이 전량 담당하고 Gemini 는 표본 감사로 내린다 (Q-81 확정)

**시점**: R014

**배경 (R013 실측)**: Gemini 호출이 **하루에 1회만** 성공했다.

```
01:09  1회 성공 (4,991 토큰)
01:10  2번째 호출 → 429
01:32  Q-62 규칙대로 15분 대기 후 재개 → ★ 또 429 → 그날 중단
```

★★ 그 결과 50건 샘플이 **전량 격리 상태**로 남았다. 500건을 만들면 500건이 격리된다.
★ R012 에서는 29회 / 164,338토큰에 429 가 0회였다. 조건이 크게 달랐다.

**★ 문제의 본질**: Gemini 가 **필수 경로**에 있었다.
생성(Opus)은 한도가 사실상 무제한인데 검증이 하루 1~2회로 막히면 파이프라인 전체가 멈춘다.

**결정 — 새 역할 분담**

| 모델 | 역할 | 권한 |
|------|------|------|
| **Opus** | 문제 생성 / 규격·프롬프트 설계 | ★ 개별 항목 최종 판정에 참여하지 않는다 |
| **Sonnet** | ★★ **역검증 + 사실 검토 + 최종 확정. 전량 담당** | ★ 최종 확정 |
| **Gemini** | ★ **표본 감사.** 하루에 쓸 수 있는 만큼만 | ★ 신호만 낸다. 어떤 항목도 뒤집지 않는다 |

★ 근거 셋
1. ★ 독립성은 유지된다. Sonnet 은 Opus 와 다른 모델이므로 자기 생성분을 자기가
   검증하는 구조가 아니다
2. ★ 품질에도 낫다. Gemini 오판 실측 — R010 정상 6건을 6건 모두 오탈락 /
   R012 탈락 3건 중 2건이 오탈락
3. ★ Gemini 는 "세 번째 관점" 으로 남는다. 하루 1~2회로도 20~30건은 볼 수 있고,
   Sonnet 이 한쪽으로 치우쳤는지 감지하는 역할에는 충분하다

### ★★★ 역검증의 정직성을 코드로 보장한다

★ 역검증은 "질문만 보고 정답을 맞혀본다" 다.
★ Sonnet 이 우리 정답을 보면서 답하면 역검증이 아니다. **그냥 동의하는 것이다.**
★ 그리고 일치 여부를 Sonnet 이 스스로 판정하면 "비슷하니 맞았다" 로 흐른다.

→ ★ 단계를 나누고 **정답 노출과 판정을 코드가 통제한다.**

```
1) export     ★ 질문만 담은 파일. **정답도 카테고리도 없다**
2) (Sonnet)   질문만 보고 답을 쓴다
3) backcheck  ★ 코드가 judgeBackcheck 로 비교한다. **Gemini 경로와 같은 함수다**
4) (Sonnet)   격리 항목 재판정 + 사실 검토
5) apply      최종 판정 반영 (★ 폐기가 일어나는 유일한 곳)
```

★ 카테고리도 담지 않는 근거: Gemini 역검증 프롬프트와 **조건을 같게** 유지해야
두 판정을 비교할 수 있다 (표본 감사의 전제다).

### ★★ 표본 감사에서 불일치가 나오면 무엇을 하는가

★★ **개별 문제의 판정을 뒤집지 않는다.** `pipeline-audit.mjs` 는 배치 파일을 쓰지 않는다.

★ 근거 — Gemini 가 Sonnet 과 다르다는 것이 "Sonnet 이 틀렸다" 를 뜻하지 않는다.
  실측이 반대 방향을 가리킨다(위 근거 2).
  ★ 성능이 더 낮은 쪽의 판정으로 더 높은 쪽을 덮으면 품질이 내려간다.

★ 그래서 **Sonnet 판정 품질의 신호**로만 쓴다.
- 불일치율이 기준(20%) 안이면 → 한쪽으로 치우치지 않았다는 근거가 된다
- 넘으면 → ★ 멈추고 **사람이 표본을 읽는다.** 셋 중 하나다 —
  (a) 문제 품질이 실제로 낮다 (b) Sonnet 판정이 느슨해졌다 (c) ★ Gemini 오판

★ 기준 20% 의 근거: R012 정상 탈락률 1~2% / R010 오탈락 사태 35%. 그 사이다.
  ★ 5% 처럼 낮게 잡으면 Gemini 자체 오판만으로 매번 멈춘다.

**★ Gemini 역검증을 지우지 않았다.** `--backcheck=gemini` 로 그대로 쓸 수 있다.
  ★ 기본값만 `none` 으로 바꿨다. 선택 단계로 내린 것이다.

## D-056. 재개가 성공하면 429 재개 한도를 돌려준다 (Q-78 확정)

**시점**: R014

**건우 확정**: (B) — 재개가 **성공하면** 429 상태를 해제한다.

**★★ R013 에서 실제로 일을 막았다**

★ 기존 코드는 게이트를 통과시킬 때 성공 여부와 무관하게 재개 1회를 소모했다.
★ 그래서 하루에 **스크립트를 하나만** 돌릴 수 있었다.
★ R013 에서 Gemini 를 필요로 한 작업이 셋이었는데(회귀 2회차 / lite 모델 측정 /
50건 샘플 역검증) **우선순위를 내가 골라야 했다.** 그것은 기획 판단이다.

**결정**: `resumes` 항목에 `outcome` 을 둔다.

| outcome | 의미 | 한도 소모 |
|---------|------|-----------|
| `pending` | 재개했으나 결과를 모른다 | ★ 소모한다 (안전한 쪽) |
| `success` | ★ 재개 뒤 호출이 성공했다 | ★★ **소모하지 않는다** |
| `rate_limited` | 재개 뒤 또 429 | 소모한다 → 그날 중단 |

★ 근거: Q-62 규칙의 목적은 "429 를 반복해 맞으며 한도를 태우지 않는 것" 이다.
★ 재개가 **성공했다면** 그 목적은 이미 달성됐다. 원래 문구도 "또 429 면" 이었다.

★★ **무한 재개가 되지 않는 근거** — 재개 직후 429 면 `rate_limited` 가 되어 그날이 끝난다.
★ 즉 **성공한 호출을 사이에 끼우지 않고는 두 번 재개할 수 없다.** 그것이 자체 제동 장치다.

★ `pending` 을 소모로 세는 근거: 결과를 모르는 재개를 공짜로 주면
한 번의 게이트 통과로 재개가 여러 번 열릴 수 있다.

★ `pipeline/src/budget.test.ts` 13건으로 고정했다.

## D-054. 한 게임 안에서 정답이 겹치는 문제를 내지 않는다 (Q-76 확정. ★ 미구현)

**시점**: R013 (명세만. Phase 3 항목)

**건우 확정**: "★★ 한 게임 세션에서 출제된 문제와 같은 정답은 나오지 않게 세팅해도 괜찮을 것 같다."

**결정**: guide 20절의 "같은 게임에서 문제 중복 금지" 에 **정답 중복 금지**를 더한다.

### ★ 정답 비교를 무엇으로 하는가 — 판단 항목이었다

**결정: 복수 정답 배열 전체(`answer_norm`)의 교집합으로 본다.** 대표 정답만 보지 않는다.

★ 근거

1. ★ 이 게임은 정답을 **정확 문자열 일치**로만 판정한다(guide 16절 / D-006).
   판정에 쓰이는 것이 `answer_norm` 전체이므로 중복 판단도 같은 기준이어야 한다.
   ★ 판정 기준과 중복 기준이 다르면 "플레이어에게는 같은 답인데 시스템은 다르게 본다" 가 생긴다
2. ★ 대표 정답만 보면 새는 경우가 실제로 있다 — R012 실측에서
   "카를 대제" 와 "카롤루스 대제" 가 서로 다른 표기로 갈렸다.
   대표 정답 비교로는 이 둘을 다른 정답으로 본다
3. ★ 배열 전체로 하면 "포르투갈어" 같은 흔한 답에서 배제 범위가 넓어진다는 우려가 있다.
   ★ 그러나 **배제는 그 게임 안에서만 유효하다.** DB에서 지우는 것이 아니다.
   30~50문제 게임에서 몇 개가 뒤로 밀리는 것은 손실이 아니다

### ★ 문제가 부족해지는 경우 — Q-22 와의 상호작용

이 조건은 출제 풀을 좁히므로 조기 종료가 더 일찍 온다.
★ **경험 규칙이 정답 중복 금지보다 우선한다**고 정했다.

```
1단계  전원 미경험 AND 정답 미사용
2단계  1명 이상 미경험 AND 정답 미사용
3단계  ★ 1명 이상 미경험 (정답 중복 허용)   ← 신설
       셋 다 비면 조기 종료 (no_questions)
```

★ 3단계를 둔 근거
- ★ 정답 중복 금지 때문에 게임이 **일찍 끝나는 것**이 정답 중복보다 나쁘다.
  30문제를 설정했는데 12문제에서 끝나면 그것이 더 큰 불만이다
- ★ 두 규칙의 무게가 다르다. 경험 규칙 위반은 "이미 아는 문제가 또 나온다" 이고,
  정답 중복은 "비슷한 게 나왔다" 다. 전자가 더 크다
- ★ 그래서 경험 규칙에는 예외를 두지 않고(기존 규칙 유지), 정답 중복 금지에만 예외를 둔다

★ 3단계로 내려간 사실은 `game_questions` 에 기록하되 **화면에는 표시하지 않는다.**
  근거 — 플레이어에게 알릴 이유가 없다. 그러나 운영자는 이 조건이 실제로
  얼마나 발동하는지 알아야 기준을 조정할 수 있다.

★ 성능 — 게임 시작 때 출제 대상의 `(question_id, answer_norm[])` 을 한 번 읽어 메모리에 둔다.
  ★ 근거: 문제 시작 절차는 30초 타이머가 시작되기 전에 끝나야 한다(04-PROTOCOL 3장).
  매 문제마다 DB 를 다시 읽으면 그 절차가 느려진다.

**명세 위치**: 01-GAME-RULES.md 7절 / 04-PROTOCOL.md 3장.

## D-052. 과다 필터링을 코드가 스스로 감지한다 — 그리고 "검증 미실행" 은 필터링과 분리한다

### 기준값과 근거

| 단계 | 기준 | ★ 왜 이 값인가 |
|------|------|----------------|
| 역검증 | 15% | 정상은 R012 실측 1~2%. ★ R010 오탈락 사태 때는 35%였다. 그 사이에 문턱을 둔다 |

숫자만이 아니라 **표본(최대 5건)** 을 함께 낸다.

**(2) 배치별로 보지 않으면 깨진 배치가 묻힌다**

★ 실측: 50건 배치가 100% 격리되었는데 전체 530건 기준으로는 12.5%여서 경고가 나오지 않았다.

## D-047. 중복 판정을 LLM 에게 맡긴다 — 유사도를 판정에서 뺀다 (Q-70 확정)

**시점**: R012 (작업 D-1 / D-2)

R011에서 "같은 정답 다른 문제" 를 구분하려고 문자 2-그램 자카드를 넣었다.

| 실제로 중복인 쌍의 유사도 | 실제로 다른 문제인 쌍 |
|---|---|
| 0.13 / 0.28 / 0.29 / 0.32 / 0.43 / 0.50 | **0.00** |

★ 모델이 같은 내용을 완전히 다른 문장으로 쓰기 때문에, 같은 문제여도 유사도가
0.13까지 내려간다. **임계값을 어디에 두든 갈리지 않는다.**
★ 건우도 12쌍을 직접 검수하고 "유사도 책정이 부정확한 것 같다" 고 확인했다.

1. ★ 유사도를 **판정 근거에서 제거**했다. 참고 수치로만 남긴다.
   `DUPE_THRESHOLDS` 상수를 지웠다 — 남겨 두면 누군가 다시 쓴다.
2. ★ 정답이 겹치면 **카테고리와 무관하게 전부 의심으로 올린다.**
   근거는 D-040 에 적은 실측이다 — 12쌍 중 11쌍(91.7%)이 실제 중복이었고,
   그중 다른 중분류에 있던 3쌍도 전부 중복이었다.
   카테고리는 **의심 강도(정렬)** 로만 쓴다.
3. ★ 판정은 **LLM 이 한다** (`dedupe-llm.ts`).

**★ LLM 판정 실측 — 건우 판정과 12/12 (100%) 일치**

```
기준: 건우 검수 결과 "'포르투갈어' 말고는 전부 중복이다"
결과: 포르투갈어 → different / 나머지 11쌍 → same
```

★ 프롬프트에서 결정적이었던 것: **"문장이 닮았는지가 아니라 묻는 대상과
필요한 지식이 같은가를 본다"** 를 앞에 두고 실측 사례를 예시로 넣은 것이다.

## D-045. 소분류 설계 원칙 — 인물·기록 소분류를 두지 않는다

**시점**: R012 (작업 C-2)

R011에서 중분류 경계는 글로 적었으나 **소분류는 검토하지 않았다.**
그 결과 포함 관계가 여러 곳에 있었고 실측에서 중복으로 드러났다.

```
애니메이션    "디즈니·픽사" ⊂ "서양 애니메이션"   → 토이 스토리 두 번
한국 문학     "근대 문학" ⊃ "시"                → 서시 두 번
발명·발견     "근현대 발명" ⊃ "과학적 발견"       → 플레밍 두 번
한국 영화     "한국 영화" ⊃ "흥행·수상 기록"      → 기생충 두 번
```

**★ 다섯 가지 원칙을 세웠다**

| # | 원칙 | 근거 |
|---|------|------|
| 1 | 한 중분류의 소분류는 **하나의 기준**으로만 나눈다 (시대/지역/장르/대상) | 축이 섞이면 포함 관계가 생긴다 |
| 2 | ★★ **"인물" 소분류를 두지 않는다** | D-040 에서 인물 **중분류**를 삭제한 것과 같은 이유 — 인물 문제는 그 인물이 활동한 시대·지역 소분류에 이미 들어간다 |
| 3 | ★★ **"기록·순위" 소분류를 두지 않는다** | (a) 축이 다르다 (b) ★ **알 가치 1인 문제를 유도한다.** 실측: "1982년 KBO 최고 타율 0.412 선수?" 가 "야구 > 선수·기록" 에서 나왔다 |
| 4 | "기타" 라는 이름의 소분류를 두지 않는다 | 무관한 것이 한 통에 들어가면 분류의 의미가 없다 |
| 5 | 소분류 사이에 포함 관계를 만들지 않는다 | 위 실측 4건 |

★ 원칙 2의 예외: 그 인물이 **분야의 분류 축으로 통용되는 경우** (클래식 음악의 작곡가,
세계 영화의 감독). 음악학·영화학의 표준 분류 축이다. 그 경우에도 `subNotes` 로 경계를 적었다.

★ 원칙 4의 취지를 지키면서 자리를 마련한 예: 종교의 "기타 종교·종파" 를
**"고대·소수 종교"** 로 바꿨다. 조로아스터교·시크교는 서로 무관하지 않다 —
"규모가 작거나 고대의 종교" 라는 일관된 축을 가진다. 이름을 그 축으로 붙였다.

**★★ 이 원칙을 단위 테스트로 고정했다. 그리고 그 테스트가 내 위반 3건을 잡았다.**
```
kr-tv|라디오·성우          원칙 2 위반 (성우가 인물 축)
esports|e스포츠 대회·선수   원칙 2 위반 (선수가 인물 축)
religion|기타 종교·종파     원칙 4 위반
```
★ 내가 세운 원칙을 내가 어겼고 테스트가 잡았다. 원칙을 글로만 남기면 지켜지지 않는다.

**★ subNotes 를 모든 소분류에 적지 않은 이유** (기술 판단)
경계 문장은 생성 프롬프트에 그대로 들어간다. 자명한 것까지 적으면
프롬프트가 길어져 **정말 중요한 경계가 묻힌다.** 겹칠 위험이 있는 39곳에만 적었다.

★ 소분류 개정으로 고아가 된 기존 문제 21건을 재배정했다 (`pipeline-remap-subs.mjs`).
★ 그중 1건은 **재배정하지 않고 검수 대기로 올렸다** — "페이커의 본명은?" 은
인물의 신상을 묻는 문제여서 새 트리에 자리가 없다.
★ 억지로 어디에 넣으면 원칙을 우회하는 셈이 된다.

## D-042. 생성 문제의 라이선스와 화면 표기를 분리한다

**시점**: R011 (작업 E)

생성 문제(`source_id='gemini-gen'`)에는 CC BY-SA 의무가 **없다.**
그런데 라이선스는 CC BY-SA 4.0 으로 두고, **화면 표기 의무는 없다고** 정했다.

| 축 | OpenTDB 문제 | 생성 문제 |
|----|-------------|----------|
| 라이선스 | CC BY-SA 4.0 (의무) | CC BY-SA 4.0 (★ 우리 선택) |
| 저작자 표시 | ★ 의무 있음 | 없음 |

★ 라이선스를 같게 두는 근거
- 저장소가 Public 이고 `manual`(직접 작성) 소스를 이미 같은 이유로 그렇게 두었다.
  한 DB 안에서 라이선스가 갈라지면 배포할 때 문제 단위로 갈라 내야 한다
- 우리가 저작권자이므로 CC BY-SA 로 두어도 잃는 것이 없다

★ 화면 문구를 고쳤다 — `문제 출처: Open Trivia Database` → `일부 문제 출처: …`
앞으로 문제 대부분이 생성 문제가 되므로 무조건 "출처는 OpenTDB" 라고 쓰면
**사실과 다른 표기**가 된다. ★ 표기를 지우는 것과 사실과 다르게 쓰는 것은 둘 다 틀렸다.
OpenTDB 문제 10건이 아직 출제되므로 표기는 유지한다.

★ 화면이 자동으로 판단하게 만들지 않았다. 그러려면 매 화면마다 소스 분포를 조회해야 한다.
표기 하나 때문에 쿼리를 추가하는 것은 과설계다(D-032와 같은 기준).
지울 수 있는 조건은 `DATA_LICENSE.md` 에 SQL 로 적어 두었다.

★ 코드에 박혀 있던 `'CC-BY-SA-4.0'` 을 없애고 `sources.license` 를 읽게 했다.
값을 코드에 박아두면 소스별로 달라지는 순간 조용히 틀린 라이선스가 기록된다.

| **중분류** | **63** | ★ 채택 |
| 대분류 | 7 | ★ 후보군이 너무 넓다. 자연과학 정답 "3" 이 서로 무관한 문제들과 충돌한다 |

**★★ 그런데 더 중요한 것을 발견했다 — 건우가 든 반례는 계층 문제가 아니었다**

```
"훈민정음을 만든 왕?"  (한국사 > 조선 전기)
"한글을 창제한 왕?"    (한국 문화유산 > 기록유산)
```

★ 이것은 중분류 검사의 결함이 아니라 **카테고리 목록의 결함**이다.
"한국 문화유산" 이라는 중분류가 존재하는 순간, 조선 시대 유물 문제는
한국사에도 문화유산에도 **합법적으로** 들어갈 수 있다.
★ 어느 계층에서 검사하든 이 목록으로는 막을 수 없다.

→ **규칙**: 중분류는 하나의 주제 축으로만 나눈다.
같은 대상을 다른 축(인물 / 유물 / 명작 / 기록)으로 다시 묶는 중분류를 만들지 않는다.

이 규칙으로 초안에서 뺀 것
- **인물(위인·현대 유명인)** — 정답이 인물인 문제는 거의 모든 중분류에서 나온다
- **건축·유적** 의 "유적" — 유적 문제는 해당 시대의 역사 중분류로 보낸다
- **한국 문화유산** (초안에는 없었으나 만들 뻔했다) — 시대 소분류로 흡수했다

**★ 검사는 세 단계로 한다** (구현: `pipeline/src/dedupe.ts`)

1. 정규화한 정답으로 **후보를 좁힌다** (`normalizeAnswer`, shared 함수 재사용)
2. 카테고리로 **의심 강도**를 정한다 (같은 중분류 > 같은 대분류 > 다른 대분류)
3. 질문 문장 유사도로 **"같은 정답 다른 문제"를 구분한다**

★ 3단계를 넣은 근거: 건우의 "문장을 하나하나 판단하는 것은 비효율" 은 **전수 비교**를 말한 것이다.
실측에서 257건의 전수 비교는 32,896쌍이지만, 정답으로 좁힌 뒤 남은 후보는 **12쌍**이었다.
후보만 문장을 비교하는 비용은 사실상 없다.

**★★ 그런데 실측이 설계의 한 부분을 반박했다. 그대로 적는다.**

3단계(질문 유사도)는 "같은 정답 다른 문제" 를 구분하려고 넣었다. **구분하지 못했다.**

| 실제 중복인 쌍의 유사도 | 실제로 다른 문제인 쌍의 유사도 |
|---|---|
| 0.13 (토이 스토리) / 0.28 (베토벤) / 0.29 (스우시) / 0.32 (기생충) / 0.43 (버버리) / 0.50 (플레밍) | 0.00 (포르투갈어) |

★ 모델이 문장을 완전히 다르게 바꿔 쓰기 때문에, 같은 문제여도 유사도가 0.13까지 내려간다.
★ 0.13과 0.00 사이에 선을 그으면 이 표본(8쌍)에서는 완벽히 갈리지만 **그것은 과적합이다.**
표본 8쌍으로 임계값을 정하지 않는다. 임계값을 그대로 두었다.

★ 더 중요한 관측 — **정답이 겹치면 카테고리와 무관하게 거의 항상 중복이었다.**

| 관계 | 쌍 수 | 실제 중복 |
|------|------|----------|
| 같은 중분류 + 같은 정답 | 9 | ★ 8 |
| 다른 중분류 + 같은 정답 | 3 | ★ 3 (태평양 / 햄릿 2쌍) |
| **합계** | **12** | **11 (91.7%)** |

★ 건우의 원칙 중 "다른 카테고리 + 같은 정답 → 대체로 문제없음" 은 이 표본에서 **성립하지 않았다.**
  · `world-geo > 대륙·바다` "가장 넓은 대양은?" vs `earth > 해양` "가장 넓은 바다는?" → 둘 다 태평양
  · `theatre > 연극 고전` vs `world-lit > 시·희곡` → 둘 다 햄릿
★ 그리고 유일한 무해 사례는 **같은 중분류 안**에 있었다(빵의 어원 / 브라질 공용어 → 포르투갈어).
  카테고리 계층이 중복 여부를 예측하지 못했다.

→ **결론**: 후보 추리기는 정답 일치만으로 하고, 카테고리는 **자동 폐기가 아니라 의심 강도(정렬)** 에만 쓴다.
  ★ 위 두 반례는 다시 카테고리 목록의 문제다 — 인접 중분류의 경계를 더 좁혀야 한다(R011 8장).
  ★ 표본이 12쌍이다. 규모가 커지면 흔한 정답(숫자·나라 이름)에서 무해한 충돌이 늘 것으로 **추정**한다.
    그때는 카테고리로 정렬하는 것이 실제로 값을 한다.

★ 유사도는 **문자 2-그램 자카드**를 쓴다. 단어 단위가 아닌 이유: 한국어는 조사가 붙어
단어 경계가 흔들린다. "한글을 창제한" 과 "한글의 창제자" 는 단어로는 하나도 겹치지 않는다.

**★ 중복 의심을 자동 폐기하지 않는다. 검수 대기로 둔다.**
근거: R010에서 내가 만든 판정 로직이 정상 문제 6건을 **전부** 오탈락시켰다.
판정 로직은 틀린다. 버리면 회복에 토큰이 들고, 남기면 사람이 한 번 보면 된다.
★ 예외: 정규화한 질문까지 완전히 같으면 그것은 판정이 아니라 동일성이다(`exact`).

## D-039. 카테고리를 생성 요청의 입력으로 둔다 — 모델이 반환한 값을 쓰지 않는다

**시점**: R011 (작업 C-2)

R010까지는 모델이 카테고리를 골랐다(`[생성 4] category — 다음 중 하나: …`).
★ 그러면 같은 문제가 라운드마다 다른 카테고리로 분류될 수 있고,
카테고리가 흔들리면 **중복 검사의 기준 자체가 흔들린다**(D-040).

→ 슬롯 단위로 `[대분류 > 중분류 > 소분류]` 를 **지정해서 보낸다.**
모델은 `slotId` 만 되돌려 주고, 카테고리는 **우리가 요청한 값을 기록한다.**

★ 그러나 모델이 "이 카테고리로는 조건을 만족하는 문제를 만들 수 없다" 고 말할 여지는 남겼다
(`offCategory: true`). 억지로 만든 문제가 실전에 나가는 것이 더 나쁘다.
그 경우는 탈락으로 처리하고 사유를 남긴다.

**실측 (R011, 270슬롯)**: `offCategory` **0건** / 슬롯 누락 **0건** / 카테고리 어긋남 **0건**.
★ 통과한 257건을 직접 읽어 확인했다. 요청한 소분류와 어긋난 문제는 없었다.

★ 부수 효과: 슬롯을 지정하니 **소분류를 돌려 쓸 수 있게 되었다**(`buildSlots` 의 `subOffset`).
오프셋 없이 두 번 돌리면 같은 소분류를 다시 요청해 중복이 난다.
★ 규모를 늘릴 때 소분류당 목표를 올리지 않고 트리를 넓히는 구조가 이것으로 성립한다.

## D-038. 접근성과 난이도를 별도 필드로 분리한다

**시점**: R011 (작업 D-1, 건우 지시)

R010의 `krAccessible` 하나에 두 가지가 섞여 있었다.

```
"한국인 대부분이 아는 분야의 어려운 문제" (조선 왕 순서)   → 좋다
"특정 집단만 아는 분야의 쉬운 문제" (페르소나5 캐릭터)     → 나쁘다
```

★ R010 실측에서 페르소나5 문제가 `krAccessible=3` 으로 통과했다.
그 3은 "게임 하는 사람은 안다" 는 뜻이었고 난이도가 적당하다는 뜻이 아니었다.

→ 두 축으로 쪼갰다.

| 필드 | 무엇을 재는가 | 1~5의 의미 |
|------|-------------|-----------|
| `accessibility` | ★ **분야**의 성질 | 5=교과 과정·국민 대다수 / 3=관심 있는 사람만 / 1=해당 커뮤니티 밖에서는 아무도 모름 |
| `difficulty` | ★ **문항**의 성질 | 5=그 분야를 잘 아는 사람도 헷갈림 / 1=조금이라도 알면 반드시 안다 |

**★ 실측에서 드러난 한계 — 두 점수 중 하나만 보면 안 된다**

```
"1924년 제1회 동계 올림픽 개최 도시?" → 샤모니   접근성 3 / 난이도 3
"1982년 KBO 최고 타율 0.412 선수?"   → 백인천   접근성 3 / 난이도 2
```

★ 난이도 2~3이지만 **방에서 아무도 못 맞힐 수 있다.** 정의대로는 맞다 —
난이도는 "그 분야를 아는 사람 기준" 이고, 야구 팬에게 백인천은 쉽다.
★ 그러나 우리가 실제로 필요한 판단은 **두 점수의 조합**이다.
→ 출제 선별은 `접근성` 을 하한으로 걸고 `난이도` 로 다양성을 주는 방식이어야 한다.
★ 하한값은 건우가 정한다(R011 8장). 코드에 임계값을 박지 않았다.

## D-037. 역검증 앞에 싼 모델 게이트를 둔다 (단계별 검수)

**시점**: R011 (작업 D-5)

건우가 "모델 여러 개가 동시에 검수 + 역검증" 을 제안했다. 의도는 검증 강도를 높이는 것이다.
★ 그런데 검수 모델 3개를 붙이면 문제 1건당 호출이 4회가 되어 처리량이 1/4 로 떨어진다.
무료 한도가 제약인 상황에서 그것은 "검증을 강화했더니 문제가 없어졌다" 로 끝난다.

**→ 단계별 게이트를 택했다.**

```
생성 → [1단계] 3.5-flash-lite 로 전량 역검증
          ├─ 맞히고 + 집합 밖 대안 없고 + 확신 0.7 이상  → 통과 (상위 모델 안 부름)
          └─ 그 밖의 경우                                → [2단계] 상위 모델로 승급
```

★ 왜 "여러 모델 동시" 보다 낫다고 판단했는가
- 여러 모델을 동시에 돌리면 **쉬운 문제에도 비싼 검증을 쓴다.**
  검증이 필요한 것은 애매한 문제인데, 어느 것이 애매한지는 한 번 물어보면 알 수 있다
- ★ 싼 모델이 못 맞히는 것과 애매한 것은 대체로 겹친다. 게이트가 그것을 걸러 준다
- 합의(voting)를 쓰지 않은 이유: 세 모델이 **같은 방향으로 틀리는** 상관관계가 있다.
  R010에서 세 모델의 품질 차이를 찾지 못했다(D-033). 표를 세는 것으로 강도가 올라가지 않는다

**실측 (R011, 270슬롯 / 257건 통과)**

| 지표 | 값 |
|------|-----|
| 1단계에서 끝난 것 | 260건 (96.3%) |
| 2단계로 승급 | 10건 (3.7%) |
| 역검증 토큰 | 게이트 39,004 + 승급 6,893 = **45,897** (건당 170) |

★★ **그런데 호출 수는 목표를 못 맞췄다. 그대로 보고한다.**

| 방식 | 역검증 호출 수 |
|------|--------------|
| 게이트 없이 상위 모델로 전량 | 11회 (생성 배치마다 1회) |
| ★ 이번에 실제로 쓴 방식 (그룹마다 승급) | **18회 (1.64배)** |

★ 원인: 승급 대상이 그룹당 1~2건인데 그것 때문에 호출 하나를 통째로 썼다.
★ 목표는 1.2~1.5배였다. **넘겼다.**
→ 코드를 고쳤다. 승급 대상을 전 그룹에서 모아 **실행 끝에 한 번만** 부른다.
  그러면 11 + 1 = 12회(1.09배)가 된다.
  ★ 이번 샘플은 고치기 전 방식으로 생성되었다. 다음 실행부터 적용된다.

★ 토큰은 줄었을 것으로 **추정**한다(게이트 모델이 훨씬 싸다). 근거는 R010 프로브에서
같은 프롬프트에 3.5-flash-lite 94토큰 / 3.6-flash 437토큰이었다는 관측이다.
★ 그러나 이번에 대조군(전량 상위 모델)을 측정하지 않았으므로 **확인 불가**다.
★ 무료 한도가 호출 수 기준인지 토큰 기준인지도 확인 불가다(D-034). 그래서 둘 다 줄이는 방향으로 만들었다.

★ 게이트가 실제로 걸러 낸 것 하나 — `"'가장자리'를 뜻하는 순우리말은?" → 언저리`
역검증이 "변두리" 라 답하고 "테두리" 를 대안으로 냈다. **진짜 애매한 문제였다.**
270건 중 역검증이 잡은 것은 3건이다(애매 1 / 불일치 2).
★ 이것이 "생성에도 역검증을 유지한다"(건우 지시)의 근거다.
생성은 원본이 없으므로 모델이 애매한 문제를 **지어낼** 수 있다.

★ 1단계와 2단계에 같은 모델을 쓰지 않는다. 생성에 쓴 모델도 제외한다(`pickBackcheckChain`).
자기가 만든 문제를 자기가 검증하면 검증이 아니다.

## D-036. 라이선스 출처를 화면에 표기한다 — Phase 7로 미루지 않는다

## D-035. 저장된 배치를 다시 판정할 수 있게 한다 — 규칙을 고칠 때마다 데이터를 잃지 않는다

**시점**: R010

**무엇이 문제였는가**

역검증 판정 규칙에 결함이 있었고(D-034 참조) 고쳐야 했다.
★ 그런데 규칙을 고치면 그 효과를 어떻게 확인하는가? 다시 가공하려면 토큰이 든다.
그리고 이 프로젝트에서 토큰은 하루 몇 만 개 수준으로 매우 제한적이다(D-034).
★ 즉 **규칙을 개선할수록 데이터를 잃는** 구조였다.

**결정**: 판정을 다시 계산하는 경로를 만든다 (`npm run pipeline:rejudge`).

저장된 것만으로 재계산이 가능하다.
- 모델의 역검증 응답 (`backcheck.answer` / `alternatives` / `confidence`)
- 우리가 만든 정답 집합 (`generated.answers`)

★ API 호출이 0회다. 실제로 이번 라운드에 이 경로로 **오탈락 6건을 회복**했다.

★ 다시 계산하는 것은 **판정**뿐이다. 생성물(번역·복수 정답)은 모델이 만든 것이므로
다시 만들려면 호출이 필요하다. 그 경계를 코드 주석에 명시했다.

★ 이것이 R002 2-3의 "원본과 가공 결과를 함께 보관한다" 가 실제로 값을 하는 지점이다.

## D-034. Gemini 무료 한도 실측 결과와 429 처리 (Q-54 확정 이행)

**시점**: R010

**Q-54 확정 사항**: 무료 한도 내에서만 운영한다. 429 가 나오면 그날 중단한다.
한도는 문서로 확인하지 않고 실측으로 파악한다.

### 실측 결과

| 항목 | 값 |
|------|-----|
| 429 를 맞기까지 성공한 클라이언트 호출 | **2회** (약 7,700~10,500토큰) |
| 그날 누적 성공 호출 (probe 포함, 추정) | 약 20여 회 / 약 3만~4만 토큰 |
| 429 응답 본문 | `RESOURCE_EXHAUSTED  You exceeded your current quota…` |
| 429 응답 헤더의 한도 정보 | **없음** (R005와 동일) |
| 429 직후 최소 호출(`1+1=?`) | ★ 5개 모델 전부 **200** |
| 429 직후 실제 크기 호출 | ★ 다시 **429** |

**★ 어느 차원의 한도인지는 확인 불가다.**
에러 본문이 RPD / RPM / TPM 중 무엇인지 말해주지 않고 헤더에도 정보가 없다.

**★ 그러나 다음은 확인되었다 (추정이 아니라 관측)**
- 작은 호출은 통과하고 큰 호출은 막힌다 → **토큰 기반 한도**가 걸려 있다
- 몇 분 뒤 작은 호출이 되살아났다 → 창(window)이 하루보다 짧다
- 그런데 큰 호출은 몇 분 뒤에도 계속 막혔다 → 창이 분 단위보다 길거나 누적이 크다

→ **가장 그럴듯한 해석(추정)**: 짧은 창의 TPM 한도와 더 긴 창의 토큰 한도가 함께 있고,
이번에는 후자에 근접했다. ★ 확정하려면 하루를 비우고 처음부터 측정해야 한다.

### 대응

1. **자체 예산 상한**을 둔다 — 하루 처리 건수와 토큰 상한. 429 를 맞기 전에 스스로 멈춘다
2. **호출 간 최소 간격 4초 → 30초**, **배치 크기 10 → 5**.
   근거: 45초에 12요청(재시도 포함)을 낸 것이 429 의 직접 원인이었다
3. **상위 모델 재시도를 1회로 제한**한다.
   3.8 에 4회 + 3.7 에 4회를 버리고 3.6 에 도달하는 것은 8요청 낭비이고,
   ★ 그 낭비가 429 를 자초했다. 품질은 세 모델이 동일했다(D-033)
4. **상태 파일을 커밋한다** — Actions 는 실행마다 새 컨테이너다.
   파일로 남기지 않으면 "어제 429 를 맞았다" 를 다음 실행이 모른다
5. ★ **게이트에 걸려 아무것도 하지 않는 것은 성공이다**(종료 코드 0).
   실패로 만들면 매일 실패 알림이 오고 진짜 실패를 놓친다

### ★ 규칙과 실측이 어긋나는 지점 — 혼자 결정하지 않았다

Q-54 의 "429 → 그날 중단" 은 **일일 한도**를 전제한 규칙이다.
그런데 실측된 429 는 더 짧은 창일 가능성이 크다.
★ 그 경우 하루를 버리는 것은 규칙의 의도가 아닐 수 있다.

→ 기본 동작은 **규칙 그대로** 두었다. 코드가 스스로 규칙을 바꾸지 않는다.
→ 대신 사람이 판단해 해제하는 명령을 만들었다 — `npm run pipeline:reset-limit`.
  ★ 자동으로 호출되는 곳은 없다.
→ 429 종류를 구분해 자동 처리할지는 **Q-62** 로 올렸다.

### ★ 유료 전환 여부도 Q 로 올렸다 (Q-63)

건우가 "월 5달러 미만이면 지불 가능" 이라고 했고, 이번 실측에서
**무료 한도로는 100건 배치조차 하루에 끝내지 못했다.**
목표가 1,000건 이상이므로 이 속도로는 수십 일이 걸린다.
★ 운영·비용 판단이므로 혼자 결정하지 않는다.

## D-033. Track D 모델 구성 — 실측으로 확정 (Q-59 종결)

**시점**: R010

### 확정 구성

| 용도 | 체인 (앞에서부터 시도) |

★ 별칭(`gemini-flash-latest` 등)을 쓰지 않는다. 가리키는 모델이 예고 없이 바뀌면
같은 프롬프트가 다른 결과를 내고 `review_queue.ai_model` 기록이 무의미해진다.

★ 모델명은 `pipeline/src/config.ts` 한 곳에만 둔다.

### ★ 왜 하나가 아니라 체인인가

R005 교훈("목록에 있다고 쓸 수 있는 것이 아니다")을 확인하려 실제로 호출했다.
그런데 **다른 종류의 문제**가 나왔다 — 404 가 아니라 **503 "high demand"** 다.

| 모델 | 최소 프롬프트 | 실제 크기 프롬프트(3,796자) | responseSchema |
|------|--------------|---------------------------|---------------|
| `gemini-3.8-flash` | 재시도 2회째 200 | ★ **5회째** 200 (3+6+12+24초 대기) | 지원 |
| `gemini-3.7-flash` | 재시도 2회째 200 | 2회째 200 | 지원 |
| `gemini-3.6-flash` | 1회 200 | ★ **1회 200** | 지원 |
| `gemini-3.5-flash` | 재시도 2회째 200 | — | 지원 |
| `gemini-3.5-flash-lite` | 1회 200 | — | 지원 |

★ **한 번의 503 을 "쓸 수 없다" 로 단정하면 안 된다.** 재시도로 구분해야 한다.
그러나 상위 모델은 **자주** 503 이 나므로, 재시도로 매달리면 요청을 낭비하고
그 낭비가 429 를 자초한다(D-034). → 상위 모델은 **1회만** 시도하고 내려간다.

### 품질 비교 (실제 프로덕션 프롬프트, 함정 문제 포함)

| 항목 | 3.8-flash | 3.7-flash | 3.6-flash |
|------|-----------|-----------|-----------|
| 함정 회피 (유일성·서술형·범위형·정상통과·외래어) | — | — | ★ **6/6** |
| 반 고흐 성만 표기 | O (7변형) | O (8변형) | O (7변형) |
| 코지마 성만 표기 (R005 미흡점) | ★ O | ★ O | ★ O |
| 영국 국기 함정 uniqueAnswer=false | O | O | O |
| schema 호출 총 토큰 (동일 프롬프트) | 3,297 | 3,112 | — |

★ **품질 차이를 찾지 못했다.** 세 모델 모두 함정을 회피하고, R005에서 미흡했던
일본 인명 성만 표기도 전부 넣었다(프롬프트 강화 효과).

### ★ 그래서 실제로는 3.6-flash 가 대부분 처리했다

100건 배치에서 **20건 전부 `gemini-3.6-flash`** 가 가공했다.
3.8 과 3.7 은 매 청크마다 503 이었다.

★ 지시가 "내려가는 경우 그 사실과 수치를 반드시 보고한다" 였으므로 명시한다 —
**더 높은 모델을 쓸 수 있었으나 무료 티어의 가용성 때문에 쓰지 못했다.**
품질 손실은 관측되지 않았다(위 표).
유료 전환으로 개선될 수 있는지는 **확인 불가**이며 Q-63 으로 올렸다.

★ 항목마다 **실제로 가공한 모델**을 기록한다(`meta.processModel`).
체인 때문에 항목별로 다를 수 있으므로, 그 값을 기록하지 않으면
`review_queue.ai_model` 이 거짓이 된다.

## D-032. 알림을 화면 고정 토스트로 바꾼다 — 표시 경로는 그대로 한 곳

**시점**: R009 (건우 지적 2건)

**무엇이 부족했는가**

D-027 에서 "서버 에러를 화면에 띄우는 경로" 를 한 곳으로 모았다.
그때는 셸 맨 위, **문서 흐름 안의 배너**로 넣었다.

★ 로비는 채팅·참가자 목록 때문에 스크롤이 길다.
아래쪽을 보고 있으면 배너가 화면 밖이어서 **스크롤을 최상단까지 올려야 보였다.**
→ "표시 경로를 만들었다" 는 달성했지만 **"사람 눈에 도달한다" 는 미완**이었다.
D-027의 목적을 절반만 이룬 상태였다.

**★ 그리고 진짜 결함이 하나 더 있었다.**
빈 방 ID 로 실패 → 올바른 ID 로 **입장 성공** → 방 안에서도
"방 ID를 입력해 주세요." 가 계속 떠 있었다.
★ 이미 해결된 문제를 화면이 계속 문제라고 말한다. 자동 만료로는 해결되지 않는다
(만료 전에 화면이 바뀌면 새 화면에서 계속 떠 있다).

**결정 — 표시 방식만 바꾸고 경로는 그대로 한 곳**

`Notice.tsx` → `Toast.tsx`. App 의 셸이 여전히 유일한 표시 지점이다.
★ 개별 화면은 여전히 에러 표시를 하지 않는다. 그 원칙을 깨지 않았다.

### (1) 위치 — 화면 아래 중앙 고정

| 후보 | 장점 | ★ 문제 |
|------|------|--------|
| 위쪽 고정 | 모바일 키보드에 가려지지 않는다 | ★ **Phase 3의 문제 지문과 남은 시간이 위에 온다.** 30초 승부의 핵심 정보를 가린다 |
| **아래쪽 고정** | ★ Phase 3의 핵심 정보를 절대 가리지 않는다. 시선·손이 이미 아래에 있다 | iOS 에서 소프트 키보드가 열리면 가려질 수 있다 |

★ **아래쪽을 택했다.** 근거는 지시에 명시된 조건이다 —
"Phase 3에서 문제 지문과 남은 시간이 화면에 나온다. 그것을 가리지 않을 위치를 지금 고를 것."
나중에 옮기지 않으려면 게임의 핵심 정보 쪽을 피해야 한다.

★ 조작 대상을 가리지 않는지는 **좌표로 실측**했다(ui-check).
`.wrap` 의 아래 여백을 180px 로 늘려 완충 구간을 만들었다.
320px 에서 토스트 높이가 133px 이었으므로 여유가 있다.
검사 대상: 채팅 입력창 / 전송 버튼 / 하단 푸터(로그아웃).
★ 처음에 140px 로 잡았더니 320px 에서 푸터의 로그아웃 버튼과 겹쳤다. 실측으로 잡았다.

★ 레이어는 `pointer-events: none`, 토스트 자신만 `auto` 다.
시각적으로 겹쳐도 그 아래 버튼을 누를 수 있다.

★ 남은 한계: iOS 소프트 키보드. 지금은 다루지 않는다([09-BACKLOG.md](09-BACKLOG.md)).
에러는 대부분 버튼을 누를 때 발생하고 그때는 키보드가 닫혀 있다.
Phase 3의 채팅 rate limit 처럼 입력 중 발생하는 에러가 생기면 그때 재검토한다.

### (2) 지속 시간 — 7초

최악의 경우 세 줄 합계가 약 70~90자다.
한국어를 초당 10~13자로 읽으면 6~9초가 필요하다. 그 중간을 잡았다.

★ 짧게 잡아도 정보가 영구히 사라지지 않는다. 같은 조작을 다시 하면 같은 토스트가
다시 뜨고 타이머도 다시 시작된다.

★ 에러 코드별로 시간을 다르게 하지 않는다. 중요도 분류는 만들지 않는다(지시).

### (3) 쌓임 — 표시 슬롯을 하나만 둔다

★ 가장 단순한 방법을 골랐다. 상태가 `ToastContent | null` **하나**다.

- 같은 에러 연타 → App 이 매번 **새 객체**를 넣으므로 `content` 의 identity 가 바뀌고,
  Toast 의 effect 가 다시 실행되며 이전 타이머를 정리하고 새로 건다.
  ★ "같은 코드면 기존 것의 타이머만 갱신" 이 별도 장치 없이 성립한다
- 다른 종류가 연달아 오면 **최신 하나만** 보여준다.
  개수 상한 장치도 필요 없다. 슬롯이 하나이므로 자동으로 1개다

★ 여러 개를 쌓는 목록·큐·우선순위를 만들지 않았다. 과설계다.

### (4) 사라지는 조건 — 세 가지뿐

1. 자동 만료 (7초) — `Toast.tsx`
2. 사용자가 "닫기" — 유지
3. ★ **화면이 바뀐다** — `App.tsx` 의 `viewKey` effect

`viewKey` = `loading` / `terminated` / `auth` / `room:<방ID>` / `home`.
바뀌면 알림을 지운다. 방을 옮기는 것도 화면 전환으로 센다.

★ 이 effect 는 에러 effect 보다 **먼저** 선언되어야 한다.
한 커밋에서 둘이 함께 실행되면 나중에 선언된 쪽이 이긴다.
에러가 살아남는 편이 안전하다(에러 때문에 화면이 바뀌는 경우가 있다).

**★ 어디까지 했고 왜 거기서 멈췄는가**

"에러의 원인이 해소되었을 때" 를 코드별로 짝짓지 않았다.
예를 들어 `NOT_ENOUGH_QUESTIONS` 를 문제 수 변경과 짝지어 지우는 식이다.

멈춘 이유
- ★ **화면 전환 + 자동 만료로 이번 증상이 전부 해결된다.** 남는 경우를 찾지 못했다
- 코드별 짝짓기는 에러 코드가 늘어날 때마다 짝을 추가해야 하고,
  빼먹으면 정확히 지금과 같은 결함이 된다. 규칙이 아니라 목록이 된다
- 설정값 관련 에러는 화면에 **별도의 즉시 검증 문구**가 이미 있다
  (`★ 지금 출제할 수 있는 문제는 53개입니다…`). 그것이 원인 해소를 실시간으로 보여준다.
  토스트는 "그 상태로 눌렀다" 는 사건의 기록이므로 시간이 지나 사라지는 것이 맞다

## D-031. UI 지적을 "지금 고칠 것" 과 "Phase 7로 미룰 것" 으로 나누는 기준

**시점**: R009 (건우: "이런 UI 적인 건 아직 미완성이긴 하지만 일단은 불편한 부분")

Phase 7이 UI 다듬기 단계다. 그때까지 참을 것인지 발견될 때마다 고칠 것인지
매번 다시 판단하지 않도록 기준을 정한다.

### ★ 지금 고친다 — 다음 중 하나라도 해당하면 **결함**으로 취급한다

## D-030. 프록시 오류 로그를 침묵시키지 않는다 — 전제가 틀렸음을 실측으로 확인

**시점**: R008

**지시받은 내용**: `[vite] ws proxy error: read ECONNRESET` 이 반복되는데
"탭 닫기·새로고침 때 나는 정상 로그이므로 조용히 처리하라" 였다.

**★ 실측 결과 그 전제가 틀렸다.** 세 상황을 각각 재현했다.

| 상황 | 프록시 로그 |
|------|-----------|
| socket.io 연결을 FIN 없이 강제 종료 (3회) | **없음** |
| ★ 실제 Chrome 에서 프록시 경유 WebSocket 을 맺고 탭 닫기 | **★ 없음** |
| ★ 서버 프로세스가 죽기 | ★ `ECONNRESET` 1건 → 이어서 `ECONNREFUSED` 가 계속 반복 |

즉 이 로그는 **"서버가 사라졌다"** 를 정확히 알려주고 있었다.
탭을 닫아서 나는 로그가 아니다.
(직전 라운드에 낡은 서버 프로세스를 종료한 적이 있는데 그때 난 것으로 **추정**한다.
건우의 화면을 직접 보지 못했으므로 그 시점을 특정할 수는 없다 — **확인 불가**)

**결정**: `ECONNRESET` 을 침묵시키지 않는다.
침묵시키면 "서버를 안 켰다 / 서버가 죽었다" 를 알 수 없게 되어 훨씬 나쁘다.
★ 지시에도 "모든 오류를 숨기지 말 것. 정상적 종료만 걸러라" 가 있었고,
실측 결과 **걸러야 할 정상적 종료가 존재하지 않았다.**

**대신 신호는 남기고 소음만 줄였다.**

1. 스택 대신 한 줄로, 무엇을 해야 하는지까지 적는다
   `[proxy] ECONNREFUSED — 게임 서버(:3000)에 연결할 수 없습니다. 다른 터미널에서 npm run dev 가 떠 있는지 확인하세요.`
2. 같은 코드가 5초 안에 반복되면 모아서 한 번만 알리고 생략 횟수를 적는다
   (socket.io 재연결 때문에 `ECONNREFUSED` 가 초당 여러 번 난다)

**구현 함정 하나**: `proxy.on('error')` 를 달아도 Vite 자신의 로그는 그대로 나온다.
Vite 가 프록시 오류를 자기 logger 로 직접 찍기 때문이다.
처음에 그렇게 만들었더니 로그가 오히려 **늘었다**(14줄 → 20줄).
→ `customLogger` 로 그 한 종류만 가로채 우리 형식으로 바꿨다. 다른 로그는 손대지 않는다.

**결과**: 서버 강제 종료 시 20줄 → **2줄**. 두 줄 모두 원인과 조치를 담고 있다.

## D-029. 브라우저 확인(ui-check)을 게이트에 넣는다 — Chrome 이 없으면 건너뛴다

**시점**: R008 (Q-61 (B) 승인)

`npm run verify` = `typecheck` + `test` + `smoke` + **`ui-check`**

**세 게이트의 역할이 다르다. 겹치지 않는다.**

| 게이트 | 무엇을 보장하는가 | 무엇을 보장하지 못하는가 |
|-------|-----------------|----------------------|
| typecheck | 타입이 맞는다 | 실행되는지 모른다 (R006) |
| smoke | 프로세스가 뜨고 응답한다 | 화면이 옳은지 모른다 |
| bot | 서버 로직과 규칙이 옳다 | ★ 클라이언트를 우회한다 (R008) |
| **ui-check** | ★ **사람이 버튼을 눌렀을 때 실제로 그렇게 동작한다** | 실제 IME 조합 / 실기기 / 사람의 판단 |

**★ Chrome 을 찾지 못하면 실패가 아니라 건너뛰기다** (종료 코드 0).
게이트가 환경에 따라 깨지면 게이트로서 신뢰를 잃는다.
건너뛴 경우 출력에 그 사실과 "통과로 간주하지 않는다" 를 명확히 남긴다.
`UICHECK_CHROME` 으로 경로를 지정할 수 있고, ★ 그 값이 있으면 그것만 쓴다
(후보 목록에 섞으면 지정한 경로가 없을 때 다른 Chrome 으로 조용히 실행된다).

**의존성**: `ws` 를 devDependency 로 추가했다.
socket.io 의 전이 의존성으로 이미 설치되어 있었지만, 전이 의존성에 기대면
상위 패키지가 바뀔 때 조용히 사라진다.

**★ 이 도구가 스스로 틀린 적이 세 번 있다.** 도구를 믿는 것도 검증해야 한다.

| 오탐 | 원인 | 고친 방법 |
|------|------|----------|
| "50문제" 가 2줄로 보였다 | 사각형 개수를 셌다. 브라우저는 글자 종류 경계에서 텍스트 상자를 쪼갠다 | 사각형의 **top 값 종류**를 센다 |
| 접속 종료 배지가 없는데 있다고 판정 | 안내 문구에도 "접속 종료" 가 들어 있었다 | `.badge.off` **요소**를 본다 |
| 방 ID 를 `/` 로 읽어 게스트 입장이 실패 | 방이 없는 화면에도 "초대 링크로 입장" 이 있어 방 생성 전에 통과했다 | 주소가 `/r/` 로 바뀌고 `.players` 가 생기는 것을 함께 본다 |

★ 교훈: **텍스트로 화면 상태를 판정하지 않는다.** 구조(선택자·주소)로 판정한다.

## D-028. 봇 테스트와 브라우저 확인의 경계를 정한다 ★

**시점**: R008 (같은 유형의 사고가 세 라운드 연속 발생한 뒤)

**무엇이 반복되었는가**

| 라운드 | 사고 | 공통점 |
|-------|------|-------|
| R005 | 봇이 사람과 **다른 경로로 서버를 띄워** 실행 불가를 놓쳤다 | 검증 대상이 사람이 쓰는 것과 달랐다 |
| R006 | 그것을 고치고 실행 확인 게이트를 만들었다 | — |
| R007 | 봇이 **소켓으로 직접 요청을 보내** 클라이언트를 우회했다. 서버는 옳게 거부했는데 화면에는 아무 안내도 없었다 | 같다 |

★ 세 번 모두 같은 문장으로 요약된다.
**"서버는 옳게 동작하는데 사람이 쓰는 경로에서는 다르게 동작한다."**

**★ 왜 반복되는가 — 구조적 원인**

봇은 소켓 클라이언트다. 사람의 경로는 **브라우저 → 클라이언트 코드 → 소켓** 이다.
봇은 그 중간을 건너뛴다. 그래서 **클라이언트 코드에 있는 결함은 원리적으로 잡을 수 없다.**
이것은 봇 테스트를 더 열심히 써서 해결되는 문제가 아니다. 검증 범위 자체가 다르다.

**결정 — 계층별로 무엇을 검증하는지 못 박는다**

| 계층 | 도구 | 검증 대상 | ★ 원리적으로 잡을 수 없는 것 |
|------|------|----------|--------------------------|
| 순수 함수 | Vitest | 정규화·힌트·순위·설정 검증 | 그 함수를 실제로 부르는지 |
| 프로세스 | smoke | 기동·응답·종료·포트 해제 | 로직과 화면 |
| 서버 로직 | bot | 규칙·권한·상태 전이·동시성·DB 기록 | ★ **클라이언트 코드 전부** (버튼 활성 여부, 표시 경로, 조건부 렌더) |
| 사람 경로 | **ui-check** | 버튼 클릭 → 서버 왕복 → 화면 표시. 조건부 UI 렌더. 레이아웃 | ★ IME 조합, 실기기, 터널, 사람의 판단 |
| 사람 | 브라우저 수동 확인 | 위 전부 + 한글 IME + 휴대폰 + "이상하다" 는 감각 | — |

**★ 규칙 세 개**

1. **서버에 새 거부 경로를 만들면, 그 사유가 사람 화면에 도달하는지 ui-check 에 항목을 추가한다.**
   봇 테스트만 추가하면 R007과 같은 사고가 반복된다
2. **조건부로 나타나는 UI 를 만들면 ui-check 에 "실제로 나타나는가" 항목을 추가한다.**
   (예: 접속 종료자에게만 보이는 "내보내기")
3. **자동화할 수 없는 것은 목록으로 관리하고 매 라운드 사람에게 확인받는다.**
   그 목록이 [10-TESTING.md](10-TESTING.md) 7장이다

**★ 자동화할 수 없다고 판단한 것과 그 이유**

| 항목 | 왜 자동화하지 않는가 |
|------|-------------------|
| 한글 IME 조합 중 Enter | CDP 로 조합 이벤트를 만들 수는 있으나, 그것은 **실제 IME 의 동작이 아니라 우리가 만든 가짜 이벤트**다. 통과해도 실제 IME 에서의 동작을 보장하지 못한다. 통과가 보장하지 못하는 테스트는 있는 것이 더 위험하다 |
| 실기기 / LTE / 터널 | 헤드리스 브라우저는 뷰포트만 흉내낸다. 모바일 키보드가 화면을 가리는지, LTE 로 실제 접속되는지는 알 수 없다 |
| "0.1초로 승부가 갈리는" 체감 | 사람이 느끼는 지연은 측정값과 다르다 |
| 색상 구분(색약) | 사람이 봐야 한다 (Phase 7) |

★ **이 표가 "무엇을 사람에게 물어야 하는가" 의 근거다.** 목록에 없는 것을 사람에게
반복해서 확인시키지 않고, 목록에 있는 것을 자동화했다고 착각하지 않는다.

## D-027. 서버 에러를 화면에 띄우는 경로를 한 곳에 둔다

**시점**: R008 (게임 시작 버튼이 무반응이던 결함)

**증상**: 문제 수를 출제 가능 수보다 크게 두고 "게임 시작" 을 누르면 아무 일도 일어나지 않았다.

**★ 원인은 추정과 달랐다.**
지시에는 "클라이언트가 버튼을 disabled 로 만들었을 가능성이 높다" 고 되어 있었다.
실제로는 **버튼이 활성이었고, 클릭도 전달되었고, 서버도 `NOT_ENOUGH_QUESTIONS` 로 옳게 거부했다.**
클라이언트가 그 에러를 받아 상태에 저장하기까지 했다.

**★ 없던 것은 표시 경로 하나다.**
안내 문구를 화면마다 각자 그리고 있었고, `App.tsx` 에서
`{notice && <p className="notice">…}` 가 **방이 없는 화면의 return 안에만** 있었다.
로비 화면의 return 에는 없었다. 그래서 로비에서 발생한 모든 서버 에러가 보이지 않았다.

**결정**

1. **셸(shell)을 하나만 둔다.** `App` 이 화면을 무엇으로 그리든 `<Notice>` 는 항상 같은 자리에 렌더된다.
   화면별 `return` 을 없애고 `view` 를 계산해 한 곳에서 렌더한다.
   ★ 화면마다 return 을 두면 그중 하나에서 빼먹는다. 실제로 그렇게 됐다
2. **`detail` 을 함께 보여준다.** `message` 는 "출제할 수 있는 문제가 부족합니다." 뿐이고
   실제 숫자와 해야 할 일은 `detail` 에 있다
3. **조용히 반환하는 코드를 없앤다.** 빈 방 ID 로 "입장" 을 누르면 아무 반응이 없었다.
   ★ 사용자에게 "무반응" 은 고장과 구분되지 않는다
4. **핸들러 예외도 사람에게 알린다.** `guard.ts` 는 예외를 로그만 남기고 끝냈다.
   ★ `INTERNAL` 은 그때까지 "정의만 되어 있고 한 번도 전송되지 않는" 코드였다.
   예외 메시지 자체는 보내지 않는다(내부 값이 새어 나갈 수 있다). 이벤트 이름과 seq 만 보낸다
5. **`BAD_REQUEST` 에 어느 요청인지 담는다.** "요청 형식이 올바르지 않습니다" 만으로는
   사용자도 개발자도 원인을 찾을 수 없다. 받은 값은 담지 않는다(채팅 본문 등이 되돌아오면 안 된다)

**★ 에러 코드가 사람 화면에 도달하는지 전수 점검한 결과**

| 코드 | 사람이 어떻게 만나는가 | 수정 전 | 수정 후 |
|------|---------------------|--------|--------|
| `NOT_ENOUGH_QUESTIONS` | 문제 수 > 출제 가능 수에서 게임 시작 | ✗ 로비에서 안 보임 | ✅ 자동 검증 |
| `INVALID_STATE` | 게임 시작 연타 / 시작 후 설정 변경 시도 | ✗ | ✅ |
| `NOT_HOST` | 방장 이전 직후 옛 방장이 버튼을 누름 (경합) | ✗ | ✅ |
| `NOT_IN_ROOM` | 내보내진 직후 조작 (경합) | ✗ | ✅ |
| `UNAUTHENTICATED` | 세션이 만료된 탭에서 조작 | ✗ | ✅ |
| `INTERNAL` | 핸들러 예외 | ✗ **전송 자체를 안 했다** | ✅ 전송 + 표시 |
| `BAD_REQUEST` | 방 ID 를 64자 넘게 입력 | 방 없는 화면에서만 | ✅ 자동 검증 |
| `ROOM_NOT_FOUND` / `ROOM_CLOSED` | 잘못된·오래된 초대 링크 | 방 없는 화면에서만 | ✅ 자동 검증 |
| `ROOM_FULL` | 11번째 사람이 입장 | 방 없는 화면에서만 | ✅ |
| `ALREADY_HAS_ROOM` | 방을 가진 채 다른 방 입장 시도 | 방 없는 화면에서만 | ✅ |

**★ 화면에서 도달할 수 없는 경로가 하나 남아 있다 — 의도적이다**

설정값 범위 위반(`BAD_REQUEST`)은 클라이언트가 **서버로 보내지 않는다.**
숫자를 한 글자 고칠 때마다 에러를 왕복시키면 화면이 에러로 도배된다.
대신 같은 자리에 검증 메시지를 즉시 보여준다.

★ 이 경우 "클라이언트와 서버 판단이 어긋나면 조용히 막힌다" 는 위험이 남는데,
**두 쪽이 `shared/validateRoomSettings` 하나를 부르므로 어긋날 수 없다** (D-026).
즉 이 경로의 안전장치는 에러 전파가 아니라 **코드 공유**다.
★ 봇 테스트가 서버 쪽 거부를 따로 검증하고 있다(문제 수 0/201/소수점 등).

**HTTP(회원가입·로그인) 에러는 이 배너를 쓰지 않는다.**
그쪽은 요청-응답이고 폼 안에 인라인으로 보여주는 것이 맞다.
★ 규칙은 "**서버가 밀어 보내는(push) 에러는 배너 하나로만 표시한다**" 다.

## D-026. 설정값 검증을 shared 의 순수 함수 하나로 공유한다

**시점**: R007 (Phase 2)

문제 수(1~200) / 카운트다운(3~60) / 시작 방식의 범위 검증을 클라이언트와 서버가
각각 따로 쓰면 반드시 어긋난다. 어긋나면 두 방향의 버그가 생긴다.

- 화면은 통과시키는데 서버가 거부한다 → 사용자는 이유를 모른다
- 화면이 막는데 서버는 허용한다 → 봇이나 조작된 클라이언트가 규칙을 넘는다

`shared/src/settings.ts` 의 `validateRoomSettings()` 하나만 쓴다.
`server/src/socket/index.ts` 와 `client/src/GameSettings.tsx` 가 같은 함수를 부른다.

**★ 공유하는 것은 "형식과 범위" 뿐이다.** 판정 권한은 서버에만 있다(guide 44절).
출제 가능 문제 수 검증(Q-21)은 DB를 봐야 하므로 shared 에 두지 않았다. 서버 전용이다.

경험률 표기(`formatExperienceRate`)도 같은 이유로 shared 에 뒀다.
"1,234문제 중 153문제 (12.4%)" 는 규칙으로 확정된 형식이고(guide 6절),
★ 분모가 0일 때 0으로 나누지 않는 처리를 한 곳에만 두어야 한다.

## D-025. 카운트다운 만료 시점에 출제 가능 수가 부족해지면 로비로 되돌린다

**시점**: R007 (Phase 2)

**명세에 없는 경로다.** 전이표(04-PROTOCOL.md)의 T04 조건은 "활성 ≥ 1" 뿐이다.

그런데 Q-11이 **카운트다운 중 신규 입장을 허용**하므로 참가자 집합이 바뀔 수 있고,
Q-21의 출제 가능 수는 참가자 집합의 함수다("한 명 이상이 미경험인 문제 수").

- 사람이 **들어오면** 가능 수는 줄지 않는다. "전원 경험" 조건이 더 어려워지기 때문이다
- 사람이 **나가면** 가능 수가 줄어들 수 있다

즉 T01에서 통과한 검증이 T04 시점에는 거짓일 수 있다.

**결정**: T04 에서 출제 가능 수를 다시 조회하고, 부족하면 **로비로 되돌리고 이유를 알린다.**

근거: 대안은 (a) 그냥 시작한다 (b) 문제 수를 자동으로 줄인다 였다.
(a)는 Q-21("부족하면 시작을 거부하고 안내")을 정면으로 위반한다.
(b)는 방장이 설정한 값과 실제 진행되는 값이 조용히 달라지므로
"게임 규칙을 임의로 바꾸지 않는다" 는 원칙에 걸린다.
되돌리는 것이 규칙을 지키면서 사용자가 다음 행동을 고를 수 있는 유일한 선택지다.

## D-024. 문제 선정·경험률의 참가자 집합에 접속 종료자도 포함한다

**자체 판단이다.** 규칙 문서가 "참가자" 의 범위를 명시하지 않았다.

로비에서 접속이 끊긴 사람은 여전히 목록에 보이고 슬롯을 갖고 있으며,
방장이 명시적으로 내보내지 않으면 그 게임에 참가한다(Q-15).

그것은 Q-20(경험 기반 선정)의 취지에 정면으로 반한다.

★ 반대 방향의 부작용도 있다. 다시 돌아오지 않을 사람 때문에 출제 가능 수가
실제보다 크게 잡힐 수 있다. 그러나 그 경우 게임 중 조기 종료(Q-22)로 흡수되고,
Q-22는 이미 그 동작을 허용하고 있다. 반대 실수(경험한 문제를 다시 내는 것)는
흡수할 장치가 없다.

★ 활성 인원(activeCount) 과는 다른 축이다.
스킵 투표 분모와 PAUSED 판정은 끊김을 즉시 반영한다(Q-29). 이 결정은 그것과 무관하다.

## D-023. PAUSED 를 Phase 2에서 구현하지 않는다 — 카운트다운 만료를 보류하는 방식으로 대신한다

**시점**: R007 (Phase 2)

**확정 규칙**은 T20 "COUNTDOWN 중 활성 0명이면 즉시 PAUSED,
remainingMs = countdownEndsAt − now" 다 (Q-30 개정).

Phase 2에서 이것을 부분 구현하면 **막다른 길이 생긴다.**

| 필요한 것 | Phase 2에 있는가 |
|----------|-----------------|
| PAUSED 30분 초과 → GAME_RESULT (T14) | ✗ GAME_RESULT 가 없다 |
| 방장 `game.resume` → 원래 상태 복귀 (T23) | ✗ |
| ★ PAUSED 중 방 삭제 타이머 정지 | 이미 구현되어 있다 (tick) |

★ 세 번째가 결정적이다. PAUSED 에 들어가면 방 삭제 타이머가 멈추는데,
나오는 경로(resume / 30분 포기)가 없으면 **그 방이 프로세스 수명 동안 영구히 남는다.**
메모리 누수이자, 그 방을 만든 사람은 다시 방을 만들 수 없게 된다(1인 1방 제약).

**결정**: Phase 2에서는 T04 의 확정 조건("활성 ≥ 1")만 지켜 **만료를 보류**한다.
활성 0명이면 카운트다운이 만료되어도 게임을 시작하지 않고, 사람이 돌아오면 시작한다.
그 사이 방 삭제 타이머는 정상 동작한다(활성 0명 10분).

**최종 규칙과 다른 점 하나**: 남은 시간을 재계산하지 않는다.
30초 카운트다운 중 1초 만에 전원이 끊기고 5분 뒤에 돌아오면,
PAUSED 규칙에서는 29초가 남아야 하지만 지금은 즉시 시작된다.

★ `tick.ts` 의 `checkCountdown()` 안에 이 자리를 주석으로 표시했다.
Phase 5에서 그 자리를 PAUSED 전이로 교체한다.
★ 봇 시나리오 `empty` 가 지금의 동작을 단정하고 있으므로, Phase 5에서 규칙을 바꾸면
그 테스트가 실패해 교체를 빼먹을 수 없다.

## D-022. 짧은 라벨의 줄바꿈을 개별 요소가 아니라 규칙으로 막는다

**시점**: R007 (건우가 "전송 버튼 글자가 세로로 쪼개진다" 를 지적)

**증상**: 채팅 전송 버튼의 "전송" 이 "전" / "송" 두 줄로 나왔다.

**원인 (헤드리스 Chrome 으로 실측)**

버튼이 flex 행의 항목이고, flex 항목의 기본값은 `flex-shrink: 1` / `min-width: auto` 다.
같은 행의 입력창이 `width: 100%` 여서 남는 폭이 없으므로 버튼이
min-content(한 글자 폭)까지 눌렸고, `white-space` 기본값이 `normal` 이라
한글 두 글자 사이에서 줄이 바뀌었다.

★ 실측값: 720px 화면에서도 버튼 폭이 56.9px(내용 폭 약 27px)로 눌려 있었다.
좁은 화면만의 문제가 아니었다.

★ **"복사" 버튼만 멀쩡했던 이유**: 그 하나에만 `white-space: nowrap` 이 붙어 있었다.
즉 규칙이 아니라 우연이었다.

**결정 — 개별 수정으로 끝내지 않는다**

1. 라벨성 요소 전체에 `white-space: nowrap` 을 건다 (`button`, `.badge`, `.seat`, `.preset`)
2. 모든 버튼에 `flex: 0 0 auto` 를 건다. 늘어나야 하는 `.tab` 은 클래스가 덮어쓴다
3. "입력 + 버튼 한 줄" 배치를 `.field-row` 하나로 통일한다.
   `.invite-row` / `.chat-input` 처럼 전용 클래스를 여러 개 두면 그중 하나에
   규칙을 빼먹는 일이 반복된다. 실제로 그렇게 해서 이 버그가 생겼다
4. 제목(`h1`)과 본문은 규칙에서 제외한다. 방 제목은 30자까지 허용되므로
   좁은 화면에서 여러 줄이 되는 것이 정상이고, 줄바꿈을 막으면 화면을 넘친다

**부수 발견**: 같은 원인으로 "방 나가기" 버튼도 390px 이하에서 두 줄로 쪼개져 있었다.
지적받은 곳만 고쳤다면 그것은 그대로 남았을 것이다.

**대가**: 아주 좁은 화면에서 긴 라벨이 들어오면 줄바꿈 대신 넘친다.
버튼 라벨은 설계상 2~6자이고, 각 라벨을 320px 에서 실측해 확인한다.

## D-021. 실행 확인(smoke)을 게이트에 넣는다 — typecheck·build 는 실행을 보장하지 않는다

**시점**: R006 (npm run dev 실행 불가 사고를 고치며)

**무엇이 드러났는가**

R005에서 다음을 모두 통과라고 보고했다.

- `npm run typecheck` 통과
- `npm run build` 통과 (shared / server / client)
- 봇 테스트 21항목 통과

**그런데 `npm run dev` 가 아예 실행되지 않았다.**

세 검증이 이 문제를 못 잡은 이유는 각각 다르다.

| 검증 | 왜 못 잡았는가 |
|------|--------------|
| typecheck | `tsc` 는 `./config.js` 를 **컴파일 후 파일**로 해석한다. 소스 시점에 그 파일이 없어도 정상이다. TS 관점에서 이 코드는 완전히 옳다 |
| build | 같은 이유. 컴파일이 성공하고 `dist/config.js` 가 실제로 만들어진다 |
| 봇 테스트 | ★ 서버를 `node server/dist/index.js` 로 띄웠다. **컴파일 산출물이라 정상 동작했다.** `npm run dev` 는 한 번도 실행하지 않았다 |

**★ 핵심은 세 번째다.** 테스트가 사람이 쓰는 실행 경로와 다른 경로를 썼다.
그래서 "테스트 전부 통과"와 "실행 불가"가 동시에 성립할 수 있었다.

**결정**

1. `npm run smoke` 를 만든다 — 빌드 → 기동 → `/healthz` 200 → 클라이언트 서빙 →
   Socket.IO 핸드셰이크 → 프로세스 종료 → 포트 해제까지 검증한다
2. `npm run verify` = `typecheck` + `test` + `smoke` 를 라운드 종료 게이트로 삼는다
3. `npm run bot` 이 서버가 없으면 **사람과 같은 경로**로 직접 띄운다.
   테스트가 다른 경로를 쓰면 이 사고가 반복된다

**smoke 를 처음 돌렸을 때 이 스크립트 자체의 오탐도 하나 잡혔다.**
종료 판정을 `exit` 콜백의 `code` 만으로 하고 있었는데,
Windows 에서 `child.kill()` 은 즉시 종료(TerminateProcess)라 `code=null, signal='SIGTERM'` 이 온다.
`code` 만 보면 "신호로 종료됨"과 "아직 안 죽음"이 둘 다 `null` 이라 구분되지 않았다.
→ `signal` 을 함께 추적하고, 판정 기준을 "프로세스가 사라지고 포트가 해제되는가" 로 바꿨다.

★ 부수 확인: Windows 에서 `child.kill()` 로는 자식의 SIGTERM 핸들러가 실행되지 않는다(실측).
사람이 터미널에서 Ctrl+C 를 누르는 경로는 이 스크립트로 재현할 수 없어 확인하지 못했다(확인 필요).
포트 해제와 프로세스 소멸은 어느 경로든 동일하므로 그것만 검증한다.

## D-020. 개발 서버도 컴파일 산출물을 실행한다 — 실행 경로를 하나로 유지

**시점**: R006. `npm run dev` 가 `ERR_MODULE_NOT_FOUND` 로 실행되지 않는 사고를 고치며.

**증상**

```
Error [ERR_MODULE_NOT_FOUND]: Cannot find module 'server\src\config.js'
imported from server\src\index.ts
```

**원인** — 두 규칙이 각각 옳고 조합이 불가능했다

| | 내용 |
|---|---|
| tsconfig | `module`/`moduleResolution` = **NodeNext**. 상대 import 에 **컴파일 결과물의 확장자(`.js`)** 를 쓰도록 요구한다. 그래서 소스는 `'./config.js'` 다 (저장소 전체 57건이 이렇게 일관되어 있었다) |
| 실행기 | 이전 dev 스크립트는 `node --experimental-strip-types --watch src/index.ts` 였다. **Node 의 타입 스트리핑은 import 문자열을 재작성하지 않는다.** `'./config.js'` 를 문자 그대로 찾고, 거기에는 `config.ts` 만 있으므로 실패한다 |

실측으로 확인했다. `--experimental-strip-types` 로 `'./dep.js'` import 는 실패하고
`'./dep.ts'` 는 성공한다. Node 22.18 에는 `.js` → `.ts` 재매핑이 없다.

**검토한 선택지**

| 안 | 내용 | 판단 |
|----|------|------|
| A | dev 도 컴파일 산출물(`server/dist/index.js`)을 실행한다 | **채택** |
| B | `tsx` 같은 실행기로 바꾼다 | 의존성이 늘고, **dev 만 소스를 실행하는 divergence 가 그대로 남는다** |
| C | 모든 상대 import 를 `.ts` 로 바꾸고 TS 5.7 의 `rewriteRelativeImportExtensions` 로 emit 시 재작성 | 의존성은 안 늘지만 57건을 고쳐야 하고, `.ts` 확장자 import 는 읽는 사람에게 낯설다. 역시 dev 만 소스를 실행한다 |

**A를 택한 이유**

1. ★ **근본 원인이 "dev 만 다른 코드 경로를 쓴 것"이다.**
   `npm start` 와 테스트는 컴파일 산출물을 실행했고 dev 만 소스를 직접 실행했다.
   그래서 아무도 그 경로를 검증하지 않았다.
   B와 C는 그 경로를 **고칠** 뿐이고, A는 그 경로를 **없앤다.**
   이제 `npm run dev` / `npm start` / `smoke` / `bot` 이 전부 같은 파일을 실행한다.
2. **소스를 한 줄도 고치지 않았다.** 57건의 `.js` 확장자는 NodeNext 기준으로 이미 옳다.
3. **의존성을 늘리지 않았다.**
4. 서버는 어차피 `@quiz/shared` 를 `shared/dist` 에서 가져오므로 **dev 에도 빌드 단계가
   이미 필요했다.** server 까지 함께 빌드하는 비용은 사실상 없다.

**구현**: `scripts/dev.mjs` — 한 번 빌드 → `tsc -b --watch` + `node --watch server/dist/index.js`.

**함께 고친 것**

- ★ `server/package.json` 의 깨진 `dev` 스크립트를 **제거했다.**
  남겨 두면 같은 함정을 다시 밟는다. 실행 진입점은 루트 `npm run dev` 하나다
- `dist` 가 없는데 `tsconfig.tsbuildinfo` 가 남아 있으면 `tsc` 가 "최신"이라 판단해
  아무것도 만들지 않는다. dev 와 smoke 가 산출물 부재를 감지해 `--force` 로 빌드한다.
  `npm run build:force` 도 추가했다

**클라이언트는 문제가 없었다.** Vite 는 `'./api.js'` 를 `/src/api.ts` 로 정상 해석한다(실측).
그래서 `vite build` 가 성공했고 문제가 서버 dev 경로에만 있었다.

## D-019. 로그인 실패 메시지는 구분하지 않되, 회원가입은 구분한다

**시점**: Phase 1 (R005)

**결정**

- **회원가입**: 아이디 중복인지 닉네임 중복인지 알려준다
- **로그인**: "아이디 또는 비밀번호가 올바르지 않습니다" 하나로 통일한다

**왜 비대칭인가**

회원가입에서 구분하지 않으면 사용자가 무엇을 고쳐야 할지 알 수 없어 **가입 자체가 불가능해진다.**
아이디를 바꿔야 하는지 닉네임을 바꿔야 하는지 모르는 채로 시행착오를 반복하게 된다.
그래서 여기서는 구분한다. "그 아이디가 존재한다"는 정보가 새지만, 친구들끼리 쓰는 서비스에서
그것을 감출 실익이 없다.

로그인에서 구분하지 않는 이유는 보안 관행 때문이 아니다. 회원가입에서 이미 알려주므로
그 논리만으로는 일관성이 없다. **실제 이유는 자동화 난이도의 차이다.**
이 서비스는 아이디가 짧고 비밀번호가 4자여서(Q-04), 로그인 응답으로 유효한 아이디 목록을
자동 수집할 수 있게 만들면 대입 공격의 표적 범위가 그대로 좁혀진다.
회원가입은 사람이 하나씩 하는 반면 로그인은 자동화하기 쉽다.

## D-017. 세션 쿠키의 Secure 속성을 요청 프로토콜에 따라 분기한다

**시점**: Phase 1 (R005)

**문제**: 이 프로젝트는 두 방식으로 접속된다.

- 개발: `http://localhost:5173` 또는 `http://localhost:3000`
- 플레이: `https://xxxx.trycloudflare.com` (터널)

`Secure` 쿠키는 http 에서 저장되지 않는다. 고정으로 붙이면 **localhost 개발 중 로그인이 아예 안 된다.**
반대로 터널(https)에서는 붙이는 것이 옳다.

**결정**: 요청이 https 로 들어왔는지 보고 결정한다. 고정값을 쓰지 않는다.
터널은 프록시이므로 `x-forwarded-proto` 를 함께 본다.

`SameSite` 는 **Lax** 로 고정한다. 오리진이 하나이므로(서버가 클라이언트를 직접 서빙)
`None` 이 필요 없고, `None` 은 서드파티 쿠키로 분류되어 모바일 사파리에서 차단될 수 있다.
`Lax` 면 초대 링크 클릭(top-level navigation)에도 쿠키가 붙는다.

**부수 결정**: `SESSION_SECRET` 을 세션 토큰 해시의 HMAC 키로 쓴다.
토큰이 256비트 랜덤이라 단순 해시로도 역산은 불가능하지만, DB만 유출되고 시크릿은 유출되지
않은 경우에 한 겹 더 막아 준다. 비용이 없고, 이것이 `SESSION_SECRET` 의 실제 용도가 된다.

## D-015. cloudflared 네트워크 단절 시 터널 URL은 유지된다 (Q-53 확정)

**시점**: Phase 1 (R005). **실측 검증 완료.**

**검증 방식**: 관리자 권한으로 방화벽 아웃바운드 규칙을 만들어 `cloudflared.exe` 의 네트워크만
100초간 차단한 뒤 규칙을 제거했다.
★ PC 전체 네트워크를 끊지 않았다. 작업 환경을 해치지 않기 위함이다.
재현 스크립트: `scripts/verify-tunnel-resilience.ps1`

**결과**

| 확인 항목 | 결과 |
|----------|------|
| 차단 중 cloudflared 프로세스 | 살아 있음 |
| 차단 중 터널 URL | 502 |
| **복구 후 같은 URL** | **200 — 유지되었다** |
| WebSocket 자동 재연결 | 성공 (`transport=websocket`) |
| 서버 프로세스 `bootedAt` | 동일 (무영향) |
| 로그의 `Requesting new quick Tunnel` | **1회만** (프로세스 시작 시) |
| 로그에 등장한 고유 URL | **1개** |
| 차단 중 로그 | `Retrying connection` 반복 → `Registered tunnel connection` 재등록 |

**해석**: URL은 **프로세스 시작 시 1회 발급**되고 그 뒤에 개별 엣지 연결이 등록된다.
즉 호스트명은 "터널(프로세스)"에 속하고 "개별 연결"에 속하지 않는다.
따라서 연결만 끊겼다 재등록되는 동안 URL이 유지된다.

**★ 부수 발견: 재연결 백오프가 지수적으로 늘어난다.**
`8s → 16s → 32s → 1m4s` 로 증가했고, 차단이 100초였는데 복구 후 재등록은
차단 해제 시점으로부터 약 30초 뒤에 일어났다.
→ **단절이 길수록 복구 후 재연결까지 최대 1분 이상 더 기다려야 할 수 있다.**
운영 문서에 이 사실을 넣었다.

**한계 (과장하지 않기 위해 명시)**: 방화벽 차단은 Wi-Fi를 실제로 끄는 것과 완전히 같지 않다.
인터페이스가 살아 있고 라우팅 테이블도 그대로다. OS 네트워크 스택 상태가 다르다.
여기서 URL이 유지되었으므로 **실제 상황에서도 유지될 가능성이 높다** 는 정도로 해석한다.

**운영 절차에 반영**: [11-DEPLOY.md](11-DEPLOY.md) 3장의 복구 절차에서
"URL 유지" 를 주 경로로, "URL 변경" 을 예외로 내렸다.

## D-014. 인프라를 클라우드에서 로컬 PC + 터널로 전면 변경

## D-013. PAUSED(일시정지) 상태 도입 — guide 9절 규칙 변경

**시점**: Phase 0 (R004). 건우 명시적 승인.

**변경 전**: 활성 플레이어가 0명이 되면 30초 유예 후 게임을 종료한다.

**변경 후**: 활성 0명이 되는 **즉시** `PAUSED` 로 전이한다. 타이머를 남은 시간으로 멈추고,
**방장이 눌러야 재개한다.** 30분이 지나면 그때 게임을 종료한다(`abandoned`).

**이유** — 이것이 이 프로젝트의 인프라와 직결된 결정이다.

D-014로 서버가 건우 PC가 되고 매번 새 터널 URL을 뿌리게 되면서,
**터널 재시작이 예외가 아니라 일상**이 되었다. 또 서버 PC의 네트워크가 드물게 1~2분 끊긴다.

**핵심은 서버 PC의 네트워크 단절이 서버 프로세스가 죽는 것이 아니라는 점이다.**
통로만 끊기고 메모리의 방과 게임은 그대로 살아 있다. 따라서 이어하기가 원리적으로 가능하다.
이것이 PC를 껐다 켜는 것과 완전히 다른 상황이다.

기존 규칙으로는 그때마다 판이 날아갔고, 더 나쁜 것은 **타이머가 계속 흘러 아무도 보지 못한 문제가
타임아웃 처리되며 경험 기록으로 소모되는 것**이었다. 경험 기록은 영구 자산이라 되돌릴 수 없다.

**설계상 중요한 세부**

- **자동 재개하지 않는다.** 친구 한 명이 먼저 접속한 순간 게임이 돌아가면,
  나머지가 새 URL을 입력하는 동안 문제가 소모된다
- 타이머는 절대 시각이 아니라 **남은 시간(remainingMs)** 으로 보존한다
- 재개 시 **epoch를 증가시키지 않는다.** 같은 문제를 이어서 하기 때문이다
- **방 삭제 타이머와 방장 이전 타이머도 PAUSED 중에는 정지한다.**
  이것을 빼먹으면 10분 뒤 방이 삭제되어 일시정지가 무의미해진다
- **경험 기록은 자동으로 충족된다.** PAUSED 중에는 정답 공개가 일어나지 않고,
  경험 기준이 "정답 공개 순간 그 자리에 있던 사람"(D-010)이므로 별도 예외 처리가 필요 없다

**검증**: cloudflared 프로세스를 강제 종료해도 서버의 `bootedAt` 이 그대로였다.
터널이 죽어도 서버 프로세스와 메모리는 전혀 영향을 받지 않는다는 실증이다. (R004 1장)

2. **경험자가 보낸 채팅에 정답이 포함되면 서버가 마스킹한다**

**이유**: guide 28절(경험자 채팅 허용)과 15절(오답도 전부 공개)의 조합에 구조적 유출 경로가 있었다.
정답을 아는 사람이 채팅에 정답을 그대로 치면, 그 사람은 점수를 못 받지만
**다른 사람이 그것을 보고 그대로 따라 쳐서 점수를 가져간다.**
경험률이 높은 사람이 많아질수록 확실하게 발생한다.

마스킹으로 유출을 차단하되, **마스킹이 왜 걸렸는지 모두가 이해할 수 있도록** 경험자를 공개하는
방향으로 규칙을 바꿨다. 가려진 이유를 알 수 없으면 더 혼란스럽다.

**설계상 중요한 세부**

- **마스크 길이는 고정이다.** `*****` 처럼 길이에 비례하는 마스크는 금지한다.
  정답 길이는 힌트보다 강한 정보이며 문제 시작 직후부터 노출되면 게임이 망가진다
- 사용자가 입력할 수 없는 **센티널 문자**(사설 사용 영역)로 치환한다.
  이모지나 특수기호를 쓰면 사용자가 직접 입력했을 때 구분되지 않는다
- **정규화 후 길이 2 이하인 정답은 메시지 전체가 정답과 같을 때만 마스킹한다.**
  그러지 않으면 정답 "달" 때문에 "달라졌네"가 마스킹되어 경험자가 정상적인 대화를 할 수 없게 되고,
  guide 28절이 보장한 "경험자도 채팅은 자유롭게 가능"이 무너진다
- **마스킹은 서버에서 한다.** 클라이언트에 원문을 보내고 CSS로 가리면 개발자 도구로 즉시 뚫린다

**알려진 한계**: `고무-줄` 처럼 기호를 끼우거나 `ㄱㅁㅈ` 처럼 초성으로 쓰면 막을 수 없다.
완벽한 차단은 fuzzy matching을 요구하는데 그것은 정답 판정 규칙(D-006)이 금지한 기술이고,
판정과 마스킹에 서로 다른 매칭 기준을 쓰면 규칙이 혼란스러워진다.
친구들끼리 하는 게임이므로 "무심코 흘리는 것"을 막는 수준으로 설계했다.

## D-010. 경험의 정의 변경 — guide 27절 개정

**시점**: R002 (Q-23/Q-24) → R003 (재검토) → **R004에서 최종 확정**

**변경 전** (guide 27절): "실제로 해당 문제를 접한 시점" 기준.

**최종 규칙**: **정답이 공개되는 순간 그 자리에 있었던 사람 전원**

- 정답자 발생 / 시간 종료 / 스킵 — 세 경로 모두 정답 공개이며 기록을 남긴다
- **`QUESTION_RESOLVED` 구간(5초)에 입장한 사람도 기록을 남긴다**
- **마지막 문제도 기록을 남긴다** (5초 대기만 생략한다)
- 강제 종료 / `abandoned` / `server_restart` 에서는 정답을 공개하지 않으므로 기록이 없다
- 문제 진행 중 연결이 끊긴 사람은 기록하지 않는다

**변경 이유 (1차, R002)**: 원래 기준으로는 잠깐 끊긴 사이 지나간 문제가 영구히 "경험함"으로
기록되어, 정답을 보지도 못한 문제에서 나중에 정답 판정이 제외되는 손해가 발생한다.

**변경 이유 (2차, R004)** — ★ R003의 판단을 뒤집은 부분이다.

R003은 "RESOLVED 구간 입장자에게 경험 기록을 남기지 않는 것이 사용자에게 유리하다"고 판단했다.
**이 판단은 방향이 반대였다.**

그 사람은 정답을 봤다. 기록을 남기지 않으면 다음 게임에서 그 문제가 나왔을 때 즉시 맞힌다.
**다른 참가자가 손도 쓸 수 없게 되는데, 그것이 바로 경험 시스템이 막으려던 상황이다.**
경험 시스템은 "그 사람을 배려하는 장치"가 아니라 "게임의 공정성을 지키는 장치"다.

**효과**: 기준이 하나로 단순해졌다. "정답 공개 순간 그 자리에 있었는가" 하나만 보면 된다.
그리고 PAUSED(D-013)에서도 별도 예외 없이 자동으로 옳게 동작한다.

## D-008. 방은 DB에, 참가자와 게임 상태는 메모리에

**시점**: R003

**결정**: `rooms` 레코드만 DB에 두고, 참가자 목록과 진행 중 게임 상태는 서버 메모리에만 둔다.
guide 48절이 이 조합을 명시적으로 허용한다.

**방을 DB에 두는 이유**

1. guide 49절이 "존재하지 않는 방"과 "이미 종료된 방"을 다르게 안내하라고 요구한다.
   메모리만 쓰면 서버 재시작 후 모든 링크가 "존재하지 않는 방"이 된다
2. "1인당 동시 보유 방 1개"를 부분 UNIQUE 인덱스로 DB가 강제할 수 있다
3. `games` 가 `room_id` 를 참조해야 게임 이력이 방과 연결된다
4. 쓰기 빈도가 극히 낮다 (생성 시 1회, 삭제 시 1회)

**참가자·게임 상태를 메모리에만 두는 이유**

1. 참가자 접속 상태는 초 단위로 바뀐다. DB에 반영하면 DB를 계속 깨워 둔다
2. 서버가 재시작되면 소켓이 전부 끊기므로 참가자 목록을 복원해도 의미가 없다

**"게임 상태 스냅샷" 요구의 해석**: 지키려는 것은 "프로세스가 죽어도 친구들의 점수와
경험 기록이 날아가지 않는 것"이다. 이는 방/참가자 상태를 통째로 저장해서가 아니라
**`answer_events` 와 `question_experiences` 를 문제 단위로 즉시 기록해서** 달성한다.
즉 "되돌릴 수 없는 사실만 즉시 기록"한다.

**부수 효과**: 프로세스 종료 시 `closed_at` 이 NULL인 방이 DB에 남아 UNIQUE 제약에 걸린다.
→ 부팅 시 정리 절차(D-007)가 필요해졌다.

## D-007. 서버 부팅 시 정리 절차 도입

**시점**: R004 (설계 결함 발견 후 수정)

**문제**: D-008의 부분 UNIQUE 인덱스와 "방 삭제는 메모리에서" 라는 설계가 만나

**처리**: 서버 부팅 시 (1) `ended_at IS NULL` 인 게임을 `server_restart` 로 종료하고,

**★ `question_experiences` 는 삭제하지 않는다.** guide 25절이 강하게 금지하고,
그 문제들은 실제로 정답이 공개되어 사람들이 화면에서 본 것이므로 기록이 옳다.

**검증**: 잔여 방 1개와 진행 중 게임 1개를 만들어 두고 서버를 재기동하자
방 0개 / 게임 0개(`end_reason='server_restart'`)가 되었고,
제약에 걸려 실패하던 방 생성이 성공했다. (R004 3장)

## D-006. 정답 판정 정규화 규칙 확정

**시점**: R002 (Q-16) + R002 (Q-36)

**결정**: NFC → 제로폭 제거 → 전각/반각 → 아포스트로피·하이픈 통일 → 공백 제거 → 소문자화.

**왜 NFC이고 NFKC가 아닌가**: NFKC는 `①` → `1`, `㈜` → `(주)`, `Ⅳ` → `IV` 처럼
**의미를 바꾸는 변환**까지 수행한다. guide 16절이 "특수문자·기호는 무시하지 않는다"고 했으므로
NFKC는 규칙을 넘어선다. NFC + 명시적 전각 변환만 한다.

**왜 NFC가 반드시 필요한가**: macOS/iOS 사파리는 한글을 NFD(자모 분리)로 보내는 경우가 있다.
NFC가 없으면 **아이폰 사용자가 눈에 똑같은 답을 쳐도 오답 처리된다.**
게임을 망치는 수준의 버그이며, 눈으로는 원인을 알 수 없다.

**왜 제로폭 문자를 따로 지우는가**: JavaScript의 `\s` 에 포함되지 않아 공백 제거로 걸러지지 않는다.
복사·붙여넣기로 흔히 섞여 들어오며 눈에 보이지 않아 디버깅이 매우 어렵다.

**왜 아포스트로피·하이픈을 통일하는가 (Q-36)**: 모바일 키보드가 `'` 를 자동으로 `’`(U+2019)로 바꾼다.
이것은 "같은 글자의 다른 표현"이지 "다른 글자"가 아니므로,
`A+B ≠ AB` 라는 규칙의 취지를 위반하지 않는다.

**바꿀 때 주의**: `NORMALIZE_VERSION` 이 바뀌면 `question_answers.answer_norm` 전체를
재계산해야 한다. **서버의 판정과 파이프라인의 저장이 반드시 같은 함수를 써야 한다.**
다르면 DB 값과 런타임 판정이 어긋나 정답이 조용히 오답 처리된다.

## D-005. 영문 힌트는 단어마다 첫 글자를 노출한다

**시점**: R004 (Q-38). ★ R002의 권장안을 뒤집었다.

**R002 권장안 (채택 안 됨)**: 전체에서 첫 글자 하나만. `New York` → `N______`

**최종 결정**: **단어마다 첫 글자, 공백 유지.** `New York` → `N__ Y___`

**이유**: 한글은 음절마다 초성을 준다(`훈민정음` → `ㅎㅁㅈㅇ`, 정보 4개).
영문만 전체에서 한 글자를 주면 **정보량이 크게 비대칭이 되어 영문 정답만 불리해진다.**
"같은 규칙의 일관된 적용"이 아니라 한쪽만 불리해지는 것이다.
단어별 첫 글자가 한글 규칙의 정보량에 더 가깝다.

**부수 결정**: 이 결정에 따라 **영문 정답은 공백을 제거하지 않고 단어 경계를 유지한다.**
한글 정답은 guide 11절대로 공백을 제거한다. 한글이 섞인 혼합 정답은 한글 규칙을 따른다.

## D-004. 짧은 정답의 힌트를 만들지 않는다 + 최종 방어선

## D-003. 스킵 임계값에 하한 2표를 둔다

**시점**: R002 (Q-28)

**문제**: guide 22절의 "활성 플레이어의 80%, 전원 동의가 되면 한 명 적은 수" 규칙을
소인원에 그대로 적용하면 **2명일 때 1표, 1명일 때 0표로 스킵된다.**
guide 22절 자신이 "0표만으로 스킵되는 등의 문제가 발생하지 않도록" 별도 처리를 요구했다.

**결정**: 하한 2표. 활성 1명이면 스킵 투표 자체가 불가능하다(방장 강제 스킵만 가능).
결과: 2명=2 / 3명=2 / 4명=3 / 5명=4 / 6명=5 / 7명=6 / 8명=7 / 9명=8 / 10명=8

**분모에 경험자를 포함하는 이유**: 경험자를 분모에서 빼면 **투표 수로 경험자 수가 역산되어
정보가 샌다.** 그래서 해당 문제의 경험 여부와 무관하게 전체 활성 플레이어를 분모로 쓴다.
(D-011로 경험자가 공개되었으므로 이 우려는 약해졌지만, 규칙을 단순하게 유지하기 위해 그대로 둔다.)

## D-002. epoch(문제 세대 번호) 도입

**시점**: R003

**문제**: guide 20절이 "결과 화면에서 입력한 메시지가 다음 문제의 정답과 우연히 일치해도
정답 처리하면 안 된다"고 명시적으로 금지했다. **그런데 상태 검사만으로는 이를 막을 수 없다.**

`host.forceEnd` 에는 담지 않는다(게임 전체 액션이므로 특정 문제에 종속되지 않는다).

**PAUSED와의 관계 (D-013)**: 재개 시 epoch를 **증가시키지 않는다.** 같은 문제를 이어서 하기 때문이다.

## D-001. 판정 블록에 await를 넣지 않는다

**시점**: R001 → R003에서 명문화

**결정**: 정답 판정과 상태 전환은 하나의 동기 실행 블록에서 수행하고,
그 블록 안에 `await` 를 절대 넣지 않는다. 판정에 필요한 데이터는 문제 시작 시점에
메모리로 미리 로드한다. DB 기록은 상태 전환이 끝난 뒤 비동기로 한다.

**이유**: Node의 단일 스레드 이벤트 루프에서는 핸들러가 `await` 없이 끝까지 실행되는 동안
다른 이벤트가 끼어들 수 없다. 이 성질 덕분에 별도의 락 없이
"한 문제의 정답자는 정확히 한 명"(guide 18절)이 보장된다.

**★ 이 규칙이 이 프로젝트에서 가장 깨지기 쉽다.** 누군가 판정 블록에 `await` 한 줄을 추가하면

- 에러가 나지 않는다
- 평소에는 정상 동작한다
- 동시 입력이 정확히 겹치는 순간에만 두 명이 정답자가 된다
- 재현이 매우 어렵다

**대응**: 판정 함수 이름에 규칙을 박아 넣고(`resolveQuestionSync`), 함수 상단에 이유를 주석으로 남기고,
동시 정답 100회 반복 테스트를 CI에 넣는다.
