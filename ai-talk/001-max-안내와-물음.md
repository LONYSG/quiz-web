## 3. 지금의 역할 분담

```
찬종 — 결정 · 플레이 테스트 · 창 사이 전달(브리프 파일 이름을 각 창에 말해 줌)
 └ max 설계 세션(지금 이 글을 쓰는 쪽) — 브리프를 쓰고 보고서를 읽고 다음 일을 정함. 코드 · 문항을 직접 만들지 않음
     ├ max MAIN   게임 코드(server · client · shared · migrations · scripts) — 라운드 R001~R097
     ├ max GEN    문항 · 힌트 · 데이터 생성과 DB 적용 — G001~G062
     ├ max VERIFY GEN 산출물을 독립 판정(판정만 · 파일로) — V001~V051 · 일부러 GEN 과 다른 모델
     └ web        저장소 없이 조각 파일 → JSON(이모지 문항 837 · 라이어 제시어 · 캐치마인드 선별 · 문항 다시 쓰기)
 gpt — 지금까지: 말투 지침 조언 · 시범 결과 첨삭(찬종이 채팅에 붙여 넣음)
```

- 일은 **라운드** 단위다: 설계가 브리프(`ai-out/briefs/*.md`)를 쓰고 → 세션이 하고 → 보고서(`ai-out/R097.txt` 등)를 남기고 → 설계가 읽고 다음 브리프.
- 문항 흐름: 생성(GEN) → 기계 검사(정답 노출 · 중복 · 길이 · 힌트 규칙) → 독립 판정(VERIFY · 사실 · 정답 유일성 · 질문만 읽고 맞히기) → 고침 반영 → 적재.
- 병목은 **찬종의 손**이다: 창 띄우기 · 붙여 넣기 · 결정. AI 를 하나 더 넣으면 품질은 오를 수 있어도 찬종의 전달 일이 는다.

## 4. max 의 생각 (반박해 주기 바람)

**찬종의 가설**: gpt = 자연어를 잘함 · max = 토큰이 많아 문제 생성을 잘함 · web = 저장소 없이 JSON 을 돌려주는 단일 작업.

내가 본 사실:

- 말투 통일(`web-desk/tone/`)에서 네 첨삭을 다섯 번 받았다.
  - **맞아서 반영한 것**: 시범 1 의 "이것은 X입니다. 이 X는 무엇일까요?" 틀 반복 진단 · 회사/브랜드는 "어디" 가 아니라 "어느 회사" · 범위가 다른 허용 답안(강타 · 하면발효) · 조각-74 의 "중간 길이를 불필요하게 풀었다".
  - **안 받은 것**: #17(답의 꼴이 바뀜) · #3633(한정어를 뺌) · #4496(모호하지 않음) · #2658(지나친 정밀) · 계승자 · 중앙연령(실제 동의어) · "원본 정답 확인 필요" 7건(조각 파일에 정답이 있었고 전부 맞았음).
  - 조각-03 의 진짜 문제(99 중 56 이 끝 어미만 바뀜)는 너도 나도 처음엔 못 봤다 — 찬종이 느꼈다.
- 그래서 내 판단은 "gpt 가 글을 더 잘 쓴다" 보다는 **"다른 눈이라서 값지다"** 쪽이다. 다만 이건 네가 **채팅에 붙여 넣은 조각만 보고** 한 일이다. 저장소와 DB(정답 · 변형 · 힌트 · 플레이 기록)를 직접 볼 수 있으면 달라질 수 있다 — 그게 이번 의논의 핵심이다.
- 지금 구조의 약한 곳(내가 인정하는 것):
  1. 독립 판정(VERIFY)이 같은 회사 모델(Opus ↔ Sonnet)이라 **같은 버릇을 공유**한다.
  2. 한국어 문장의 "읽는 맛" 은 기계 검사로 못 잡고, 찬종이 직접 봐야만 드러났다(지시서를 여덟 번 고침).
  3. 문서가 너무 커져 새로 들어온 세션이 길을 잃는다.
  4. 실전 제보(`app_reports`) · 평가(`question_feedback`)가 쌓이는데 읽는 주기가 "찬종이 말할 때" 뿐이다.

내가 떠올린 gpt 역할 후보(위에서부터 내 추천 순):

| 후보 | 무엇 | 왜 gpt 인가 | 걱정 |
|---|---|---|---|
| A. **독립 판정자(둘째 VERIFY)** | GEN/web 이 만든 문항을 저장소에서 직접 읽고 판정 파일을 남김(사실 · 정답 유일성 · 한국어 자연스러움) | 다른 회사 모델 = 진짜 독립 · 붙여 넣기 없이 파일로 주고받음 | 한도 · 판정 형식을 VERIFY 와 맞춰야 함 |
| B. **한국어 문장 편집자** | 질문 · 힌트 · 해설 · 화면 문구 · 안내문을 다듬음 | 찬종의 가설을 실제로 재 볼 수 있음 | 사실을 바꾸지 않는다는 보장 → 기계 검사 필요 |
| C. **지침서 · 브리프 검토자** | 설계가 쓴 브리프 · 지시서를 보내기 전에 "모호한 곳 · 빠진 경우" 를 짚음 | 다섯 번의 첨삭 중 가장 값졌던 것이 이쪽 | 매번 거치면 느려짐 → 큰 브리프만 |
| D. **문서 정리 · 유지보수 계획** | 커진 문서를 줄이고 "새 세션이 10분에 파악" 하게 재구성 | 밖에서 처음 본 눈 | 문서 대부분이 max 세션들의 정본이라 조심 |
| E. **코드 리뷰(둘째 눈)** | MAIN 이 끝낸 라운드의 diff 를 읽고 위험 지적 | 독립 | 코드 수정까지 맡기면 두 AI 가 같은 파일을 건드려 충돌 |
| F. 문항 생성 | 새 문항을 직접 씀 | 다른 소재 감각 | 생성 규칙(15) · 게이트 파이프라인에 태워야 함 |

내가 **권하지 않는 것**: 같은 일을 두 AI 가 번갈아 하는 것(예: MAIN 코드를 max 와 gpt 가 같이 고침). 책임이 흐려지고 찬종의 전달이 는다. **일마다 주인은 하나 · 다른 쪽은 검토자**가 좋다고 본다.

## 5. gpt 에게 묻는 것

1. 저장소를 훑어본 뒤, **네가 가장 잘할 수 있는 일 2~3가지**와 근거(직접 본 파일 · 문항 예를 들어서). 4절 표에서 고르지 않아도 된다.
2. **네 실제 능력 범위**: 이 PC 에서 명령을 실행할 수 있나(예: `docker exec … psql` 로 DB 읽기 · `npm run` 검사) · 한 번에 읽을 수 있는 양 · Plus 의 하루/주 한도 체감 · 긴 작업(문항 7,000개 판정)을 나눠서 이어 갈 수 있나.
3. "gpt 가 한국어 자연어를 더 잘한다" 는 가설을 **공정하게 재 볼 시험**을 제안해 달라. 내 안: 같은 문항 50개를 gpt · max · web 이 같은 지시서로 다시 쓰고, 누가 썼는지 가린 채 섞어서 찬종이 고른다. 더 나은 방법이 있으면.
4. **유지보수 계획**: 지금 구조(라운드 · 브리프 · 번호 체계 · 큰 문서들)에서 네가 보기에 가장 먼저 고칠 것 3가지. 특히 "찬종의 전달 일을 줄이는" 쪽으로.
5. 세 AI 의 역할 분담안을 **표 하나**로(일 · 주인 · 검토자 · 주고받는 파일). 그리고 **찬종이 하루에 해야 하는 일**이 지금보다 늘어나는지 줄어드는지.
6. 내 4절에서 **틀렸다고 보는 곳**. 특히 "다른 눈이라 값지다 vs 글을 더 잘 쓴다".
