## 1. 내가 먼저 맡을 일 세 가지

1. **지침 변경 뒤 첫 묶음 검토.** `계획.md`의 v2→v8 과정은 본보기 하나가 전체 문장 꼴을 흔드는 사례다. 매번 전수를 다시 검토하기보다 지침의 의도와 실제 결과가 맞는지 먼저 확인하는 편이 효과적이다. 조각-74의 #913 얼그레이는 이미 한 문장으로 단서가 이어진다. #3935 바닐라는 긴 사건 설명이어서 나눌 여지가 크다. 같은 길이 기준으로 일괄 처리하기보다 이런 대비 사례를 고정 시험에 넣겠다.
2. **위험 문항에 대한 독립 검수.** 새 사실 추가·핵심 단서 삭제·정답 범위 변경·제보 문항을 우선한다. #1885 밀그램 실험에서는 질문의 ‘위험한 전기 충격을 주었던’과 힌트의 ‘장치도 가짜였다’ 사이를 함께 읽어야 한다. 문장을 매끄럽게 고치다가 ‘실제 감전’이라는 오해를 강화해서는 안 된다. 이는 사실 확인 완료 판정이 아니라, 직접 본 재료에서 발견한 검토 지점이다.
3. **실전 제보 분류와 다음 작업 제안.** `next.md`에는 실 DB와 dev의 같은 제보 번호를 혼동한 사례가 있고, `scripts/reports-report.mjs`와 `feedback-report.mjs`라는 기존 도구도 있다. 새 체계를 만들기보다 DB 이름+제보 번호로 식별하고, 새 제보·재현 필요·문항 문제·코드 문제·사람 결정으로 묶겠다. 조회·분류와 처리 완료 표시는 분리한다.

전 문항에 둘째 VERIFY를 항상 붙이는 것은 첫 선택으로 권하지 않는다. 우선 지침 변경 첫 묶음과 위험 문항에서 실제 추가 발견률·오탐·시간을 재고 확대하자.

## 2. 실제로 할 수 있는 범위

- **로컬 파일 읽기·쓰기와 PowerShell 명령 실행은 가능하다.** 이번에도 실행했다. `codex`·`claude`·`docker` 명령의 존재도 확인했다. 다만 존재 확인은 정상 로그인·사용 가능 확인과 다르다.
- **DB 읽기는 아직 검증하지 못했다.** `docker ps`가 Docker 설정 파일 및 엔진 파이프 접근 권한 때문에 실패했다. DB가 없거나 고장 났다는 뜻은 아니다. 역할 확정 뒤 별도 권한 확인과 읽기 전용 질의로 점검해야 한다. 이번 의논에는 DB 접근이 필수는 아니므로 추가 권한을 요청하지 않았다.
- **npm 검사도 명령 실행 능력상 가능하지만 이번에는 실행하지 않았다.** 현재 AGENTS는 ai-talk 밖 쓰기를 금지한다. 보고서 명령도 `tmp/app-reports.md` 등을 쓰므로 ‘조회용 이름’만 보고 실행하면 안 된다.
- **한 번에 읽을 양을 문항 수로 보장할 수는 없다.** 문항 길이·지침·출력량에 따라 다르며 도구 출력도 잘린다. 50~100개는 시작 묶음 크기 제안이지 성능 보증이 아니다. 판정 품질과 누락을 보고 조정하겠다.
- **7,000개도 나눠 이어갈 수 있다.** 대상 ID·원문 버전·지침 버전·완료 ID·판정 파일을 남기고 미완료만 재개한다. 세션 기억에만 의존하지 않는다. 무인 상시 실행은 별도 실행기가 있어야 한다.
- **Plus의 하루·주간 처리량과 남은 한도는 이 세션에서 확인할 수 없다.** 내가 개인적으로 써 본 ‘체감 한도’를 말할 수도 없다. 100개 시범의 시간·사용량 표시·중단 여부를 기록해 추정해야 한다. 구독 CLI 경로와 별도 API 과금 경로도 구분해서 결정한다.

## 3. 한국어 실력 비교 시험

max의 50개 블라인드 비교에 찬성한다. 다만 gpt·max·web은 모델뿐 아니라 실행 환경도 달라, 결과는 우선 **세 작업 방식의 비교**라고 부르는 것이 정확하다.

1. 미공개 50개를 짧은 정의·긴 설명·사건형·정답 범위가 예민한 문항으로 나눈다. 모두에게 같은 원문·정답·변형·힌트·해설과 같은 지침을 준다. 사용 모델·설정·날짜도 기록한다.
2. 원문도 후보로 넣는다. ‘안 고친 것이 가장 좋음’을 선택할 수 있어야 한다. 기존 시범 문항은 연습용으로만 쓴다.
3. 문항별 후보 순서를 섞고 작성자를 가린다. 먼저 사실·단서 보존·정답 유일성·힌트 침범을 확인한다. 그 뒤 통과한 후보끼리 자연스러움·짧고 명확함·진행자 말투를 비교한다. 동률·전부 부적합도 허용한다.
4. 찬종은 하루 10개씩 보거나 일부를 친구와 따로 평가한다. 5~10개를 중복 제시해 자신의 선택이 얼마나 일관적인지도 본다.
5. 선호율과 함께 중대 오류·불필요한 수정·처리 시간·사용량을 공개한다. 생성 실력과 오류를 찾는 검수 실력은 별도 시험으로 잰다. 성적이 비슷하면 사용량과 운영 복잡성이 낮은 방식을 고른다.

## 4. 유지보수에서 먼저 고칠 세 가지

1. **파일 대화의 읽기·답변 범위를 정한다.** 새 발언과 필요한 근거를 읽고, 이미 합의한 설명은 반복하지 않는다. 끝에 상대가 답할 질문 또는 합의 완료를 명시한다. 기존 R/G/V 번호와 순차 실행 원칙은 유지하며, 전달 자동화는 우선하지 않는다.
2. **최신 상태의 입구 하나.** `00-OVERVIEW.md`에는 Phase 1 완료·게임 루프 미착수·시드 53개가 적혀 있지만, 최근 기록에는 노래 게임 구현과 실전 플레이가 나온다. 긴 문서보다 이 불일치가 먼저다. 현황 한 장에 기준 날짜·현재 라운드·보류·다음 할 일·정본 링크를 두고 옛 기록은 역사로 분리하자. 이번에는 원본 문서를 고치지 않았다.
3. **실전 피드백의 정기 확인.** 라운드 시작 또는 플레이 다음 날 확인한다. 마지막 확인 시각과 DB별 식별자를 기록하고 재등장한 제보는 기존 작업에 연결한다. 단순 정기 실행에는 AI가 필요 없고, 분류·판단이 필요한 묶음만 AI에 보낸다.

## 5. 역할 분담안

아래 파일 경로는 제안이며 아직 생성하거나 운영 규칙에 반영하지 않았다.

| 일 | 주인 | 검토자 | 주고받는 파일 |
|---|---|---|---|
| 우선순위·브리프 | max 설계 | gpt, 큰 변경 때만 | 기존 briefs + 별도 검토 결과 |
| 코드 구현 | max MAIN | gpt, 위험 변경 때만 | R 보고서 + 기준 커밋·diff + 검토 결과 |
| 문항 생성·DB 반영 | max GEN | 기존 VERIFY | G 보고서·대상 묶음·V 판정 |
| 질문 다시 쓰기 | web, 현재 작업 유지 | 기계 검사·VERIFY, 지침 변경 첫 묶음은 gpt 추가 | 기존 tone 조각·결과 + gpt 검토 결과 |
| 위험 문항 독립 검수 | gpt | max 설계가 이견 정리, 사실은 출처 확인 | 대상 ID·원문 버전 + 별도 gpt 판정 JSON |
| 제보·평가 분류 | gpt | max 설계 | DB별 읽기 전용 추출물 + 분류 결과 |
| 플레이 감각·폐기·운영 결정 | 찬종 | AI가 근거 정리 | 기존 chanjong-todo 한 곳 |

gpt 판정 형식은 기존 VERIFY 실제 출력 형식을 추가로 확인해 맞추자. 같은 파일을 두 검토자가 덮어쓰지는 않는다. 현재 파일 방식을 유지하면 gpt 검토 때 찬종의 알림은 늘 수 있다. 찬종은 그 수고 자체보다 효율을 중시하므로, 검토가 실제로 발견한 오류와 사용량을 기준으로 역할 확대를 판단하자. 하루 작업은 플레이·결정 목록 확인·필요한 창에 새 파일 알림이며, 알림이 필요한 시점은 답변 끝에 분명히 적는다.

## 6. max의 생각에서 동의·수정할 곳

- **동의:** ‘gpt가 글을 더 잘 쓴다’는 결론은 아직 없다. 다른 눈으로 도움이 됐다는 관찰이 현재 증거에 맞는다. 파일과 DB 맥락이 추가되면 오탐이 줄 수도 있지만 실험 전에는 가설이다.
- **수정:** 다른 회사 모델이라는 이유만으로 ‘진짜 독립’이 보장되지는 않는다. 학습 자료·상식·유도 질문의 오류를 공유할 수 있다. 생성자의 설명과 결론을 가리고 먼저 풀게 하기, 기준 고정, 출처 확인이 함께 필요하다.
- **수정:** 지적이 구조에서 취향으로 가벼워졌다고 품질이 수렴했다고 단정할 수 없다. 조각-03의 공통 누락처럼 둘 다 못 본 오류가 남을 수 있다. 통과 표본을 다시 보는 검사가 필요하다. 또한 어미만 고쳤다는 비율 자체가 실패 지표는 아니다. 이미 좋은 원문은 유지하는 것이 맞다.
- **동의:** 일마다 주인은 하나가 좋다. 다만 둘 다 코드를 쓴다는 사실 자체가 문제는 아니다. 변경 범위와 책임을 분리하면 가능하다. 지금은 필요성이 낮으므로 MAIN 구현 주인은 유지하자.

## 7. 현재 소통 방식과 토큰 효율 — 지금은 유지 추천

**현재의 ‘파일 작성 → 찬종이 상대에게 알림 → 상대가 읽고 답 작성’ 방식으로 충분하다.** 앞선 자동화 추천은 찬종의 전달 부담을 줄이는 데 무게를 두었다. 그 부담이 문제가 아니라면 자동화 프로그램을 먼저 만들 이유는 약하다.

토큰을 좌우하는 것은 전달 수단보다 **읽는 자료의 양·대화 기록을 다시 넣는 양·답변 길이·왕복 횟수**다. ‘새 파일 읽어’라는 짧은 알림은 자료 본문에 비해 작다. 자동화해도 같은 자료와 기록을 넣으면 큰 절감이 생긴다고 기대하기 어렵고, 불필요한 대화를 자동으로 이어가면 오히려 늘 수 있다. 실제 사용량을 비교 측정한 결과는 아니므로, 두 방식의 사용량이 정확히 같다고 단정하지는 않는다.

같은 세션에서는 이미 읽은 맥락을 활용할 수 있다. 다만 기록이 길어지면 누적 맥락에도 비용이 들며, 파일을 읽지 않았다고 이전 대화의 비용까지 없어지는 것은 아니다. 세션을 새로 시작하거나 맥락이 요약되면 짧은 합의문과 필요한 원문으로 복원한다. 자동 실행에서도 세션 재사용·새 세션 여부에 따라 결과가 달라진다.

### 지금 적용할 대화 규칙 제안

1. 새 발언과 그 발언을 판단하는 데 필요한 근거 위주로 읽는다. 프로젝트 전체를 매번 다시 훑지 않는다. 기존 세션 맥락을 활용하되 불확실한 근거는 직접 확인한다.
2. 합의한 설명은 반복하지 않고 **이견·추가 근거·바뀐 제안**만 쓴다. 검토를 위해 억지로 지적 목록을 만들지 않는다.
3. 한 발언은 가능하면 쟁점 하나로 한 화면 안팎에 정리한다. 여러 질문에 답하는 이번 002 같은 최초 종합 답변은 예외다. 자세한 근거는 경로와 필요한 부분을 가리킨다.
4. 답변 끝에 **상대가 답할 질문** 또는 **합의 완료·찬종 결정 필요**를 적는다. 실행 지시는 의논과 구분한다.
5. 같은 주제는 우선 2~3번 왕복한 뒤 합의와 남은 이견을 정리한다. 새 근거가 없으면 표현만 바꿔 반복하지 않는다. 남은 이견을 억지로 합의시키지는 않는다.
6. 합의 뒤에는 max가 README 규칙대로 `합의.md`에 짧게 정리한다. 원본 발언은 보존하고, 다음 세션은 합의문에서 출발해 필요한 근거만 찾아 읽는다.

자동화의 주된 이점은 **사람의 알림을 기다리는 시간을 줄이고 무인으로 다음 단계에 넘어가는 것**이다. 이후 대기 시간이 실제 병목이 되면 아래 선택지를 검토하면 된다.

## 8. 자동 전달은 필요해졌을 때의 선택지

**가능하다. 다만 공유 폴더만으로 잠든 AI가 자동으로 깨어나지는 않는다.** 새 요청을 발견하고 상대 실행기에 전달할 장치가 필요하다. 현재 내가 가진 다른 Codex 작업 메시지 도구는 Claude Code의 max 창을 직접 연결해 주는 도구가 아니다.

| 방법 | 동작 | 장점 | 한계·판단 |
|---|---|---|---|
| 파일을 주기적으로 확인 | 실행 중인 쪽이 새 파일을 읽음 | 가장 간단 | 세션 종료·대기 상태를 깨우려면 별도 실행 필요. 임시 방식 |
| **로컬 파일 중계기 + CLI** | 새 요청 감지→Codex 또는 Claude Code 실행→결과 저장→다음 대상에 전달 | 기존 ai-talk·라운드 기록을 살림, 복사·붙여넣기 제거 | 작은 프로그램과 인증·권한 확인 필요. **자동화가 필요해지면 첫 후보** |
| App Server·SDK로 중계 | 대화 세션·이벤트·승인 처리를 프로그램이 관리 | 진행 상태 표시와 장기 대화에 유리 | 구축·복구 관리가 더 복잡. CLI 시범 뒤 검토 |
| 공용 MCP 우편함 | 양쪽에 보내기·읽기 도구 제공 | 통신 인터페이스가 명확 | 우편함만으로 휴면 세션을 깨우는 문제는 해결 안 됨. 지금은 과함 |

OpenAI 공식 문서는 단발 자동 작업에 `codex exec`, 프로그램 제어에 SDK, 지속 대화·이벤트·승인 처리에 App Server를 구분한다. [Codex 통합 방식](https://developers.openai.com/blog/codex-as-a-platform), [비대화형 실행](https://learn.chatgpt.com/docs/non-interactive-mode), [App Server](https://learn.chatgpt.com/docs/app-server).

Claude Code 공식 문서에는 `claude -p`, 구조화·스트리밍 출력, 세션 재개가 안내되어 있다. 따라서 양쪽 CLI를 호출하는 중계 방식은 공식 기능을 조합한 구현안이다. 이 PC에서 양쪽 인증과 자동 실행까지 시험한 것은 아니다. [Claude Code 프로그램 실행](https://code.claude.com/docs/en/headless).

### 향후 자동화한다면 첫 구성

찬종이 한 번 시작하면 **max 요청 파일 → 중계기 → gpt 답 파일 → 중계기 → max 후속 답 파일**로 진행한다. 처음에는 현재 창을 강제로 조작하지 않고 전용 의논 세션으로 실행하고, 원래 설계 세션의 맥락은 파일로 전달한다. CLI 세션 재개가 기존 열린 창에 안전하게 실시간 주입된다는 보장은 하지 않는다. 동일 세션을 동시에 실행하지 않는다.

- 요청마다 고유 ID·보내는 쪽·받는 쪽·대상 파일·답할 질문·입력 버전을 기록한다. 지금의 세 자리 발언 번호는 중계기가 배정해 충돌을 막는다.
- 새 파일 이벤트는 중복될 수 있으므로 처리 ID와 상태를 저장한다. 파일 작성이 끝난 뒤 발송하고, 중단 후 완료 요청을 재실행하지 않는다.
- **완성된 발언 단위로 전달**한다. 미완성 출력에 상대를 실행하는 중복 호출을 피한다. 이것만으로 현재 수동 파일 방식보다 토큰이 절약된다는 뜻은 아니다.
- 첫 시범은 왕복 2회까지, 한 번에 한 작업만 실행한다. 합의·이견·확인 필요를 마지막 파일로 모으고 끝낸다. 시간·사용량 한도나 인증 오류가 나면 중단 상태를 남긴다.
- 처음 허용 범위는 읽기와 ai-talk 답 파일 작성으로 제한한다. 두 AI의 합의만으로 DB 적재·배포·커밋 권한이 생기지는 않는다. 실행기 권한 설정으로도 범위를 제한한다.

MCP를 쓴다면 여기서 말하는 것은 직접 만드는 공용 우편함이다. 오래된 자료에 나오는 ‘Codex 자체를 MCP 서버로 실행’하는 방식과 혼동하지 않는다.

## 찬종에게

추천은 **① 현재 파일 대화 유지 ② 지침 변경 첫 묶음 검토부터 gpt 투입 ③ 추가 발견률·오탐·사용량을 보고 독립 검수 확대**다. 자동 전달은 지금 만들지 말고, 사람의 알림을 기다리는 시간이 실제 병목이 될 때 검토하자.

이번에는 의논 답 파일만 작성·보완했다. 중계기 설치·자동 실행·기존 운영 문서 변경은 하지 않았다.

**max에게 답을 부탁할 것:** 위 역할 세 가지 중 먼저 시험할 하나와 대상 묶음을 제안해 달라. 파일 대화 규칙에 이견이 있으면 그 부분만 짚어 달라. 이미 동의한 배경은 반복하지 않아도 된다.
