# 문항 다시 쓰기(말투 통일 v2) — 계획 (설계 2026-11-11 · 찬종 결정)

v1(같은 날 새벽)은 "질문문 끝 어미를 '~은?' 으로 맞춘다" 였다. 찬종이 GPT 에서 받아 온 `quiz_standardization_v2_design_guide.md`(Story / Decisive / Rebuild)를 설계가 검토하고 찬종에게 물어 아래로 바꿨다. v1 지시서는 버렸다.

## 0. 찬종 결정 (2026-11-11 · 제출 폼 3회)

| 물음 | 결정 |
|---|---|
| 다시 쓰는 강도 | **가벼운 Story** — 설명 → 마지막 질문 흐름으로 다시 쓴다. 힌트 · 해설 내용은 그대로 |
| 끝 어미 | **"~일까요?" 계열**(이것은 무엇일까요 · 이 사람은 누구일까요 …) — "~은?" 4,460 을 바꾼다 |
| 설명문 말투 | "~습니다" 기본 + 진행자 말투 자유. **"~는데요" = 앞에서 "~습니다" 로 끊었거나 말이 길어질 때 부드럽게 이어 주는 말**(찬종 본보기 = 지시서 1절 스카치테이프 짧은 꼴 · 긴 꼴). 횟수 규칙 없음 · 2회 넘으면 대개 부자연 |
| 한 문장 문항 4,004 | 길이로 가르지 않는다 — **짧게 설명되는 답은 짧은 꼴 · 어려워서 풀어 써야 하면 긴 꼴** · 억지로 늘리지 않는다(설계의 첫 예시는 "억지로 늘린 느낌" 으로 기각) |
| 힌트 말투 | **"~입니다"** — 끝 어미만(7,161 이 "~다") · 해설 "~다" 1,089 도 "~니다" · 이모지 문항은 손대지 않음 |
| 재료 | 조각에 **정답 · 힌트 · 해설을 같이 준다**("잘못된 레시피의 재료로 요리하라는 꼴이 되면 안 된다") |
| 새 사실 | **허용하되 표시**(`added`) — 널리 알려진 것만 · VERIFY 는 표시된 것만 사실 확인 |
| 폐기 | 억지로 살리지 않는다 — `discard` 사유 넷(narrow · unclear · thin · empty) · "어렵다" 는 사유 아님 · **표시만, 실제 비활성 · 재생성은 찬종이 목록을 본 뒤** |
| 누가 | 시범 = 웹 Sonnet 5.5 → **결과를 GPT 에 넣어 첨삭** → 지침 확정 → 전수는 Sonnet → **VERIFY 세션이 최종 검수 뒤 적재** |

GPT 문서에서 받은 것: 마지막 문장이 답의 종류를 묻는다 · 기계적 어미 통일 금지 · 유형 섞은 시범 먼저 · 생성/검수 분리. 안 받은 것: 힌트 전면 재작성(활성 7,880 전부 hint-v7 · blind 95% — "Decisive" 는 H9 와 같은 말) · "25초 힌트" 전제(실제 10초) · 14 필드 스키마 · 12 모듈(이미 있는 파이프라인).

## 0-1. 시범 1 결과 (2026-11-11 저녁 · 조각-00 47문항 · 웹 Sonnet + GPT 첨삭)

- 좋음: 힌트 45 전부 끝 어미만 바뀜 · 정답 노출 0 · 숫자 · 고유명사 변화 0 · 새 사실 0 · "~데요" 2회 0 · 긴 꼴 20 은 원문 흐름 유지 · 길이 +13%.
- 나쁨: 짧은 꼴 20 중 12 가 `이것은 …입니다. 이 X 는 무엇일까요?` 틀 반복(정보 그대로 · 길이만 늘어남) · discard 2(소급입법 금지 · 탄소 배출 계수)는 둘 다 "비슷한 용어가 여럿" — 살릴 수 있음.
- 찬종 결정: ① **정의형 짧은 문항 = 한 문장 그대로 + "~일까요?"**(사연 · 변화가 있는 문항만 2문장 짧은 꼴) ② **웹은 질문만 돌려준다 · 힌트 · 해설 끝 어미는 GEN 이 따로**(웹이 질문을 풍부하게 고쳐 힌트와 겹치면 GEN 이 힌트를 조정 — 웹은 `hint_overlap` · `added` 로 표시) ③ 시범 한 번 더(조각-01 · 짧은 문항 위주 50) + GPT 첨삭 한 번 더.
- 지시서 v3: 세 꼴(line · short · long) · 틀 반복 나쁜 예 · narrow 좁힘 + `aliases` · 5절 = 힌트 · 해설 읽기만 · 결과 = 변경분.
- 전수 예상: 이모지 뺀 7,151 · 100문항씩 **약 72 조각**(출력이 질문만이라 가능 — 시범 2 출력 길이로 확정).

## 1. 단계

1. **시범** — `보낼것/조각-00.txt`(47문항 · 불만 문항 5 + 스카치테이프 · 사무라이 + 이모지 2 + 한 줄 4 + 한 문장 17 + 2~4문장 20) → 웹 Sonnet → `받은것/결과-00.json`.
2. **GPT 첨삭** — `gpt-첨삭-프롬프트.md` + 지시서 · 조각 · 결과 첨부 → 돌아온 글을 `받은것/결과-00-gpt첨삭.md` 에 → 설계 창에 "tone 시범 확인".
3. **지침 확정** — 설계가 결과 + 첨삭을 읽고 지시서를 고친다 · 찬종이 20개쯤 눈으로 본다 · 필요하면 시범 한 번 더(다른 47).
4. **전수** — 조각 크기는 시범의 출력 길이를 보고 정한다(입력에 정답 · 힌트 · 해설이 붙어 v1 의 100문항보다 무겁다 — 50~80 예상 → 100~158 조각). 이모지 729 는 조각에서 뺀다.
5. **검사 · 적재** — 조각이 쌓이면 GEN 라운드: 기계 검사(§2) → VERIFY 표본 + `added` 있는 문항 전수 사실 확인 → 통과분만 두 DB 적용(before 같을 때만 · undo) → `hint-check-active` 막힘 0.
6. **폐기 목록** — discard 를 사유별로 모아 찬종에게 → 비활성 · 재생성 결정.
7. **생성 쪽** — 15 §3-1 · 생성 프롬프트에 같은 꼴(설명 → "~일까요?") · 힌트 "~입니다".

## 2. 기계 검사 (조각마다)

| 검사 | 통과 |
|---|---|
| id 집합 · verdict | 조각과 같음 · rewrite / keep / discard |
| 끝 | 질문이 `?` 하나로 끝남 · 끝 어미 "~까요?" · 질문 뒤 설명 0 |
| 정답 노출 | 정답 · 변형이 질문 · 힌트에 없음 |
| 보존 | 원문 질문의 숫자 · 따옴표 안 글이 남아 있음 |
| 새 것 | 원래 질문 · 힌트 · 해설에 없던 숫자 · 따옴표 글이 있으면 `added` 에 적혀 있어야 함(없으면 보류) |
| 힌트 | 내용 같음(끝 어미만 다름) · 120자 이하 · 질문과 겹치는 사실 없음(H3) |
| 말투 | "~는데요" 3회 이상 = 경고 · "~이다/~했다" 설명문 = 보류 |
| 길이 | short ≤ 130자 · long ≤ 220자(시범 뒤 조정) |
