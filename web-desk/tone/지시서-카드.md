# 문항 카드 통째로 보기 — 지시서 (v0 시범 · 2026-11-13 · max 초안 — gpt 가 020 답에서 고친다)

한 문항 = 카드 한 장(질문 · 힌트 · 해설). 지금까지는 질문만 다듬었다(`지시서.md`). 이 일은 **카드를 통째로** 본다: 세 칸이 제 역할을 하는지 보고, 모자란 칸만 고치고, 그 문항이 낼 만한 문제인지(알가치)도 적는다.

기획자 말(2026-11-13): "힌트는 말 그대로 답을 맞히게 돕는 것. 해설에는 잡지식 · 토막 상식 · 재미있는 간단한 에피소드 · 역사를. 어려운 문제 · 생소한 개념은 문제 – 힌트 – 해설에 걸쳐 다양한 시각과 개념을. 쉬운 문제는 잡지식 + '이런 게 있어?' 하는 토막 상식을. 알가치가 떨어지면 폐기하거나 낮음으로, 답은 좋은데 질문이 좋지 않으면 다시 쓴다."

입력: `보낼것/조각-NN.txt`(문항마다 id · 등급 1~5 · 질문 · 정답 · 힌트 · 해설).

## 1. 세 칸의 역할

| 칸 | 언제 보나 | 할 일 | 하지 말 것 |
|---|---|---|---|
| **질문** | 처음 | 정답 하나를 가리키는 단서. 진행자 말투(`지시서.md` v10.2 §2~§5 그대로) | 단서 없는 한 줄 · 이름 나열 · 정답 글자 |
| **힌트** | 못 맞힐 때 | **맞히게 돕는다** — 정답의 핵심을 다른 쪽에서 한 번 더 짚는 한 줄. 아는 사람은 힌트만 보고도 답이 떠오른다 | 정답 글자 · 조각 · 다른 이름(H2 · H10) · 질문의 되풀이 · 잡지식 자랑 |
| **해설** | 정답이 공개된 뒤 | **"아, 그렇구나 / 이런 게 있어?"** — 정답에 얽힌 토막 상식 · 짧은 일화 · 유래 · 뒷이야기 **하나**(한두 문장). 맞힌 사람도 얻어 가는 것 | 질문 · 힌트에 이미 나온 사실 · "X는 Y입니다" 꼴의 정답 되풀이 · 사전 뜻풀이만 |

- **어려운 문항(등급 4 · 5) · 생소한 개념**: 세 칸이 **서로 다른 각도**를 맡는다 — 예: 질문 = 무엇인가(정의 · 원리) / 힌트 = 어디서 보나(쓰임 · 예 · 가까운 것) / 해설 = 어떻게 생겼나(유래 · 이름 뜻 · 일화). 재료가 많으면 가장 맞히기 좋은 것을 질문에, 가장 재미있는 것을 해설에 둔다.
- **쉬운 문항(등급 1 · 2)**: 질문은 원래 관계를 살린 채 잡지식 하나(`지시서-재구성.md` §2) · 해설은 "이런 게 있어?" 하는 토막 상식 하나.

## 2. 재료 — 있는 것을 먼저 옮기고, 새 사실은 출처와 함께

1. **카드 안에 이미 있는 사실을 먼저 쓴다.** 옛 힌트 · 해설의 사실은 앞선 검수를 거쳤다 — 칸을 옮기는 것(힌트의 일화 → 해설 · 해설의 정의 → 질문)은 출처가 필요 없다. **좋은 재료를 버리지 않는다.**
   - 나쁜 예(#30 H2O · 재구성-01): 옛 해설 `물은 약 4도에서 밀도가 가장 커서, 겨울 호수는 얼음이 위에 뜨고 바닥 물은 덜 언다.` 를 버리고 `물 분자는 전체적으로 전기적 중성이지만 …` 으로 바꿨다 — 더 밋밋해졌다. 옛 문장이 해설로 더 좋다.
2. 카드 안 재료로 모자랄 때만 **새 사실**을 넣는다 — 실제로 연 페이지의 URL 을 `claims` 에. 못 찾으면 넣지 않는다.
3. 이미 제 역할을 하는 칸은 **건드리지 않는다**(`keep`). 고치는 수를 늘리는 것이 목표가 아니다. 끝말만 "~다." 면 "~입니다"로(이것은 `keep` 이 아니라 `ending`).

## 3. 알가치 — 이 문항을 낼 만한가

| 값 | 뜻 |
|---|---|
| `good` | 친구들 앞에서 맞히면 기분 좋고, 몰랐어도 답을 들으면 "아!" 한다. 상식으로 통하거나 이야깃거리가 된다 |
| `ok` | 평범하지만 낼 만하다 |
| `low` | 낼 수는 있지만 재미가 약하다 — 지엽 · 숫자 암기 · 마니아만 아는 것. 덜 나오게 한다 |
| `drop` | 빼자 — 답을 들어도 "그래서?" · 시효가 지남 · 정답이 사람마다 다르게 쓸 말 · 문제로 성립이 약함 |

`low` · `drop` 에는 `worth_why` 한 줄. 정답(키워드)은 좋은데 질문이 나쁜 것은 `drop` 이 아니라 **질문을 `rebuild`** 한다.

## 4. 출력 — `받은것/카드-NN.json`

```json
{ "chunk": "18", "results": [
  { "id": 4314, "worth": "good",
    "question": { "verdict": "rewrite", "text": "…무엇일까요?" },
    "hint": { "verdict": "ending", "text": "…씁니다." },
    "explanation": { "verdict": "keep" },
    "claims": [], "note": "" },
  { "id": 30, "worth": "ok",
    "question": { "verdict": "rebuild", "text": "…" },
    "hint": { "verdict": "rewrite", "text": "…" },
    "explanation": { "verdict": "rewrite", "text": "…", "from": "옛 해설의 4도 사실을 살림" },
    "claims": [ { "claim": "…", "source_url": "https://…" } ], "note": "" }
] }
```

- 칸마다 `verdict`: `keep`(그대로 — text 없음) · `ending`(끝말만) · `rewrite`(카드 안 재료로 다시 씀 — 새 사실 0) · `rebuild`(새 사실을 넣어 다시 씀 — claims 필수). 질문의 `rewrite` = 지금까지의 다듬기.
- `worth` 는 모든 문항에. `drop` 이면 세 칸은 `keep` 으로 두고 고치지 않는다.
- 입력의 모든 id 를 순서대로 · 누락 · 중복 없이. 정답은 바꾸지 않는다.
- 제출 전: 세 칸에 같은 사실이 두 번 나오지 않는가 · 힌트에 정답 낱말이 없는가 · 해설이 "아 그렇구나"인가 · 새 사실마다 claims 가 있는가.
