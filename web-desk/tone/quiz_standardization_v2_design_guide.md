# 퀴즈 표준화 v2.0

## 설계 방향 및 작업 프로세스 제안서

-   문서 목적: Claude Code 등 개발·AI 도구에 전달해 7,880개 한국어 파티
    퀴즈 데이터의 리빌딩 계획과 구현 방식을 설계하기 위한 기준 문서
-   버전: 2.0
-   확정 방향: **Story / Decisive / Rebuild**
-   대상: 20\~40대 한국어 사용자 중심의 친구 간 단답형 파티 퀴즈
-   게임 동작: 플레이어가 채팅으로 단답형 정답을 입력하며, 문제 공개 후
    25초가 지나면 힌트 공개

# 1. 프로젝트 목표

이번 작업은 기존 퀴즈의 문장 끝맺음이나 어미를 일괄 통일하는 단순 교정
프로젝트가 아니다.

기존 7,880개 문항의 질문·정답·힌트·해설을 원본 자료로 삼아, **정답과
검증된 핵심 사실은 보존하면서 질문과 힌트를 게임에 적합한 완성도 높은
콘텐츠로 전면 재설계(Rebuild)** 하는 것이 목표다.

최종 결과물은 다음 조건을 만족해야 한다.

1.  한국어로 자연스럽게 읽히는 이야기형·해설형 질문
2.  질문 마지막에서 정답의 종류와 요구 형태를 명확히 제시
3.  질문과 겹치지 않으면서 정답을 떠올리게 돕는 결정적 힌트
4.  정답, 날짜, 숫자, 고유명사, 핵심 사실의 정확성
5.  정답 외의 다른 답이 합리적으로 성립하지 않는 질문
6.  채팅 기반 단답형 게임에서 읽고 이해하기 쉬운 길이와 표현
7.  원본과 수정본의 추적 가능성, 배치 단위 재작업 가능성

## 1.1 확정된 제작 방향

  -----------------------------------------------------------------------
  항목                    결정                    적용 의미
  ----------------------- ----------------------- -----------------------
  문제 문체               **Story**               배경과 설명이
                                                  자연스럽게 이어지는
                                                  해설형 서술

  힌트 강도               **Decisive**            정답을 떠올릴 수 있을
                                                  만큼 구체적이고 유효한
                                                  추가 단서

  재작성 범위             **Rebuild**             기존 질문을
                                                  참고자료로만 사용하고
                                                  질문·힌트를 전면 재설계
  -----------------------------------------------------------------------

## 1.2 작업의 핵심 원칙

> 문장을 길게 만드는 것이 목적이 아니다. 읽는 동안 단서가 자연스럽게
> 쌓이고, 마지막 질문에서 정답을 명확하게 요구하는 좋은 퀴즈를 만드는
> 것이 목적이다.

# 2. 문제 작성 지침: Story

## 2.1 기본 문체

사용자가 제시한 좋은 문항 예시의 공통점은 다음과 같다.

-   첫 문장에서 정답의 범주를 자연스럽게 제시한다.
-   정의, 배경, 역사적 맥락, 특징, 일화 등의 정보가 목록처럼 나열되지
    않고 문장 간 흐름을 갖는다.
-   "\~인데요", "\~했다고 합니다", "\~이기도 했습니다" 등의 연결 표현을
    문맥에 맞게 사용한다.
-   마지막 문장에서 앞서 설명한 대상을 다시 지칭하며 명확한 질문을
    던진다.
-   문장 수를 기계적으로 제한하지 않는다. 정보량과 주제에 맞는 길이를
    선택한다.

권장되는 기본 전개는 다음과 같다.

1.  **대상 소개:** "이것은", "이 사람은", "이 책은", "이 현상은" 등으로
    답의 범주를 알려준다.
2.  **핵심 설명:** 정의, 배경, 탄생 과정, 역사적 맥락 등 핵심 정보를
    제공한다.
3.  **추가 단서:** 특징, 일화, 관련 인물, 대표 사례 등으로 정답 후보를
    좁힌다.
4.  **최종 질문:** 앞서 설명한 대상을 다시 지칭하고 답을 요구한다.

이 구조는 참고용이지 고정 템플릿이 아니다. 모든 문항에 네 단계를 억지로
적용하지 않는다.

## 2.2 길이와 문장 구성

-   짧은 개념 문제는 2\~3문장으로 끝낼 수 있다.
-   인물·역사·사건 문제는 필요한 경우 4\~5문장 이상을 사용할 수 있다.
-   일화가 핵심 단서라면 이야기 흐름을 살린다.
-   정의가 핵심인 문제는 정의를 먼저 제시해도 된다.
-   불필요한 배경 설명으로 문장을 늘리지 않는다.
-   문항을 소리 내 읽었을 때 어색한 연결이나 반복이 없어야 한다.

## 2.3 연결 표현

문맥에 따라 다음과 같은 표현을 활용한다.

  기능          표현 예시
  ------------- ---------------------------------
  배경 소개     "\~에서 비롯된 개념인데요."
  사실 연결     "\~라고 합니다."
  특징 설명     "\~한 특징이 있습니다."
  추가 정보     "이뿐만 아니라", "또한"
  역사적 맥락   "\~하던 시기에 등장했습니다."
  일화 소개     "\~했다는 이야기도 전해집니다."
  마무리        "이것은 무엇일까요?"

특정 어미를 반복적으로 붙이지 않는다. "\~인데요"를 모든 문장에 사용하는
식의 기계적인 문체 통일은 금지한다.

## 2.4 마지막 질문

모든 일반 문항은 마지막에 명확한 질문을 둔다. 질문 표현은 정답의 종류에
맞춰야 한다.

  정답 유형   질문 예시
  ----------- ---------------------------------------------
  개념·사물   이것은 무엇일까요?
  인물        이 사람은 누구일까요?
  장소·국가   이곳은 어디일까요? / 이 나라는 어디일까요?
  책·작품     이 책은 무엇일까요? / 이 작품은 무엇일까요?
  사건·현상   이 사건을 무엇이라고 할까요?
  동식물      이 동물은 무엇일까요?
  연도        몇 년일까요?
  색상        무슨 색일까요?

마지막 질문은 장식이 아니다. 플레이어가 입력해야 할 답의 범주와 형태를
결정한다.

# 3. 힌트 작성 지침: Decisive

## 3.1 문제와 힌트의 역할 분리

힌트는 문제의 요약이나 반복이 아니다. 문제에서 제공하지 않은 새로운
단서를 추가해야 한다.

  -----------------------------------------------------------------------
  구분                    문제                    힌트
  ----------------------- ----------------------- -----------------------
  목적                    정답을 추론할 맥락 제공 정답을 떠올릴 수 있도록
                                                  결정적 정보 추가

  정보                    정의, 배경, 특징, 역사, 별도 고유명사, 별칭,
                          대표 사례               관련 인물, 핵심 연관
                                                  정보

  표현                    자연스러운 설명과       짧고 직접적인 단서
                          이야기 흐름             

  중복                    기준 정보               문제에 나온 정보의 단순
                                                  반복 금지

  정답 노출               금지                    금지
  -----------------------------------------------------------------------

## 3.2 결정적 힌트의 기준

힌트는 정답 후보를 실질적으로 좁힐 수 있어야 한다. 지나치게 일반적인
연상 단서만 제공하는 것은 기준 미달이다.

-   약한 힌트: "과학과 관련된 인물입니다."
-   중간 힌트: "전기 기술의 발전에 기여한 인물입니다."
-   결정적 힌트: 문제에 나오지 않은 별도의 구체적 연관 정보를 제시해
    정답을 떠올릴 수 있게 하는 단서

예시:

-   인물 문제: "이 인물의 이름은 자기장과 관련된 단위에도 남아
    있습니다."
-   책 문제: 문제에서 책 제목을 직접 언급하지 않았다면, 널리 알려진
    별칭이나 편찬 배경과 연결되는 별도 단서를 활용할 수 있다.
-   역사 인물 문제: 문제에서 언급하지 않은 관련 사건이나 장소와의 연결을
    제공할 수 있다.

실제 문항에서는 힌트가 사실인지, 문제와 중복되지 않는지, 정답을 그대로
노출하지 않는지 별도로 검수한다.

## 3.3 25초 공개 조건

힌트는 문제 공개 후 25초가 지나면 공개된다.

따라서 다음을 지킨다.

-   짧고 빠르게 읽힌다.
-   한 번 읽으면 의미가 파악된다.
-   문제의 문장을 그대로 반복하지 않는다.
-   정답을 떠올릴 수 있는 구체적인 연결고리를 제공한다.
-   정답 자체나 사실상 동일한 표현을 노출하지 않는다.

**Decisive는 정답 공개를 의미하지 않는다.** 문제에 없는 결정적 추가
정보를 제공한다는 뜻이다.

# 4. Rebuild 원칙과 사실 보존

## 4.1 원본의 취급

기존 질문은 완성된 문항의 틀이 아니라 사실을 추출하기 위한 원본 자료다.

### 보존할 항목

-   정답과 정답의 의미
-   사실로 확인된 날짜, 숫자, 고유명사
-   정답을 특정하는 데 필요한 핵심 단서
-   기존 해설에 포함된 유효한 정보
-   원본 ID 및 원본 데이터

### 새롭게 설계할 항목

-   질문의 첫 문장과 전체 이야기 흐름
-   정보의 순서와 문장 구성
-   마지막 질문
-   힌트의 소재와 표현
-   필요시 해설의 구성과 표현

원본 데이터는 덮어쓰지 않는다. 원본과 수정본을 별도 필드 또는 별도
파일로 보존한다.

## 4.2 정답 불변 원칙

정답은 재작성 과정에서 임의로 바꾸지 않는다.

다만 다음 상황은 자동 수정하지 말고 검수 대상으로 분류한다.

1.  기존 정답 자체가 잘못된 경우
2.  정답은 맞지만 질문의 설명이 잘못된 경우
3.  질문과 정답은 맞지만 다른 답도 성립하는 경우
4.  정답의 표기 방식이나 별칭에 문제가 있는 경우

이 유형을 서로 구분해서 기록한다.

## 4.3 사실 보존과 신규 정보

리빌딩 과정에서 새로운 사실을 추가할 수 있지만, 검증되지 않은 사실을
생성해서는 안 된다.

특히 엄격하게 확인할 항목:

-   인물의 생몰 연도와 활동 시기
-   사건의 발생 연도와 순서
-   국가·도시·기관·작품의 공식 명칭
-   수치·단위·순위·통계
-   "최초", "유일", "최고", "최대" 등의 최상급 표현
-   역사적 일화와 발언의 출처
-   발명·발견의 귀속처럼 논쟁이 있는 주장

기존 원문에 있다는 이유만으로 사실이라고 확정하지 않는다.

## 4.4 답 가능성과 정답 유일성

완성된 질문을 독립적으로 읽고 다음을 확인한다.

1.  질문이 요구하는 답이 하나로 특정되는가?
2.  다른 정답도 합리적으로 성립하지 않는가?
3.  정답의 범주와 질문의 표현이 일치하는가?
4.  필요한 조건과 맥락이 문제 안에 모두 있는가?
5.  플레이어가 별도 자료 없이 문제만으로 답을 추론할 수 있는가?

복수 답이 가능하면 문항을 수정하거나 보류한다. 해설에서만 제한 조건을
추가해 모호성을 해소해서는 안 된다. 제한 조건은 질문 자체에 있어야 한다.

# 5. 데이터 구조와 저장 형식

## 5.1 권장 필드

  필드                     용도             처리 기준
  ------------------------ ---------------- -------------------------------
  `id`                     문항 고유 ID     기존 ID 유지
  `original_question`      기존 질문        원문 보존
  `answer`                 정답             원칙적으로 불변
  `original_hint`          기존 힌트        원문 보존
  `original_explanation`   기존 해설        원문 보존
  `revised_question`       새 질문          Story 기준으로 전면 재작성
  `revised_hint`           새 힌트          Decisive 기준으로 전면 재작성
  `revised_explanation`    새 해설          필요한 경우에만 수정
  `answer_aliases`         허용 정답 표기   실제 채점 기준에 맞게 관리
  `fact_check_status`      사실 검증 상태   미검증·검증 완료·보류
  `quality_status`         문항 품질 상태   대기·초안·수정·통과·보류
  `review_reason`          검수 사유        오류·모호성·보류 사유 기록
  `sources`                검증 출처        확인 가능한 출처 정보 저장
  `revision_version`       수정 버전        변경 이력 추적

`revised_explanation`은 무조건 새로 쓰지 않는다. 기존 해설이 정확하고 새
질문과도 일치하면 유지한다. 새 질문과 불일치할 때만 수정한다.

## 5.2 JSONL 예시

한 줄에 한 문항을 저장하는 JSONL을 작업용 형식으로 권장한다.

``` json
{
  "id": "Q000001",
  "original_question": "기존 질문 원문",
  "answer": "정답",
  "original_hint": "기존 힌트",
  "original_explanation": "기존 해설",
  "revised_question": "새로 작성한 이야기형 질문",
  "revised_hint": "문제와 중복되지 않는 결정적 힌트",
  "revised_explanation": "검수 후 확정된 해설",
  "answer_aliases": [],
  "fact_check_status": "verified",
  "quality_status": "passed",
  "review_reason": "",
  "sources": [],
  "revision_version": "2.0"
}
```

실제 구현에서는 프로젝트의 기존 데이터 형식과 게임 엔진의 요구사항을
먼저 확인한 후 최종 스키마를 확정한다. JSONL은 권장안이지 기존 시스템을
확인하지 않고 강제할 형식은 아니다.

## 5.3 상태값

  상태                    의미                          다음 작업
  ----------------------- ----------------------------- -----------
  `pending`               작업 전                       리빌딩
  `drafted`               초안 작성 완료                검수
  `fact_check_required`   사실 확인 필요                출처 확인
  `revision_required`     품질 기준 미달                재작성
  `passed`                검수 통과                     배포 대기
  `hold`                  정답·사실관계에 중대한 문제   별도 판단

사실 검증과 문항 품질 검수는 별도 상태로 관리하는 것이 바람직하다. 예를
들어 질문의 문체 검수는 통과했지만 사실 검증은 보류 중일 수 있다.

# 6. 7,880개 작업 프로세스

전체 작업은 다음 단계로 운영한다.

## 1단계: 원본 분석 및 사실 추출

-   원본 파일의 포맷, 인코딩, 필드, 문항 수를 확인한다.
-   질문·정답·힌트·해설을 분리한다.
-   질문에서 핵심 사실, 고유명사, 숫자, 날짜를 추출한다.
-   정답과 질문의 일치 여부를 점검한다.
-   기존 문항의 오류나 모호성을 표시한다.
-   중복 문항이나 거의 같은 문항을 식별한다.

산출물: 문항별 사실 목록 및 데이터 품질 보고서

## 2단계: 질문 리빌딩

-   정답의 범주를 파악한다.
-   주제에 맞는 가장 자연스러운 설명의 출발점을 고른다.
-   핵심 단서와 보조 단서를 자연스러운 순서로 배치한다.
-   Story 문체로 질문을 작성한다.
-   마지막에 정답의 종류에 맞는 질문을 둔다.
-   불필요한 문장과 중복 정보를 제거한다.

산출물: Story 질문 초안

## 3단계: 힌트 리빌딩

-   문제에 이미 사용한 정보를 식별한다.
-   문제에서 사용하지 않은 별도의 단서를 찾는다.
-   정답을 떠올릴 수 있을 만큼 구체적으로 작성한다.
-   정답 자체가 노출되는지 확인한다.
-   25초 후 공개되는 상황에서 빠르게 읽히는 길이로 다듬는다.

산출물: Decisive 힌트 초안

## 4단계: 독립 검수

-   질문만 읽고 정답을 추론할 수 있는지 확인한다.
-   핵심 사실을 원본 및 신뢰할 수 있는 자료와 대조한다.
-   다른 정답이 성립할 가능성을 확인한다.
-   힌트가 문제와 중복되지 않는지 확인한다.
-   힌트만으로 정답이 노출되지 않는지 확인한다.
-   해설이 최종 질문과 일치하는지 확인한다.

산출물: 통과·수정·보류 판정 및 검수 로그

## 5단계: 최종 확정 및 배포

-   수정 사항을 반영한다.
-   정답과 채점용 별칭을 확인한다.
-   필수 필드 누락 여부를 확인한다.
-   통과 문항만 게임 데이터로 내보낸다.
-   원본과 최종본의 변경 이력을 보존한다.

산출물: 배포 가능한 최종 문항 및 품질 보고서

# 7. 배치 전략

7,880개를 한꺼번에 처리하지 않는다.

  구간                 작업량 목적
  ------------ -------------- ---------------------------
  파일럿                 50개 기준 검증 및 지침 보정
  1차 본작업            200개 다양한 유형에서 품질 확인
  정규 작업        100개 단위 안정적인 반복 생산
  최종 통합      전체 7,880개 중복·누락·일관성 검사

## 7.1 파일럿 50개 선정

무작위 50개만 뽑기보다는 문항 유형과 난이도를 고려해 다양한 사례를
포함한다.

가능하면 다음 유형을 포함한다.

-   인물
-   역사·사건
-   개념·이론
-   책·작품
-   과학·기술
-   사물·도구
-   동식물
-   장소·국가
-   스포츠
-   언어·문화
-   숫자·계산형
-   이모지형 등 특수 유형

파일럿의 목적은 생산량이 아니라 기준의 실효성을 검증하는 것이다. 파일럿
50개를 검수하기 전에는 대량 작업을 시작하지 않는다.

## 7.2 배치 단위 운영

-   배치마다 고유한 batch ID를 부여한다.
-   원본 ID를 유지한다.
-   생성과 검수 결과를 분리해 저장한다.
-   실패 문항만 재처리할 수 있어야 한다.
-   한 배치의 결과가 다른 배치의 원본을 덮어쓰지 않도록 한다.
-   배치별 통과율, 보류율, 사실 오류율, 재작업률을 기록한다.

100개는 초기 운영 기준이다. 모델의 컨텍스트 한계, 비용, 검수 품질,
실패율을 측정해 조정할 수 있다.

# 8. 독립 검수 기준

## 8.1 질문 검수

-   첫 문장에서 정답의 범주를 자연스럽게 안내하는가?
-   문장 사이에 논리적 흐름이 있고 단서가 자연스럽게 쌓이는가?
-   핵심 정보가 빠지거나 잘못 바뀌지 않았는가?
-   날짜·숫자·인명·지명·작품명이 정확한가?
-   마지막 문장이 명확하게 정답을 묻는가?
-   정답 외에 다른 답이 합리적으로 성립하지 않는가?
-   불필요한 반복이나 장황한 문장이 없는가?
-   한국어 어순과 표현이 자연스럽고 소리 내 읽어도 어색하지 않은가?

## 8.2 힌트 검수

-   문제에 등장하지 않은 새로운 정보를 제공하는가?
-   정답을 떠올릴 수 있을 만큼 구체적인가?
-   정답 명칭이나 사실상 동의어를 직접 노출하지 않는가?
-   문제의 내용과 사실적으로 충돌하지 않는가?
-   25초 후 빠르게 읽고 이해할 수 있는가?

## 8.3 사실 검수

-   정답이 신뢰할 수 있는 자료로 확인되는가?
-   질문에 쓰인 핵심 사실이 확인되는가?
-   새로 추가한 정보도 검증되었는가?
-   사실의 시점과 현재 기준이 혼동되지 않는가?
-   논쟁 중인 내용을 근거 없이 단정하지 않는가?
-   원문 오류를 수정하거나 보류했는가?

## 8.4 통과 기준

다음 항목은 하나라도 문제가 있으면 통과시켜서는 안 된다.

-   정답 또는 핵심 사실의 오류
-   정답의 모호성 또는 복수 정답 가능성
-   힌트의 정답 직접 노출
-   질문과 힌트의 실질적인 중복
-   질문과 정답의 불일치

문장 취향에 관한 사소한 개선은 필수 오류와 구분해 관리할 수 있다.

# 9. 문항 유형별 작성 전략

모든 문항을 같은 문장 틀에 넣지 않는다. 정답 유형에 따라 가장 자연스러운
이야기의 출발점을 고른다.

  유형          권장 전개
  ------------- ------------------------------------------------------
  인물          활동 시기 → 주요 업적 → 특징적인 일화
  역사적 사건   시대적 배경 → 사건의 전개 → 역사적 의미
  개념·이론     개념의 의미 → 제안 배경 → 활용·영향
  책·작품       저자·제작 배경 → 내용·특징 → 작품의 의미
  사물·도구     용도 → 구조·작동 원리 → 사용 사례
  동식물        서식지·외형 → 생태적 특징 → 독특한 행동
  장소·국가     위치·환경 → 역사·문화적 특징 → 식별 단서
  과학·기술     원리 → 발견·개발 배경 → 응용 사례
  스포츠        경기 상황 → 규칙·기술의 특징 → 용어
  언어·문화     표현의 의미 → 유래 → 실제 사용 맥락
  숫자·계산     필요한 조건 → 계산 또는 판단 과정 → 답의 단위·정밀도

이 표는 강제 템플릿이 아니라 문항에 맞는 자연스러운 전개를 선택하기 위한
참고 기준이다.

## 9.1 이모지 문제

기존 데이터에서 이모지 조합 자체가 문제인 문항은 별도 유형으로 취급한다.

-   이모지 배열 유지
-   이모지 순서 유지
-   이모지에 대응하는 정답 유지
-   일반 문항과 별도 유형으로 분류
-   사용자가 허용하지 않는 한 이모지를 임의로 교체하거나 재배열하지
    않는다.

# 10. 단답형 채점 데이터

질문을 리빌딩하더라도 채점 기준은 별도로 관리한다.

-   정답의 대표 표기를 유지한다.
-   실제로 같은 대상을 가리키는 별칭만 `answer_aliases`에 추가한다.
-   띄어쓰기, 외래어 표기, 약칭 등을 어디까지 허용할지 게임의 기존 채점
    정책을 확인한다.
-   동의어를 무분별하게 추가하지 않는다.
-   질문에서 요구하는 답의 범주와 채점 데이터가 일치하는지 확인한다.
-   정답 표기 변경이 필요한 경우에는 원본 정답을 덮어쓰지 않고 변경
    사유와 승인 상태를 기록한다.

# 11. AI 도구와 역할 분담

이 프로젝트는 특정 AI 하나에 종속될 필요가 없다. Claude Code, ChatGPT,
다른 LLM, 스크립트, 외부 팩트체크 도구를 조합할 수 있다.

중요한 것은 도구의 이름보다 역할과 검증 구조다.

## 11.1 ChatGPT가 맡을 수 있는 역할

ChatGPT를 작업에 참여시키는 경우 다음 역할에 활용할 수 있다.

### 기획·설계

-   표준화 지침과 데이터 스키마 검토
-   문항 유형 분류 체계 설계
-   프롬프트와 검수 기준 설계
-   파일럿 문항의 문체·힌트 기준 조정

### 콘텐츠 리빌딩

-   원본 문항에서 핵심 사실과 정답 단서 추출
-   Story 스타일 질문 재작성
-   Decisive 힌트 작성
-   기존 해설과 새 질문의 일치 여부 검토
-   여러 재작성안의 자연스러움 비교

### 품질 검수

-   질문의 논리적 모호성 및 복수 정답 가능성 검토
-   문제와 힌트의 중복 검토
-   정답 노출 여부 검토
-   사실 검증이 필요한 주장 표시
-   배치별 문체 일관성 검토

### 결과 분석

-   배치별 통과율과 오류 유형 분석
-   반복적으로 발생하는 품질 문제 파악
-   지침과 프롬프트 개선안 제시
-   샘플 데이터의 수정 전후 비교

### 한계와 주의사항

-   LLM의 기억만으로 역사적·과학적 사실을 확정해서는 안 된다.
-   출처가 필요한 주장은 신뢰할 수 있는 원자료로 확인해야 한다.
-   생성 모델이 작성한 결과를 같은 모델이 검수하는 것만으로 독립 검증이
    되지는 않는다.
-   대량 파일 처리와 데이터 변경은 실행 환경 및 도구의 실제 접근 권한에
    따라 달라진다.
-   ChatGPT가 반드시 프로젝트에 참여해야 하는 것은 아니다. Claude Code나
    다른 도구만으로도 동일한 절차를 구현할 수 있다.

## 11.2 Claude Code가 주도하는 경우의 권장 역할

Claude Code는 프로젝트 저장소와 파일을 직접 다루는 오케스트레이션·구현
환경으로 활용할 수 있다.

권장 업무:

1.  원본 데이터와 게임 코드 구조 조사
2.  데이터 스키마와 백업 정책 설계
3.  문항 유형 분류 및 배치 생성 스크립트 작성
4.  LLM 호출을 통한 질문·힌트 초안 생성
5.  결과를 구조화된 파일로 저장
6.  규칙 기반 자동 검증 수행
7.  검수 대상만 별도 큐로 분리
8.  수정·승인·배포 이력 관리
9.  최종 데이터 내보내기 및 리포트 생성

Claude Code가 모든 문항을 직접 작성하더라도 다음 원칙은 동일하게
적용한다.

-   생성과 검수를 별도 단계로 나눈다.
-   생성 결과를 즉시 원본 데이터에 반영하지 않는다.
-   자동 검증으로 확인할 수 있는 항목은 코드로 검사한다.
-   사실 확인이 필요한 문항은 출처 기반 검증 또는 사람의 검토를 거친다.
-   보류 문항을 억지로 통과시키지 않는다.

# 12. Claude Code에 권장하는 구현 아키텍처

아래는 Claude Code가 프로젝트를 조사한 뒤 구체화할 수 있는 권장
설계안이다. 현재 원본 파일 포맷이나 게임의 기술 스택을 확인하지 않은
상태이므로, 실제 구현 전에 저장소를 조사해야 한다.

## 12.1 파이프라인 개요

``` text
원본 데이터
    |
    v
데이터 로더 및 스키마 검사
    |
    v
원본 백업 및 ID 확인
    |
    v
문항 유형 분류
    |
    v
핵심 사실 / 정답 단서 추출
    |
    v
질문 리빌딩 (Story)
    |
    v
힌트 리빌딩 (Decisive)
    |
    v
자동 검증
    |
    +---- 실패 ----> 수정 큐 / 보류 큐
    |
    v
독립 품질 검수
    |
    +---- 수정 필요 ----> 재작성
    |
    v
사실 검증 완료 및 승인
    |
    v
최종 데이터 생성
    |
    v
게임 데이터 배포
```

## 12.2 권장 모듈

프로젝트 구조는 실제 저장소에 맞춰 정하되, 기능적으로 다음 모듈을
분리하는 것이 좋다.

  모듈                 책임
  -------------------- -----------------------------------
  `ingestion`          원본 파일 읽기, 인코딩·필드 검사
  `normalization`      필드 정규화, ID·공백·문자열 처리
  `classification`     문항 유형 분류
  `fact_extraction`    정답과 핵심 사실 추출
  `question_rebuild`   Story 질문 생성
  `hint_rebuild`       Decisive 힌트 생성
  `fact_check`         출처 확인 및 사실 검증 상태 관리
  `quality_review`     문체·논리·정답 유일성 검수
  `validation`         스키마·필수 필드·규칙 기반 검사
  `batch_manager`      배치 실행, 재시도, 진행 상태 관리
  `export`             승인 문항의 게임용 데이터 출력
  `reporting`          배치별 통계와 오류 보고서 생성

## 12.3 생성과 검수의 분리

최소한 다음 두 가지 역할을 별도로 운영한다.

**생성 단계** - 원본을 분석한다. - 핵심 사실을 추출한다. - Story 질문과
Decisive 힌트를 작성한다. - 출처와 불확실한 사실을 표시한다.

**검수 단계** - 생성된 질문을 원본과 독립적으로 대조한다. - 사실과
정답을 확인한다. - 질문만 읽고 정답이 특정되는지 검토한다. - 다른 정답이
가능한지 검토한다. - 힌트가 중복되거나 정답을 노출하는지 확인한다. -
통과·수정·보류를 판정한다.

가능하다면 검수 모델에는 생성 모델의 내부 추론이나 작성 의도를 전달하지
말고, 원본 자료와 생성 결과, 검수 기준을 제공한다. 검수자가 결과를
독립적으로 판단할 수 있어야 한다.

## 12.4 규칙 기반 자동 검증

LLM에게 맡길 필요가 없는 검사는 코드로 수행한다.

예시:

-   문항 ID 중복 여부
-   원본 문항 수와 결과 문항 수 비교
-   필수 필드 누락
-   빈 질문·힌트·정답
-   JSON 파싱 오류
-   허용되지 않은 상태값
-   원본 정답 필드의 임의 변경 여부
-   중복된 결과 레코드
-   배치 간 ID 중복
-   배포 대상 중 검수 미통과 문항 존재 여부

정규식이나 문자열 비교만으로 자연어의 사실 정확성, 정답 유일성, 힌트의
결정성을 완전히 판단할 수는 없다. 이런 항목은 LLM 보조 검수와 사람의
검토를 병행한다.

## 12.5 실패와 재시도 정책

-   LLM 호출 실패는 문항 상태와 구분해 기록한다.
-   구조화 출력 파싱 실패는 제한된 횟수만 재시도한다.
-   재시도 시 원본 데이터가 중복 생성되지 않도록 ID 기반으로 멱등성을
    보장한다.
-   사실이 불확실한 문항은 무리하게 재생성하지 않고 보류한다.
-   검수에서 탈락한 문항은 탈락 이유를 보존하고 해당 이유를 해결하는
    방향으로 재작성한다.
-   사람의 승인 없이 `hold`나 `revision_required`를 `passed`로 바꾸지
    않는다.

# 13. 품질 지표와 완료 기준

단순히 몇 개를 생성했는지만으로 프로젝트 진행 상황을 판단하지 않는다.

배치별로 다음 지표를 기록한다.

  지표               의미
  ------------------ ----------------------------------------
  처리 수            생성 파이프라인이 처리한 문항 수
  생성 성공률        구조화된 초안 생성 성공 비율
  사실 검증 완료율   필요한 사실 확인이 끝난 비율
  1차 검수 통과율    첫 검수에서 통과한 비율
  재작업률           수정 후 다시 검수해야 하는 비율
  보류율             사실·정답 문제로 확정하지 못한 비율
  정답 불일치율      원본 정답과 수정 결과의 불일치 비율
  힌트 중복률        문제와 힌트가 실질적으로 중복되는 비율
  복수 정답 발견률   질문에서 다른 답도 성립하는 비율
  배포 가능 수       모든 필수 검증을 통과한 문항 수

완료 기준은 단순한 생성 성공이 아니다.

**배포 가능 문항 = 필수 필드 정상 + 사실 검증 완료 + 질문 품질 통과 +
힌트 품질 통과 + 정답·채점 기준 확인**

# 14. 특수 사례와 주의사항

## 14.1 기존 문항에 사실 오류가 있는 경우

-   기존 정답을 임의로 수정하지 않는다.
-   오류가 있는 문장과 근거를 기록한다.
-   신뢰할 수 있는 출처로 확인한다.
-   정답 자체의 수정이 필요하면 별도 승인 대상으로 분류한다.
-   수정할 수 없거나 근거가 불충분하면 보류한다.

## 14.2 역사적 논쟁이나 귀속 문제가 있는 경우

"최초로 발명했다", "처음 발견했다" 등의 표현은 특히 주의한다. 여러
인물의 기여가 얽혀 있거나 역사적 해석이 갈리는 경우, 단정적인 문장을
피하고 검증 가능한 범위로 질문을 재구성한다.

## 14.3 이모지형 문항

이모지 배열과 순서를 보존한다. 일반적인 Story 질문으로 억지 변환하지
말고 별도 유형으로 관리한다.

## 14.4 숫자·계산형 문항

-   필요한 단위와 정밀도를 명시한다.
-   계산을 독립적으로 다시 수행한다.
-   반올림 조건이 있으면 질문에 표시한다.
-   답의 동등한 표기나 수학적 표현을 확인한다.
-   계산형 문항을 불필요하게 긴 이야기형으로 만들지 않는다.

## 14.5 해설 필드

해설은 질문과 힌트의 역할을 대신하지 않는다. 기존 해설이 정확하면
유지하고, 질문을 재구성하면서 설명이 어긋났을 때만 수정한다. 게임에서
해설을 언제 보여주는지 기존 UI 동작도 확인한다.

## Claude Code 작업 요청

이 문서는 퀴즈 표준화 v2.0의 콘텐츠 방향과 품질 기준을 정의한다.

현재 요청은 곧바로 7,880개 문항을 수정하는 것이 아니라, **기존
프로젝트와 데이터 구조를 조사하고 이 기준을 실제로 구현할 수 있는 작업
계획 및 기술 설계를 제안하는 것**이다.

### 확정된 콘텐츠 기준

-   문제 문체: Story
-   힌트 강도: Decisive
-   재작성 범위: Rebuild
-   기존 정답과 검증된 핵심 사실은 보존한다.
-   기존 질문은 사실 추출을 위한 참고자료로 취급한다.
-   질문과 힌트는 전면 재설계할 수 있다.
-   문제는 자연스러운 해설형 흐름을 갖고 마지막에 명확한 질문을 둔다.
-   힌트는 문제에 없는 새로운 결정적 단서를 제공하며 정답을 직접
    노출하지 않는다.
-   문제 공개 25초 후 힌트가 공개되는 게임 조건을 고려한다.
-   사실 검증과 문항 품질 검수를 분리한다.
-   검수되지 않은 문항은 자동으로 배포하지 않는다.

### 먼저 수행할 조사

1.  저장소의 디렉터리와 기술 스택을 조사한다.
2.  원본 퀴즈 데이터 파일의 위치와 포맷을 확인한다.
3.  실제 문항 수가 7,880개인지 확인한다.
4.  질문·정답·힌트·해설 필드와 누락·중복·인코딩 문제를 조사한다.
5.  게임에서 문항과 힌트가 로드되고 표시되는 방식을 확인한다.
6.  정답 채점, 별칭, 띄어쓰기, 오탈자 처리 방식을 확인한다.
7.  기존 데이터나 코드에 영향을 주지 않는 백업·버전 관리 방법을
    제안한다.

### 설계안에 포함할 내용

1.  현재 시스템 및 데이터 구조 분석
2.  권장 데이터 스키마와 마이그레이션 계획
3.  문항 유형 분류 방식
4.  원본 사실 추출 방식
5.  Story 질문 생성 프롬프트 설계
6.  Decisive 힌트 생성 프롬프트 설계
7.  생성 단계와 독립 검수 단계의 분리 방법
8.  LLM 및 외부 자료를 이용한 사실 검증 전략
9.  코드로 자동화할 수 있는 검증 규칙
10. 배치 처리, 재시도, 실패·보류 관리
11. 50개 파일럿 운영 계획
12. 100개 단위 정규 처리 계획
13. 진행 상황과 품질 지표
14. 게임 데이터로 최종 내보내는 방식
15. 비용·속도·품질 간의 트레이드오프

### 제안해야 할 실행 계획

우선 파일럿 50개를 대상으로 한다.

-   유형별로 다양한 문항을 선정한다.
-   원본을 보존하고 별도 결과 파일에 초안을 생성한다.
-   Story 질문과 Decisive 힌트를 작성한다.
-   사실 검증과 품질 검수를 분리한다.
-   통과·수정·보류 사유를 기록한다.
-   결과를 사람이 검토할 수 있는 리포트로 제공한다.
-   파일럿 결과에 따라 프롬프트와 검수 규칙을 개선한다.

파일럿이 승인되기 전에는 전체 7,880개에 대한 대량 수정이나 원본
덮어쓰기를 실행하지 않는다.

### 작업 방식에 대한 요구

-   먼저 조사 결과와 설계안을 제시하고 승인을 기다린다.
-   현재 프로젝트의 실제 구조를 확인하지 않은 채 파일 경로나 기술 스택을
    가정하지 않는다.
-   구현이 필요한 경우 변경 범위, 위험, 백업, 롤백 계획을 먼저 설명한다.
-   생성 결과와 검수 결과를 분리해서 보존한다.
-   사실이 불확실한 문항을 임의로 완성하지 않는다.
-   자동 검증과 사람의 판단이 필요한 검증을 구분한다.
-   모든 작업은 재실행 가능하고 결과를 추적할 수 있어야 한다.

**이번 단계의 산출물은 코드 변경이 아니라, 저장소 조사 보고서·데이터
구조 분석·권장 아키텍처·단계별 구현 계획·파일럿 계획이다.**

# 16. 최종 권장사항

이 프로젝트에서 가장 중요한 위험은 생성량이 아니라 **대량 생성 과정에서
사실 오류, 어색한 문장, 힌트 중복이 누적되는 것**이다.

따라서 다음 원칙을 권장한다.

1.  원본을 절대 덮어쓰지 않는다.
2.  50개 파일럿으로 문체와 힌트 기준을 먼저 확정한다.
3.  생성과 검수를 분리한다.
4.  사실 검증은 출처 기반으로 진행한다.
5.  코드로 검사할 수 있는 항목은 자동화한다.
6.  모호하거나 불확실한 문항은 보류한다.
7.  통과한 문항만 게임에 배포한다.
8.  모든 결과와 수정 이력을 추적 가능하게 만든다.

ChatGPT를 콘텐츠 기획·리빌딩·검수·품질 분석에 활용할 수도 있고, Claude
Code가 파일 처리와 생성·검수 파이프라인을 주도하도록 설계할 수도 있다.
두 도구를 함께 사용할 수도 있지만 필수는 아니다.

**도구를 먼저 정하기보다, 원본 데이터 구조를 확인하고 품질 기준을
자동화할 수 있는 설계를 먼저 확정하는 것이 우선이다.**
