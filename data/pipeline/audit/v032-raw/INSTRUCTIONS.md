# V032 힌트 판정 기준 (모든 판정자 공통 — 이 파일이 기준 전체다)

너는 독립된 판정자다. DB 쓰기 · 파일 고치기 · 질문 고치기 금지. 판정만 한다. 결과는 JSON 파일로만 쓴다(지정 경로).
웹 확인 허용: 위키백과 API(curl, action=query&prop=extracts&explaintext=1) · WebFetch · WebSearch. 키가 필요한 API 금지. User-Agent 에 개인 정보(이메일 · 이름) 금지 — 'quiz-web-v032/1.0' 만.

## 0. 대상이 무엇인가
GEN(G027)이 **등급 3** 문항의 일반 힌트(general_hint, 한 줄)를 hint-v7 기준으로 다시 썼다(해설은 둘째 줄로 바꾼 것도 있다). 입력 JSON 한 조각에 문항 목록: id · q(질문) · ans(대표 정답) · variants(받아 주는 다른 표기) · hint(새 힌트) · ex(해설) · g(=3) · worth(알가치 1~3) · l1·l2·l3(분야) · flag(rand=무작위 · miss=blind 판정자가 못 맞힘 · gen=GEN 이 손질 · edge=경계 · weak=GEN 이 약하다고 적음 · dalri='~와 달리' · num=숫자 정답 · exfill=해설만 보려고 넣음) · oldHint · oldEx(전) · exChanged(해설이 바뀜). 힌트 판정은 모든 항목, **해설(explanation) 판정은 exChanged=true 인 항목만**(아니면 explanation.verdict="none").

## 1-1. 이 라운드의 추가 기준 (설계 결정)
- ★ 등급 3 은 **핵심 한 줄**이 기준이다(H13) — 알가치 2·3 은 연결 고리가 없어도 된다. "연결 고리가 없어 약하다" 는 fix 가 **아니다**: 정답을 아는 사람이 읽고 '아 그거!' 가 되면 ok. 알가치 1 은 핵심 + 연결 고리 하나.
- 새 category 셋(기존 core-miss · too-weak · h2 · h10 · h3 · fact · explain · readability · blank 에 더한다):
  - **h3-deixis** — 힌트가 질문을 봐야 아는 지시어('이 웹툰 · 이 걸그룹 · 이 감독 · 이 곡')를 쓴다. 작품 · 그룹 이름을 적어야 한다(정답 글자가 아니면).
  - **h10-near** — 비슷한 말과 안 가른다(핵심이 옆의 말에도 맞다) · 또는 옆 이름을 '~와 달리' 로 꺼내 가른다(H10 끝 예시: 그 이름을 친 사람이 오답이 된다).
  - **h7-digits** — 숫자 정답의 힌트가 자릿수 · 범위 꼴('세 자리 수') 이거나 **무엇의 수인지 + 왜 그 수인지** 가 없다.
- 숫자 정답(flag=num)은 H7: 무엇의 수 + 왜 그 수인지가 있으면 ok.
- fix 는 제안 문구를 **반드시** 낸다(전체 문구, 120자 안, 한 문장 '~다.' 체, 정답·변형 글자 금지).

## 2. verdict
힌트마다 하나:
- ok — 판정 문장 ① ② 둘 다 예, H2·H10·H3 위반 없음, 사실 확인됨.
- fix — 아래 category 중 하나에 걸린다. proposal 에 **힌트 전체 문구**(120자 안 · 한 문장 · "~다." 체)를 낸다. 사실 주장은 출처.
- unsure — 판정이 갈린다(이유를 reason 에).

★ "너무 세다 · 떠먹여 준다" 는 fix 사유가 아니다(D-311). 약해서(① '아 그거!' 가 안 돼서) 는 fix 가 된다. blind(힌트만 보고 맞히기)는 하지 않는다 — 이름은 판정자가 아는 만큼만 본다.
등급 5 / 알가치 1 은 H13 에 따라 핵심 + 연결 고리 하나다. 연결 고리가 없다고 fix 하지 않는다(핵심이 분명하면 ok) — 핵심이 약할 때만.

category (하나):
- core-miss — 힌트가 핵심이 아니다(둘째 줄 · 수치 · 연도 · 뒷이야기 · 조연 · 세부).
- too-weak — ① '아 그거!' 가 안 된다(정답을 아는 사람도 이 힌트로는 못 떠올린다. 질문·정답을 알고 읽어도 이 힌트가 정답을 가리키지 않는다).
- h2 — 정답 글자 · 정답을 이루는 낱말의 조각(한 글자 포함) · 우리말 옮김 · 번역 · 한자 뜻풀이 · 풀어 쓴 조각.
- h10 — 받아 주지 않는 다른 이름(우리말·원어·옛 이름·본명·약칭) · 정답이 아닌 이름(좁은 말·옆의 말)으로 유도 · 이름이 바뀐 대상의 옛 이름 유도.
- h3 — 질문의 조건·정의를 다른 말로 되풀이.
- fact — 사실이 틀렸거나 확인 못 함(단정어: 처음·최초·유일·가장·모두·연도).
- explain — 새 해설(ex)이 둘째 줄이 아니다 / 힌트와 같은 사실을 나눈다 / 정답을 알리는 문장이다 / 해설의 사실이 틀렸다. (ex 가 있을 때만; 힌트는 ok 여도 가능)
- readability — 읽기 어렵다(전문어를 안 풀었다 · 문장이 꼬였다).
- blank — 빈칸 '○' 글자 수가 들어 있다(H7 꼴).
- ok — 위반 없음.

## 3. facts
힌트(와 새 해설)의 사실 주장마다 하나씩: {claim, status: true|false|unverified, basis: web|knowledge, url}. 연도·직함·'처음·유일·가장·모두' 는 문서와 글자 단위로 대조. sources 가 있으면 먼저 그 url 을 열어 본다. 모든 항목에 최소 한 번은 웹 근거를 시도한다(위키 API). 모르면 unverified 라고 쓴다 — 추측으로 true 라고 쓰지 않는다.

## 4. 출력 (JSON 배열 한 파일, 조각에 있는 모든 id 가 한 번씩 — 빠뜨리지 않는다)
[{"id":"4810","verdict":"ok|fix|unsure","category":"…","proposal":null 또는 "새 힌트 전체","reason":"한 줄(한국어)","facts":[{"claim":"…","status":"true","basis":"web","url":"…"}],"explanation":{"verdict":"ok|fix|unsure|none","category":"…","proposal":null,"reason":"…"}}]
- explanation 필드: ex 가 비었으면 verdict:"none". ex 가 있으면 둘째 줄인가 · 사실 · 힌트와 겹침 0 · 정답 알림 문장 없음 · 120자 안팎을 본다. 해설 제안은 proposal 에 전체 문구.
- 제안 문구도 H2·H10 을 지키고 정답·변형 글자를 넣지 않는다.
- 판정 결과 JSON 만 쓴다. 다른 파일 쓰기·수정 금지.

## 5. 보정 (VERIFY 가 보정 표본 10 을 직접 판정해 맞춘 눈금)
- 질문이 이미 말한 정의·조건을 힌트가 다른 말로 한 번 되풀이했어도, **힌트에 새 정체·연결 고리가 함께 있으면 ok**(reason 에 '약한 H3' 만 적는다). 힌트가 질문을 되풀이할 뿐 새 사실이 없을 때만 category h3 로 fix.
- 줄거리 요약·대표작·위치·대표 쓰임으로 정답을 규정하면 ok (예: 무녀도 '무당 모화 … 물에 잠겨 죽는 이야기' · 소백산 '충북 단양과 경북 영주 사이 백두대간 … 희방폭포' · 스코티시 폴드 '귀가 납작 … 테일러 스위프트').
- 정답을 아는 사람이 읽어 '그거!' 가 안 되는 한국 대중문화·고전의 막연한 소개는 too-weak 후보 — 단 판정자가 지식으로만 약하다고 하지 말고, 힌트가 **정답이 아닌 다른 대상에도 똑같이 들어맞는지**를 본다(들어맞으면 too-weak, 안 맞으면 ok·약함 메모).
- '꼴' 힌트(같은 소리를 되풀이한 부사 · 두 글자 · 외자 …)가 **핵심 의미와 함께** 있으면 ok, 꼴만이면 fix(core-miss).
- 비슷한 말·옆의 말을 '~와 뜻이 비슷하지만' 으로 건네면 그 말을 친 사람이 오답이 된다 — 그 말이 정답 변형에 없으면 h10 후보(unsure 로 올려 reason 에 쓴다).
- 사실은 반드시 위키 원문(ko 먼저 · en)에서 **문장 단위로** 대조하고 facts[] 에 url 을 남긴다. 판정 근거에 '질문에 무엇이 적혀 있는가' 를 쓸 때는 입력의 q 에서 확인한 것만 쓴다.
- ok 가 너무 후하지 않게: 의심이 있으면 unsure + reason. fix 는 제안 문구를 반드시 낸다(전체 문구, 120자 안).
