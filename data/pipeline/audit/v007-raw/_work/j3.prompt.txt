## 일하는 방법
- 입력 순서대로 항목마다 한 객체를 만든다(RUBRIC.md 의 "결과 형식"). **빠뜨리거나 순서를 바꾸지 않는다.**
- **15건마다 저장**한다: `C:/work/quiz-web/data/pipeline/audit/v007-raw/j3.pNN.json` (NN = 01, 02, …) — 그 15건만 담은 JSON 배열(Write 도구). 이미 있는 pNN 파일은 건너뛰고 이어서 한다(중단 대비). 마지막 조각은 15건보다 짧을 수 있다.
- 항목 하나를 판정할 때: 질문·정답·변형·해설·힌트를 **원문 그대로 읽고**, 규칙 하나씩 점검한다. 판정 근거에 질문·힌트의 구절을 인용할 때는 입력에서 그대로 가져온다(교훈 A). 추측을 사실처럼 쓰지 않는다. `selfJudge` 와 `warn` 은 참고일 뿐이다.
- **난이도 재채점은 전부**(RUBRIC "난이도 읽기"): `score.dif` 와 `score.difWhy`("묻는 사실: … — 단계명") 를 모든 항목에 적는다. 재채점 결과 4~5 가 된 항목은 `webOpen` 이 false 였어도 facts 의 url 을 열어야 한다.
- `webOpen: TRUE` 항목: facts[] 의 url 을 **WebFetch 로 열어** 질문·해설의 주장마다 대조하고(같은 url 은 항목당 한 번), 힌트가 있으면 `hintSources` 도 열어 힌트 주장도 대조한다. 결과 facts 에 주장마다 `result`/`source` 를 적는다. 문서에서 못 찾으면 `unverified`(거짓 아님). **GEN 이 단 url 이 틀린 사실을 뒷받침하지 않는다**는 점에 주의 — 단서의 숫자·연도·직함·단정어를 문서와 글자 단위로 대조한다.
- 제안 문구(질문·힌트)는 쓰기 전에 `node C:/work/quiz-web/data/pipeline/audit/v007-raw/_work/chk.mjs hint|question <ref> "문구"` 로 기계 검사한다(막힘이 나오면 고친다 · 120자 · 줄바꿈 없음). 제안에 넣은 새 사실은 url 을 열어 확인하고 `facts` 에 `proposal:true` 로 적는다.
- WebSearch 는 **이 조각에서 8회 이내**(제안의 새 사실을 찾을 때만). WebFetch 가 주 수단이다. 429(사용량 한도)가 나면 멈추고 저장된 곳까지만 보고한다 — 모델을 바꾸지 않는다.
- 끝에 `node -e` 로 모든 pNN 파일을 합쳐 개수와 ref 순서가 `j3.refs.json` 과 같은지 대조하고, 합친 결과를 `C:/work/quiz-web/data/pipeline/audit/v007-raw/j3.out.json` 에 쓴다.
- reason 은 **한 줄**. fix/drop/unsure 는 어느 규칙인지 쓴다. ok 는 짧게(근거가 약한 ok 는 note 에 "애매" 를 적는다 — VERIFY 가 다시 읽는다).
