## 1단계 — 질문만 (파일 `data/pipeline/audit/v037-raw/in/pNN-A.json`: id · question_text 뿐)
정답·힌트·해설·등급을 아직 모른다. 모르는 채로 문항마다:
- `ask` — 질문이 **무엇을 묻는지 한 줄**. "어떤 종류의 것 + 핵심 단서" 꼴(예 "리버풀 기술자가 발명한 축구 장비"). 질문만 읽고도 이 한 줄을 못 쓰겠으면 ⓒ.
- `guess` — 정답 추측(짧은 답 하나). 모르면 "?". 못 맞히는 것은 흠이 아니다 — 무엇을 묻는지 모르는 것이 흠이다.
- `read` — a / b / c (19 §8-1 "무슨 말이야 테스트": a 3초 안에 둘 다 안다 · b 두 번 읽어야 한다 · c 읽어도 모르겠다) + `read_why` 한 줄.
경계 예: a — "1889년 리버풀의 기술자 존 브로디가 발명한 축구 장비입니다. 공이 골문을 지났는지를 두고 벌어지던 다툼을 끝냈습니다. 무엇일까요?" / a — "한글을 만든 임금은?" 같은 짧고 자연스러운 질문. b — "금속이 전자를 내주고 비금속이 그것을 받아 서로 반대 전하를 띠면서 끌어당기는 결합으로, 소금이 대표적인 것은?"(문장은 하나뿐인데 주어 둘) / b — 지시어 "이 장치"가 멀리 있는 것. c — 첫 두 문장이 정답과 무관한 인물 소개라 무엇을 묻는지 끝까지 안 잡히는 것 / c — 쉼표로 정보 넷을 이은 비문학 지문 꼴.
- 결과를 `data/pipeline/audit/v037-raw/out/pNN-A.json` 에 저장한다 — JSON 배열, 입력 순서 그대로, 객체 `{"id","ask","guess","read","read_why"}`. 저장 뒤 **`node data/pipeline/audit/v037-raw/_work/unlock.mjs pNN`** 을 실행한다(저장 안 된 A 에는 B 가 열리지 않는다). **그 전에는 B 파일(in/pNN-B.json)도 targets.json 도 열지 않는다.**

## 2단계 — 같은 문항을 정답·힌트·해설·등급을 연 뒤 (`in/pNN-B.json`. 맨 뒤 `worth_stored` 는 아래 `worth_v` 를 매긴 다음에만 본다)
객체 키(전부 — 빠뜨리지 않는다) :
- `ask_ok` true/false — 1단계 `ask` 가 정답의 종류와 맞는가. false 면 읽기를 사실상 c 로 본다(`read_final` 에 적는다: a/b/c).
- `read_final` a/b/c — 정답을 안 뒤의 읽기 판정(1단계 read 를 올릴 수는 있어도 낮추지 않는다. 기준: ask_ok false → c).
- `subj` ok/dup + `subj_why` — S 주어·지시어: dup = ⑴ 같은 대상을 "이것·그·이 ○○"로 두 번 이상 다른 꼴로 가리킴 ⑵ 문장마다 주어가 바뀌어 지시어가 무엇을 받는지 안 잡힘 ⑶ 끝 수식절에 정답 아닌 주어가 낌("…로, 월성 발전소는 무거운 물을 쓰는 것은?") ⑷ 한 문장에 주어 둘. 경계 예: dup — "이 고을의 면은 … 그 바뀐 이름으로 시가 되었다가 …"(지시어 둘이 서로 다른 것을 받음) / ok — "한글을 만든 임금은 누구일까요?"(지시어 없음) · "…가 있습니다. 이 도시는?"(지시어 하나가 바로 앞 대상을 받음).
- `comp` ok/cramped + `comp_why` — C 축약: cramped = ⑴ 한 문장 70자 초과 ⑵ 쉼표 3개 이상으로 성격 다른 정보를 이음 ⑶ 연결 어미(고·며·지만·는데) 셋 이상 ⑷ 한 문장짜리 질문이 90자 초과. 어느 꼴인지 `comp_why` 에 적는다. 경계 예: cramped — 한 문장 92자 "…로, …인 것은?" / ok — 두 문장 각 40자 안의 자연스러운 질문. 길이는 직접 센다(공백 포함 글자 수).
- `fix_text` — read_final b/c · subj dup · comp cramped 중 하나라도면 **고친 질문 전문**, 아니면 null. 규칙: 전체 240자 안 · **문장마다 70자 안 · 2~4문장** · 묻는 문장이 끝 · 한정어 그대로 · 정답·변형·조각 누설 없음 · **해설의 정보를 끌어오지 않음**(질문에 이미 있는 사실만 풀어 쓴다) · 사실을 바꾸지 않음 · 첫 문장에 분야·정체 단서(19 §8-2 ⑨) · 정답이 아닌 주어는 문장으로 분리 · 낯선 용어는 괄호 한 구절로 풀되 정답을 드러내지 않음. 이미 자연스러운 질문은 건드리지 않는다(늘리라는 뜻이 아니다).
- `fix_len`(글자 수) · `fix_sentences`(문장 수) — fix_text 가 있을 때만(없으면 null).
- `hint_refit` yes/no + `hint_why` — fix_text 가 있을 때 힌트가 어긋나는가(힌트가 기대던 단서가 새 질문에서 빠짐 · 힌트가 새 질문 문구를 되풀이 H3 · 새 질문이 힌트 내용을 이미 말함). fix_text 없으면 no.
- `worth_v` 1/2/3 + `worth_why` — 19 §9-1 로 알가치를 **저장값을 보기 전에** 매긴다(한국의 보통 어른이 "알아 둬야지"를 느끼는가: 일반 상식·유래·일상 말 = 3 / 교과·전공·취미 세부 = 2 / 낯선 인물·작품 이름·숫자·연도 암기 = 1).
- `flags` — 배열. 눈에 띄는 것만 한 줄씩("variant_missing: …" · "fact_doubt: …" · "not_unique: …" · "hint_leak" 등). 웹 확인은 하지 않는다 — 의심만.
- `verdict` keep/fix + `verdict_why` — fix_text 가 있으면 fix.
저장: `data/pipeline/audit/v037-raw/out/pNN-B.json` — JSON 배열, 입력 순서 그대로, 객체마다 `"id"` + 위 키 전부(1단계 키는 다시 쓰지 않는다 — 합치는 건 설계 쪽 스크립트).

## 규칙
- **엄격함을 일정하게**: 의심스러우면 b/dup/cramped 쪽으로 기울이되, 이미 자연스럽고 짧은 질문까지 고치려 하지 않는다. fix 비율이 조각마다 들쭉날쭉해지지 않게 위 경계 예에 견준다.
- 한글 JSON 이스케이프(`\n` · 따옴표)를 깨지 않게 쓴다(Write 도구 사용 · 질문 안 큰따옴표는 이스케이프).
- DB·코드·문서·웹 금지. 마지막 답은 "건수 N · fix a · read b/c 각 · 파일 2개 저장" 한 줄만.
