[Q-01] 배포 플랫폼과 DB 최종 확정
──────────────────────────────────────────
- 배경: guide 18/44/45/46/48절이 서버 authoritative + 지속 연결 + 영속 DB를 요구한다.
  설계 담당 AI 제안(Render + Neon/Supabase)을 2026-09-03 기준으로 실제 확인한 결과,
  Fly.io는 무료 티어가 폐지되어 후보에서 탈락했고, Render의 무료 PostgreSQL은 생성 후 30일 만에
  만료되어 영속 DB로 쓸 수 없다는 사실이 확인되었다. 즉 "서버 무료 + DB 무료"는 서로 다른
  두 벤더를 조합해야 한다. 상세 수치는 3장 참조.
- 선택지:
  (A) Render Free(Node 단일 인스턴스, 정적 프론트도 같은 서버에서 서빙) + Neon Free PostgreSQL
      장점: 설계안 그대로. 표준 Node/TS라 테스트·로컬 개발·AI 인수인계가 가장 쉬움.
            WebSocket 공식 지원 확인됨. Neon은 비활성으로 프로젝트가 삭제/정지되지 않음.
      단점: 15분 무입력 시 슬립 → 콜드 스타트 약 1분 + 메모리 게임 상태 소실(Q-02).
            Neon 무료는 프로젝트당 0.5GB / 월 100 CU-시간 제한.
  (B) Render Free + Supabase Free PostgreSQL
      장점: 대시보드가 편하고 DB 용량 500MB, 부가 기능(Auth/Storage) 확장 여지.
      단점: "1주 비활성 시 프로젝트 일시정지" → 친구들이 한 달 안 모이면 DB가 멈추고
            수동 복구가 필요하다. 이 프로젝트의 사용 패턴(가끔 모여서 플레이)과 상성이 나쁨.
  (C) Cloudflare Workers + Durable Objects(SQLite) + D1
      장점: 콜드 스타트가 사실상 없음(수 ms). 슬립 개념 자체가 없음. "방 하나 = Durable Object
            하나"가 guide 18절이 요구하는 단일 스레드 원자적 처리 모델과 구조적으로 정확히 일치.
            WebSocket Hibernation으로 유휴 연결 비용 0. 무료 한도가 이 규모에 매우 여유로움.
      단점: 일반 Node 서버가 아니라서 학습·디버깅·로컬 재현 난도가 올라가고 벤더 락인이 생긴다.
            무료 플랜 CPU 10ms/호출 제한, D1 쓰기 10만 행/일 제한.
            "다른 AI가 clone해서 이어받는다"(61절)는 목표에서 진입장벽이 A보다 높다.
  (D) Oracle Cloud Always Free VM에 직접 호스팅
      장점: 상시 가동, 슬립 없음, 사양 여유(ARM), DB도 같은 VM에 설치 가능.
      단점: 신용카드 등록 필요(과금은 없다고 안내되나 확인 필요), 인스턴스 생성 가용성이
            지역별로 불안정, OS·보안·백업·HTTPS를 직접 운영해야 함. 관리 부담이 가장 큼.
- 권장안: (A). 이유는 세 가지다.
  첫째, guide의 최우선 4요소(50절)를 Node 단일 프로세스 모델이 가장 단순하게 만족한다.
  둘째, 55~72절의 문서·인수인계 요구를 고려할 때 표준 스택이 유리하다.
  셋째, 콜드 스타트는 Q-02의 대응으로 실사용 영향을 거의 없앨 수 있다.
  다만 (C)는 실시간 게임 관점에서 기술적으로는 (A)보다 우수한 면이 분명히 있으므로,
  건우가 학습·락인을 감수할 의향이 있다면 진지하게 고려할 가치가 있다. 임의로 정하지 않는다.
- 영향 범위: 높음. 서버 런타임 모델과 DB 접근 계층 전체가 달라진다. Phase 3 이후 교체는 사실상 재작성.
- 시급도: [즉시]

[Q-02] 콜드 스타트(슬립) 대응 방식
──────────────────────────────────────────
- 배경: Render 무료 웹 서비스는 15분간 인바운드 트래픽(HTTP 요청 또는 기존 연결로 들어오는
  WebSocket 메시지)이 없으면 슬립되고, 재기동에 약 1분이 걸린다. 중요한 함정은 두 가지다.
  (1) 서버가 클라이언트로 내보내는 메시지는 인바운드가 아니므로 슬립을 막지 못한다.
      즉 로비에서 아무도 채팅하지 않고 15분이 지나면, 접속자가 있어도 슬립될 수 있다.
  (2) 슬립은 프로세스 종료다. 메모리에 있던 방과 진행 중 게임 상태가 전부 사라진다.
      이는 guide 45/46/47절 요구를 정면으로 깨뜨린다.
  월 750 인스턴스-시간은 31일(744시간)을 덮으므로 "상시 가동" 자체는 한도 내에서 가능하다.
  (워크스페이스당 750시간이므로 무료 서비스는 사실상 1개만 상시 가동 가능)
- 선택지:
  (A) 접속자가 있을 때만 클라이언트가 주기적 heartbeat(예: 4분 간격)를 서버로 보낸다.
      아무도 없으면 슬립을 허용한다.
      장점: 실제 사용자 트래픽이므로 정책상 문제 없음. 방에 사람이 있는 동안은 절대 슬립되지 않아
            메모리 상태가 안전하다. 인스턴스-시간도 실제 사용량만큼만 쓴다.
      단점: 아무도 없다가 처음 들어오는 사람은 최대 1분 대기. → "서버를 깨우는 중" 화면으로 완화.
  (B) 외부 크론(GitHub Actions, cron-job.org 등)으로 10~14분마다 24시간 핑을 보내 상시 가동.
      장점: 첫 접속자도 즉시 진입.
      단점: 실사용자 없이 무료 리소스를 상시 점유하는 형태라 Render 정책상 권장되지 않는다
            (명시적 금지 여부는 확인 불가). 750시간을 거의 다 소진해 여유가 없어진다.
  (C) 대응하지 않고 감수한다. 첫 진입자가 1분 기다리고, 로비 방치 중 슬립되면 방이 사라진다.
      단점: 방이 사라지는 건 감수 가능한 수준이 아니라고 판단한다.
  (D) 유료 인스턴스(월 7달러 수준)로 전환.
      단점: "모든 비용은 무료" 전제 위반.
- 권장안: (A) + 첫 진입 시 "서버 준비 중" UI + 배포/재시작으로 인한 상태 소실에 대비해
  게임 진행 중 최소 스냅샷(현재 문제 인덱스, 점수, 경험 기록)을 DB에 즉시 반영.
  경험 기록과 점수는 어차피 DB에 남아야 하므로(48절) 이 부분은 추가 비용이 거의 없다.
- 영향 범위: 중간. 클라이언트 heartbeat와 서버 상태 스냅샷은 나중에도 추가 가능하지만,
  스냅샷 설계는 게임 상태 자료구조와 함께 잡는 편이 훨씬 싸다.
- 시급도: [즉시] (Q-01에서 A/B를 고르면 필수, C를 고르면 불필요)

- 배경: 37절이 "구현 UX를 검토하여 결정"이라고 명시한 항목이다.
  제약은 하나뿐이다 — 게임 중 채팅이 문제 변경마다 초기화되면 안 된다(36·37절).
- 선택지:
  (A) 완전 연속: 방에 들어온 순간부터 게임 종료까지 하나의 채팅 스트림.
      게임 시작/문제 전환/정답 공개는 시스템 메시지로 같은 스트림에 삽입.
      장점: 구현이 가장 단순하고, 대화 맥락이 끊기지 않는다. 재접속 복구도 한 벌만 다루면 된다.
      단점: 게임 시작 시 화면이 이전 잡담으로 차 있어 문제에 집중이 덜 될 수 있다.
  (B) 분리: 게임 시작 시 채팅 영역을 비우고 새 세션 시작. 로비 채팅은 별도 보관.
      장점: 게임 화면이 깨끗하다.
      단점: "게임 시작 직전의 대화"가 사라져 어색하다. 재접속 시 어느 스트림을 복구할지 규칙이 늘어난다.
  (C) 연속이되 게임 시작 지점에 구분선(시스템 메시지)만 삽입.
      장점: (A)의 단순함 + (B)의 시각적 구분을 모두 얻는다.
- 권장안: (C). 실질적으로 (A)이고 UI에서 "── 게임 시작 ──" 구분선을 넣는다.
- 영향 범위: 중간. 나중에 (A)↔(B) 전환은 채팅 저장 구조와 재접속 복구 로직을 건드린다.
- 시급도: [P2 전]

[Q-15] "나가기" 기능 유무와 연결 종료 시 슬롯 점유 정책
──────────────────────────────────────────
- 배경: 4절은 "누군가 나가서 자리가 생기면 다시 입장 가능"이라 하고, 34절은 연결이 끊긴
  플레이어의 복귀를 보장하라고 한다. 이 둘은 충돌 가능성이 있다. 연결 끊긴 사람이 슬롯을
  계속 점유하면 새 친구가 못 들어오고, 즉시 슬롯을 반환하면 복귀할 자리가 없어질 수 있다.
  또한 guide 어디에도 "명시적으로 방을 나가는" 기능이 기술되어 있지 않다.
- 선택지:
  (A) 명시적 "나가기" 버튼 제공. 나가기 = 슬롯 즉시 반환(복귀 시 새 참가자로 취급).
      연결 종료(비자발적) = 슬롯을 게임 종료 시점까지 유지.
      장점: 의도적 퇴장과 사고를 명확히 구분한다. 34절 복귀 보장이 확실해진다.
      단점: 게임 중 방이 만석이면 새 친구가 못 들어온다(하지만 이건 원래 규칙 범위 내).
  (B) 나가기 버튼 제공 + 연결 종료도 N분 후 슬롯 반환(예: 5분).
      장점: 완전히 이탈한 사람의 자리를 재활용할 수 있다.
      단점: N분 후 돌아온 사람이 만석이면 못 들어와 33/34절 취지가 약해진다.
  (C) 나가기 버튼 없음. 브라우저를 닫는 것만이 퇴장. 슬롯은 방 수명까지 유지.
      단점: 로비에서 "방을 떠나고 싶다"는 기본 동작이 불가능하다. 방장 이전(5절) 트리거도 애매해진다.
- 권장안: (A). 추가로 "게임 종료 후 로비로 돌아온 시점"에 연결이 끊긴 채로 남아 있는
  플레이어의 슬롯은 반환한다. 이렇게 하면 게임 중에는 복귀가 보장되고, 게임 사이에 정리된다.
- 영향 범위: 높음. 4절 인원 제한, 5절 방장 이전, 22절 스킵 분모, 34절 복귀가 모두 여기에 걸린다.
- 시급도: [P2 전] (늦어도 Phase 5 전)

[Q-16] 정답 문자열 정규화 세부 규칙 (유니코드 / 전각 / 자모)
──────────────────────────────────────────
- 배경: 16절은 "띄어쓰기 무시, 영문 대소문자 무시, 특수문자는 무시하지 않음, fuzzy 금지"까지만
  정한다. 실제 구현에서는 다음이 문제가 된다.
  (1) macOS/iOS 사파리는 한글을 NFD(자모 분리)로 보내는 경우가 있어, 눈에 같아 보여도
      바이트가 달라 오답 처리된다. 이건 게임을 망치는 수준의 버그다.
  (2) 전각 문자(Ａ, ！)와 반각 문자.
  (3) 탭·연속 공백·앞뒤 공백, 유니코드 공백(U+00A0 등).
  (4) 한글 자모만 입력한 경우.
- 선택지:
  (A) 최소 정규화: 유니코드 NFC 정규화 + 모든 공백류 제거 + 영문 대소문자 통일.
      그 외 문자는 손대지 않음(특수문자 유지 = 16절 준수).
  (B) (A) + 전각→반각 변환 추가.
  (C) 정규화 없이 원문 그대로 비교.
      → NFD 문제로 iPhone 사용자가 정답을 못 맞히는 사고가 확실히 발생. 채택 불가.
- 권장안: (B). NFC 정규화와 전각→반각은 "실제 문자열 차이"를 지우는 것이 아니라
  같은 글자의 다른 표현을 통일하는 것이므로 16절의 취지(A+B ≠ AB)를 위반하지 않는다고 판단한다.
  다만 이는 규칙 해석이 들어가므로 건우 확인을 요청한다.
- 영향 범위: 중간. 정답 판정의 핵심이라 Phase 3 시작 시 확정되어야 하고, 나중에 바꾸면
  기존 게임 결과의 재현성이 달라진다.
- 시급도: [P3 전]

[Q-17] 마지막 문제에서 정답이 나온 경우 5초 대기 여부
──────────────────────────────────────────
- 배경: 19절은 정답 처리 후 무조건 5초 대기라고 하고, 21절은 "마지막 문제라면 5초를 기다리지 않고

- 선택지:
  (A) 마지막 문제는 정답이든 시간 종료든 5초를 기다리지 않고 즉시 결과 화면.
      단점: 정답자와 정답이 화면에 뜨자마자 결과로 넘어가 "누가 마지막을 먹었는지" 확인할 틈이 없다.

      단점: 21절 명문 위반. 채택 불가.
- 권장안: (B). 21절이 5초 생략을 규정한 대상은 "아무도 못 맞히고 시간이 다 된" 재미없는 구간이고,
  정답이 나온 순간은 이 게임에서 가장 중요한 리액션 구간이라고 판단한다. 다만 이는 해석이므로
  건우 확인이 필요하다. 확인 전에는 구현하지 않는다.
- 영향 범위: 낮음(로직상). 그러나 게임 체감에는 직접 영향.

[Q-18] 채팅 길이 제한과 도배(rate limit) 정책
──────────────────────────────────────────
- 배경: guide에 언급이 없다. 그런데 54절이 정의한 핵심 재미가 "채팅창에 미친 듯이 답을 입력하는 것"
  이므로, 일반적인 채팅 rate limit(초당 1회 등)을 그대로 적용하면 게임성이 직접 훼손된다.
  반대로 아무 제한이 없으면 한 명이 초당 수십 개를 보내 서버와 다른 사람 화면을 마비시킬 수 있다.
- 선택지:
  (A) 길이 제한만(예: 100자). rate limit 없음.
      단점: 자동 스크립트나 키 반복으로 도배 가능. 친구들끼리라 악의적 사용은 낮다고 볼 수도 있다.
  (B) 길이 제한 + 관대한 rate limit (예: 3초에 10개, 초과분은 조용히 무시).
      장점: 정상적인 빠른 타이핑(초당 3개 수준)은 절대 막히지 않으면서 폭주만 차단한다.
  (C) 엄격한 rate limit (초당 1~2개).
      단점: 게임성 훼손. 채택 불가.
- 권장안: (B). 상한은 100자, 3초 이동 윈도 10개. 초과 시 "오답입니다" 같은 메시지 없이
  (15절 취지에 맞게) 본인에게만 조용히 억제 안내. 실측 후 수치 조정.
- 영향 범위: 낮음. 서버 설정값.
- 시급도: [P3 전]

[Q-28] "활성 플레이어"의 정의와 소인원 스킵 최소 투표 수
──────────────────────────────────────────
- 배경: 22절은 활성 플레이어의 80%를 기준으로 하고, 전원 동의가 되는 경우 한 명 적은 수를 쓴다고
  한다(10→8, 9→8, 8→7, 7→6). 이 규칙을 소인원에 그대로 적용하면 다음과 같이 무너진다.
    6명 → ceil(4.8)=5, 전원 아님 → 5표
    5명 → ceil(4.0)=4, 전원 아님 → 4표
    4명 → ceil(3.2)=4, 전원 → 3표
    3명 → ceil(2.4)=3, 전원 → 2표
    2명 → ceil(1.6)=2, 전원 → 1표   ← 1명만 투표해도 스킵. 문제.
    1명 → ceil(0.8)=1, 전원 → 0표   ← 0표로 스킵. 22절이 명시적으로 막으라고 한 상황.
  또한 "활성"의 정의도 필요하다. 연결 종료자를 제외하는 것은 22절에 명시되어 있으나,
  "해당 문제를 이미 경험해서 정답 판정에서 제외된 플레이어"를 분모에 포함할지는 미정이다.
- 선택지 (최소 투표 수):
  (A) 최소 2표를 하한으로 둔다. 활성 1명이면 스킵 투표 불가(방장 강제 스킵만 가능).
      → 2명=2표(전원), 3명=2표, 4명=3표, 5명=4표, ... 10명=8표
  (B) 최소 2표 + 3명 이하일 때는 전원 동의 요구.
      → 2명=2표, 3명=3표, 4명=3표, ...
      단점: 22절의 "전원 동의를 요구하게 되면 한 명 적은 수"라는 원칙을 소인원에서 뒤집는다.
  (C) 활성 3명 미만이면 스킵 투표 기능 자체를 비활성화(방장 강제 스킵으로 안내).
- 선택지 (활성 정의):
  (가) 활성 = 현재 연결되어 있고 게임에 참가 중인 플레이어. 경험 여부 무관.
  (나) 활성 = (가) 중에서 해당 문제를 미경험한 플레이어만.
- 권장안: (A) 하한 2표 + (가) 경험 여부 무관.
  이유: (나)를 택하면 경험자가 몇 명인지가 투표 수에서 역산되어 28절의 "타인은 경험 여부를 알 수

[Q-29] 연결 종료 판정 기준 (몇 초 후 비활성으로 간주)

- 배경: guide에 수치가 없다. 그런데 이 값은 22절 스킵 분모, 5절 방장 이전, 33절 게임 계속,

  (A) WebSocket 연결 끊김 즉시 "비활성"으로 표시하되, 슬롯과 점수는 유지(Q-15).

      장점: 스킵 분모가 정확해진다. 실시간 게임에 맞는다.
      단점: 순간적인 끊김에도 방장이 넘어간다. 다만 5절이 게임 중단 없이 이전하라고 하고,

- 권장안: (C). 스킵 분모와 활성 인원 표시는 연결 끊김 즉시 반영,

  스킵이 막히는 문제도 피한다.

[Q-31] 강제 종료된 게임에서 "다시 하기" 가능 여부
──────────────────────────────────────────
- 배경: 8절은 "게임 종료 후 같은 방에서 다시 플레이할 수 있다"고 하고, 25절은 강제 종료 시
  "당시까지의 점수를 기준으로 결과 화면 표시, 게임 종료"라고 한다. 강제 종료도 8절의

- 선택지:
  (A) 강제 종료도 정상 종료와 동일하게 결과 화면 → 다시 하기 가능.
      장점: 방장이 "이번 판 접고 다시 하자"라고 할 수 있는 자연스러운 흐름. 25절도 결과 화면을

  (B) 강제 종료는 다시 하기 불가, 로비로만 복귀.
      장점: FORCE_ENDED를 별도 상태로 둔 의미가 살아난다.

  화면 흐름은 GAME_RESULT와 동일하게 처리한다. 결과 화면에 "강제 종료됨"만 표시한다.
- 영향 범위: 낮음~중간. 상태 머신 설계에 영향.

[Q-32] 결과 화면 이후 로비 복귀 흐름

[Q-33] 실제 키보드 단축키 배정
──────────────────────────────────────────
- 배경: 24절이 "구현자가 적절한 단축키를 선정"하라고 위임했으나, 두 개의 강한 제약이 있다.
  (1) 브라우저 기본 단축키와 충돌 금지  (2) 일반 텍스트 입력을 방해하면 안 됨.
  이 게임은 "채팅 입력창에 포커스가 있는 상태가 기본"이므로, 일반 문자 키는 전부 쓸 수 없다.
  따라서 사실상 조합키 또는 기능키만 가능하다.
- 선택지 (제안안):
  (A) 조합키 중심
      Enter                : 메시지/답안 전송 (14절)
      Ctrl + Space (또는 F2): 스킵 투표 토글
      Ctrl + Shift + S     : 방장 강제 스킵 (확인창)
      Ctrl + Shift + E     : 방장 강제 종료 (확인창)
      Enter / Y            : 확인창 확인
      Esc / N              : 확인창 취소
      Esc                  : 입력창 포커스 해제 → 이 상태에서만 단일 문자 단축키 활성
      Tab / Shift+Tab      : 브라우저 기본 유지(접근성)
      주의: Ctrl+Shift+S 등이 일부 브라우저 확장과 충돌할 수 있음 → 실측 검증 필요.
  (B) 기능키 중심
      F2 = 스킵 투표, F3 = 강제 스킵, F4 = 강제 종료
      장점: 텍스트 입력과 절대 충돌하지 않는다.
      단점: 모바일에서는 의미가 없고(터치로 대체), F 키는 노트북에서 Fn 조합이 필요할 수 있다.
  (C) 두 방식 병행 지원(둘 다 동작).
- 권장안: (C) — 조합키와 F 키를 모두 받아들이고, 화면에는 (A)를 표기.
  확인창은 23절 요구대로 방향키/Enter/마우스/터치 모두 지원.
  실제 키 확정 전에 브라우저(Chrome/Edge/Safari)에서 충돌 실측을 하고 결과를 문서에 남긴다.
- 영향 범위: 낮음. 키 매핑은 설정 테이블로 분리하면 변경이 쉽다.
- 시급도: [나중] (Phase 7). 단 스킵 투표는 Phase 4에 나오므로 그때 임시 키 필요.

[Q-35] 경험자에 의한 정답 유출 (게임성 취약점)
──────────────────────────────────────────
- 배경: 이건 내가 규칙을 읽으며 발견한 구조적 문제다. 게임 규칙 변경 제안이 아니라

- 선택지:
  (A) 아무 조치도 하지 않는다. 규칙 그대로 두고 친구들 간의 매너에 맡긴다.

  (B) 경험자의 메시지가 현재 문제의 정답과 일치하면, 그 메시지만 다른 사람에게 보내지 않는다
      (본인에게는 표시). 다른 사람은 그 사람이 무언가 썼는지도 모른다.
      장점: 유출을 원천 차단. 28절의 "타인은 경험 여부를 알 수 없다"도 유지된다.
      단점: 15절("오답도 그냥 채팅으로 남는다")의 예외가 생긴다. 규칙 변경에 해당.
  (C) 경험자 화면의 입력창에 경고만 표시("정답을 적으면 다른 사람에게 보입니다").
      장점: 규칙 변경 없이 인지만 준다.
- 권장안: 판단하지 않고 건우에게 넘긴다. 다만 (A)로 두더라도 이 사실을 문서에 알려진 특성으로
  기록해 두는 것을 권한다. 나중에 "왜 이러냐"는 질문이 나올 때 근거가 된다.
  개인적으로는 (C)를 기본으로 두고, 실제로 문제가 되면 (B)를 건우 승인 후 도입하는 순서를 제안한다.
- 영향 범위: 중간. (B)는 채팅 브로드캐스트 경로에 개인별 필터가 필요한데,
  이 구조 자체는 Q-25 때문에 어차피 필요하다.
- 시급도: [P4 전] (인지는 지금, 결정은 나중에 해도 됨)

3-1. 제안된 방향이 guide 요구사항을 충족하는지 (18/44/45/46/47/48절 기준)

[18절 — 선착순 판정 및 race condition]  충족 (조건부)
  Node.js는 단일 스레드 이벤트 루프이므로, "정답 판정 → 상태 전환"을 하나의 동기 실행 블록
  안에서 처리하면 두 요청이 끼어들 수 없다. 즉 별도의 락 없이 원자성이 보장된다.
  조건: 판정 블록 안에 await(DB 조회 등)를 넣으면 그 지점에서 다른 이벤트가 끼어들어
  원자성이 깨진다. 따라서 반드시
    (1) 판정에 필요한 데이터(현재 문제의 정답, 참가자별 경험 여부)를 문제 시작 시점에
        메모리로 미리 로드해 두고,
    (2) 판정과 상태 전환은 동기 코드로만 수행하고,
    (3) DB 기록(점수, 경험, 통계)은 상태 전환이 끝난 뒤 비동기로 수행한다.
  이 설계 규칙은 문서에 명시적으로 못 박아야 한다. 나중에 누가 판정 함수 안에 await를 하나
  추가하는 순간 게임의 핵심 규칙이 조용히 깨지기 때문이다.
  또한 18절이 요구하는 "처리 순서 추적"은 서버 수신 시 단조 증가 시퀀스 번호를 부여해 충족한다.

[44절 — 서버 authoritative]  충족
  13개 항목 모두 서버 메모리의 게임 상태에서만 변경되고, 클라이언트는 이벤트 전송과 렌더링만
  담당한다. Socket.IO의 서버→클라 브로드캐스트로 상태를 전파한다.

[45절 — 실시간 동기화]  충족
  방 단위 브로드캐스트(Socket.IO room)로 8개 항목을 전파한다.
  "클라이언트가 30초 지났다고 자체 판단" 금지는, 클라이언트 타이머가 0에 도달해도
  아무 상태 전환도 하지 않고 서버 이벤트를 기다리게 구현하면 된다.

[46절 — 타이머 동기화]  충족 (구현 주의 필요)
  서버가 문제 시작 시 questionStartedAt / questionEndsAt(서버 epoch ms)을 함께 보낸다.
  클라이언트는 접속 시 왕복 지연을 측정해 서버-클라이언트 시계 오프셋을 추정하고,
  그 오프셋을 적용해 남은 시간을 렌더링한다. 백그라운드 복귀 시에는 재계산만 하면 되므로
  자동으로 재동기화된다. 실제 문제 종료는 서버 타이머가 단독으로 결정한다.
  주의: 서버 타이머를 setTimeout 하나에만 의존하면 이벤트 루프 지연에 따라 30초가 30.4초가 될 수
  있다. 정확도를 위해 짧은 주기 체크 + 종료 시각 비교 방식을 권한다("정확히 30초" 요구, 10절).

[47절 — 새로고침 / 재접속]  충족
  httpOnly 쿠키 세션으로 계정을 식별하고, 방의 참가자 레코드를 계정 ID 기준으로 유지한다.
  소켓이 새로 붙으면 기존 플레이어 레코드에 재연결한다. Q-06의 결정이 이 로직의 전제가 된다.

[48절 — 데이터 영속성]  충족
  계정/닉네임/경험 기록/게임 기록/점수/통계 원천은 PostgreSQL, 진행 중 게임 상태는 서버 메모리.
  48절이 이 조합을 명시적으로 허용한다.
  단 하나의 실질적 위험은 "서버 프로세스가 죽으면 진행 중 게임이 사라진다"는 점이다.
  이건 스택의 문제가 아니라 무료 티어(슬립/재배포)의 문제이며 Q-02에서 다룬다.

[결론] 제안된 방향(Node/TS 단일 인스턴스 + Socket.IO + React/Vite + PostgreSQL)은
guide의 모든 검증 대상 절을 충족한다. 단일 인스턴스 전제가 18절을 가장 싸게 만족시킨다는
설계 담당 AI의 판단에 동의한다. 다중 인스턴스로 가면 Redis pub/sub과 분산 락이 필요해지고
무료 범위를 벗어난다는 지적도 타당하다.
확장 대비로는, 방 단위 상태 접근을 하나의 인터페이스(예: RoomStore)로 감싸두면
나중에 Redis 어댑터를 끼우는 형태로 열어둘 수 있다. 지금 그 인터페이스만 두는 것은
52절의 "과도한 하드코딩 회피"와 "과복잡화 금지" 사이에서 적절한 수준이라고 본다.

Socket.IO vs 순수 ws에 대한 의견: Socket.IO를 권장한다. 자동 재연결, 방(room) 개념,
하트비트, 폴백이 기본 제공되어 34/45/47절 구현량이 크게 줄어든다. 오버헤드는 이 규모에서 무의미하다.


3-2. 무료 서비스 실지 확인 결과 (확인일: 2026-09-03)

[Render — Free Web Service]  ✔ 사용 가능

  · 슬립: 15분간 인바운드(HTTP 요청 또는 기존 연결의 수신 WebSocket 메시지)가 없으면 스핀다운.
  · 복구: 다음 HTTP 요청 또는 새 WebSocket 연결 시 재기동, 약 1분 소요. 그동안 로딩 페이지 표시.
  · 무료 인스턴스 시간: 워크스페이스당 월 750시간. 스핀다운 상태는 시간을 소모하지 않음.
    (31일 = 744시간이므로 이론상 1개 서비스는 상시 가동 가능)
  · RAM / CPU: 공식 무료 문서에 수치 미기재 → 확인 불가.
    (일반적으로 512MB / 0.1 CPU로 알려져 있으나 이는 추정이며 확인이 필요하다)
  · 아웃바운드 대역폭: 무료도 월 포함량에 계산되며 초과 시 결제 수단이 있으면 청구,
    없으면 서비스 중단. 정확한 포함 GB 수치는 문서에서 확인 불가.
  · 신용카드 필요 여부: 확인 불가 (무료 문서에 언급 없음).
  · 중요: 스핀다운은 프로세스 종료이므로 메모리에 있던 방/게임 상태가 전부 사라진다.

[Render — Free PostgreSQL]  ✘ 사용 불가 (영속 DB로 부적합)
  · 용량 1GB, 워크스페이스당 1개, 관리형 커넥션 풀링 미지원.

    48절의 장기 보존 요구를 만족할 수 없다. 이 사실이 설계 담당 AI의 제안(Render 또는 Fly)에서
    가장 중요하게 수정되어야 할 부분이다.

[Fly.io]  ✘ 신규 계정 무료 불가

[Neon — Free plan]  ✔ 사용 가능 (권장)

  · 네트워크 전송: 프로젝트당 월 5GB
  · 프로젝트 100개 / 프로젝트당 브랜치 10개
  · CU-시간 소진 시: 컴퓨트가 정지되고 기존 연결이 끊기며 새 연결 불가. 다음 청구 주기에 복구.

  · 비활성으로 인한 프로젝트 삭제/영구 정지 없음 → 이 프로젝트의 사용 패턴과 잘 맞는다.
  · ★ 주의사항: 서버가 커넥션 풀을 상시 열어두면 Neon이 스케일 투 제로에 들어가지 못해

3-3. 슬립(cold start)이 실시간 게임에 미치는 영향과 대응

영향은 두 층위로 나뉜다.

(1) 첫 접속 지연 — 체감 불편, 치명적이지 않음
    아무도 접속하지 않은 상태에서 친구가 초대 링크를 클릭하면 약 1분간 로딩 페이지를 본다.
    "서버를 깨우는 중입니다 (최대 1분)" 안내를 자체 UI로 제공하면 감내 가능한 수준이다.
    다만 Render의 로딩 페이지는 우리 앱 코드가 아직 안 떠 있는 상태라 커스터마이즈가
    불가능할 수 있다 → 확인 필요.

(2) 진행 중 상태 소실 — 치명적
    이쪽이 진짜 문제다. 슬립은 프로세스 종료이므로 방과 게임이 통째로 사라진다.
    사라지면 45/46/47절 요구가 무너지는 것을 넘어, 친구들이 게임 도중 방에서 튕겨 나간다.
    발생 조건은 "15분간 인바운드 없음"이다. 게임 중에는 채팅이 오가므로 위험이 낮지만,
    로비에서 친구를 기다리는 15분, 또는 문제를 보고 아무도 아무 말 안 하는 구간이 누적되면
    실제로 발생할 수 있다. 결정적으로 서버→클라 아웃바운드(타이머 갱신 등)는 슬립을 막지 못한다.

대응 방안 (Q-02에서 결정)
  a. 클라이언트 heartbeat: 소켓이 연결되어 있는 동안 4분마다 클라이언트가 서버로 ping을 보낸다.
     이것이 인바운드 WebSocket 메시지이므로 슬립이 방지된다. 접속자가 있는 동안은
     절대 슬립되지 않으므로 (2)가 원천 차단된다. 인스턴스 시간도 실제 사용량만 소모한다.
     → 가장 비용 대비 효과가 크다. 권장.
  b. 상태 스냅샷: 게임 진행 중 핵심 상태(현재 문제 인덱스, 점수, 경험 기록)를 DB에 즉시 반영해
     프로세스가 죽어도 최소한 점수와 경험은 남게 한다. 재배포 시에도 유효하다.
     완전 복구는 아니지만 "친구들의 기록이 날아가는" 최악은 막는다.
  c. 배포 시점 관리: 무료 단일 인스턴스는 무중단 배포가 불가능하다.
     게임 중 배포하면 그 방이 죽는다. → "플레이 중에는 배포하지 않는다"를 운영 규칙으로 문서화.
  d. Cloudflare Durable Objects(Q-01의 C)를 선택하면 (1)(2)(c)가 모두 사라진다.
     이것이 그 선택지의 가장 큰 실질 이점이다.


3-4. 더 나은 대안 제시

- Q-01의 (C) Cloudflare Workers + Durable Objects를 정식 대안으로 올린다.
  이 게임의 요구(방 단위 단일 스레드 권위 서버 + 지속 WebSocket + 무료 + 슬립 없음)와
  DO의 설계가 거의 일대일로 대응한다. 기술적 적합성만 보면 Render보다 낫다.
  Render를 권장안으로 둔 이유는 오직 "표준 Node 스택이 문서화·인수인계·테스트에서 유리하다"는
  55~72절 요구 때문이다. 최종 판단은 건우에게 맡긴다.
- Q-01의 (D) Oracle Cloud Always Free도 무료·상시 가동이라는 점에서 유효하지만,

6-1. 53절 Phase 1~7에 대한 총평

문제 A — Phase 5(실시간 안정성)의 일부는 "나중에 붙일 수 없다"
  Phase 5에 "동시 정답 race condition"과 "타이머 동기화"가 들어 있는데,
  이 둘은 기능이 아니라 아키텍처 성질이다. Phase 3에서 정답 판정을 아무렇게나 만들어 두고
  Phase 5에서 원자성을 "추가"하는 것은 사실상 재작성이다.
  → Phase 3에서 처음부터 "방 단위 직렬 처리 + 판정 블록 내 await 금지 + 서버 시각 기준 타이머"로
     구현해야 한다. Phase 5에서는 이것을 검증·보강하는 것으로 성격을 바꾸기를 제안한다.

문제 B — Phase 6(경험 시스템)은 Phase 3의 정답 판정에 직접 개입한다  ← 지시받은 검토 항목
  건우의 우려가 정확하다. 경험 시스템은 독립된 부가 기능이 아니라 다음 세 지점에 침투한다.
    (1) 정답 판정 경로 — 28·29절: 경험자의 메시지는 판정 대상에서 제외되어야 한다.
        이건 판정 함수의 입력 조건 자체가 바뀌는 것이다.
    (2) 문제 선정 경로 — 30절: 어떤 문제를 낼지가 참가자 경험 이력에 종속된다.
    (3) 브로드캐스트 경로 — 28절: 경험 알림은 본인에게만 가야 하므로,
        "모두에게 같은 페이로드를 보낸다"는 단순 구조로 만들어 두면 나중에 전부 뜯어야 한다.
  → Phase 3에서 다음 세 가지 "자리"만 미리 만들어 두기를 제안한다. 로직은 비워도 된다.
    · 판정 자격 게이트: canAnswer(player, question) 형태의 훅. Phase 3에서는 항상 true를 반환.
    · 문제 선정 인터페이스: selectNextQuestion(pool, players) 형태. Phase 3에서는 무작위.
    · 개인별 페이로드 분리: 브로드캐스트 시 플레이어별로 다른 필드를 붙일 수 있는 구조.
    이 세 가지를 미리 두는 비용은 작고(각각 함수 하나), 나중에 붙이는 비용은 크다.
    52절이 경계한 "과도한 하드코딩 회피"의 정당한 적용 사례라고 본다.
  → 추가로, 경험 기록의 DB 쓰기(EXP-01, Q-23)는 Phase 6까지 미루지 말고 Phase 3~4에 넣기를
    권한다. 기록만 먼저 쌓아두면, Phase 6에서 판정 제외·경험률 UI를 붙일 때
    실제 데이터로 검증할 수 있다. 반대로 Phase 6에 몰아넣으면 그때까지의 모든 게임이
    경험 기록 없이 지나가 테스트 데이터가 없다.

문제 C — 퀴즈 데이터 소스 미결정 상태에서 Phase 3을 어디까지 갈 수 있는가  ← 지시받은 검토 항목
  결론: 소스가 미정이어도 Phase 3은 100% 완료 가능하다. 단 한 가지 조건이 있다.
  "문제 데이터 구조(스키마)"만 확정되면 된다 (Q-03).
  근거:
    · Phase 3의 구성 요소(문제 표시 / 30초 타이머 / 채팅 / 정답 판정 / 선착순 / 점수 /
      정답 공개 / 다음 문제)는 문제가 어디서 왔는지에 전혀 의존하지 않는다.
    · 필요한 것은 "정답 배열을 가진 문제 객체"뿐이다.
    · 개발·테스트용으로 수동 작성 시드 30~50문제면 충분하고, 오히려 테스트에는
      정답에 특수문자·영문·복수 정답이 포함된 의도적 케이스가 있는 편이 낫다(70절).
  따라서 권장 순서는: Q-03의 "구조"만 먼저 확정 → 시드 50문제 수동 작성 → Phase 3 진행
  → 실제 소스는 Phase 5~6 사이에 결정. 이렇게 하면 데이터 소스 결정이 개발을 막지 않는다.
  주의: 시드 데이터는 반드시 최종 스키마와 동일한 형태로 작성해야 한다. 임시 형식으로 만들면
  나중에 마이그레이션이 필요해진다.

6-2. 조정 제안 (Phase 0 신설 + Phase 3/5/6 성격 조정)

  Phase 0 — 기반 (신설 제안)
    · 저장소 생성, 문서 골격(docs\ 12개 파일 스텁), .gitignore, .gitattributes
    · 모노레포 스캐폴딩 (server / client / shared)
    · 최소 동작: "접속하면 서버 시각을 실시간으로 받는" WebSocket Hello World
    · ★ 이 상태로 Render + Neon에 실제 배포를 한 번 완주한다.
    · 왜 지금 배포하나: 무료 티어의 제약(슬립, WebSocket 통과 여부, 환경 변수, 빌드)을
      Phase 5에서 발견하면 되돌리는 비용이 크다. Walking skeleton을 먼저 세워
      "로컬에서 되는데 배포하면 안 되는" 리스크를 초기에 제거한다.
    · 소요 예상: 짧음. 그러나 가치가 가장 크다.

  Phase 1 — 계정 / 방            (53절 원안 유지)
  Phase 2 — 로비                 (53절 원안 유지, 단 경험률 표시는 더미값 → Phase 6에서 실값)
  Phase 3 — 핵심 게임 루프       (53절 원안 + 아래 추가)
    추가: 방 단위 직렬 처리 구조, 서버 시각 기준 타이머, 판정 자격 게이트(빈 껍데기),
          문제 선정 인터페이스(무작위), 개인별 페이로드 분리 구조,
          경험 기록 DB 쓰기(Q-23 결정 반영)
  Phase 4 — 게임 시스템          (53절 원안 유지: 힌트/스킵/강제스킵/강제종료/결과/다시하기)
  Phase 5 — 실시간 안정성        (성격 조정: 신규 구현이 아니라 검증·보강)
    중간 참가, 연결 종료, 재접속, 상태 복구가 신규 구현.
    race condition과 타이머 동기화는 Phase 3 구조의 검증(테스트 작성).
  Phase 6 — 경험 시스템 완성     (기록은 Phase 3에서 이미 시작됨)
    판정 제외 규칙 활성화, 경험률 실값, 개인 알림, 경험 기반 문제 선정
  Phase 7 — UI/UX                (53절 원안 유지)

6-3. 각 Phase를 실제로 테스트하려면 무엇이 필요한가  ← 지시받은 검토 항목

  공통 준비물 (Phase 3 착수 전에 만들어 두는 것을 강하게 권한다)
    · 봇 클라이언트 스크립트 (scripts\bot.ts 형태)
      브라우저 창을 10개 띄우는 것은 현실적으로 불가능하다. Node에서 socket.io-client로
      가상 플레이어 N명을 접속시키고 임의 시각에 메시지를 보내게 하는 스크립트가 필요하다.
      이것 하나가 아래 테스트의 대부분을 가능하게 한다.
    · 시드 데이터 투입 스크립트 (scripts\seed.ts)
    · 단위 테스트 러너: Vitest 권장 (Vite와 같은 계열이라 설정이 간단)

  Phase별 필요 테스트
    Phase 1  계정/방
      · 회원가입/로그인 정상·실패 케이스
      · 닉네임 중복(Q-05 결정에 따라) 및 대소문자 구분
      · 10명 정원 초과 입장 거부 → 봇 11명 접속
      · 방장 이탈 → 권한 이전
      · 없는 방 링크 접근
    Phase 2  로비
      · 참가자 목록 실시간 동기화 (봇 입퇴장)
      · 설정값 경계 검증 (Q-10/Q-11 결정값의 최소·최대·초과)
      · 카운트다운 정상 진행 및 취소
    Phase 3  핵심 게임  ← 가장 중요
      · ★ 동시 정답 테스트: 봇 10명이 같은 순간에 동일 정답 전송 → 정답자가 정확히 1명인지.
        100회 이상 반복해서 단 한 번도 2명이 나오지 않아야 한다(18·49절).
        서버 처리 시퀀스 번호 로그로 순서를 검증한다.
      · ★ 타이머 종료 직전 정답: 29.9초 시점 정답 전송을 반복 → 서버 상태 기준 처리 확인
      · ★ 정답 직후 메시지: 정답 확정 후 도착한 메시지가 판정되지 않는지
      · ★ 결과 화면 입력이 다음 문제 정답으로 처리되지 않는지 (20절, 가장 놓치기 쉬운 함정)
      · 정답 판정 단위 테스트: 정상/오답/대소문자/띄어쓰기/특수문자(A+B vs AB)/복수 정답/
        NFC·NFD 한글/전각 (16·17절, Q-16)
      · 타이머 정확도: 30초 오차 측정
      · 10명 동시 접속 부하: 봇 10명이 초당 3개씩 채팅 → 지연·누락 측정
    Phase 4  게임 시스템
      · 힌트 노출 타이밍(정확히 10초 전) 및 힌트 문자열 규칙 (단위 테스트)
      · 스킵 임계값 계산 단위 테스트: 활성 1~10명 전 구간 (Q-28 결정값 표와 대조)
      · 투표/취소 반복, 투표 중 인원 변동 시 임계값 재계산
      · 스킵과 정답 동시 발생 (봇으로 같은 순간 전송, 49절)
      · 강제 스킵/강제 종료 확인창 조작(키보드·마우스·터치)
      · 마지막 문제 처리 (정답/시간종료/스킵 세 경우, Q-17·Q-27)
      · 다시 하기 후 점수 초기화 + 경험 기록 유지 확인
    Phase 5  실시간 안정성
      · 중간 참가: 문제 진행 중 봇 입장 → 남은 시간·힌트 상태가 정확히 복원되는지
      · 연결 종료: 봇 강제 종료 → 게임 계속, 점수 유지, 스킵 분모 변화
      · 재접속: 봇 재연결 → 점수·색상·경험 여부 유지, 중복 플레이어 미생성(47절)
      · 새로고침 반복 테스트 (브라우저에서 수동)
      · 서버 재시작 시 동작 확인 (Q-02 대응의 실효성 검증)
      · 백그라운드 탭 → 복귀 시 타이머 재동기화 (모바일 브라우저에서 반드시 실제 테스트)
    Phase 6  경험 시스템
      · 처음 보는 문제 / 이미 경험한 문제
      · 경험자의 메시지가 판정에서 제외되는지, 본인 알림만 표시되는지
      · 다른 플레이어에게 경험 정보가 새지 않는지 (네트워크 페이로드를 직접 검사)
      · 강제 종료 후 / 재게임 후 경험 기록 유지 (25·8절)
      · 중간 참가자의 경험 처리 (27절 세 가지 케이스 전부)
      · 연결 종료 중 지나간 문제의 경험 기록 (Q-24 결정에 따라)
      · 전원 경험 문제만 남은 상황 (Q-22) — 시드를 소량으로 만들어 재현
    Phase 7  UI/UX
      · 실기기 테스트: iPhone Safari, Android Chrome (배포 URL로)
      · 모바일 키보드가 올라온 상태에서 문제·타이머가 가려지지 않는지
      · 전송 후 키보드가 닫히지 않고 연속 입력이 되는지 (14절, iOS에서 특히 까다로움)
      · 단축키 충돌 실측 (Chrome/Edge/Safari)
      · 색상 10종 구분 가능성, 색약 시뮬레이션

  실제 사람 10명이 필요한 시점
    위 대부분은 봇으로 대체 가능하다. 진짜 사람이 필요한 것은
    Phase 7의 모바일 실기기 테스트와, 최종적으로 "재미있는가"를 확인하는 플레이테스트다.
    친구들을 부르는 것은 Phase 4 완료 시점(게임이 처음부터 끝까지 돌아가는 시점)이
    가장 효율적이라고 본다.

[8-3] 서버 재시작 시 진행 중 게임 소실 — 가장 큰 실질적 리스크
  무료 단일 인스턴스 구조의 본질적 약점이다. 슬립뿐 아니라 재배포, OOM, 플랫폼 재시작에도
  동일하게 발생한다. guide 45/46/47절은 이 상황을 상정하지 않았다.
  Q-02의 대응(heartbeat + 상태 스냅샷 + 배포 시점 관리)으로 실용적 수준까지 낮출 수 있으나,
  완전히 없애려면 Cloudflare Durable Objects(Q-01의 C)로 가거나 유료로 가야 한다.
  건우가 이 리스크의 존재를 알고 (A)를 선택하는 것과, 모르고 선택하는 것은 다르다고 보아
  명시적으로 기록한다.

[8-4] Neon 커넥션 풀과 CU-시간 소진
  3-2에 적었듯, 커넥션 풀을 상시 열어두면 Neon이 스케일 투 제로에 못 들어가
  월 100 CU-시간이 한 달을 못 버틸 수 있다. 설계 시점에 idle timeout을 반드시 넣어야 하고,
  이건 나중에 발견하면 "월말에 갑자기 DB가 멈추는" 형태로 나타난다.
  Neon 최소 CU 값은 확인하지 못했다(확인 불가). Q-01에서 (A)를 택하면 실제 계정에서 확인하겠다.

[8-6] 모바일 키보드 UX — 14절 요구와 iOS Safari의 현실
  14절은 "매번 입력창을 클릭해야 하는 구조는 피한다"를 요구한다.
  iOS Safari는 전송 후 포커스 유지가 까다롭고, 키보드가 올라오면 뷰포트가 줄어들어
  문제·타이머가 가려지기 쉽다. 이 게임은 빠른 연속 입력이 핵심(50절)이라
  모바일 UX가 실패하면 모바일 플레이어는 사실상 경쟁에서 배제된다.
  Phase 7에서 실기기 테스트 없이 완료 처리하면 안 되는 항목으로 표시해 둔다.
  14절 자신이 "모바일 브라우저 특성상 필요하면 자연스러운 터치 입력을 허용한다"고
  여지를 두었으므로 규칙 위반은 아니지만, 형평성 문제로 남는다.

[8-7] 한글 입력 조합(IME) 중 Enter 처리
  한글 IME는 조합 중에도 Enter 키 이벤트가 발생해, 조합을 확정하는 Enter가
  메시지 전송으로 오인되어 "훈민정" 같은 미완성 문자열이 전송되는 고전적 버그가 있다.
  선착순 게임에서 이건 치명적이다(0.1초 차이로 승패가 갈리는데 오타로 날아간다).
  대응은 조합 상태(compositionstart/end)를 추적해 조합 중 Enter를 무시하는 것이다.
  기술적 사항이므로 자체 판단으로 처리하되, Phase 3의 필수 테스트 항목으로 등록한다.
