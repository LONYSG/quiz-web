1. Cloudflare quick tunnel 검증 결과

1-1. 기본 조건 (공식 문서 확인일 2026-09-07)

  · 설치: winget install --id Cloudflare.cloudflared → 버전 2026.8.3 설치 완료
  · 기동: cloudflared tunnel --url http://localhost:3000
  · ★ 계정·도메인 불필요. 공식 문서가 "without adding a site to Cloudflare's DNS" 라고 명시.
    무료.
  · ★ WebSocket: **지원됨.** 실측으로 확인했다(1-3).
    공식 문서에 명시적 언급은 없으나, 미지원 프로토콜로 Server-Sent Events(SSE)만 명시되어 있다.
    우리는 SSE를 쓰지 않으므로 무관하다.
  · 동시 처리 제한: "Currently, this limit is 200 in-flight requests.
    If a Quick Tunnel hits this limit, the HTTP response will return a 429 status code."
    → 10명 규모에서는 전혀 무관하다. WebSocket은 연결 하나가 유지되는 방식이라
      in-flight 요청으로 계속 잡히지 않는다(추정. 실측에서 문제가 없었다).
  · 세션 지속 시간 제한: 공식 문서에 언급 없음. 확인 불가.
    실측에서는 수십 분간 유지되었으나 게임 한 판(최대 약 2시간)을 검증하지는 못했다.
  · 대역폭 제한: 문서에 언급 없음. 확인 불가.
  · ★ 이용 약관: 공식 문서 문구 —
    "Quick Tunnels are intended for testing and development only.
     For production use, create a remotely-managed tunnel."
    "We don't guarantee any SLA or uptime of TryCloudflare"
    → 친구들끼리 가끔 쓰는 용도이므로 "testing and development" 범위 안이라고 판단한다.
      상시 서비스로 키우려면 다른 방식이 필요하다. 이 사실을 docs/11-DEPLOY.md에 명시했다.

1-2. ★ 네트워크 단절 후 URL 유지 여부 — 부분 검증

  [먼저 밝힐 것] 지시받은 방식(Wi-Fi를 1~2분 끄고 다시 켜기)을 그대로 수행하지 못했다.
    · PC 전체 네트워크를 끊는 것은 건우의 작업 환경을 해치는 조치라 하지 않았다.
    · 대안으로 cloudflared만 방화벽으로 차단하려 했으나 **관리자 권한이 없어 불가능했다**
      (실제로 확인: IsInRole(Administrator) = False).
    · 따라서 "프로세스는 생존한 채 네트워크만 끊기는" 경우를 강제로 재현하지 못했다.

  [대신 검증한 것과 그 결과]

  (1) ★ 서버 프로세스가 터널 상실에 영향을 받는가 — 검증 완료, 영향 없음
      cloudflared를 강제 종료(taskkill)한 뒤 서버 헬스체크를 확인했다.
        종료 전  bootedAt=1788740534685  uptimeMs=45087
        종료 후  bootedAt=1788740534685  uptimeMs=113799
      ★ bootedAt이 완전히 동일하다. 즉 터널이 죽어도 서버 프로세스와 메모리는
        전혀 영향을 받지 않는다.
      ★ 이것이 PAUSED 설계의 실증이다. "네트워크 단절 = 통로만 끊김, 메모리는 살아 있음"이
        추측이 아니라 확인된 사실이 되었다.

  (2) 터널이 죽었을 때 기존 URL의 반응 — 검증 완료
      cloudflared 종료 직후: HTTP 502 (엣지는 호스트명을 알지만 오리진에 닿지 못함)
      그 뒤 다시 확인:       HTTP 530 (터널 등록 해제됨)

  (3) ★ cloudflared를 재시작하면 URL이 바뀌는가 — 검증 완료, **바뀐다**
        재시작 전: https://visitor-alexander-possibilities-tournament.trycloudflare.com
        재시작 후: https://rated-hopes-pretty-motor.trycloudflare.com
      새 URL은 200, 이전 URL은 530.

  (4) ★ URL이 언제 발급되는가 — 로그 분석
      cloudflared 로그의 순서가 결정적인 증거다.
        line 6  : "Requesting new quick Tunnel on trycloudflare.com..."   ← URL 요청
        line 9  : "|  https://rated-hopes-pretty-motor.trycloudflare.com  |"  ← URL 출력
        line 57 : "Registered tunnel connection connIndex=0 ..."          ← 연결 등록
      ★ URL은 **프로세스 시작 시 1회 발급**되고, 그 뒤에 개별 엣지 연결이 등록된다.
        즉 호스트명은 "터널(프로세스)"에 속하지 "개별 연결"에 속하지 않는다.

  [결론 — 추정과 확인의 구분]
    · **확인된 사실**: cloudflared를 재시작하면 URL이 바뀐다.
      터널이 죽어도 서버 프로세스와 메모리는 무사하다.
    · **추정**: 네트워크만 끊겼다 붙어서 엣지 연결이 재등록되는 경우에는 URL이 유지될 것이다.
      근거는 (4)의 발급 시점이다. 다만 **직접 확인하지 못했으므로 추정이다.**
    · docs/11-DEPLOY.md에 **두 경우를 모두 적었다.** 어느 쪽이든 건우가 대응할 수 있다.
      - URL 유지: 브라우저가 알아서 재연결 → 세션 쿠키도 살아 있음 → 방장이 "재개"만 누르면 끝
      - URL 변경: 새 링크 공유 → 친구들 재로그인 → 방 재입장 → 방장이 "재개"
    · Q-53으로 올린다. 건우가 실제로 Wi-Fi를 껐다 켜서 확인해 주면 문서를 확정할 수 있다.
      확인 절차도 문서에 적어 두었다.

1-3. 외부 접속 검증 (수치)

  터널 URL: https://rated-hopes-pretty-motor.trycloudflare.com (검증 시점 기준)

  (1) HTTPS 페이지 열림
      GET /healthz → http_status=200, total=1.41s (첫 요청, 연결 수립 포함)
      응답 본문: {"ok":true,"phase":"phase0","serverTime":...,"bootedAt":...,"dbActiveMs":...}

  (2) ★ WebSocket 연결과 유지 — 성공
      Socket.IO 핸드셰이크(polling) → http_status=200
      transports:['websocket'] 강제 연결 → **transport=websocket 확인**
      server.hello 수신 확인, time.ping/pong 6회 왕복 성공.
      ★ 이 프로젝트가 성립하는지 여부를 가르는 검증이었고 통과했다.

  (3) 집 네트워크 밖에서의 접속 — **미검증**
      휴대폰 LTE 등 외부망에서의 접속은 확인하지 못했다.
      다만 Cloudflare 엣지를 경유하는 구조상 접속 경로가 로컬 네트워크와 무관하고,
      실측에서 엣지 위치가 hkg09(홍콩) / icn05(서울)로 잡힌 것으로 보아
      외부에서도 동일하게 동작할 것으로 **추정**한다.
      ★ 건우가 휴대폰 LTE로 터널 URL에 접속해 보면 즉시 확인된다.

  (4) 오프셋 측정값 — 로컬과 외부 비교

      로컬 직결 (http://localhost:3000)
        transport=websocket
        RTT 1ms (6회 측정 모두 1ms)
        offset +4.5ms (전 측정 동일)

      터널 경유 (wss)
        transport=websocket
        RTT   188 / 204 / 179 / 149 / 257 / 133 ms
        offset -21 / +15 / -14.5 / +3.5 / +49.5 / ... ms

      ★ 해석이 중요하다.
        · 터널 경유에서 **같은 시점의 오프셋 추정이 70ms 폭으로 흔들렸다.**
          이는 편도 지연이 비대칭이기 때문이며, 평균이나 중앙값을 쓰면 이 흔들림이
          그대로 반영된다.
        · R003 2-4에서 "최근 5회 중 RTT가 가장 작은 측정의 offset을 채택"하기로 한 결정이
          **실제로 유의미하게 작동했다.** RTT 133ms 측정이 가장 정확한 추정이 된다.
        · 30초 타이머 관점에서 수십 ms 오차는 화면 표시에만 영향을 주고,
          정답 인정 경계는 서버의 endsAt이므로 게임 판정에는 영향이 없다(설계대로).

1-4. 대안 조사 (A-4)

  WebSocket이 정상 동작했으므로 대안을 채택할 필요가 없다.
  참고로 정리만 남긴다.
    · ngrok 무료: 계정 필요, 동시 터널 1개, 세션 시간 제한이 있는 것으로 알려져 있음(확인 불가)
    · localtunnel: 계정 불필요하나 안정성이 낮다고 알려져 있음(확인 불가)
    · 포트 포워딩: 지시대로 후보에서 제외

    T22 QUESTION_RESOLVED → PAUSED   remainingMs = nextAt − now
    T23 PAUSED → pausedFrom (방장 재개)  종료 시각 = now + remainingMs, epoch 증가 없음
    T13 PAUSED → GAME_RESULT (방장 강제 종료)
    T14 PAUSED → GAME_RESULT (30분 초과, abandoned)

  · 제거한 것
    기존 T05(COUNTDOWN → LOBBY, 활성 0명)와 T13(QUESTION_ACTIVE → GAME_RESULT, 활성 0명)을
    PAUSED 경로로 교체했다. graceUntil을 제거했다.

  · 타이머 설계 갱신
    tick 검사 항목에 "PAUSED 방은 건너뛴다"와 "PAUSED 30분 초과 → T14"를 추가했다.
    hostGrace와 방 삭제 타이머에 "PAUSED 중 정지" 조건을 붙였다.

  · 새 이벤트 3종
    C→S game.resume(방장) / S→C game.paused / S→C game.resumed
    ★ game.resumed에는 새 종료 시각을 반드시 담는다(클라이언트 타이머 재동기화).

  · 재접속 스냅샷에 paused 블록 추가
    { pausedFrom, remainingMs, pausedAt, abandonAt } | null

  · 접속 종료 표시 5초 유예를 T-LEAVE에 반영
    ★ "표시는 5초 후, 스킵 분모·활성 인원 판정은 즉시" 로 두 축을 분리했다.

  [★ 상태 머신 전체를 다시 검토해 발견한 것 — 지시받은 점검]

  (1) epoch와의 상호작용 — 문제 없음. 단 명시가 필요했다
      재개 시 epoch를 증가시키지 않으므로, PAUSED 이전에 보낸 메시지가 재개 후 늦게 도착하면
      epoch 검사를 통과한다.
      ★ 검토 결과: 그래도 잘못된 정답 인정은 일어나지 않는다.
        "수신 시각 ≤ endsAt" 조건과 resolved 플래그가 남아 있기 때문이다.
        다만 재개 직후 몇 초간은 "멈추기 전에 보낸 메시지"가 정답 처리될 수 있다.
        이는 그 사람이 멈추기 전에 이미 답을 알고 보낸 것이므로 규칙 위반이 아니라고 판단했다.
      → 04-PROTOCOL.md 동시 발생 시나리오에 이 케이스를 명시적으로 추가했다.

  (2) resolved 플래그 — 문제 없음
      PAUSED에 보존되고 재개 시 그대로 복원된다. QUESTION_RESOLVED에서 멈췄다가 재개하면
      resolved=true 상태로 돌아와 5초 대기를 이어간다. 올바르다.

  (3) skipVotes — 문제 없음. 단 재개 시 임계값 재평가가 필요하다
      PAUSED 중 인원이 바뀔 수 있으므로(입장 허용), 재개 시점의 활성 인원으로
      임계값을 다시 계산해야 한다. 이미 도달해 있으면 재개 직후 스킵이 발동한다.
      → 04-PROTOCOL.md의 T23 부수 효과에 반영했다.

  (4) ★ hostGrace — 문제 발견, 수정함
      기존 설계대로면 방장이 끊긴 뒤 30초가 지나면 방장이 이전된다.
      그런데 활성 0명이면 **이전할 대상이 없다.** 타이머만 만료되고 아무 일도 일어나지 않거나,
      구현에 따라서는 오류가 난다.
      → **활성 0명 동안에는 hostGrace 타이머를 정지한다.** 활성 1명 이상이 생긴 시점부터
        30초를 센다. 지시받은 규칙에 이미 포함되어 있던 내용이고, 전이표에 명시했다.

  (5) ★ 방 삭제 타이머 — 문제 발견, 지시대로 수정
      Q-14의 "활성 0명 10분이면 방 삭제"를 그대로 두면, PAUSED 30분 규칙보다 먼저 발동해
      **10분 뒤 방이 사라지고 일시정지가 무의미해진다.**
      → PAUSED 중에는 방 삭제 타이머를 정지하고, abandoned 된 뒤에 시작한다.
        이것을 빼먹으면 PAUSED 기능 전체가 무의미해지는 결정적 항목이다.

  (6) ★ LOBBY와 GAME_RESULT는 PAUSED로 가지 않는다 — 판단 필요했던 지점
      지시에 명시되어 있었지만 근거를 문서에 남겼다.
      두 상태에는 흐르는 타이머가 없으므로 멈출 것이 없다.
      기존 방 삭제 경로(활성 0명 10분)를 그대로 탄다.

  (7) 경험 기록 — 별도 처리 불필요 확인
      Q-47의 기준("정답 공개 순간 그 자리에 있던 사람")이 단일 기준이므로,
      PAUSED 중에는 정답 공개가 일어나지 않아 **자동으로 기록이 남지 않는다.**
      ★ 예외 처리 코드가 전혀 필요 없다. 이것이 Q-47의 단일 기준이 주는 이점이다.
      → 01-GAME-RULES.md와 migrations/0001_init.sql 주석 양쪽에 명시했다.

  (8) 힌트 재개 처리 — 지시대로 반영
      hintPushed=false이고 remainingMs ≤ 10000이면 재개 직후 tick이 push한다.
      hintPushed=true였으면 다시 push하지 않는다.
      재접속 스냅샷에도 같은 조건(남은 시간 10초 이하)을 적용한다.

  (9) 추가로 발견 — abandoned 시 game_questions.resolution
      PAUSED 30분 초과로 종료될 때 진행 중이던 문제를 어떻게 기록할지가 없었다.
      → 강제 종료와 동일하게 resolution='aborted'로 기록한다.
        스키마의 CHECK 제약과 주석에 "aborted = 정답을 공개하지 않고 중단됨
        (강제 종료 / abandoned / server_restart)" 으로 명시했다.

4-4. ★ 구현 중 발견한 실제 버그 2건

  (1) buildNormalizedIndex의 인덱스 매핑이 이모지에서 어긋났다 — 테스트가 잡았다

      정규화 결과 문자열(norm)과 원문 인덱스의 대응표(map)를 만들 때
      **코드 포인트 단위로 map 항목을 넣고 있었다.**
      이모지처럼 서로게이트 페어(UTF-16 코드 유닛 2개)인 문자에서
      norm에는 2개가 들어가는데 map에는 1개만 들어가 이후 인덱스가 전부 밀렸다.

      증상: '🍎 apple'에서 'apple'을 찾아 원문 구간으로 되돌리면 'pple'이 나왔다.

      수정: 출력 문자열의 **코드 유닛마다** map 항목을 하나씩 넣도록 고쳤다.

      ★ 이 함수는 Phase 6 마스킹의 기반이다. 여기서 잡지 못했다면
        "이모지가 섞인 채팅에서만 마스킹 위치가 한 글자씩 밀리는" 버그가 되었을 것이고,
        원인을 찾기 매우 어려웠을 것이다.

  (2) g 플래그가 붙은 정규식으로 .test()를 호출하고 있었다 — 코드 검토로 발견

      const ZERO_WIDTH_RE = /[​-‍﻿]/g;  ← g 플래그
      ...
      if (ZERO_WIDTH_RE.test(piece)) { ... }

      JavaScript에서 g 플래그가 붙은 정규식의 .test()는 lastIndex를 전진시킨다.
      같은 입력에 대해 호출마다 다른 결과가 나온다.

      수정: 판정용 비-global 정규식(ZERO_WIDTH_TEST_RE)을 분리했다.
      회귀 테스트 추가: "같은 함수를 여러 번 호출해도 결과가 같다"

6-1. 왜 바꿔야 했는가

  원래 설계는 GitHub Actions가 DB에 직접 적재하는 것이었다.
  DB가 건우 PC의 로컬 PostgreSQL로 바뀌면서 외부에서 접근할 수 없게 되었다.

6-2. 새 흐름

    GitHub Actions (클라우드)                      건우 PC (로컬)
    ─────────────────────────                      ──────────────
    1. 수집   OpenTDB → 원본 JSONL
    2. 필터   규칙 기반 사전 제거 (LLM 호출 없이 약 20% 제거)
    3. 가공   Gemini: 판정 + 번역 + 복수 정답 배열
    4. 검증   Gemini 역검증 + 규칙 검사 3종
    5. 커밋   결과 JSON을 저장소에 push
                     │
                     │  git pull
                     ▼
                                            6. 검수  JSON 직접 편집
                                            7. 적재  scripts/pipeline-load.mjs → DB

6-3. 디렉터리와 파일 형식

    data/pipeline/
      raw/opentdb/2026-09-07.jsonl              소스 원본 (append-only)
      processed/opentdb/2026-09-07-batch01.json 가공 + 역검증 결과
      approved/opentdb/...                      ★ 검수 승인. 적재 대상
      rejected/opentdb/...                      반려. 프롬프트 개선에 쓴다

  ★ 원본을 저장소에 넣을지에 대한 판단 (지시받은 항목)
    → 넣는다. OpenTDB 전량 4,500건이 JSONL로 약 1.5MB라 부담이 없다.
      원본을 버리면 가공 규칙이 바뀔 때마다 소스를 다시 긁어야 하는데
      레이트 리밋 때문에 전량 수확에 약 12분이 걸린다(R002 실측).
    ★ 단 위키데이터처럼 원본이 수십 MB를 넘는 소스가 생기면 그때 재검토한다.
      그 경우 원본은 로컬에만 두고 raw/를 .gitignore에 넣는다.
      이 조건을 pipeline/README.md에 명시했다.

  raw는 소스 무관 표준 포맷(RawQuestion)이다.
  ★ 새 소스를 붙이는 작업 = 이 포맷으로 변환하는 함수 하나를 추가하는 것.
    이후 단계(2~7)는 소스를 전혀 모른다.

6-4. 중복 적재 방지 (지시받은 항목)

  (sourceId, sourceRef)가 키다. 세 겹으로 막는다.
    1. 수집 단계   raw/에 이미 있는 sourceRef는 다시 받지 않는다
    2. 적재 스크립트  적재 전 DB 조회로 건너뛴다
    3. ★ DB 제약   questions에 부분 UNIQUE (source_id, source_ref)

6-5. ★ 검수 방식 재검토 (Q-45 재판단, 지시받은 항목)

  R002는 "Phase 0~4 동안 CSV 왕복, 이후 최소 관리 페이지"로 정했다.
  파일 기반으로 바뀐 지금 다시 판단하면 **JSON 직접 편집이 낫다.**

  근거
    · 파일 기반이라 어차피 JSON을 다루게 되었다. CSV로 바꿨다 되돌리는 변환 단계가
      순수한 추가 작업이 된다.
    · CSV는 왕복 과정에서 인코딩·따옴표 사고가 나기 쉽다.

    · ★ git diff로 무엇을 고쳤는지 볼 수 있다. CSV 왕복은 이 이력이 남지 않는다.
    · 검수는 review.status를 pending → approved/rejected로 바꾸고
      파일을 approved/ 또는 rejected/로 옮기는 것이다. 단순하다.

  → Q-45의 결정을 "CSV 왕복" 에서 "JSON 직접 편집" 으로 바꾼다.
    최소 관리 페이지 필요 여부는 Phase 4 완료 후 판단한다(Q-58로 남겼다).

  (1) 가공 결과가 git에 남아 diff로 검토할 수 있다.
      Gemini 프롬프트를 고쳤을 때 결과가 어떻게 달라졌는지 눈으로 볼 수 있다.
      DB 직접 적재였다면 이 비교가 불가능했다. 프롬프트 개선의 피드백 루프가 생긴다.
  (2) CC BY-SA share-alike 의무(Q-41)가 자연스럽게 충족된다.
      파생 데이터가 공개 저장소에 그대로 있으므로 별도 배포 절차가 필요 없다.
  (3) 되돌리기 쉽다. 잘못 가공된 배치를 git revert로 되돌릴 수 있다.
  (4) API 키가 로컬에 필요 없다. GEMINI_API_KEY는 GitHub Secrets에만 둔다.
      저장소가 Public이므로 키를 다루는 곳을 하나로 줄이는 것이 안전하다.

6-7. 이번 라운드에 만든 것 / 만들지 않은 것

[Q-53] cloudflared 네트워크 단절 시 URL 유지 여부
──────────────────────────────────────────
- 배경: 1-2 참조. 운영 절차가 여기에 달려 있다.
  URL이 유지되면 세션 쿠키까지 살아 있어 재로그인 없이 "재개"만 누르면 되고,
  바뀌면 새 링크를 뿌리고 전원이 다시 로그인해야 한다.
- 확인된 것: cloudflared를 재시작하면 URL이 바뀐다. 로그상 URL은 프로세스 시작 시
  1회 발급되고 그 뒤에 개별 연결이 등록된다.
- 추정: 연결만 재등록되는 경우에는 URL이 유지될 것이다.
- 확인하지 못한 이유: 방화벽 규칙에 관리자 권한이 필요했고, PC 전체 네트워크를 끊는 것은
  작업 환경을 해쳐 하지 않았다.
- 확인 방법: 터널을 띄운 상태에서 Wi-Fi를 1~2분 껐다 켠 뒤
  (1) 터미널 B가 살아 있는가 (2) 같은 URL로 접속되는가 (3) WebSocket이 재연결되는가
- 영향 범위: 낮음. docs/11-DEPLOY.md에 두 경우를 모두 적어 두어 어느 쪽이든 대응 가능하다.
