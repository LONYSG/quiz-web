1-1. GitHub Pages 적용 가능성 (A-1)

  ★ 결론: 설계 담당 AI의 판단이 맞다. 이 프로젝트에 GitHub Pages 단독 구성은 적용 불가다.
    다섯 개 근거를 하나씩 검증했고 전부 성립한다. 반박할 지점을 찾지 못했다.

  근거 1 — 정적 호스팅이라 Node 프로세스를 돌릴 수 없다
    성립한다. GitHub Pages는 정적 파일 배포 전용이고 서버 사이드 실행 환경이 없다.
    guide 44절이 서버 authoritative를 13개 항목에 대해 요구하는데, 실행 주체가 없으면
    이 요구를 담을 곳이 없다.

  근거 2 — 브라우저 → Supabase 직접 통신으로는 guide 18·44절을 만족할 수 없다
    성립한다. 그리고 이것이 가장 결정적이다.
    · guide 18절은 "서버가 먼저 정상적으로 수신하고 처리한 정답 제출"을 승자 기준으로 요구하고,
      "클라이언트의 시간을 기준으로 하지 않는다"를 명시한다.
      브라우저가 직접 DB에 쓰는 구조에서 선착순을 정하려면 결국 DB의 write 순서에 기대야 하는데,
      이건 각 클라이언트의 네트워크 지연이 그대로 승부에 반영되는 것이고
      무엇보다 클라이언트가 "정답이 맞다"고 판정한 뒤에 쓰기를 시도하게 된다.
    · 판정 로직이 클라이언트에 있으면 개발자 도구로 조작할 수 있다.
      guide 44절이 "게임의 중요한 판정은 클라이언트가 결정하지 않는다"를 명시적으로 금지한다.

  근거 3 — 문제 데이터를 브라우저가 직접 읽으면 정답이 노출된다
    성립한다. 그리고 이 프로젝트에서는 특히 치명적이다.
    · Supabase의 Row Level Security로 "정답 컬럼만 숨기기"는 컬럼 단위 권한으로 가능하지만,
      그러면 클라이언트가 정답을 알 수 없으니 판정을 못 한다. 판정을 하려면 정답이 필요하고,
      정답을 주면 노출된다. 이 모순을 RLS로 풀 수 없다.
    · 더 심각한 것은 힌트다. R003 3-1에서 명세하듯 힌트는 남은 10초 시점에 서버가 push해야 한다.
      클라이언트가 문제와 함께 힌트를 미리 받으면(또는 정답에서 힌트를 계산하면)
      개발자 도구로 30초 시점에 이미 힌트를 볼 수 있다. guide 11절이 무너진다.
    · 마스킹(Q-35/Q-42)도 서버에서 치환해야 한다는 것이 확정 사항이다.
      클라이언트가 정답을 알고 있으면 마스킹 자체가 무의미하다.

  근거 4 — Supabase Edge Functions는 stateless라 guide 18절의 원자적 상태 전환을 못 만족한다
    성립한다. 다만 정확히 말하면 "불가능"이 아니라 "가능하게 만드는 비용이 매우 크다"다.
    · Edge Function은 요청마다 새로 실행되므로 방의 게임 상태를 메모리에 들고 있을 수 없다.
      상태를 DB에 두고 매 요청이 읽고 쓰는 구조가 되는데, 그러면 두 개의 동시 정답 요청이
      같은 상태를 읽고 둘 다 "내가 첫 정답자"라고 판단하는 고전적 race condition이 생긴다.
    · 이를 막으려면 DB 수준의 원자적 조건부 갱신
      (예: UPDATE ... WHERE resolved = false 의 영향 행 수가 1인지 확인)이 필요하다.
      이건 기술적으로 가능하다. 즉 근거 4는 "원자성 확보가 불가능하다"까지 주장하면 과하다.
    · 그러나 30초 타이머, 5초 대기, 10초 힌트 push, heartbeat, 브로드캐스트를
      stateless 함수로 구성하려면 별도의 스케줄러와 실시간 채널을 조합해야 하고,
      guide 46절(서버 시각 기준 타이머 동기화)과 45절(서버가 상태를 결정)을
      만족시키는 데 드는 복잡도가 단일 Node 프로세스보다 몇 배 커진다.
    → 정정: "만족하지 못한다"가 아니라 "만족시킬 수는 있으나 비용이 훨씬 크고
      건우의 1순위 기준(유지보수 용이성)에 정면으로 어긋난다"가 정확한 서술이다.
      결론은 같다.

  근거 5 — 게임 로직을 PostgreSQL 함수로 구현하면 유지보수성이 나빠진다
    성립한다. 그리고 이 프로젝트에서는 특별히 더 나쁘다.
    · guide 70절이 요구하는 테스트(정답 판정, 상태 전이, 동시 정답 100회 반복 등)를
      PL/pgSQL로 작성·실행하는 것은 Vitest로 하는 것보다 훨씬 번거롭다.
    · guide 61절의 "다른 AI가 clone해서 이어받는다"는 시나리오에서, 게임 규칙이
      마이그레이션 SQL 안의 저장 프로시저에 흩어져 있으면 파악 비용이 급증한다.
    · R002에서 확정한 정규화·힌트·마스킹 순수 함수를 shared\에 두고 서버와 파이프라인이
      공유하는 설계가 불가능해진다(PL/pgSQL과 TypeScript로 두 번 구현해야 하고
      두 구현이 어긋나면 정답이 조용히 오답 처리된다).

  ★ A-1 추가 검토 — "GitHub Pages(프론트) + 별도 Node 서버(백엔드)" 조합

    이 조합은 기술적으로 가능하다. 하지만 실익이 없고 손해가 명확하다.

    실익 쪽
      · GitHub Pages는 무료이고 CDN이 붙어 정적 파일 전송이 빠르다.
      · Render Free의 아웃바운드 대역폭 소비를 줄인다.
      → 그런데 이 프로젝트의 정적 파일은 React 번들 하나이고 동시 사용자는 최대 10명이다.
        절약되는 대역폭이 무의미하다. R002 3-2에서 확인했듯 Render 무료 대역폭 포함량은
        문서에서 확인하지 못했으나(확인 불가), 10명 규모에서 문제가 될 여지는 없다.

    손해 쪽 — ★ 쿠키 세션이 cross-origin이 된다 (Q-07 확정 사항과 직접 충돌)
      Q-07에서 "httpOnly 쿠키 + 서버측 세션 레코드, 30일 슬라이딩"으로 확정했다.
      프론트가 lonysg.github.io 이고 서버가 xxx.onrender.com 이면 두 오리진이 완전히 다르다.
      이때 발생하는 것을 구체적으로 적는다.
      (a) 쿠키를 보내려면 SameSite=None + Secure 를 반드시 붙여야 한다.
          SameSite=Lax(기본값)로는 cross-site XHR/WebSocket 핸드셰이크에 쿠키가 붙지 않는다.
      (b) SameSite=None 쿠키는 서드파티 쿠키로 분류된다.
          ★ Safari의 ITP는 서드파티 쿠키를 기본 차단하고, Chrome도 서드파티 쿠키 제한을
            강화해 왔다. 즉 아이폰 사용자가 로그인을 유지하지 못할 가능성이 크다.
            guide 41·43절이 모바일 동시 플레이를 필수 요구사항으로 두고 있고,
            건우의 친구 중 아이폰 사용자가 있을 것이므로 이건 실제 장애가 된다.
            (Safari의 정확한 현재 동작은 버전에 따라 다르므로 확인 필요로 표시한다.
             다만 "확실히 동작한다"고 가정할 수 없다는 점이 이미 충분한 근거다.)
      (c) 서버에 CORS 설정(Access-Control-Allow-Origin 고정 + Allow-Credentials)이 필요해지고,
          Socket.IO에도 별도 cors 옵션이 필요하다. 설정이 하나 틀리면 원인 파악이 어려운
          "로컬에선 되는데 배포하면 안 되는" 문제가 생긴다.
      (d) 초대 링크(guide 4절)의 도메인과 API 도메인이 달라져, 링크 처리 로직이
          두 오리진을 인지해야 한다.
      (e) 배포 대상이 둘로 늘어나 버전 불일치(프론트는 새 프로토콜, 서버는 구 프로토콜)가
          발생할 수 있다. 단일 인스턴스 무중단 배포가 불가능한 상황에서 배포 단위가
          늘어나는 것은 순수한 손해다.

    ★ 결론: R002 1-7의 판단(Node 서버가 프론트를 직접 서빙 → 오리진 하나)을 유지한다.
      오리진이 하나면 (a)~(e) 전부가 존재하지 않는 문제가 된다.
      쿠키는 SameSite=Lax로 충분하고 서드파티 쿠키 차단의 영향을 받지 않는다.
      CORS 설정이 아예 필요 없다. 배포 단위도 하나다.
      GitHub Pages를 쓰지 않는 것이 이 프로젝트에서는 더 단순하고 더 안전하다.

    ★ 다만 "GitHub 무료 도메인"이 건우에게 실제로 주는 이점 하나는 인정한다.
      github.io 주소가 onrender.com 주소보다 기억하기 쉽고 신뢰감이 있다.
      이 부분은 나중에 커스텀 도메인을 쓰거나, 그대로 onrender.com 주소를 쓰는 것으로
      해결한다(초대 링크는 복사해서 공유하는 방식이므로 주소를 외울 필요가 없다 — guide 4절).

1-2. Supabase Free 재평가 (A-2)

  ★ 결론: 설계 담당 AI의 판단이 맞다. 문제는 "휴면" 자체가 아니라 "복구가 수동"이라는 점이다.
    확인일 2026-09-04, Supabase 공식 문서 기준.

  [일시정지 조건] 확인 완료
    공식 문서 문구: "A Free plan project is considered inactive if it does not receive
    sufficient user database activity over the past week."
    보충 설명: 지난 7일간 매일 몇 건 정도의 DB 요청이 있으면 일시정지를 피할 수 있다.
    → 즉 "1주 비활성"이 맞다. 그리고 판단 기준은 DB 활동량이다.
      ★ 이 프로젝트의 사용 패턴(친구들이 가끔 모여서 플레이)은 정확히 이 조건에 걸린다.
        2주 동안 아무도 게임을 안 하면 일시정지된다.

  [복구 방법] ★ 확인 완료 — 수동이다
    공식 문서 기준: 자동 복구가 아니다. Supabase 대시보드에 로그인해 해당 프로젝트를 선택하고
    "Resume project" 버튼을 눌러 확인해야 한다.
    → 설계 담당 AI의 지적이 사실이다. 친구가 "게임하자"고 했을 때 건우가 자리에 없으면
      아무도 DB를 깨울 수 없다. 방장이 접속해도 서버는 DB에 연결하지 못하고,
      게임을 시작할 수 없다. 건우가 폰으로 대시보드에 로그인해 버튼을 눌러야 한다.
    ★ 이것이 이 프로젝트에서 Supabase Free를 배제하는 결정적 이유다.

  [복구 소요 시간] 제3자 자료 기준 약 30초 ~ 3분 (공식 문서에 수치 미기재, 확인 불가)
    커뮤니티에는 훨씬 오래 걸리거나 복구가 진행되지 않는 사례 보고도 있다.
    → 즉 "버튼을 누르면 곧 된다"고 가정할 수도 없다.

  [장기 일시정지 시 삭제 여부] 확인 완료 (일부는 자료 간 불일치)
    · 공식 문서: "Once the project is paused, there is a 1-year window to restore the project
      on the platform from within Supabase Studio."
      → 1년 안에는 Studio에서 복구 가능. 1년이 지나면 Studio 복구 불가.
    · 제3자 자료: 90일을 넘기면 자동 Restore 버튼이 비활성화되고 프로젝트 고유
      인프라(API URL 등)가 회수되며, 백업을 내려받아 새 프로젝트로 옮겨야 한다는 서술이 있다.
      ★ 90일과 1년 두 수치가 상충한다. 어느 쪽이 현재 정책인지 확정하지 못했다(확인 불가).
        다만 어느 쪽이든 "방치하면 손이 많이 가는 상태가 된다"는 결론은 동일하다.
    · 데이터 자체가 즉시 삭제되는 것은 아니다.

  [무료 플랜 커넥션 수 제한] ★ R001에서 확인 불가였던 항목 — 이번에 확인
    제3자 자료 기준(공식 문서에서 직접 확인하지 못했으므로 확인 필요로 표시):
      Nano(무료) / Micro 컴퓨트: 직접 연결 60개, 풀러(Supavisor) 클라이언트 연결 200개
      Small: 90 / 400,  Medium: 120 / 600
      풀러 한도는 하드코딩되어 있어 컴퓨트 크기를 올리지 않으면 변경할 수 없다.
    → 이 프로젝트는 단일 인스턴스 + 풀 최대 5개 연결(R002 1-6)이므로 전혀 문제가 없다.
      즉 커넥션 수는 Supabase 배제 사유가 아니다. 배제 사유는 오직 수동 복구다.

  [그 밖의 제약]
    · DB 500MB, 파일 스토리지 1GB, egress 5GB, 조직당 활성 프로젝트 2개 (R002 확인분 유지)
    · Pro 플랜($25/월)로 올리면 비활성 일시정지가 사라지지만 예산을 크게 초과한다.

  ★ Neon과의 직접 비교 (A-2의 핵심 쟁점)
    ┌────────────────┬───────────────────────────┬──────────────────────────────┐
    │                │ Supabase Free             │ Neon Free                    │
    ├────────────────┼───────────────────────────┼──────────────────────────────┤
    │ 유휴 시 동작   │ 1주 비활성 → 프로젝트     │ 5분 유휴 → 컴퓨트 스케일     │
    │                │ 일시정지                  │ 투 제로(정지)                │
    │ 복구 방식      │ ★ 수동. 대시보드에서      │ ★ 자동. 다음 쿼리가 오면     │
    │                │ 사람이 버튼을 눌러야 함   │ 스스로 깨어남                │
    │ 복구 소요      │ 30초~3분 (확인 불가,      │ 수백 ms (공식 문서:          │
    │                │ 더 걸린 사례 보고 있음)   │ "within a few hundred        │
    │                │                           │ milliseconds")               │
    │ 사람 개입      │ 필요 (건우가 없으면 못 함)│ 불필요                       │
    │ 방치 시        │ 90일~1년 후 복구 난이도   │ 데이터 유지, 정지·삭제 없음  │
    │                │ 급상승                    │                              │
    │ 별도 한도      │ 없음(용량 제외)           │ ★ 월 100 CU-시간             │
    └────────────────┴───────────────────────────┴──────────────────────────────┘

    → 두 서비스의 위험은 성격이 완전히 다르다.
      Supabase의 위험은 "사람이 없으면 아무도 못 고친다"이고,
      Neon의 위험은 "너무 많이 쓰면 월말에 멈춘다"다.
      이 프로젝트의 사용 패턴(가끔, 짧게)에서는
      Supabase의 위험은 거의 확실히 발생하고 Neon의 위험은 거의 발생하지 않는다.
      1-3의 계산이 이를 뒷받침한다.

    ★ 따라서 Supabase는 Free 기준으로 이 프로젝트에 부적합하다.
      건우의 이전 프로젝트에서 잘 쓰였던 이유는 그 프로젝트가 매일 트래픽이 있었거나,
      건우가 항상 대시보드에 접근 가능한 상황이었기 때문일 것으로 추정한다.
      이 프로젝트는 "친구들이 건우 없이도 놀 수 있어야 한다"는 성격이 다르다.
      (이 추정이 틀렸다면, 즉 항상 건우가 함께 접속하는 전제라면 Supabase도 후보가 된다.
       그 경우 알려주면 재검토하겠다.)

1-3. Neon Free vs Launch 재계산 (A-3)

  [먼저 R002의 계산에 있던 오독을 정정한다]
    R002 1-4 시나리오 1은 "월 약 30시간 활성"을 가정했다. 이것은 활성 시간이고,
    CU-시간이 아니다. 0.25 CU에서 30시간 활성은 30 × 0.25 = 7.5 CU-시간이다.
    (R002의 금액 계산 $0.80은 7.5 CU-시간 기준이라 맞았지만,
     "월 약 30 CU-시간"으로 읽으면 4배 과대평가가 된다.)
    → 즉 Free 한도 100 CU-시간에 대해 여유는 3배가 아니라 약 13배다.
      설계 담당 AI의 재계산 방향이 옳고, 실제로는 더 여유롭다.

  [Neon 최소 CU 값 — 재확인 결과]
    ★ 확인 완료: 최소 컴퓨트 크기는 0.25 CU다(1 GB RAM). 0.25 CU와 0.5 CU는 공유 컴퓨트다.
      1 CU ≈ 4 GB RAM. Free 플랜은 최대 2 CU(8 GB)까지 지원한다.
    ★ 확인 불가: Free 플랜에서 오토스케일링의 기본 최솟값이 0.25인지 1인지는
      공식 문서에서 확정하지 못했다. 문서의 API 예시에는 1~2 CU 구성이 나온다.
      → 따라서 아래 추산은 0.25 CU와 1 CU 두 경우를 모두 계산한다.
        프로젝트 생성 후 대시보드에서 오토스케일링 최솟값을 0.25로 설정할 수 있는지
        건우가 확인해 주면 확정할 수 있다.

  [스케일 투 제로 동작 확인]
    · 5분 유휴 후 자동 정지. Free는 비활성화 불가, 유료는 해제 가능.
    · ★ 재활성화는 새 쿼리가 도착하면 "수백 ms 안에" 자동으로 일어난다(공식 문서 문구).
      사람 개입이 없다. 이것이 Supabase와의 결정적 차이다.
    · 정지 중에는 활성 컴퓨트 시간이 과금되지 않는다.

  [월 사용량 추산 — 세 시나리오]
    가정: 게임 세션이 끝나면 5분 뒤 정지되므로, 세션마다 "실사용 + 5분 꼬리"를 활성으로 계산.
          R002 1-6의 idle timeout 설계(풀 최소 연결 0, 유휴 60초, DB 헬스체크 없음)가
          지켜진다고 전제한다. 이 전제가 깨지면 아래 계산은 전부 무의미해진다.

    ┌──────────┬──────────────────┬──────────┬───────────────┬───────────────┐
    │ 시나리오 │ 플레이 패턴      │ 활성시간 │ 0.25 CU 기준  │ 1 CU 기준     │
    ├──────────┼──────────────────┼──────────┼───────────────┼───────────────┤
    │ 가벼움   │ 주 1회 × 2시간   │ 약 12h   │ 3 CU-h  (3%)  │ 12 CU-h (12%) │
    │ 예상     │ 주 3회 × 2시간   │ 약 30h   │ 7.5 CU-h (8%) │ 30 CU-h (30%) │
    │ 무거움   │ 주 5회 × 3시간   │ 약 75h   │ 19 CU-h (19%) │ 75 CU-h (75%) │
    │ 과부하   │ 매일 × 4시간     │ 약 135h  │ 34 CU-h (34%) │ ★ 135 CU-h    │
    │          │                  │          │               │   (한도 초과) │
    └──────────┴──────────────────┴──────────┴───────────────┴───────────────┘
      괄호 안은 Free 한도 100 CU-시간 대비 사용률.
      데이터 파이프라인(R002 2-3)의 배치 잡도 DB를 깨우지만, 하루 몇 분 수준이라 무시했다.
      단 대량 적재를 돌리는 날에는 몇 시간이 추가될 수 있다.

    ★ 판단:
      0.25 CU로 동작한다면 어떤 시나리오에서도 Free가 안전하다(최대 34%).
      1 CU가 최솟값이라면 "무거움"에서 75%까지 올라가고 "과부하"에서는 초과한다.
      즉 위험은 오토스케일링 최솟값이 무엇인지에 달려 있다.

  [Free 한도 도달 시 무슨 일이 일어나는가] — R002에서 확인한 내용 유지
    Neon FAQ 문구 기준: 프로젝트의 컴퓨트가 다음 청구 주기까지 또는 업그레이드할 때까지
    정지된다. 기존 연결이 끊기고 새 연결을 열 수 없다. 데이터는 삭제되지 않는다.
    ★ 즉 최악의 경우는 "월말 며칠 동안 게임을 못 한다"이고, 데이터 손실은 없다.
      그리고 그 자리에서 Launch로 업그레이드하면 즉시 풀린다.

  [Free → Launch 전환이 코드 변경 없이 되는가]
    ★ 판단: 된다고 본다. 근거는 다음이다.
      · 플랜 변경은 Neon 콘솔의 결제 설정에서 이루어지며 프로젝트·브랜치·엔드포인트는
        그대로 유지된다. 연결 문자열이 바뀌지 않으므로 DATABASE_URL을 고칠 필요가 없다.
      · R002 1-7의 플랫폼 중립 규칙(접속 정보는 환경 변수로만, 표준 pg 드라이버만 사용)을
        지키면 애플리케이션은 플랜 차이를 인지하지 못한다.
    ★ 단 "플랜 변경 시 연결 문자열이 절대 바뀌지 않는다"를 공식 문서에서 명시적으로
      확인하지는 못했다(확인 불가). 전환 시 DATABASE_URL을 한 번 확인하는 절차를
      docs\11-DEPLOY.md에 남기는 것으로 대비한다.

  [★ Free 한도 근접을 미리 알 수 있는가] — 이번 조사의 약한 지점
    · Neon 콘솔에 사용량 지표가 있다(Billing 페이지 / Projects 페이지 / 프로젝트 대시보드에서
      Compute, Storage, History, Network transfer를 확인 가능). Neon API로도 조회 가능하다.
    · ★ 그러나 Free 플랜 사용자에게 한도 근접 이메일 경고가 발송되는지는
      공식 문서에서 확인하지 못했다(확인 불가). 해당 문서 페이지는 유료 사용량 기반 플랜을
      중심으로 서술되어 있고 Free 플랜의 알림 여부를 명시하지 않는다.
    → 따라서 "알림이 온다"에 의존하지 않는 대비가 필요하다. 제안은 다음이다.
      (a) docs\11-DEPLOY.md에 "월 1회 Neon 콘솔에서 CU-시간 사용률을 확인한다"를
          운영 절차로 명시한다.
      (b) ★ 더 나은 방법: 서버가 자체적으로 DB 활성 시간을 누적 기록한다.
          커넥션 풀이 처음 연결을 열 때와 마지막 연결을 닫을 때의 시각을 로그로 남기면
          "이번 달 DB를 몇 시간 깨워 두었는지"를 우리가 직접 알 수 있다.
          Neon API를 붙이지 않고도 사용률을 추정할 수 있어 가볍다.
          이건 Phase 0에서 로그 한 줄로 시작할 수 있다.
      (c) 위험을 감지하면 그때 Launch로 전환한다(코드 변경 없음).

1-4. 최종 권장 (A-4)

  ★ 설계 담당 AI의 판단에 동의한다.
    권장: Render Free (Node 서버가 프론트엔드까지 직접 서빙) + Neon Free 로 시작하고,
          첫 달 사용량을 확인한 뒤 필요하면 Neon Launch로 전환한다.

  R002가 Launch를 권장했던 것을 이 라운드에서 철회한다. 철회 이유를 명확히 적는다.
    · R002는 활성 시간(30h)을 CU-시간으로 오독해 Free 한도의 30%를 쓴다고 봤다.
      실제로는 0.25 CU에서 8%다. 대비의 필요성이 R002가 생각한 것보다 훨씬 작다.
    · Free → Launch 전환이 코드 변경 없이 가능하므로, 미리 유료로 시작하는 것의
      유일한 이점("사고를 예방한다")이 크지 않다. 사고가 나도 그 자리에서 전환하면 풀린다.
      그리고 사고의 최대 피해는 "며칠 게임 못 함"이며 데이터 손실이 없다.
    · 건우의 예산 조건은 "월 5달러 미만이면 지불 가능"이지 "지불하는 것이 좋다"가 아니다.
      필요 없는 지출을 미리 하지 않는 것이 맞다.

  ★ 다만 Free로 시작하는 것에는 조건이 붙는다. 이 조건이 지켜지지 않으면 Free는 위험하다.
    조건 1 — R002 1-6의 커넥션 풀 방침을 Phase 0에서부터 적용한다.
             풀 최소 유지 연결 0 / 유휴 연결 종료 60초 / 풀 최대 5 /
             DB를 건드리는 주기 쿼리 금지 / 헬스체크는 DB 미접근 / 지연 연결.
             ★ 이것 하나가 지켜지지 않으면 월 182 CU-시간(0.25 CU 기준)이 되어
               Free 한도를 즉시 초과한다. 가장 중요한 단일 설정이다.
    조건 2 — Neon 프로젝트 생성 후 오토스케일링 최솟값을 0.25 CU로 설정한다.
             설정이 불가능하다면(Free 기본이 1 CU라면) "무거움" 시나리오에서 75%까지 가므로
             사용량 관찰 주기를 짧게(월 2회) 한다.
    조건 3 — 1-3 (b)의 DB 활성 시간 자체 로깅을 Phase 0에 넣는다.
             알림에 의존하지 않고 우리가 직접 사용률을 안다.
    조건 4 — Neon 콘솔 사용량 확인 절차를 docs\11-DEPLOY.md에 운영 항목으로 남긴다.

  최종 구성 정리
    · 서버        Render Free (Node.js + TypeScript, 단일 인스턴스, WebSocket)
    · 프론트엔드  같은 Render 서비스가 정적 빌드 산출물을 직접 서빙 (오리진 1개)
    · DB          Neon Free PostgreSQL (스케일 투 제로 5분, 자동 재활성)
    · 슬립 대응   접속자가 있는 동안 클라이언트 heartbeat 4분 (Q-02 확정)
    · 데이터 트랙 GitHub Actions + Gemini 무료 한도 (R002 2-3)
    · 월 비용     $0
    · 전환 경로   사용량 증가 시 Neon Launch(종량제, 월 $1~3 추정)로 대시보드에서 전환

  이 구성으로 Q-39를 확정 제안한다. 최종 결정은 건우가 한다.

2-0. 상태 표현에 대한 자체 판단 (guide 9절이 위임한 사항)

  guide 9절은 상태 6종을 개념으로 제시하고 "실제 구현 방식이나 이름은 적절하게 판단해서
  결정한다"고 위임했다. 그리고 Q-31에서 "FORCE_ENDED는 종료 사유로만 기록하고
  화면 흐름은 GAME_RESULT와 동일"이 확정되었다.

  따라서 다음과 같이 표현한다.
    · room.state (5종)    LOBBY / COUNTDOWN / QUESTION_ACTIVE / QUESTION_RESOLVED / GAME_RESULT
    · game.endReason (4종) completed / force_ended / no_questions / no_players

  guide 9절의 6개 상태와의 대응
    LOBBY            → room.state = LOBBY
    COUNTDOWN        → room.state = COUNTDOWN
    QUESTION_ACTIVE  → room.state = QUESTION_ACTIVE
    QUESTION_RESOLVED→ room.state = QUESTION_RESOLVED
    GAME_RESULT      → room.state = GAME_RESULT, endReason = completed
    FORCE_ENDED      → room.state = GAME_RESULT, endReason = force_ended
  ★ 규칙을 줄인 것이 아니다. FORCE_ENDED로 끝난 게임과 정상 완주한 게임은
    endReason으로 구분되고, 결과 화면에 "강제 종료됨"이 표시되며(Q-31), DB에도 기록된다.
    바뀐 것은 "화면 전환 경로가 하나"라는 점뿐이고 이는 Q-31의 확정 사항이다.

  추가로 두 개의 파생 상태 값이 필요하다. 이들은 room.state와 직교한다.
    · room.graceUntil        활성 0명 30초 유예 만료 시각 (Q-30). null이면 유예 중 아님.
    · room.hostGraceUntil    방장 권한 이전 30초 유예 만료 시각 (Q-29). null이면 유예 중 아님.

──────────────────────────────────────────

    room { id, title, hostAccountId, createdAt }

    정답 판정        해당 없음
    스킵 투표        불가 (에러 응답)
    방장 액션        설정 변경 / 게임 시작 / 접속 종료자 강제 퇴장(Q-15)
    입장            허용 (정원 10명 미만이면)
    퇴장            허용

  클라이언트 화면 (guide 6절)

    방장 표시 / 문제 수 / 시작 방식 / 초대 링크 복사 / 게임 시작 버튼(방장만) /
    참가자별 경험률("1,234문제 중 153문제 (12.4%)" 형식, Q-12) / 로비 채팅

  시간 제한
    없음. 단 활성 인원 0명이 10분 이상 지속되면 방을 삭제한다(Q-14).

[COUNTDOWN]
──────────────────────────────────────────
  추가 데이터
    countdownEndsAt   (서버 epoch ms)
    settingsLocked = true

  허용되는 사용자 행동
    채팅            허용. 정답 판정 대상 아님
    스킵 투표        불가
    방장 액션        카운트다운 취소(Q-11) / 접속 종료자 강제 퇴장

    퇴장            허용

  화면
    "N초 후 시작" 카운트다운 + 로비 정보 유지 + 채팅 유지 + 방장에게 취소 버튼

  시간 제한
    countdownEndsAt 도달 시 QUESTION_ACTIVE로 전이(T04).
    활성 0명 유예 만료 시 LOBBY로 복귀(T05).

[QUESTION_ACTIVE]
──────────────────────────────────────────
  추가 데이터
    game { id, startedAt, plannedQuestionCount, usedQuestionIds Set }
    currentQuestion {
      epoch                  ★ 문제마다 1씩 증가하는 단조 정수. 2-3의 핵심 장치
      index                  1-based
      questionId
      text
      categoryName
      answersNorm  Set<string>    ★ 정규화된 정답 집합. 문제 시작 시 메모리 로드
      displayAnswer
      answersRaw   string[]       마스킹 매칭용 원문 표기 목록
      hint | null                 미리 계산해 두되 클라이언트로는 10초 시점에만 push
      hintPushed   boolean
      explanation | null
      experiencedAccountIds Set   ★ 문제 시작 시점 기준. 중간 참가로 갱신될 수 있음
      startedAt, endsAt           (서버 epoch ms, endsAt = startedAt + 30000)
      resolved     boolean        ★ 원자적 전환 플래그
    }
    skipVotes Set<accountId>
    scores    Map<accountId, number>
    graceUntil | null

  허용되는 사용자 행동
    채팅            허용 (guide 12·13절)
    정답 판정        ★ 조건: 상태 = QUESTION_ACTIVE, resolved = false,
                    메시지의 epoch = currentQuestion.epoch,
                    서버 수신 시각 ≤ endsAt,
                    발신자가 이 문제를 경험하지 않음(Q-23 기준)
    스킵 투표        허용 (활성 2명 이상일 때. Q-28)
    방장 액션        강제 스킵 / 강제 종료 / 접속 종료자 강제 퇴장
    입장            허용 (중간 참가, guide 31절)
    퇴장            허용 (게임 계속, guide 33절)

  화면
    "문제 n / N" / 문제 내용 / 남은 시간 / 힌트(10초 이하일 때) /
    경험자 닉네임 목록(전원 공개, Q-35) / 본인이 경험자면 "이미 풀어본 퀴즈입니다" 배지 /
    점수판(접속 종료 표기 포함) / 스킵 투표 수와 임계값 / 채팅 / 단축키 안내

  시간 제한
    30초 정확히. endsAt 도달 시 QUESTION_RESOLVED(timeout)로 전이.
    남은 시간 10초가 되는 순간 서버가 힌트를 push한다(hintPushed로 1회만).

[QUESTION_RESOLVED]
──────────────────────────────────────────
  추가 데이터
    resolution {
      epoch                  방금 끝난 문제의 epoch (그대로 유지)
      reason                 correct | timeout | skip_vote | host_skip
      winnerAccountId | null
      displayAnswer
      explanation | null
      nextAt                 (서버 epoch ms) = 전이 시각 + 5000
    }
    ★ currentQuestion.epoch은 아직 증가하지 않는다. 다음 문제 시작 시점에 증가한다.

  허용되는 사용자 행동
    채팅            ★ 허용 (guide 20절 명시). 입력창을 닫지 않는다
    정답 판정        ★ 하지 않는다. 이 구간의 메시지는 어떤 문제의 정답으로도 판정되지 않는다
    스킵 투표        불가 (문제가 이미 끝났다)
    방장 액션        강제 종료 허용 / 접속 종료자 강제 퇴장.
                    ★ 강제 스킵은 무의미하므로 무시한다
    입장            허용. 경험 처리 여부는 Q-23 기준(정답 공개 시점)에 따라
                    이 구간 입장자는 경험 기록 대상이 아니다 (2-2 T-JOIN 참조)
    퇴장            허용

  화면
    정답 공개(정답자 닉네임 / 정답 / +1점) 또는 시간 종료 / 스킵 안내 +
    해설(있으면) + 점수판 갱신 + 채팅 유지 + "N초 후 다음 문제"

  시간 제한
    5초. nextAt 도달 시 다음 문제 또는 결과 화면으로 전이.
    ★ 마지막 문제에서는 이 상태를 거치지 않는다 (Q-17). 2-2 참조.

[GAME_RESULT]
──────────────────────────────────────────
  추가 데이터
    result {
      gameId, endReason, ranking[] { rank, accountId, nickname, colorIndex, score, connected },
      lastQuestionReveal | null    ★ Q-47 관련. 아래 참조
      abortedNote | null           조기 종료 사유 문구 (Q-22 / Q-30)
    }
    settingsLocked = true (다시 하기 또는 로비로 갈 때 해제)

  허용되는 사용자 행동
    채팅            ★ 허용 (Q-32 확정: 결과 화면에서도 채팅 유지)
    정답 판정        하지 않는다
    스킵 투표        불가
    방장 액션        "다시 하기" / "로비로" / 접속 종료자 강제 퇴장
    입장            허용. 입장자는 결과 화면을 본다 (guide 49절 "게임이 이미 종료된 방")
    퇴장            허용

  화면
    순위 / 닉네임(색상) / 점수 / 참가자 상태 (guide 38절) + 동점 공동 순위 (guide 39절) +
    endReason이 force_ended면 "강제 종료됨" 표시 (Q-31) +
    조기 종료면 사유 표시 (Q-22) +
    방장에게 "다시 하기" / "로비로" 버튼, 그 외에게 "방장이 다음 게임을 준비 중입니다" +
    채팅 유지

  시간 제한
    없음. 방장 액션을 기다린다 (Q-32).
    단 활성 0명 10분이면 방 삭제 (Q-14).

2-2. 전이표

  표기: [ID] 출발 → 도착 / 트리거 / 조건 / 부수 효과
  ★ 부수 효과에 "경험 기록"이 적힌 곳이 곧 Q-23/24가 규정한 정답 공개 시점이다.

──── 게임 시작 ────

[T01] LOBBY → COUNTDOWN
  트리거: 방장 game.start
  조건:   settings.startMode = countdown
          AND 문제 수 검증 통과 (1~200, Q-10)
          AND 카운트다운 초 검증 통과 (3~60, Q-11)
          AND ★ 출제 가능 문제 수 ≥ settings.questionCount (Q-21 서버 재검증)
          AND 활성 플레이어 ≥ 1
  효과:   settingsLocked = true, countdownEndsAt = now + countdownSec×1000
          game.countdownStarted 브로드캐스트

[T02] LOBBY → QUESTION_ACTIVE
  트리거: 방장 game.start
  조건:   settings.startMode = instant, 그 외 T01과 동일
  효과:   게임 레코드 생성(games INSERT), 점수 전원 0으로 초기화,
          첫 문제 선정 및 시작 (아래 [문제 시작 공통 절차])

[T03] COUNTDOWN → LOBBY
  트리거: 방장 game.cancelCountdown (Q-11)
  조건:   없음
  효과:   countdownEndsAt = null, settingsLocked = false
          game.countdownCancelled 브로드캐스트

[T04] COUNTDOWN → QUESTION_ACTIVE
  트리거: now ≥ countdownEndsAt
  조건:   활성 플레이어 ≥ 1
  효과:   T02와 동일

[T05] COUNTDOWN → LOBBY
  트리거: graceUntil 만료 (활성 0명이 30초 지속, Q-30)
  조건:   활성 플레이어 = 0
  효과:   게임을 시작하지 않고 로비로 되돌린다. settingsLocked = false

──── 문제 종료 (정답 공개 경로 3종 + 미공개 경로 2종) ────

[T06] QUESTION_ACTIVE → QUESTION_RESOLVED
  트리거: 채팅 메시지가 정답과 일치
  조건:   ★ resolved = false
          AND 메시지 epoch = currentQuestion.epoch
          AND 서버 수신 시각 ≤ endsAt
          AND 발신자가 이 문제 미경험
          AND normalize(text) ∈ answersNorm
          AND isLastQuestion = false
  효과:   resolved = true (즉시, 동기)
          정답자 점수 +1
          ★ 경험 기록: 이 시점 접속 중인 모든 플레이어에게 question_experiences 기록 (Q-23/24)
          answer_events INSERT (정답 이벤트, response_ms 포함)
          game_questions UPDATE (resolution=correct, winner)
          question.resolved 브로드캐스트 (nextAt = now + 5000)
          스킵 투표 초기화는 다음 문제 시작 시점에 수행

[T07] QUESTION_ACTIVE → QUESTION_RESOLVED
  트리거: now ≥ endsAt (타이머 만료)
  조건:   resolved = false AND isLastQuestion = false
  효과:   resolved = true, 정답 공개, ★ 경험 기록(접속자 전원),
          resolution = timeout, nextAt = now + 5000

[T08] QUESTION_ACTIVE → QUESTION_RESOLVED
  트리거: 스킵 투표 수가 임계값에 도달
  조건:   resolved = false AND 활성 ≥ 2 AND votes ≥ threshold(활성 수) AND isLastQuestion = false
  효과:   ★ Q-27 확정대로 시간 종료와 동일 경로를 재사용한다.
          정답 공개 + ★ 경험 기록(접속자 전원) + resolution = skip_vote + nextAt = now + 5000

[T09] QUESTION_ACTIVE → QUESTION_RESOLVED
  트리거: 방장 host.forceSkip 확인
  조건:   resolved = false AND isLastQuestion = false
  효과:   T08과 동일. resolution = host_skip

[T10] QUESTION_ACTIVE → GAME_RESULT   (마지막 문제, Q-17)
  트리거: T06 / T07 / T08 / T09 중 하나
  조건:   ★ isLastQuestion = true
  효과:   해당 사유대로 정답 공개 처리(경험 기록 포함, Q-47 참조)
          ★ 5초를 기다리지 않고 즉시 GAME_RESULT
          endReason = completed, 순위 확정, game_players UPDATE, games UPDATE

[T11] QUESTION_ACTIVE → GAME_RESULT   (방장 강제 종료)

──── [문제 시작 공통 절차] ────

  T02 / T04 / T14가 공통으로 수행한다. ★ 순서가 중요하다.

  1. 문제 선정 (Q-20 2단계 알고리즘, 이미 출제한 문제 제외)
     · 1단계: 현재 활성+비활성 참가자 전원이 미경험인 문제 풀에서 무작위
     · 2단계: 1단계가 비면, 1명 이상 미경험인 문제 풀에서 미경험자 수 가중 무작위
     · 둘 다 비면 문제 선정 실패 → T15 (조기 종료)
     ★ 선정 시점 문제는 Q-50으로 올린다 (게임 시작 시 전량 선정 vs 매 문제 선정).
       이 절차는 "매 문제 선정"을 전제로 작성했다.
  2. 정답 집합 로드: question_answers에서 answer_norm 전체를 Set으로 메모리에 적재
  3. 마스킹용 원문 표기 목록(answersRaw) 적재
  4. 힌트 미리 계산 (shared 순수 함수, Q-37 방어선 적용)
  5. 경험자 집합 계산: 현재 참가자 각자가 이 문제를 경험했는지 question_experiences 조회
  6. ★ epoch += 1, resolved = false, skipVotes 초기화, hintPushed = false
  7. startedAt = now, endsAt = startedAt + 30000
  8. game_questions INSERT (started_at)
  9. question.started 브로드캐스트 (개인별 selfExperienced 포함, 3-2)

  ★ 1~5는 DB 접근이 있으므로 await를 포함한다. 이 절차는 판정 블록이 아니므로 허용된다.
    핵심은 "6~9가 완료된 뒤에는 판정에 필요한 모든 데이터가 메모리에 있다"는 것이다.
    이 덕분에 정답 판정 블록에서 await가 필요 없어진다 (2-3).

2-3. 동시 발생 시나리오

  [★ 설계 원칙 — 코드 주석과 docs\04-PROTOCOL.md 양쪽에 반드시 남긴다]

    원칙 1. 방 단위 직렬 처리.
            Node.js는 단일 스레드 이벤트 루프이므로, 하나의 이벤트 핸들러가
            await 없이 끝까지 실행되는 동안 다른 이벤트가 끼어들 수 없다.
    원칙 2. ★ 판정과 상태 전환은 하나의 동기 실행 블록에서 수행한다.
            그 블록 안에 await를 절대 넣지 않는다.
            이 규칙이 깨지면 guide 18절의 "한 문제에 정답자는 정확히 한 명"이
            조용히 무너진다. 에러도 나지 않고 대부분의 경우 정상 동작하다가
            동시 입력이 겹치는 순간에만 두 명이 정답자가 된다. 재현과 발견이 매우 어렵다.
    원칙 3. 판정에 필요한 데이터(정답 집합, 참가자별 경험 여부, 힌트, 마스킹용 표기)는
            문제 시작 시점에 메모리로 미리 로드한다. [문제 시작 공통 절차] 참조.
    원칙 4. DB 기록은 상태 전환이 끝난 뒤 비동기로 수행한다.
            DB 쓰기 실패가 게임 진행을 막지 않는다. 실패는 로그로 남기고 재시도한다.
    원칙 5. 모든 인바운드 이벤트에 서버 수신 시 단조 증가 시퀀스를 부여한다 (3-5).

  [★ 두 겹 방어 장치]

    장치 A — resolved 플래그
      QUESTION_ACTIVE → QUESTION_RESOLVED 전환 함수의 첫 줄에서 동기적으로 확인·설정한다.
        if (q.resolved) return;   // 이미 끝난 문제
        q.resolved = true;        // 여기서 즉시 세운다
      이 두 줄 사이에 await가 없으므로 두 번째 요청이 끼어들 수 없다.
      guide 18절의 "QUESTION_RESOLVED가 한 번만 발생"을 보장한다.

    장치 B — ★ epoch (문제 세대 번호)
      클라이언트는 chat.send / skip.vote / host.forceSkip 에 자신이 보고 있는 epoch를 담는다.
      서버는 수신 시 currentQuestion.epoch와 비교한다.
        · 일치하지 않으면 → 정답 판정에서 제외한다. 채팅으로만 표시한다.
        · 일치하면 → 나머지 조건을 검사한다.
      ★ 이것이 guide 20절이 명시적으로 금지한 함정을 구조적으로 막는 유일한 방법이다.
        상태 검사만으로는 막을 수 없는 이유:
          사용자가 QUESTION_RESOLVED 구간(5초)에 "훈민정음"을 입력했고,
          그 메시지가 네트워크 지연으로 5초 뒤 다음 문제가 시작된 직후에 서버에 도착했다면,
          서버 상태는 이미 QUESTION_ACTIVE이므로 상태 검사를 통과한다.
          그리고 새 문제의 정답이 우연히 "훈민정음"이면 정답으로 처리된다.
          → guide 20절이 "우연히 일치하더라도 정답 처리하면 안 된다"고 못 박은 바로 그 케이스다.
        epoch가 다르면(사용자는 이전 문제의 epoch를 보냈다) 판정하지 않으므로 원천 차단된다.

  [시나리오별 처리]

  (a) 두 사람이 거의 동시에 정답 제출
      두 메시지는 서버의 이벤트 큐에 순서대로 들어온다. 먼저 처리된 쪽이 장치 A로
      resolved를 세우고 정답자가 된다. 두 번째는 첫 줄에서 return하고 일반 채팅으로만 표시된다.
      ★ 승부 기준은 서버가 먼저 수신·처리한 것이다. 클라이언트 시각이나 지연 보정은
        일절 하지 않는다 (guide 18절).
      ★ 두 번째 사람에게 "오답입니다" 같은 메시지를 보내지 않는다 (guide 15절).
        그 사람의 메시지는 그냥 채팅으로 남는다.

  (b) 타이머 만료와 정답 제출이 동시
      두 경로 모두 같은 전환 함수를 호출하고 장치 A로 하나만 성공한다.
      ★ 추가 규칙: 정답 판정은 "서버 수신 시각 ≤ endsAt"을 요구한다.
        타이머 만료 체크가 100ms 주기이므로, 만료 후 최대 100ms 동안은 상태가 아직
        QUESTION_ACTIVE다. 이 구간에 도착한 늦은 정답을 인정하면 30초를 넘긴 답이
        인정되는 것이므로, 수신 시각으로 잘라낸다.
      → guide 49절 "타이머 종료 직전 정답은 서버의 실제 문제 상태를 기준으로 처리"를
        "서버가 기록한 종료 시각 기준"으로 구체화한 것이다.

  (c) 스킵 임계값 도달과 정답 제출이 동시
      장치 A로 하나만 성공한다. 스킵이 먼저면 resolution = skip_vote가 되고
      뒤에 온 정답은 채팅으로만 남는다(점수 없음). 정답이 먼저면 resolution = correct가 되고
      스킵 투표는 무시된다.
      ★ guide 49절이 요구하는 "일관된 순서"가 장치 A 하나로 보장된다.

  (d) 방장 강제 스킵과 정답 제출이 동시
      (c)와 동일. 강제 스킵도 같은 전환 함수를 거친다.
      ★ 강제 스킵 요청에도 epoch를 담는다. 방장이 확인창을 띄우고 있는 동안 문제가
        정답으로 끝났다면, 확인을 눌러도 epoch가 달라 무시된다. 이것이 없으면
        다음 문제가 시작된 직후에 이전 문제의 강제 스킵이 도착해 새 문제를 스킵해 버린다.

  (e) 방장 강제 종료와 정답 제출이 동시
      강제 종료가 먼저 처리되면 상태가 GAME_RESULT가 되고, 정답 메시지는 상태 검사에서
      탈락해 채팅으로만 남는다.
      정답이 먼저 처리되면 QUESTION_RESOLVED가 되고 정답은 인정된다(+1점, 경험 기록 남음).
      그 뒤 강제 종료가 T12로 처리되어 GAME_RESULT로 간다.
      ★ 강제 종료에는 epoch를 담지 않는다. 게임 전체를 끝내는 액션이므로 특정 문제에
        종속되지 않는다. 대신 확인창을 거친다 (guide 25절).

  (f) 정답 확정 직후 도착한 메시지
      resolved = true이므로 장치 A에서 걸러지고, 상태도 QUESTION_RESOLVED다.
      채팅으로만 표시된다 (guide 20절 "이 시점의 메시지는 현재 문제의 정답으로 판정하지 않는다").

  (g) ★ QUESTION_RESOLVED 구간에 입력된 메시지가 다음 문제의 정답과 우연히 일치
      장치 B(epoch)로 차단된다. 위 [두 겹 방어 장치] 설명 참조.
      ★ 이 케이스는 guide 70절의 필수 테스트 항목으로 등록한다.
        테스트 방법: 봇이 문제 1의 RESOLVED 구간에 "문제 2의 정답"을 전송하도록 만들고,
        전송을 5초 이상 지연시켜 문제 2 시작 직후에 서버에 도달하게 한다.
        문제 2가 정답 처리되지 않아야 통과다.
      ★ 추가 안전장치: 클라이언트도 자신이 QUESTION_RESOLVED 상태이면 전송하는 메시지에
        그 시점의 epoch를 담는다. 즉 epoch는 "메시지를 입력한 순간의 문제 세대"다.

  (h) 스킵 투표 중 인원 변동으로 임계값이 바뀌어 이미 도달 상태가 되는 경우
      인원 변동 이벤트(T-JOIN / T-LEAVE / T-KICK) 처리 블록 안에서 동기적으로
      임계값을 재평가한다. 재평가 결과 votes ≥ threshold면 그 자리에서 T08을 수행한다.
      ★ 재평가를 다음 tick으로 미루면, 그 사이에 도착한 정답과 경쟁하면서 순서가
        불명확해진다. 같은 블록 안에서 처리해야 순서가 결정적이다.
      ★ 반대 방향(인원이 늘어 임계값이 올라가 이미 던진 표가 부족해지는 경우)도
        같은 자리에서 재평가한다. 이때는 아무 일도 일어나지 않고 skip.voteUpdated만 나간다.
      임계값 표 (Q-28 확정): 활성 2명=2 / 3명=2 / 4명=3 / 5명=4 / 6명=5 / 7명=6 /
                              8명=7 / 9명=8 / 10명=8. 활성 1명이면 투표 불가.
      ★ 분모는 해당 문제의 경험 여부와 무관한 전체 활성 플레이어다 (Q-28).

  (i) 마지막 플레이어가 정답을 맞히는 동시에 연결이 끊기는 경우
      두 이벤트(chat.send, disconnect)의 서버 수신 순서가 결과를 결정한다.
      · 정답이 먼저 처리되면: 정답 인정(+1점). 경험 기록은 "정답 공개 시점의 접속자"이고
        그 순간 그 사람은 아직 접속 중이므로 기록된다.
        그 뒤 disconnect가 처리되어 활성 0명 → graceUntil 설정 → 30초 후 T13.
      · disconnect가 먼저 처리되면: 그 플레이어는 connected = false가 되고,
        뒤에 도착한 정답 메시지는 "미접속 플레이어의 메시지"다.
        ★ 이 경우를 어떻게 처리할지 규칙이 없다. 판단이 필요하다.
        제안(자체 판단): 미접속 플레이어의 메시지는 판정하지 않는다.
          근거: 소켓이 이미 끊어졌으므로 그 메시지는 서버가 정상적으로 수신·처리한
          정답이라 보기 어렵고, Q-29가 "연결 끊김을 즉시 반영"하도록 확정했다.
          그리고 Socket.IO에서 disconnect 이후에 그 소켓의 메시지가 도착하는 일은
          실제로는 거의 없다(같은 소켓의 이벤트는 순서가 보장된다).
        → 즉 실무적으로는 "정답이 먼저" 케이스만 발생한다고 본다.

  (j) 추가 발견 — 같은 사람이 같은 문제에 여러 번 정답 문자열을 보내는 경우
      guide 54절이 정의한 재미가 "미친 듯이 답을 입력하는 것"이므로 흔하게 발생한다.
      첫 번째가 정답으로 처리되고 resolved가 세워지므로 두 번째부터는 채팅으로만 남는다.
      ★ Q-18의 rate limit(3초 이동 윈도 10개)이 이 연타를 막지 않도록 주의한다.
        초당 3개 수준의 정상 입력은 절대 억제되지 않아야 한다.

  (k) 추가 발견 — 경험자가 정답 문자열을 보내는 경우
      판정 대상에서 제외되고(Q-28/guide 28절), 마스킹 대상이 된다(Q-35).
      ★ 이때 판정 경로와 마스킹 경로가 완전히 분리되어야 한다. 3-3에서 명세한다.

2-4. 타이머 설계

  [서버 측]

  · ★ 전역 tick 하나로 모든 방을 순회한다. 방마다 setTimeout/setInterval을 두지 않는다.
    자체 판단 근거: 방 수가 많지 않고(친구들끼리 쓰는 서비스), 타이머 핸들이 방 생명주기와
    엉키면 누수와 중복 실행이 생긴다. 전역 tick 하나면 상태 검사가 한 곳에 모이고
    "tick 안에서는 다른 이벤트가 끼어들지 않는다"는 성질을 그대로 활용할 수 있다.

  · tick 주기 100ms. 매 tick에서 방마다 다음을 순서대로 검사한다.
      1. COUNTDOWN: now ≥ countdownEndsAt → T04
      2. QUESTION_ACTIVE:
         a. hintPushed = false AND (endsAt - now) ≤ 10000 → 힌트 push, hintPushed = true
         b. now ≥ endsAt → T07 (또는 마지막 문제면 T10)
      3. QUESTION_RESOLVED: now ≥ resolution.nextAt → T14 / T15
      4. graceUntil 만료 → T05 / T13
      5. hostGraceUntil 만료 → T-HOST
      6. 방 삭제 조건 (활성 0명 10분) → T-ROOMDEL

  · ★ guide 10절 "정확히 30초"에 대한 판단
    setTimeout(30000) 단독은 이벤트 루프가 바쁘면 지연되어 30.4초가 될 수 있고,
    Node의 타이머는 지연을 보정해 주지 않는다.
    → 채택 방식: 절대 시각(endsAt)을 저장하고 100ms tick에서 비교한다.
      최대 오차는 +100ms이며 이는 사용자가 인지할 수 없는 수준이다.
      ★ 중요한 것은 "정답 인정 여부의 경계는 tick이 아니라 endsAt"이라는 점이다(2-3 (b)).
        즉 tick 오차가 게임 판정에 영향을 주지 않는다. 오차는 화면 전환 시점에만 나타난다.
    → 더 정밀한 하이브리드(대략 시각까지 setTimeout으로 자고 마지막 200ms만 촘촘히 확인)는
      과설계로 판단해 채택하지 않는다. 필요해지면 나중에 tick 주기만 줄이면 된다.

  · ★ 힌트를 서버가 push해야 하는 이유 (재확인)
    힌트를 question.started에 미리 담아 보내면 클라이언트가 30초 시점에 이미 힌트를
    가지고 있어 개발자 도구로 볼 수 있다. guide 11절(30~11초 힌트 없음)이 무너진다.
    따라서 서버가 남은 10초 시점에 question.hint 이벤트로 push한다.
    ★ 재접속·중간 참가 시 남은 시간이 10초 이하라면 스냅샷에 힌트를 포함한다(3-4).

  [클라이언트 측 — 시계 오프셋 측정]

  · 측정 절차
      1. 클라이언트가 time.ping { t0: Date.now() } 전송
      2. 서버가 time.pong { t0, tServer: Date.now() } 응답
      3. 클라이언트가 t1 = Date.now() 기록
      4. rtt = t1 - t0
         offset = tServer - (t0 + rtt / 2)      ← 서버시각 - 추정 클라시각
  · 측정 시점: 소켓 연결 직후 즉시 3회 연속(200ms 간격), 이후 30초마다 1회,
    그리고 문서 가시성이 복귀할 때 즉시 1회.
  · ★ 채택 값: 최근 5회 측정 중 rtt가 가장 작은 측정의 offset을 사용한다.
    자체 판단 근거: RTT가 작은 측정일수록 편도 지연의 비대칭이 작아 오프셋 추정이 정확하다.
    평균이나 중앙값은 큰 RTT 측정에 오염된다. NTP가 쓰는 방식과 같은 원리다.
  · 남은 시간 렌더링
      remaining = endsAt - (Date.now() + offset)
      화면에는 Math.max(0, Math.ceil(remaining / 1000))을 표시한다.
  · ★ 클라이언트 타이머가 0에 도달해도 어떤 상태 전환도 하지 않는다 (guide 45절).
    "결과 확인 중..." 정도만 표시하고 서버의 question.resolved를 기다린다.
    이것이 guide 45절 "클라이언트가 자체적으로 30초가 지났으니 다음 문제라고 판단하는 구조를
    기본 판정 로직으로 사용하면 안 된다"의 구현이다.

  [백그라운드 복귀 시 재동기화 — guide 46절]

  · document의 visibilitychange에서 visible이 되면 다음을 순서대로 수행한다.
      1. time.ping 즉시 1회 (오프셋 재측정)
      2. state.resync 전송
      3. 서버가 room.state 전체 스냅샷 응답 (3-4)
  · ★ 오프셋 재측정을 먼저 하는 이유: 모바일 브라우저는 백그라운드에서 타이머를 조이거나
    멈추고, 기기가 절전에서 복귀하면 시스템 시각이 보정되기도 한다. 오프셋이 낡은 상태에서
    스냅샷을 받으면 남은 시간이 틀리게 표시된다.
  · 소켓이 재연결된 경우에는 T-RECONNECT가 이미 스냅샷을 보내므로 state.resync가 중복되지
    않도록 클라이언트가 연결 상태를 확인한 뒤 보낸다.

3. Socket 이벤트 프로토콜
═══════════════════════════════════════════════════════════════

3-0. 공통 규약

  · 라이브러리: Socket.IO (R001 8-11 자체 판단, 승인됨)
  · 이벤트 이름은 `영역.동작` 점 표기. 소문자 카멜케이스.
  · 인증은 HTTP 핸드셰이크 시 httpOnly 쿠키로 이루어진다 (Q-07).
    소켓 이벤트로 로그인하지 않는다. 오리진이 하나이므로 쿠키가 그대로 붙는다 (1-1).
  · 모든 C→S 이벤트는 서버에서 다음을 순서대로 검사한다.
      1. 세션 유효성 → 실패 시 error { code: 'UNAUTHENTICATED' }
      2. 방 소속 여부 → 실패 시 error { code: 'NOT_IN_ROOM' }
      3. 권한 (방장 전용 액션) → 실패 시 error { code: 'NOT_HOST' }
      4. 상태 적합성 → 실패 시 error { code: 'INVALID_STATE' }
      5. 페이로드 스키마 → 실패 시 error { code: 'BAD_REQUEST' }
    ★ 클라이언트를 신뢰하지 않는다 (guide 44절). 클라이언트가 버튼을 숨기더라도
      서버가 모든 액션의 권한과 상태를 다시 검사한다.
  · 서버는 절대 정답 문자열을 QUESTION_ACTIVE 중에 클라이언트로 보내지 않는다.
    힌트도 10초 시점에만 보낸다 (2-4).

  S→C  game.result

         abortedNote: string | null
       }
       ★ 순위는 서버가 계산한다. 동점 공동 순위(guide 39절: 15/15/12 → 1/1/3)도 서버가 매긴다.

──── 시각 / 연결 유지 ────
  C→S  time.ping   { t0 }
  S→C  time.pong   { t0, tServer }
  C→S  heartbeat   { }                 ★ 4분마다. Q-02. Render 슬립 방지
  C→S  state.resync { }
       → 서버가 room.state로 응답

  ★ heartbeat에 대한 메모
    Socket.IO 자체의 ping/pong은 엔진 레벨의 프레임이며, Render가 이를 "인바운드
    WebSocket 메시지"로 계산하는지 확인할 수 없다(확인 불가).
    따라서 애플리케이션 레벨 heartbeat를 별도로 둔다. 4분 주기이므로 15분 슬립 기준에
    충분한 여유가 있고, 10명이 4분에 한 번 보내는 트래픽은 무시할 수 있다.
    ★ heartbeat 핸들러는 DB를 건드리지 않는다 (1-4 조건 1).

3-2. ★ 개인별 페이로드 분리

  [먼저 범위를 좁힌다]
    지시받은 대로 확인했다. Q-35에서 "경험자 닉네임 목록을 전원에게 공개"가 확정되었으므로,
    "누가 경험자인지"는 이제 공개 정보다.
    따라서 개인별 분리가 실제로 필요한 것은 두 가지뿐이다.
      (1) question.started / question.experiencedUpdated 의 selfExperienced
          — 사실 이것은 experiencedNicknames에 자기 accountId가 있는지 보면 알 수 있으므로,
            엄밀히 말하면 개인별 필드가 필요 없다.
          ★ 그래도 서버가 명시적으로 보내는 것을 권장한다. 근거:
            클라이언트가 목록을 검색해 판단하는 로직은 accountId 비교 실수 하나로
            "배지가 안 뜨거나 남에게 뜨는" 버그가 된다. 서버가 단정해서 보내면 그 실수가 없다.
            비용은 필드 하나이므로 사실상 0이다.
      (2) chat.message 의 text와 masked
          — 이것만이 진짜로 수신자마다 값이 달라야 하는 필드다.
            타인에게는 치환본 + masked=true, 발신자 본인에게는 원문 + masked=true (R002 6-4).
            마스킹이 걸리지 않은 메시지는 전원 동일 + masked=false.

    ★ 결론: R002가 우려한 만큼 복잡하지 않다. 사실상 chat.message 하나만 개인별로 갈린다.
      따라서 무거운 일반화 장치를 만들지 않는다. guide 52절의 "과복잡화 금지"를 적용한다.

  [메커니즘 — 최소 설계]

    브로드캐스트 헬퍼를 두 종류만 만든다.

    (가) emitRoom(room, event, payload)
         방 전체에 동일한 페이로드를 보낸다. 대부분의 이벤트가 이것을 쓴다.
         Socket.IO의 room broadcast 한 번이므로 비용이 가장 낮다.

    (나) emitRoomPerPlayer(room, event, basePayload, overrideFn)
         overrideFn(player) 가 부분 객체를 반환하면 basePayload와 병합해 개별 emit한다.
         null을 반환하면 basePayload를 그대로 보낸다.
         ★ 사용처는 chat.message와 question.started / question.experiencedUpdated 세 곳뿐이다.
         ★ 10명이므로 개별 emit 10회의 비용은 무시할 수 있다.

    ★ 규칙: overrideFn은 반드시 동기 함수여야 한다. 안에서 await를 하지 않는다.
      마스킹 계산에 필요한 정답 집합과 경험자 집합은 이미 메모리에 있다 (2-3 원칙 3).

  [selfVoted 처리]
    skip.voteUpdated의 selfVoted도 개인별 값이지만, 이것은 클라이언트가 자기 투표 상태를
    로컬에 들고 있으면 되므로 서버가 보낼 필요가 없다.
    ★ 자체 판단: skip.voteUpdated는 (가) emitRoom으로 동일 페이로드를 보내고,
      selfVoted는 클라이언트 로컬 상태로 관리한다. 재접속 시에는 room.state 스냅샷에
      selfVoted를 담아 복구한다(스냅샷은 애초에 개인별로 만들어진다).
      이렇게 하면 초당 여러 번 발생할 수 있는 투표 갱신 이벤트가 개별 emit이 되지 않는다.

3-3. ★ 마스킹과 정답 판정의 분리

  [원칙]
    · 정답 판정은 "수신 직후의 입력 처리"다. 입력은 항상 클라이언트가 보낸 원문이다.
    · 마스킹은 "브로드캐스트 직전의 출력 변환"이다. 출력만 바꾼다.
    · ★ 두 경로는 데이터를 공유하지 않는다. 마스킹 결과가 판정 입력으로 흘러들어갈 수 있는
      코드 경로가 존재하지 않도록 만든다.

  [chat.send 처리 파이프라인 — 순서 고정]

    onChatSend(socket, { text: rawInput, epoch }) {
      // ── 단계 1. 검증 (동기)
      //   세션 / 방 소속 / 길이 100자 초과 절단 또는 거부 / rate limit (Q-18)
      //   rate limit 초과 시 chat.throttled를 본인에게만 보내고 종료
      //
      // ── 단계 2. 판정 경로 (동기, await 금지)
      //   입력: rawInput  ★ 이 단계는 마스킹을 전혀 알지 못한다
      //   판정 조건 (모두 만족해야 정답 후보):
      //     room.state === QUESTION_ACTIVE
      //     q.resolved === false
      //     epoch === q.epoch                        ← 장치 B
      //     receivedAt <= q.endsAt                   ← 2-3 (b)
      //     player.connected === true
      //     !q.experiencedAccountIds.has(accountId)  ← guide 28절, Q-23 기준
      //     q.answersNorm.has(normalize(rawInput))   ← 4장 정규화 함수
      //   만족하면 resolveQuestion('correct', accountId) 호출 (장치 A 포함)
      //
      // ── 단계 3. 브로드캐스트 경로 (동기)
      //   maskedText = maskAnswers(rawInput, q, sender)   ← 아래 조건일 때만 치환
      //   emitRoomPerPlayer('chat.message', base, p =>
      //       p.accountId === sender.accountId ? { text: rawInput, masked } : null)
      //
      // ── 단계 4. DB 기록 (비동기, 여기서부터 await 허용)
      //   정답이었다면 answer_events INSERT
      //   경험자의 정답 일치였다면 was_eligible=false로 INSERT (통계용)
      //   일반 채팅은 저장하지 않는다 (Q-09)
    }

    ★ 단계 2가 단계 3보다 먼저인 이유
      정답이 확정되면 question.resolved를 보내야 하는데, 그보다 먼저 chat.message가
      나가야 화면에 "철수: 훈민정음" 다음에 "정답! 철수"가 뜬다.
      → 그래서 단계 2에서는 판정만 하고, 이벤트 전송 순서는 단계 3(chat.message) →
        resolveQuestion이 큐에 넣은 question.resolved 순으로 맞춘다.
      ★ 구현 지침: resolveQuestion은 상태 전환만 동기로 하고,
        question.resolved emit은 단계 3 이후에 수행한다.
        (전환과 전송을 분리해도 원자성은 유지된다. 원자성은 resolved 플래그가 보장한다.)

    ★ 마스킹 대상 조건 (Q-35 / Q-43)
      다음을 모두 만족할 때만 마스킹한다.
        room.state === QUESTION_ACTIVE          ← RESOLVED 이후에는 마스킹하지 않는다
        AND q.resolved === false
        AND q.experiencedAccountIds.has(sender.accountId)   ← 경험자의 메시지만
      ★ 미경험자의 메시지는 절대 마스킹하지 않는다.
        R002 6-5 케이스 14가 지적한 위험이 여기서 차단된다.
        그리고 설령 마스킹 조건 판정이 틀려서 미경험자의 메시지가 마스킹되더라도,
        단계 2는 이미 rawInput으로 판정을 끝냈으므로 정답 판정은 영향을 받지 않는다.
        ★ 이 이중 안전성이 파이프라인을 이 순서로 고정하는 이유다.

  [인덱스 매핑 구현 지침 — R002 6-3의 까다로운 부분]

    문제: 정규화는 공백을 제거하고 문자를 바꾸므로, 정규화 문자열에서 정답을 찾아도
          원문의 어느 구간을 가려야 하는지 알 수 없다.

    ★ 선행 처리 — NFC를 먼저 전체에 적용한다
      NFC 정규화는 문자 단위가 아니라 시퀀스 단위로 결합한다(e + U+0301 → é).
      따라서 문자 하나씩 매핑을 만들면 결합이 일어나는 지점에서 인덱스가 어긋난다.
      → 해결: 원문에 먼저 NFC를 적용해 rawNfc를 만들고, 그 rawNfc를 기준으로 매핑을 만든다.
        마스킹 결과도 rawNfc를 치환해 만든다.
      ★ 부작용: 사용자에게 표시되는 채팅 텍스트가 NFC 정규화된 형태가 된다.
        시각적으로 동일하므로 문제가 없다고 판단한다. 이 점을 문서에 명시한다.

    절차
      1. rawNfc = raw.normalize('NFC')
      2. rawNfc를 코드 포인트 단위로 순회하며 두 배열을 만든다.
           norm: 정규화 결과 문자열 (NFC 이후 단계 = 제로폭 제거, 전각→반각,
                 아포스트로피·하이픈 통일(Q-36), 공백 제거, 소문자화)
           map:  norm의 각 문자가 rawNfc의 어느 인덱스에서 왔는지
         ★ 문자 하나가 0글자로 사라질 수 있고(공백, 제로폭) 1글자로 바뀔 수 있다.
           2글자 이상으로 늘어나는 변환은 이 정규화에 없다(NFKC를 쓰지 않기 때문이다).
           이 사실이 매핑을 단순하게 유지해 준다.
      3. 정답 후보를 길이 내림차순으로 정렬한다 (R002 6-3: 긴 것 우선 치환)
      4. 각 후보의 정규화 값을 norm에서 indexOf로 찾는다.
         · 후보의 정규화 길이가 2 이하이면(Q-43) norm 전체가 후보와 완전히 같을 때만 매칭
         · 그 외에는 부분 포함 매칭
      5. 찾은 [s, e) 구간을 map으로 원문 구간 [map[s], map[e-1] + (그 문자의 길이)) 로 되돌린다
      6. 그 구간을 센티널 문자(U+E000, Q-42)로 치환한다. 치환 후 남은 부분에서 다시 검색해
         같은 후보가 여러 번 나오면 모두 치환한다.
      7. 치환이 일어났으면 masked = true

    ★ 주의: 치환 후 인덱스가 어긋나므로, 뒤에서 앞으로 치환하거나 매칭 구간을 모두 수집한
      뒤 한 번에 조립한다. 후자를 권장한다.

    ★ 클라이언트 렌더링 (Q-42)
      센티널 U+E000은 사설 사용 영역이라 사용자가 키보드로 입력할 수 없다.
      클라이언트는 이 문자를 만나면 "가려짐" 칩으로 렌더한다.
      ★ 렌더링에 실패하더라도 정답 문자열은 이미 서버에서 제거되었으므로 유출되지 않는다.
      ★ 길이는 항상 센티널 1글자다. 정답 길이가 새지 않는다 (Q-35 확정 사항).

    ★ 한계 (문서에 명시)
      "고무-줄"처럼 기호를 끼우거나 "ㄱㅁㅈ"처럼 초성으로 쓰면 막을 수 없다.
      완벽한 차단은 fuzzy matching을 요구하는데 guide 16절이 이를 금지한다.
      친구들끼리 하는 게임이므로 "무심코 흘리는 것"을 막는 수준으로 설계했다.
      docs\07-DECISIONS.md에 이 판단 근거를 남긴다.

3-4. 재접속 상태 복구 페이로드

  [단일 스냅샷 이벤트 room.state 로 통일한다]

    ★ 판단: 중간 참가(guide 31절)와 재접속(guide 34절)은 같은 페이로드를 쓴다.
      근거를 밝힌다.
      · guide 31절이 중간 참가자에게 요구하는 항목(현재 문제 / 남은 시간 / 현재 힌트 상태 /
        현재 점수 / 참가자 목록 / 채팅)은 guide 34절이 재접속자에게 요구하는 항목의
        부분집합이다.
      · 두 경우의 차이는 "내 점수가 0인가 이전 값인가", "내 색상이 새로 배정되는가 유지되는가"
        인데, 이는 서버가 스냅샷을 만들 때 이미 결정되어 값으로 들어간다.
        페이로드 구조를 다르게 할 이유가 없다.
      · 페이로드를 하나로 두면 state.resync도 같은 것을 재사용할 수 있고,
        테스트도 한 벌로 끝난다. guide 52절의 과복잡화 금지에 부합한다.
      ★ 단 구분 정보가 필요한 곳이 하나 있다. 클라이언트가 "지금 처음 들어온 것인지
        돌아온 것인지"에 따라 안내 문구를 다르게 보여주고 싶을 수 있다.
        → 스냅샷에 reason 필드를 둔다: 'join' | 'reconnect' | 'resync'

  [room.state 페이로드]

    {
      reason: 'join' | 'reconnect' | 'resync',
      serverTime,                          ← 오프셋 보정 보조용
      seq,                                 ← 현재 서버 시퀀스 (3-5)

      me: { accountId, nickname, colorIndex, isHost, connected },

      room: {
        id, title, hostAccountId,
        state: 'LOBBY'|'COUNTDOWN'|'QUESTION_ACTIVE'|'QUESTION_RESOLVED'|'GAME_RESULT',
        maxPlayers: 10,
        settings: { questionCount, startMode, countdownSec },
        settingsLocked,
        availableQuestionCount                ← Q-21 상한 안내
      },

      players: [                              ← guide 34·35절
        { accountId, nickname, colorIndex, connected, isHost, joinOrder, score }
      ],

      countdown: { endsAt } | null,

      question: {                             ← QUESTION_ACTIVE / QUESTION_RESOLVED 일 때만
        epoch, index, total,
        text, categoryName,
        startedAt, endsAt,
        hint: string | null,                  ★ 남은 시간이 10초 이하일 때만 값이 온다
                                                 (2-4). 그 전에는 반드시 null
        experiencedNicknames: [{ accountId, nickname, colorIndex }],
        selfExperienced: boolean,
        resolved: boolean,
        resolution: {                         ← QUESTION_RESOLVED 일 때만
          reason, winnerAccountId, displayAnswer, explanation, nextAt
        } | null
      } | null,

      skip: { votes, threshold, activeCount, selfVoted } | null,

      chat: [ { id, seq, accountId, nickname, colorIndex, text, masked, ts } ],
                                              ★ 최근 200개 (Q-19)
                                              ★ 이 배열의 text도 수신자 기준으로 마스킹된다.
                                                 스냅샷은 애초에 개인별로 만들어지므로
                                                 자연스럽게 처리된다

      result: {                               ← GAME_RESULT 일 때만
        gameId, endReason, ranking, lastQuestionReveal, abortedNote
      } | null,

      experienceRates: [ { accountId, experienced, total } ] | null   ← LOBBY 일 때만
    }

  ★ 스냅샷 생성 시 주의
    · 힌트는 반드시 남은 시간 조건을 서버가 검사한 뒤에 넣는다. 조건을 빼먹으면
      재접속만으로 힌트를 미리 볼 수 있는 우회로가 생긴다.
    · 정답 문자열은 QUESTION_ACTIVE 스냅샷에 절대 넣지 않는다.
      resolution.displayAnswer는 QUESTION_RESOLVED 이후에만 값이 있다.
    · chat 배열의 과거 메시지 마스킹은 "그 메시지를 보낸 시점의 문제"가 아니라
      "현재 진행 중인 문제의 정답"을 기준으로 하면 안 된다.
      ★ 이건 놓치기 쉬운 함정이다. 판단: 마스킹은 메시지를 브로드캐스트할 때 이미
        확정되므로, chatBuffer에는 원문과 함께 "치환된 텍스트"를 미리 저장해 둔다.
        스냅샷은 저장된 값을 그대로 쓴다. 재계산하지 않는다.
        · 저장 형태: { rawNfc, maskedText | null, senderAccountId }
        · 스냅샷 생성 시 수신자가 발신자면 rawNfc, 아니면 maskedText ?? rawNfc
      이렇게 하면 문제가 바뀌어도 과거 메시지의 마스킹이 흔들리지 않는다.

3-5. 시퀀스 번호

  · 서버에 프로세스 전역 단조 증가 카운터를 둔다. 모든 인바운드 소켓 이벤트를 처리할 때
    가장 먼저 seq를 발급한다.
  · 자료형: number를 쓴다. Number.MAX_SAFE_INTEGER(약 9.007×10^15)까지 안전하므로
    이 프로젝트에서 넘칠 일이 없다. BigInt는 불필요한 복잡도다.
  · ★ 프로세스가 재시작되면 0부터 다시 시작한다. 이것이 문제가 되는가?
    판단: 문제가 되지 않는다. seq의 목적은 "한 문제 안에서 어느 메시지가 먼저 도착했는지"를
    추적하는 것이고, 재시작하면 진행 중이던 게임 자체가 사라진다(R002 8-3).
    다만 DB에 저장되는 answer_events.submitted_seq는 게임 간 비교가 무의미해지므로,
    ★ answer_events에는 seq와 함께 response_ms(문제 시작 이후 경과 ms)를 반드시 저장한다.
    통계와 사후 검증은 response_ms로 하고, seq는 같은 문제 안의 순서 확인에만 쓴다.

  · 남기는 위치
    (가) 로그  — 모든 인바운드 이벤트를 한 줄로 남긴다.
         형식: seq / 시각 / roomId / accountId / event / epoch / 요약
         ★ 정답 판정 관련 이벤트는 판정 결과(eligible / matched / accepted 또는 거부 사유)도
           함께 남긴다. guide 18절 "처리 순서를 명확하게 추적"의 실질적 구현이다.
         ★ 채팅 본문 전체를 로그에 남기지 않는다. 길이와 해시 정도만 남긴다.
           공개 저장소에 로그가 실려 나갈 일은 없지만, 플랫폼 로그에 대화가 쌓이는 것을
           피한다. 정답 일치 여부 판정에 필요한 정보는 "matched: true/false"로 충분하다.
    (나) DB   — answer_events.submitted_seq 에만 저장한다.
         일반 채팅은 DB에 저장하지 않으므로(Q-09) seq도 저장하지 않는다.
    (다) chat.message 페이로드에 seq를 실어 보낸다.
         클라이언트가 메시지 정렬과 중복 제거에 쓴다. 재접속 시 스냅샷의 seq와 비교해
         이후 메시지만 이어 붙일 수 있다.

4-0. 설계 방침

  · R002 3장의 문제 데이터 구조(sources / categories / question_raw / questions /
    question_answers / review_queue)를 그대로 이어받는다. 변경 없다.
  · 게임 서버가 읽고 쓰는 테이블과 데이터 파이프라인이 쓰는 테이블을 명확히 나눈다.
      게임 서버가 쓰는 것:  accounts, sessions, rooms, games, game_players,
                            game_questions, question_experiences, answer_events
      게임 서버가 읽기만:   questions, question_answers, categories
      파이프라인 전용:      sources, question_raw, review_queue
                            (+ questions, question_answers 에 쓰기)
    ★ 이 단방향 관계를 docs\03-DATA-MODEL.md에 명시한다 (R002 2-3 지침).
  · 모든 시각 컬럼은 timestamptz를 쓴다. 서버가 UTC로 저장하고 표시만 로컬로 한다.
  · ★ 쓰기 빈도를 항상 함께 명시한다. Neon Free 한도(1-3)와 직결되기 때문이다.

4-1. 계정 / 세션

[accounts]
  id              bigserial PK
  login_id        text NOT NULL UNIQUE
  password_hash   text NOT NULL
  nickname        text NOT NULL UNIQUE
  created_at      timestamptz NOT NULL DEFAULT now()
  updated_at      timestamptz NOT NULL DEFAULT now()

  · nickname: PostgreSQL의 text UNIQUE는 기본적으로 대소문자를 구분하므로
    guide 3절("Player와 player는 다른 닉네임")과 Q-05(전역 유일)가 그대로 만족된다.
    ★ 별도 처리가 필요 없다. citext나 lower() 인덱스를 쓰면 오히려 규칙을 깨뜨린다.
  · ★ login_id의 대소문자 처리는 guide에 규정이 없다.
    자체 판단: 아이디는 대소문자를 구분하지 않고 유일하게 한다.
    근거: 로그인 시 대소문자를 틀려 실패하는 것은 순수한 불편이고, 닉네임과 달리
    아이디는 화면에 표시되지 않아 구분할 이유가 없다.
    구현: login_id는 소문자로 정규화해 저장하고 UNIQUE를 건다. 원본 입력은 보관하지 않는다.
    ★ 이견이 있으면 알려주면 바꾼다.
  · password_hash: argon2id 권장 (R001 8-11 승인). 최소 8자 (Q-04).
    ★ Q-04에 따라 복구 기능을 만들지 않으므로, 관리 스크립트
      (scripts/reset-password.ts 형태)를 R004에서 제공하고 docs에 사용법을 남긴다.
  · 쓰기 빈도: 가입 시 1회, 닉네임·비밀번호 변경 시 1회. 사실상 0.

[sessions]
  id              uuid PK DEFAULT gen_random_uuid()
  account_id      bigint NOT NULL FK → accounts
  token_hash      text NOT NULL UNIQUE
  created_at      timestamptz NOT NULL DEFAULT now()
  expires_at      timestamptz NOT NULL
  last_seen_at    timestamptz NOT NULL DEFAULT now()
  user_agent      text NULL

  인덱스: (token_hash) UNIQUE, (account_id), (expires_at)

  · 쿠키에는 랜덤 토큰 원본을 담고 DB에는 해시만 저장한다.
    ★ DB가 유출되어도 세션을 탈취할 수 없게 한다. 저장소가 Public인 프로젝트이므로
      이런 기본 방어는 확실히 해 둔다.
  · ★ Q-06(계정당 활성 연결 1개)과의 관계에 대한 자체 판단
    세션은 계정당 여러 개를 허용하고, 소켓 연결만 1개로 강제한다.
    근거: 세션을 1개로 제한하면 폰에서 로그인하는 순간 PC가 로그아웃되어,
    "PC에서 게임하고 폰으로도 접속해 보는" 흔한 동작이 불가능해진다.
    Q-06이 막으려는 것은 "한 사람이 슬롯 2개를 점유하는 것"이므로 소켓 레벨 제한으로 충분하다.
  · ★ 30일 슬라이딩 갱신의 쓰기 빈도 완화 (Q-07)
    매 요청마다 last_seen_at을 UPDATE하면 DB 쓰기가 폭증하고 DB가 계속 깨어 있게 되어
    Neon 스케일 투 제로를 방해한다(1-4 조건 1과 정면 충돌).
    자체 판단: expires_at 까지 남은 기간이 전체 기간의 절반(15일) 미만일 때만 갱신한다.
    즉 한 세션당 최대 15일에 한 번 UPDATE한다.
    효과: 사용자 체감은 동일(30일 슬라이딩)하면서 쓰기는 사실상 0이 된다.
  · 만료 세션 정리: 별도 크론을 두지 않는다. ★ DB를 주기적으로 깨우는 잡을 만들지 않는다.
    로그인 시도 시 그 계정의 만료 세션만 함께 지운다(기회주의적 정리).
  · 쓰기 빈도: 로그인 1회 + 15일에 1회. 무시 가능.

4-2. 방

[rooms]
  id              text PK               ★ 초대 링크에 들어가므로 추측 불가한 랜덤 문자열
  title           text NOT NULL
  host_account_id bigint NOT NULL FK → accounts     생성 당시 방장(이후 이전되어도 갱신 안 함)
  created_by      bigint NOT NULL FK → accounts
  created_at      timestamptz NOT NULL DEFAULT now()
  closed_at       timestamptz NULL

  인덱스: UNIQUE (created_by) WHERE closed_at IS NULL      ← Q-14 "1인당 동시 1개"를 DB가 강제
          (closed_at)

  ★ 방을 DB에 둘 것인가 (지시받은 판단 항목)
    결론: 둔다. 단 참가자 목록과 진행 중 게임 상태는 메모리에만 둔다.

    근거
    (1) guide 49절이 "존재하지 않는 방 링크"와 "게임이 이미 종료된 방"을 각각 다르게
        안내하라고 요구한다. 서버 재시작으로 메모리가 비면 이 둘을 구분할 수 없어
        모든 링크가 "존재하지 않는 방"이 된다. rooms 레코드가 있으면
        "이 방은 종료되었습니다"를 정확히 안내할 수 있다.
    (2) Q-14의 "1인당 동시 보유 방 1개"를 부분 UNIQUE 인덱스로 DB가 강제할 수 있다.
        메모리로만 관리하면 재시작 후 제한이 풀린다.
    (3) games 테이블이 room_id를 참조해야 게임 이력이 방과 연결된다 (guide 40절 통계).
    (4) 쓰기 빈도가 극히 낮다. 방 생성 시 INSERT 1회, 삭제 시 UPDATE 1회.
        Neon 관점에서 부담이 전혀 없다.

    반대로 참가자 목록과 게임 상태를 메모리에만 두는 근거
    (1) guide 48절이 "현재 진행 중인 실시간 게임 상태는 서버 메모리와 영속 데이터베이스를
        적절히 조합해 구현할 수 있다"고 명시적으로 허용한다.
    (2) 참가자 접속 상태는 초 단위로 바뀐다. 이를 DB에 반영하면 DB가 계속 깨어 있게 되어
        1-4 조건 1이 무너진다.
    (3) 서버가 재시작되면 소켓이 전부 끊기므로 참가자 목록을 복원해도 의미가 없다.

    ★ Q-02의 "게임 상태 DB 스냅샷" 요구와의 관계
      Q-02가 지키려는 것은 "프로세스가 죽어도 친구들의 점수와 경험 기록이 날아가지 않는 것"이다.
      이는 방/참가자 상태를 저장해서 달성하는 것이 아니라,
      answer_events와 question_experiences를 문제 단위로 즉시 기록해서 달성한다(4-4, 4-5).
      즉 "방 상태를 통째로 스냅샷"하지 않고 "되돌릴 수 없는 사실만 즉시 기록"한다.
      ★ 이 해석을 docs\07-DECISIONS.md에 남긴다. 재시작 후 진행 중이던 게임 자체는
        복원되지 않으며, 그 게임은 endReason 없이 ended_at만 비어 있는 상태로 DB에 남는다.
        시작 시 그런 미완결 게임을 정리하는 절차를 R004에서 넣는다.

4-3. 게임

[games]
  id                      bigserial PK
  room_id                 text NOT NULL FK → rooms
  started_at              timestamptz NOT NULL DEFAULT now()
  ended_at                timestamptz NULL
  end_reason              text NULL      'completed'|'force_ended'|'no_questions'|'no_players'
  setting_question_count  int NOT NULL
  setting_start_mode      text NOT NULL  'instant'|'countdown'
  setting_countdown_sec   int NULL
  planned_question_count  int NOT NULL   시작 시점의 출제 가능 수 검증 결과 (Q-21)
  ended_question_count    int NULL       실제로 출제된 문제 수 (조기 종료 시 더 작다)

  인덱스: (room_id), (started_at)
  쓰기 빈도: 게임 시작 시 INSERT 1회, 종료 시 UPDATE 1회. 게임당 2회.

[game_players]
  game_id           bigint NOT NULL FK → games
  account_id        bigint NOT NULL FK → accounts
  PRIMARY KEY (game_id, account_id)
  color_index       smallint NOT NULL
  joined_at         timestamptz NOT NULL      ★ 중간 참가 판별에 사용
  is_midgame_join   boolean NOT NULL
  final_score       int NULL                  게임 종료 시에만 채운다
  final_rank        smallint NULL             동점 공동 순위 (guide 39절)
  connected_at_end  boolean NULL

  인덱스: (account_id)
  쓰기 빈도: 참가 시 INSERT 1회(중간 참가 포함), 종료 시 UPDATE 1회.

  ★ 게임 진행 중에 점수를 UPDATE하지 않는다. 이것이 이 스키마의 핵심 결정이다.
    근거: 점수는 answer_events(정답 이벤트)로부터 완전히 계산할 수 있다.
    문제가 해결될 때마다 game_players.final_score를 UPDATE하면 30문제 게임에서
    30번의 UPDATE가 발생하는데, 같은 정보를 answer_events INSERT 하나로 이미 남기고 있다.
    → 중복 쓰기를 없애고, 대신 이력이 남는 INSERT를 정본으로 삼는다.
    → 재시작 복구 관점에서도 answer_events가 있으면 점수를 재구성할 수 있으므로
      Q-02 요구를 만족한다.
    → final_score는 게임 종료 시 한 번 확정해 넣는다. 이후 통계 조회가 조인 없이 빨라진다
      (파생 값의 의도적 비정규화. 그 근거를 docs에 남긴다).

[game_questions]
  game_id           bigint NOT NULL FK → games
  question_index    smallint NOT NULL         1-based
  PRIMARY KEY (game_id, question_index)
  question_id       bigint NOT NULL FK → questions
  epoch             int NOT NULL              ★ 2-3 장치 B의 epoch. 사후 추적용
  started_at        timestamptz NOT NULL
  resolved_at       timestamptz NULL
  resolution        text NULL   'correct'|'timeout'|'skip_vote'|'host_skip'|'aborted'
  winner_account_id bigint NULL FK → accounts
  skip_votes_at_end smallint NULL
  active_at_end     smallint NULL             해결 시점 활성 인원 (스킵 임계값 검증용)

  인덱스: (question_id), (winner_account_id)
  UNIQUE (game_id, question_id)    ★ 한 게임에서 같은 문제 중복 출제 금지 (FLOW-10)를 DB가 강제

  쓰기 빈도: 문제 시작 시 INSERT 1회, 해결 시 UPDATE 1회. 문제당 2회.
  ★ 시작 시 INSERT를 하는 이유: 강제 종료(resolution='aborted')된 문제도 기록에 남아야
    "이 게임에서 몇 번째 문제까지 갔는지"를 알 수 있다. 해결 시에만 쓰면 중단된 문제가 사라진다.

4-4. 문제 경험 (guide 26절의 장기 자산)

[question_experiences]
  account_id            bigint NOT NULL FK → accounts
  question_id           bigint NOT NULL FK → questions
  PRIMARY KEY (account_id, question_id)
  first_experienced_at  timestamptz NOT NULL DEFAULT now()
  first_game_id         bigint NULL FK → games

  인덱스: (question_id)     경험자 수 집계용
          PK가 (account_id, question_id)이므로 "이 계정이 이 문제를 경험했는가"는 PK 조회

  · 쓰기 시점: ★ Q-23 확정대로 "정답이 공개되는 시점"에 그 시점 접속 중인 플레이어에게만.
    정답 공개 경로 3종(T06 정답자 / T07 시간 종료 / T08·T09 스킵)에서만 쓴다.
    ★ T11(강제 종료), T13(활성 0명)에서는 쓰지 않는다 (Q-25 확정).
  · 구현: 문제 해결 블록이 끝난 뒤 비동기로 다중 행 INSERT 1회.
      INSERT INTO question_experiences (account_id, question_id, first_game_id)
      VALUES (...), (...), ...
      ON CONFLICT (account_id, question_id) DO NOTHING
    ★ ON CONFLICT DO NOTHING이 중요하다. 이미 경험한 사람이 다시 그 문제를 보는 경우
      (경험자는 판정에서 제외되지만 문제 자체는 보인다) first_experienced_at이
      덮어써지면 "처음 경험한 시점"이 손실된다.
  · 쓰기 빈도: 문제당 1회(최대 10행). 30문제 게임이면 30회.
    ★ 게임 중에는 어차피 DB가 깨어 있어야 하므로 Neon 관점에서 문제없다.
    ★ 이 쓰기는 지연시킬 수 없다. Q-23이 "즉시"를 확정했고, guide 25절이
      "강제 종료해도 이미 남은 경험 기록은 롤백되면 안 된다"를 요구하므로,
      게임 종료 시 일괄 기록하면 강제 종료 시 누락된다.
  · ★ 삭제하지 않는다. guide 25·26절이 장기 보존을 요구한다.
    "다시 하기"(T16)에서도 초기화하지 않는다 (guide 8절).

4-5. 응답 기록 (guide 40절 통계 원천)

[answer_events]
  id                bigserial PK
  game_id           bigint NOT NULL FK → games
  question_index    smallint NOT NULL
  question_id       bigint NOT NULL FK → questions
  account_id        bigint NOT NULL FK → accounts
  submitted_seq     bigint NOT NULL           ★ 3-5 시퀀스
  received_at       timestamptz NOT NULL
  response_ms       int NOT NULL              ★ 문제 시작 이후 경과 (서버 수신 시각 기준)
  matched           boolean NOT NULL          정답 문자열과 일치했는가
  was_eligible      boolean NOT NULL          판정 자격이 있었는가 (경험자면 false)
  accepted          boolean NOT NULL          최종적으로 정답자가 되었는가
  reject_reason     text NULL   'already_resolved'|'experienced'|'epoch_mismatch'|'past_deadline'
                                |'not_connected'

  인덱스: (game_id, question_index), (account_id), (question_id)

  ★ 저장 대상을 좁힌다 (Q-09와 일관)
    저장하는 것:
      (a) 정답 문자열과 일치한 모든 메시지 (matched = true)
          → accepted 여부와 reject_reason으로 "왜 정답이 안 됐는지"까지 남는다.
            guide 18절의 순서 추적과 동시 정답 사후 검증에 필수적이다.
      (b) 그 외에는 저장하지 않는다.
    저장하지 않는 것:
      일반 오답 채팅. guide 54절의 "미친 듯이 입력하는" 특성상 양이 매우 많고,
      Q-09에서 채팅 로그를 DB에 저장하지 않기로 확정했다.

  ★ 쓰기 빈도: 문제당 보통 1~3행(정답 문자열을 친 사람 수). 30문제면 30~90행.
    한 문제에서 여러 명이 동시에 정답을 쳐도 최대 10행이다. 부담이 없다.

  ★ 이 테이블이 Q-02의 "게임 진행 중 상태 스냅샷"을 실질적으로 담당한다.
    프로세스가 죽어도 (game_questions + answer_events)로 점수를 재구성할 수 있고,
    question_experiences는 이미 확정되어 있다.

4-6. ★ guide 40절 통계 역검증

  guide 40절이 향후 활용 후보로 든 9종을 이 스키마로 계산할 수 있는지 하나씩 확인했다.

  1. 플레이한 문제 수
     계산 가능. game_players.joined_at 이후에 시작된 game_questions를 센다.
       SELECT count(*) FROM game_questions gq
       JOIN game_players gp ON gp.game_id = gq.game_id AND gp.account_id = :id
       WHERE gq.started_at >= gp.joined_at
     ★ 중간 참가자(guide 32절)가 참가 전 문제를 자기 통계에 포함하지 않게 된다.
       joined_at이 있기 때문에 정확히 계산된다.
     ★ 접속이 끊겼던 구간의 문제는 어떻게 세는가? 이 스키마로는 구분되지 않는다.
       판단: guide 33절이 연결 종료자도 게임에 계속 참가한 것으로 취급하므로
       "플레이한 문제 수"에 포함하는 것이 정합적이다. 문제없다.

  2. 정답 수
     계산 가능. game_questions.winner_account_id = :id 를 센다.
     (answer_events.accepted = true 로도 계산 가능하며 두 값이 일치해야 한다.
      ★ 이 일치 여부를 테스트 항목으로 등록한다. 불일치는 판정 로직 버그의 신호다.)

  3. 정답률
     계산 가능. 2 / 1.

  4. 문제별 정답 여부
     계산 가능. game_questions (game_id, question_index, question_id, winner_account_id).

  5. 문제별 응답 시간
     계산 가능. answer_events.response_ms.
     ★ 단 범위에 제약이 있다. 정답 문자열을 친 사람의 응답 시간만 남는다.
       "오답을 친 사람이 몇 초에 반응했는가"는 남지 않는다(일반 채팅을 저장하지 않으므로).
       guide 40절의 예시가 "평균 정답 시간 3.1초"이므로 요구는 충족한다고 판단한다.
       ★ 이 한계를 명시하고 Q-52로 올린다.

  6. 카테고리별 성적
     계산 가능. game_questions ⋈ questions.category_id ⋈ categories.
     정답 수 / 플레이 수를 카테고리로 묶는다.
     ★ R002 3장에서 카테고리를 처음부터 넣기로 한 판단이 여기서 값을 한다.
       나중에 넣으면 이미 쌓인 게임 기록의 카테고리를 소급할 수 없다.

  7. 게임별 점수
     계산 가능. game_players.final_score (종료된 게임) 또는 answer_events 집계(진행 중).

  8. 게임 참가 기록
     계산 가능. game_players ⋈ games (started_at, ended_at, end_reason 포함).

  9. 문제 경험 기록
     계산 가능. question_experiences.

  ★ 결론: 9종 전부 계산 가능하다. 스키마를 고칠 필요가 없다.
    유일한 제약은 5번의 범위(정답 시도만)이며 Q-52로 확인받는다.

  ★ 추가로 guide 40절 예시의 "총 풀이 문제 1,240개"는 1번으로,
    "과학 정답률 72%"는 6번으로 계산된다. 예시가 모두 커버된다.

4-7. 쓰기 빈도 종합 및 Neon 영향 검토

  ┌──────────────────────┬──────────────────────────┬──────────────────────┐
  │ 테이블                │ 쓰기 시점                │ 30문제 게임 1판 기준 │
  ├──────────────────────┼──────────────────────────┼──────────────────────┤
  │ accounts             │ 가입/변경                │ 0                    │
  │ sessions             │ 로그인 / 15일마다        │ 0                    │
  │ rooms                │ 방 생성 / 삭제           │ 0~2                  │
  │ games                │ 시작 / 종료              │ 2                    │
  │ game_players         │ 참가 / 종료 확정         │ 10 + 10 = 20         │
  │ game_questions       │ 문제 시작 / 해결         │ 30 + 30 = 60         │
  │ question_experiences │ 정답 공개 시 배치 INSERT │ 30회 (최대 300행)    │
  │ answer_events        │ 정답 문자열 일치 시      │ 30~90                │
  ├──────────────────────┼──────────────────────────┼──────────────────────┤
  │ 합계                  │                          │ 약 150~200회 쓰기    │
  └──────────────────────┴──────────────────────────┴──────────────────────┘

  · 30문제 게임 한 판(약 18분)에 150~200회 쓰기다. 초당 0.2회 수준이다.
    Neon 컴퓨트에는 부담이 전혀 없다.
  · ★ 중요한 것은 쓰기 횟수가 아니라 "DB를 깨워 두는 시간"이다.
    게임 중에는 계속 쓰기가 발생하므로 DB가 깨어 있다. 이는 불가피하고 정상이다.
    게임이 끝나면 쓰기가 멈추고 5분 뒤 스케일 투 제로에 들어간다.
    → 1-3의 활성 시간 추산("실사용 + 5분 꼬리")이 이 스키마에서 성립한다.
  · ★ 지키지 말아야 할 것 (1-4 조건 1의 재확인)
    - 주기적 카운터 갱신을 만들지 않는다. (game_players.final_score를 진행 중에
      UPDATE하지 않기로 한 것이 이 원칙의 적용이다)
    - 세션 last_seen_at을 매 요청마다 UPDATE하지 않는다. (4-1의 15일 규칙)
    - 만료 세션 정리 크론을 만들지 않는다. (4-1의 기회주의적 정리)
    - 헬스체크가 DB를 건드리지 않는다.
    - heartbeat 핸들러가 DB를 건드리지 않는다.
    - 로비의 경험률 조회는 로비 진입과 참가자 변동 시에만 한다. 주기 갱신하지 않는다.

4-8. 인덱스 / 제약 정리

  UNIQUE 제약이 규칙을 강제하는 지점 (애플리케이션 버그를 DB가 막아 준다)

    · question_answers: UNIQUE (question_id, answer_norm)   R002 3장. 정규화 중복 변형 차단

    · answer_events (account_id)                      개인 통계
    · game_questions (question_id)                    문제별 정답률 통계
    · game_players (account_id)                        개인 게임 이력
    · questions (status, is_active, category_id)       출제 대상 조회 (R002 3장)

  ★ 문제 선정 쿼리의 성능 메모
    Q-20의 2단계 알고리즘은 "참가자 전원이 미경험인 문제"를 찾아야 한다.
    문제 수 1,100건 × 참가자 10명이면 대상이 매우 작으므로,
    ★ 게임 시작 시 참가자별 경험 문제 ID 집합을 한 번에 조회해 메모리로 올리고
      선정은 메모리에서 수행하는 것을 권장한다.
      SELECT account_id, question_id FROM question_experiences
      WHERE account_id = ANY($1)
    이러면 매 문제마다 DB를 다시 조회하지 않아 쓰기·읽기 모두 줄어들고,
    2-3 원칙 3(판정 데이터를 메모리에 미리 로드)과도 일관된다.
    ★ 중간 참가자가 생기면 그 사람의 집합만 추가 조회한다.

4-9. 마이그레이션 방식

  ★ 이 항목은 유지보수성에 큰 영향을 주므로 Q-49로 올린다. 권장안과 근거만 적는다.

  후보
  (A) 순수 SQL 마이그레이션 파일 + 아주 작은 러너
      migrations/0001_init.sql, 0002_add_xxx.sql ... 를 순서대로 적용하고
      적용 이력을 schema_migrations 테이블에 남기는 100줄 이하의 스크립트.
      쿼리는 pg 드라이버로 직접 작성. 타입은 shared\에 수동 정의.
      장점: ★ 어떤 AI·어떤 개발자도 SQL은 그대로 읽는다. 생성 코드나 DSL이 끼어들지 않는다.
            guide 61절(다른 AI가 clone해서 이어받는다)에 가장 유리하다.
            스키마가 문서 그 자체가 된다(docs\03-DATA-MODEL.md와 1:1 대응).
      단점: 컴파일 타임 타입 안전성이 없다. 쿼리 오타가 런타임에 발견된다.
            수동 타입 정의와 실제 스키마가 어긋날 수 있다.
  (B) Drizzle ORM
      장점: TypeScript로 스키마를 정의하고 타입이 자동 추론된다. 마이그레이션 생성도 자동.
            SQL에 가까워 학습 부담이 Prisma보다 작다.
      단점: 스키마 정의가 TS DSL이 되어 SQL을 직접 읽을 수 없다.
            drizzle-kit의 마이그레이션 생성 결과를 매번 검토해야 한다.
  (C) Prisma
      장점: 생태계가 크고 문서가 많다. 타입 안전성이 가장 강하다.
      단점: 독자 스키마 언어 + 코드 생성 + 별도 엔진. 무게가 가장 크다.
            ★ Neon의 스케일 투 제로와 커넥션 풀 설정을 세밀하게 통제하기 어려울 수 있다
              (확인 필요). 1-4 조건 1이 가장 중요한 설정인데 이를 통제하기 어렵다면 부적합하다.

  ★ 권장: (A). 근거는 건우의 1순위 기준이 "Claude Code가 유지보수하기 쉬울 것"이라는 점이다.
    타입 안전성보다 "스키마와 쿼리가 그 자리에 그대로 보이는 것"이 이 기준에 더 부합한다고
    판단한다. 그리고 1-4 조건 1(커넥션 풀 idle timeout)을 pg 드라이버로 직접 통제할 수 있다.
    타입 안전성의 손실은 (i) shared\에 테이블별 타입을 수동 정의하고
    (ii) 주요 쿼리에 대한 통합 테스트를 두는 것으로 보완한다.
    최종 결정은 건우가 한다.

[Q-47] 마지막 문제의 정답 공개와 경험 기록 처리
──────────────────────────────────────────
- 배경: Q-17(마지막 문제는 5초를 기다리지 않고 즉시 결과 화면)과
  Q-23/24(경험 기록은 정답이 공개되는 시점에 남긴다)가 만나는 지점에 빈틈이 있다.
  마지막 문제에서 5초 대기를 생략하면 정답 공개 화면이 사실상 표시되지 않는다.
  그러면 두 가지가 불명확해진다.
    (1) 마지막 문제의 경험 기록이 남는가
    (2) 마지막 문제의 정답을 플레이어가 어디서 보는가
  또한 관련 케이스가 하나 더 있다. QUESTION_RESOLVED 구간(5초)에 입장한 사람은
  정답을 화면에서 보게 되지만, Q-23 기준으로는 "정답 공개 시점"이 이미 지났으므로
  경험 기록이 남지 않는다. guide 27절 원문("정답이 공개된 문제를 실제로 화면에서
  확인할 수 있었다면 경험 처리")과 반대 결과다.
- 선택지:
  (A) 정답 공개 이벤트는 발생시키고(경험 기록 남김) 즉시 결과 화면으로 전환한다.
      결과 화면 상단에 "마지막 문제 정답: OOO"을 표시한다.
      그리고 RESOLVED 구간 입장자는 경험 기록을 남기지 않는다(Q-23 문자 그대로).
      장점: 모든 문제가 동일하게 경험 기록을 남겨 규칙이 대칭이다.
            정답을 볼 수 있는 곳이 명확하다.
      단점: RESOLVED 구간 입장자가 "정답을 봤는데 경험 기록이 안 남는" 비대칭이 남는다.
  (B) (A) + RESOLVED 구간 입장자도 경험 기록을 남긴다.
      장점: guide 27절 원문의 취지("실제로 접했으면 경험")에 더 가깝다.
      단점: Q-23이 확정한 "정답 공개 시점의 접속자"라는 단일 기준이 흔들린다.
            "정답 공개 시점 또는 RESOLVED 구간 중 접속"이라는 두 조건이 된다.
  (C) 마지막 문제는 정답을 공개하지 않고 경험 기록도 남기지 않는다.
      장점: 5초 생략과 가장 일관된다.
      단점: 마지막 문제만 경험 기록이 안 남아 규칙이 비대칭이다.
            그리고 정답을 아무도 못 보고 게임이 끝나 허탈하다.
- 권장안: (A). 근거는 두 가지다.
  첫째, Q-17이 생략한 것은 "5초 대기"이고 "정답 공개" 자체가 아니라고 읽는 것이 자연스럽다.
  둘째, 마지막 문제만 경험 기록이 빠지면 나중에 "왜 이 문제만 다시 나오지"라는 혼란이 생긴다.
  RESOLVED 구간 입장자 문제는 (A)대로 두는 것을 권한다. 그 사람은 문제를 풀 기회가 없었고,
  경험 기록이 없으면 나중에 그 문제를 정상적으로 풀 수 있으므로 사용자에게 유리하다.
- 영향 범위: 중간. 경험 기록은 되돌리기 어려운 장기 데이터다.
- 시급도: [즉시] (Phase 3의 상태 머신 구현 전. R004 Phase 0에는 영향 없음)

[Q-48] "다시 하기"와 "로비로"의 실질 차이, 그리고 강제 퇴장자의 결과 포함 여부
──────────────────────────────────────────
- 배경 1: Q-31에서 "다시 하기 = 직전 설정값만 불러오고 게임은 자동 시작되지 않으며
  방장이 시작 버튼을 눌러야 한다"가 확정되었다. Q-32에서는 결과 화면에 "다시 하기"와
  "로비로" 두 버튼이 있다. 그런데 두 버튼 모두 결과적으로 LOBBY로 가고 설정도 유지된다면
  (설정은 어차피 방에 남아 있다) 실질 차이가 없어 버튼이 둘일 이유가 없다.
- 배경 2: Q-15에서 방장이 접속 종료자를 강제 퇴장시킬 수 있다.

- 선택지 (배경 1):
  (A) 버튼을 하나로 통합한다. "로비로 돌아가기" 하나만 둔다.
      장점: 가장 단순하고 혼란이 없다.

  (B) 차이를 UI로만 둔다. "다시 하기"는 로비로 가면서 시작 버튼에 포커스를 두고,
      "로비로"는 설정 편집 영역을 펼친다. 서버 동작은 동일.
      장점: 두 버튼의 의도(바로 또 하자 / 설정 좀 바꾸자)가 살아난다. 구현이 가볍다.
  (C) "다시 하기"는 설정 변경을 잠근 채 시작만 가능하게 하고, "로비로"는 설정을 풀어 준다.
      단점: 방장이 마음을 바꿔 설정을 고치려면 다시 로비로 가야 해서 불편하다.
- 선택지 (배경 2):
  (가) 강제 퇴장자의 game_players 레코드를 유지해 그 게임 결과에는 남긴다.

       단점: guide 33절 위반 소지. 그 사람이 얻은 점수 기록이 사라진다.
- 권장안: 배경 1은 (B), 배경 2는 (가).

[Q-50] 문제 선정 시점 — 게임 시작 시 전량 선정 vs 매 문제 선정
──────────────────────────────────────────
- 배경: Q-20의 2단계 선정 알고리즘은 "참가자"의 경험 이력에 종속된다. 그런데

- 선택지:
  (A) 게임 시작 시 N개를 전량 선정해 고정한다.

      단점: 중간 참가자의 경험 이력이 선정에 반영되지 않는다. 중간 참가자가 이미
            경험한 문제가 뒤에 그대로 나온다. Q-20의 취지가 약해진다.
  (B) 매 문제마다 그 시점 참가자 기준으로 선정한다. (2-2 [문제 시작 공통 절차]가 이 전제)

      단점: 문제 소진 여부를 미리 알 수 없어 조기 종료(T15)가 게임 중간에 발생할 수 있다.
            Q-21의 시작 시 검증은 "그 시점의 가능 수"에 대한 검증이 된다.
  (C) 절충: 시작 시 출제 가능 풀의 개수만 계산해 Q-21 검증에 쓰고, 실제 문제는
      매 문제마다 선정한다. 이미 출제한 문제는 제외한다.
      장점: 두 요구를 모두 만족한다.
      단점: 시작 시 검증을 통과했어도 중간 참가로 가능 수가 줄어 조기 종료될 수 있다.
            (이 경우는 Q-22가 이미 조기 종료를 허용하고 있으므로 규칙 위반은 아니다)
- 권장안: (C). 2-2의 명세는 (C)를 전제로 작성했다.
  근거: Q-20이 "미경험자 수 가중"을 요구하는데 이는 참가자 집합에 대한 함수이므로,

[Q-51] 연결 끊김 감지 지연 — Socket.IO ping 설정
──────────────────────────────────────────
- 배경: ★ 이번 라운드에서 발견한 문제다.
  Q-29는 "스킵 투표 분모와 활성 인원 표시는 연결 끊김 즉시 반영"으로 확정되었다.
  그런데 "연결이 끊겼다"를 서버가 아는 시점은 상황에 따라 다르다.
    · 브라우저 탭을 닫거나 새로고침하면 TCP 연결이 정상 종료되어 즉시 disconnect가 온다.
      → 이 경우는 진짜로 "즉시"다.
    · ★ 지하철 터널, 와이파이 단절, 기기 절전처럼 네트워크가 끊기면 TCP가 조용히 죽는다.
      서버는 Socket.IO의 ping/pong 타임아웃이 만료될 때까지 그 소켓을 살아 있다고 본다.
      Socket.IO 기본값은 pingInterval 25초 / pingTimeout 20초로, 최악의 경우 약 45초가
      지나야 감지된다.
  즉 Q-29의 "즉시"가 실제로는 최대 45초 지연될 수 있고, 그 동안 스킵 투표 분모에
  유령 플레이어가 남아 투표가 통과되지 않는다.
- 선택지:
  (A) pingInterval 10초 / pingTimeout 10초. 최대 약 20초 안에 감지.
      장점: Q-29의 취지에 가깝다. 스킵이 막히는 시간이 줄어든다.
      단점: 모바일에서 일시적인 지연이 잦으면 오탐(멀쩡한 사람이 끊긴 것으로 표시)이
            늘어난다. 표시가 깜빡이면 사용자 경험이 나빠진다.
  (B) 기본값(25/20초, 최대 약 45초) 유지.
      장점: 오탐이 적다. 모바일 친화적이다.
      단점: 스킵 분모에 유령이 최대 45초 남는다. 30초 문제 하나가 그 사이에 끝난다.
  (C) pingInterval 15초 / pingTimeout 10초 (최대 약 25초) + 애플리케이션 heartbeat를
      보조 신호로 사용.
      Q-02에서 이미 4분 heartbeat를 넣기로 했는데, 이를 30초로 줄이면 서버가
      "이 클라이언트는 살아 있다"를 더 자주 확인할 수 있다.
      단 heartbeat는 슬립 방지 목적이므로 주기를 줄이면 Render 인바운드 트래픽이 늘어난다
      (10명 × 2회/분 = 분당 20건. 무시 가능한 수준이다).
      장점: 감지 시간과 오탐 사이의 균형이 가장 좋다.
      단점: 설정이 두 곳으로 나뉜다.
- 권장안: (C). pingInterval 15초 / pingTimeout 10초, 애플리케이션 heartbeat 30초.
  ★ 단 Q-02 확정 사항인 "heartbeat 4분"을 30초로 바꾸는 것이므로 건우 확인이 필요하다.
    4분을 유지해야 한다면 (A)를 택한다.
  ★ 그리고 어느 값을 택하든, 실제 모바일 환경에서 오탐 빈도를 측정하는 것을
    Phase 5의 테스트 항목으로 등록한다. 값은 실측 후 조정한다.
- 영향 범위: 낮음. 설정값이다. 다만 Q-29의 실질적 동작을 결정한다.
- 시급도: [P4 전] (스킵은 Phase 4, 연결 안정성은 Phase 5)

6. 자체 판단 항목 / 다음 라운드 제안

6-1. 이번 라운드 자체 판단 항목 (기술적이고 되돌리기 쉬운 것만)

  아래는 질문하지 않고 결정했다. 이견이 있으면 알려주면 즉시 바꾼다.

  상태·전이
  · room.state 5종 + game.endReason 4종으로 표현한다. guide 9절의 FORCE_ENDED는
    endReason 값으로 남고 화면 흐름은 GAME_RESULT와 동일하다 (Q-31 확정 사항의 구현).
  · T13(활성 0명 종료) 시 정답을 공개하지 않는다. Q-25(강제 종료 시 미공개)와 같은 논리.
  · QUESTION_RESOLVED 구간에서 방장 강제 스킵 요청은 무시한다(무의미하므로).
  · 강제 종료 요청에는 epoch를 담지 않는다(게임 전체 액션이므로 특정 문제에 종속되지 않음).
  · 강제 스킵·스킵 투표 요청에는 epoch를 담는다(문제에 종속되므로).
  · 미접속 플레이어의 메시지는 정답 판정하지 않는다 (2-3 (i)).

  타이머
  · 방마다 타이머를 두지 않고 전역 100ms tick 하나로 모든 방을 순회한다.
  · 정답 인정 경계는 tick이 아니라 endsAt(서버 기록 종료 시각)으로 판정한다.
  · 클라이언트 오프셋은 최근 5회 측정 중 RTT가 가장 작은 것의 값을 채택한다.
  · 오프셋 측정은 연결 직후 3회(200ms 간격), 이후 30초마다, 가시성 복귀 시 즉시.

  프로토콜
  · 이벤트 이름은 `영역.동작` 점 표기.
  · skip.voteUpdated는 전원 동일 페이로드로 보내고 selfVoted는 클라이언트 로컬 상태로 둔다.
    (투표 갱신은 빈번하므로 개별 emit을 피한다)
  · selfExperienced는 클라이언트가 목록에서 유추하지 않고 서버가 명시적으로 보낸다.
  · 중간 참가와 재접속과 resync가 room.state 단일 스냅샷을 공유하고 reason 필드로 구분한다.
  · 마스킹은 브로드캐스트 시점에 확정해 chatBuffer에 원문과 치환본을 함께 저장한다.
    스냅샷에서 재계산하지 않는다 (3-4의 함정 방지).
  · 마스킹 매칭 전에 원문에 NFC를 먼저 적용하고, 그 결과를 기준으로 인덱스 매핑을 만든다.
    따라서 표시되는 채팅 텍스트는 NFC 정규화된 형태가 된다.
  · 시퀀스는 number를 쓴다(BigInt 불필요). 프로세스 재시작 시 0부터 시작하며,
    통계·사후 검증은 response_ms로 하고 seq는 같은 문제 안의 순서 확인에만 쓴다.
  · 로그에 채팅 본문을 남기지 않는다(길이와 일치 여부만).

  DB
  · login_id는 대소문자를 구분하지 않고 유일하게 한다(소문자 정규화 저장).
    nickname은 guide 3절대로 대소문자를 구분한다.
  · 세션은 계정당 여러 개 허용, 소켓 연결만 1개 강제 (Q-06 해석).
  · 세션 슬라이딩 갱신은 남은 기간이 절반(15일) 미만일 때만 수행한다.
  · 만료 세션 정리 크론을 만들지 않는다(로그인 시 기회주의적 정리).
  · rooms는 DB에 두고 참가자·게임 상태는 메모리에만 둔다 (4-2에 근거 상술).
  · game_players.final_score를 게임 진행 중에 UPDATE하지 않는다.
    점수는 answer_events로부터 계산하고, 종료 시 한 번 확정 값을 넣는다.
  · game_questions에 UNIQUE (game_id, question_id)를 걸어 한 게임 내 중복 출제를 DB가 막는다.
  · question_experiences는 ON CONFLICT DO NOTHING으로 첫 경험 시각을 보존한다.
  · answer_events는 "정답 문자열과 일치한 메시지"만 저장한다(일반 오답 채팅 미저장).
  · 게임 시작 시 참가자별 경험 문제 ID 집합을 한 번에 조회해 메모리로 올리고,
    문제 선정은 메모리에서 수행한다.

  저장소

6-3. 우려 사항

  · ★ 2-3 원칙 2(판정 블록에 await 금지)가 이 프로젝트에서 가장 깨지기 쉬운 규칙이다.
    나중에 누군가 "여기서 경험 여부를 한 번 더 확인하자"며 await 한 줄을 넣는 순간
    guide 18절이 조용히 무너지고, 평소에는 정상 동작하다가 동시 입력이 겹칠 때만
    두 명이 정답자가 된다. 재현이 매우 어렵다.
    → 대응: (i) 판정 함수 이름에 규칙을 박아 넣는다(예: resolveQuestionSync).
            (ii) 함수 상단에 규칙과 이유를 주석으로 명시한다.
            (iii) docs\04-PROTOCOL.md에 별도 절로 남긴다.
            (iv) 동시 정답 100회 반복 테스트를 CI에 넣어 회귀를 잡는다.
  · ★ 1-4 조건 1(커넥션 풀 idle timeout)도 같은 성격이다. 설정 하나가 빠지면
    Neon Free 한도를 즉시 초과한다. Phase 0에서 넣고 문서와 주석에 이유를 남긴다.
  · Neon Free 오토스케일링 최솟값이 0.25인지 1인지 확인하지 못했다(확인 불가).
    1이라면 "무거움" 시나리오에서 한도의 75%를 쓴다. 건우가 프로젝트 생성 후
    대시보드에서 확인해 주면 1-3의 추산을 확정할 수 있다.
  · Neon Free 사용자에게 한도 근접 알림이 오는지 확인하지 못했다(확인 불가).
    알림에 의존하지 않는 대비(1-3 (b)의 자체 로깅)를 Phase 0에 넣는 것으로 처리했다.
  · Supabase의 장기 일시정지 후 삭제 기준이 자료마다 90일과 1년으로 엇갈린다(확인 불가).
    Supabase를 쓰지 않기로 하면 무관한 사항이다.
  · Render Starter 가격($7)과 Supabase 커넥션 한도(60/200)는 제3자 자료 기반이라
    확인 불가에 준한다. 다만 1-4의 권장안은 이 수치에 의존하지 않는다.
  · ★ 3-4의 chatBuffer 마스킹 저장 방식은 메모리에 원문과 치환본을 둘 다 들고 있게 된다.
    방마다 500개 × 두 벌이므로 용량 자체는 문제없다. 다만 "원문이 서버 메모리에 남아 있다"는
    점은 인지해 둘 필요가 있다. 클라이언트로 나가지 않으므로 유출 경로는 아니다.
  · ★ 3-3의 마스킹 인덱스 매핑이 이 프로젝트에서 가장 구현 난도가 높은 부분이다.
    Phase 6에서 구현할 때 단위 테스트를 먼저 쓰는 것을 권한다(R002 6-5의 16케이스).
