## 1. 조직과 MAIN 의 자리

```
찬종(사용자 · 운영/기획 결정권자)
  └ 설계·지시 에이전트 (당신) — 라운드 브리핑을 쓰고, 보고서를 읽고, 다음 라운드를 설계한다
       ├ GEN    — 문제 데이터 생성 · 생성 규칙 · 적재(지시가 있을 때)           보고서 ai-out/Rnnn.txt (MAIN 과 번호 공유)
       ├ VERIFY — 생성물 독립 판정                                              보고서 ai-out/Vnnn.txt
       └ MAIN   — 웹/모바일 풀스택 (server/ client/ shared/ migrations/ scripts/) 보고서 ai-out/Rnnn.txt
```

- 라운드 번호 `Rnnn` 은 GEN 과 MAIN 이 **같이** 쓴다 (R038~R046 은 MAIN, R047 은 GEN). 다음 MAIN 라운드는 R048 이후 빈 번호.
- 찬종은 당신이 쓴 브리핑을 MAIN 창에 그대로 붙여 넣는다(가끔 "이어서 진행." 만 덧붙인다). **브리핑 전체가 곧 지시다.**
- MAIN 이 **건드리지 않는 것**:
  - 문제 데이터(questions · question_answers · 힌트 · 분류 등) — "★ 문제 데이터는 건드리지 마라" 가 매 라운드 들어간다. DB 구조 변경은 MAIN 이 한다(백업 뒤).
  - `docs/media-deep-review.md` 등 GEN 이 관리하는 검토 파일 — MAIN 은 커밋할 때 늘 빼 왔다(`git add -A -- . ':!docs/media-deep-review.md'`).
  - 파이프라인(`pipeline/` · `scripts/pipeline-*.mjs`)은 GEN 영역.

## 4. 라운드는 이렇게 돌아갔다 (지시 방식)

### 4-1. 브리핑 모양 (구 에이전트가 쓰던 것 — 그대로 써도 잘 돌아간다)

```
■ 응답 방식 규칙
[cmd 창] 요약만. 최대 5줄.
[정식 응답] C:\work\quiz-web\ai-out\R0NN.txt 에 UTF-8 + LF 로.  헤더: ROUND / DATE / TASK / STATUS(완료 · 부분완료 · 결정대기)
■ 절대 원칙 (매번 같은 8개)
 (1) 게임 규칙을 임의로 단순화·변경하지 않는다. 모호하면 Q 로 올린다.
 (2) 운영적·기획적 판단은 혼자 결정하지 않는다. 기술적이고 되돌리기 쉬운 것만 자체 판단하고 기록한다.
 (3) 모든 응답은 한국어.  (4) 추측을 확정처럼 쓰지 않는다("추정" · "확인 필요").  (5) 비밀값을 커밋하지 않는다(문서에도 .env 값 금지 — 이름만).
 (6) 라운드 종료 전 npm run verify 통과.  (7) ★★ 브리핑에 사실처럼 적힌 것은 검증 대상 — 다르면 보고서에 명시.  (8) git 에러면 먼저 VPN.
★ 이 세션은 MAIN · 먼저 직전 보고서를 읽어라 · 문제 데이터는 건드리지 마라 · DB 를 고치기 전에 백업 · 단계마다 커밋 + 06-WORKLOG
■ 0장 디자인 원칙 / ■ 할 일 A · B · C … (찬종의 말을 따옴표로 인용 + 요구 사항) / ■ 마무리(검사 · 문서 목록 · 커밋 · push) / 보고서 목차
```

### 4-2. MAIN 이 지켜 온 작업 방식 (새 지시에도 기본값으로 둔다)

1. **직전 보고서 → 브리핑 → 코드 순으로 읽고 시작.** 브리핑 속 "사실" 은 코드 · 실측으로 먼저 확인하고, 다르면 보고서에 적는다(원칙 7).
   - 예: R046 "방이 없어진다" 는 맞았지만 "마지막" 의 기준이 둘(게임 중 = 접속자 기준 · 로비 = 목록 기준)이었다.
   - 예: R046 은 원인이 하나 더 있었다(DB 가 "만든 사람" 기준으로 열린 방 하나를 막음 — 브리핑에 없음).
2. **A → B → C 순서로 · 단계마다 커밋 · 06-WORKLOG 체크박스.** 커밋 끝줄 `Co-Authored-By` · push 는 라운드 끝.
3. **화면은 "그림으로 확인한 것만 됐다"** (찬종 R042 확정). `npm run build` → ui-check 로 찍기 → **이미지를 직접 본다** → 고침 → 다시 찍기.
   크기: PC 1280×720 · 1536×864 · 1536×730 · 1920×1080 · 2560×1440 / 모바일 360 · 390 · 430. 방장 · 게스트 둘 다. 그림은 `docs/design/rNNN/`.
4. **사람 동작은 진짜 클릭**(R044~) — CDP 마우스 입력(`realClick` · `realType`). `element.click()` 은 덮인 버튼 · 바깥 누르기 · 순서 결함을 못 본다(R044 A-2 · R045 D 를 놓친 이유).
5. **결함은 먼저 재현하고 고친다.** 새 검사는 **고치기 전 빌드로 먼저 돌려 잡히는지** 확인하고(R045 이모티콘 · 닉네임) 고친 뒤 다시 돌린다. 재현 못 하면 잰 값과 함께 "재현 안 됨 · 확인 필요" 로 쓴다(R044 A-1).
6. **검사가 왜 못 잡았나** 를 보고서에 적고, 그 구멍을 메우는 검사를 더한다(10-TESTING 라운드별 장).
7. **규칙 · 결정은 문서로**: 01(규칙) · 07(D-nnn — 결정 · 원인 · 되돌리는 법) · 04 · 05 · 06 · 10 · 13 · PLAY-GUIDE · DB-ADMIN — 브리핑이 꼽은 것 + 바뀐 곳.
8. **판단은 기술적이고 되돌리기 쉬운 것만** · 전부 보고서 "판단" 목록과 07 에 남긴다. 운영 · 기획 판단은 Q 로 올리거나 보고서 맨 앞 "건우(찬종)가 볼 것" 에 적는다.
9. **보고서 맨 앞 "건우가 볼 것"** 은 짧게 — 찬종에게 확인을 요청하지 않는다(브리핑이 그렇게 지시했다). 대신 판단 · 확인 못 한 것 · 실기기로 볼 것(13-PENDING A 번호)을 적는다.
10. **"통과" 는 끝까지 돈 것만.** 멈춘 것 · 못 돌린 것은 이름을 적는다.

### 4-3. 보고서(`ai-out/R0NN.txt`) 모양

헤더 → `[cmd 창 요약]` 5줄 → `0. 건우가 볼 것` → 브리핑이 정한 목차(원인 · 구현 · 그림으로 찾은 것 표 · 경우의 수 표 · 테스트 결과(봇 각각 · verify 단계별) · 새 결정 항목) → 마지막에 고친 문서 목록. 그리고 `ai-out/README.md` 에 한 줄.

## 6. 알아 둘 환경 · 함정

- **찬종 PC 에는 늘 `npm run dev`(감시 서버 · tsc watch) · `npm run dev:tunnel` · 브라우저가 떠 있다.** 그 프로세스들은 건드리지 않는다.
  - 봇은 3000 번에 떠 있는 감시 서버를 그대로 쓴다. `server/dist` 가 바뀌면 감시 서버가 다시 뜨고, **다시 뜨는 몇 초 동안 봇이 연결 실패**한다 → 서버가 뜬 뒤 다시 돌리면 된다.
  - 봇이 도는 동안 `npm run build` 하지 않는다(서버가 계속 다시 뜬다).
- ★★ **메모리가 빠듯하다(16GB 중 남는 것 1~3GB).** R043 · R045 · R046 에서 Claude Code 가 **오래 도는 백그라운드 실행(봇 전체 + verify)을 메모리 부족으로 멈췄다.**
  그때는 앞에서(foreground · 10분 한도) 단계별로 나눠 끝까지 돌렸다. ui-check:social 은 10분을 넘을 수 있어 `UICHECK_NO_CHAIN=1 … --social` + `--profile` + `--emoji` 로 나눈다.
- 화면 검사는 **빌드된 결과**를 본다 — 고친 뒤 꼭 `npm run build`.
- Windows: Bash 는 Git Bash. heredoc 안 따옴표가 잘 깨진다 → 긴 스크립트는 파일로 써서 실행. 파이썬 출력은 `PYTHONIOENCODING=utf-8`(cp949 오류).
- DB: 고치기 전 `npm run db:backup`(백업은 `backups/`). 마이그레이션은 `npm run db:migrate`.

## 9. 구 에이전트 방식에서 고치면 좋을 점 (제안)

1. **결정 번호가 겹쳤다** — `docs/07-DECISIONS.md` 에 **D-174 · D-175 가 두 개씩** 있다(MAIN R038 · GEN R047). MAIN 은 D-227 까지 썼는데 GEN 은 따로 셌다.
   → 세션별로 번호를 나누거나(예: GEN 은 `DG-nnn`), 쓰기 전에 07 의 맨 위 번호를 확인하라고 브리핑에 넣어 달라. 겹친 두 개는 한 번 정리가 필요하다(누가 고칠지 지시해 달라).
2. **라운드 번호를 GEN 과 MAIN 이 같이 쓴다** — 보고서만 보고 누구 라운드인지 헷갈린다. MAIN `Rnnn` / GEN `Gnnn` 처럼 나누면 README 도 보기 쉽다.
3. **브리핑 한 번이 너무 크다** — R043(A-1~A-10 + B + C + D) · R046(A~E + 경우의 수 84칸)은 한 라운드에 컨텍스트가 여러 번 넘쳤다. 한 라운드 3~5 항목 · 경우의 수 같은 큰 검사는 따로 떼면 품질이 오른다.
4. **"끝날 때 봇 전체 + verify 한 번에"** — 찬종 PC 메모리로는 세 라운드 연속 백그라운드가 멈췄다. 방법은 둘 중 하나로 정해 주면 된다:
   (a) 끝 점검 전에 찬종에게 dev 서버 · 터널을 잠시 끄게 한다 / (b) "단계별로 끝까지 돌면 통과로 친다" 를 규칙으로 둔다.
5. **반복되는 고정 지시는 문서로** — 스크린샷 크기 · 디자인 원칙(R043 0장) · 절대 원칙 8개 · 보고서 형식을 `docs/` 한 곳(예: `docs/16-MAIN-ROUND.md`)에 두고 브리핑에서는 "그대로" 만 적으면 브리핑이 짧아진다.
6. **항목마다 "다 됐다" 의 기준을 적어 주면 좋다** — 지금까지 효과가 컸던 것: "진짜 클릭으로 확인" · "고치기 전 빌드로 검사가 잡는지 먼저" · "경우의 수 표 · 확인 못 한 칸은 '확인 못 함'".
7. **실기기 확인 목록(13-PENDING)을 주기적으로 찬종과 정리** — A 번호가 계속 쌓이기만 했다. 몇 라운드마다 "이번 판에서 봐 줄 것 3개" 처럼 묶어 주면 실사용 피드백이 빨라진다.
8. 잘 된 점(유지 권장): 원칙 7(브리핑의 사실도 검증) · "그림으로 확인한 것만" · "건우가 볼 것" 맨 앞 · 단계 커밋 · 판단은 되돌리기 쉬운 것만.
