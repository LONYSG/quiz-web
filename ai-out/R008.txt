  [그러면 무엇이 문제였는가 — 실제 브라우저로 확인]

    헤드리스 Chrome 으로 실제 화면을 조작해 단계별로 쟀다.

      게임 시작 버튼이 존재하고 활성인가   → {exists:true, disabled:false, visible:true}
      클릭이 전달되는가                    → true
      서버가 거부하는가                    → ★ 거부한다 (게임이 시작되지 않았다)
      ★ 화면에 사유가 표시되는가           → ★ **표시되지 않는다**

  [확정된 원인 — App.tsx 의 렌더 구조]

    App.tsx 는 화면마다 return 을 따로 두고 있었고, 안내 문구가
    **"방이 없는 화면" 의 return 안에만** 있었다.

      if (room.snapshot && socket) {
        return (
          <main className="wrap">
            <Lobby … />          ← ★ notice 를 그리는 코드가 없다
            <footer …>
          </main>
        );
      }

      return (                    ← 방이 없는 화면
        <main className="wrap narrow">
          …
          {notice && <p className="notice">{notice}</p>}   ← 여기에만 있다
          …
      );

    에러는 정상적으로 도착해 useRoom 이 상태에 저장했고, App 의 useEffect 가
    setNotice 까지 호출했다. **그 값을 그리는 코드가 로비 화면에 없었을 뿐이다.**

  ★ 그래서 이것은 NOT_ENOUGH_QUESTIONS 만의 문제가 아니었다.
    **로비 화면에서 발생하는 모든 서버 에러가 보이지 않았다.**

  ★ 봇 테스트가 통과한 이유는 지시에 적힌 것과 같다.
    봇은 소켓으로 직접 요청하고 error 이벤트를 배열에 모아 단정한다.
    "그 에러가 화면에 그려지는가" 는 봇의 관심 밖이다. 구조적으로 잡을 수 없다.

      .notice  주황 계열 + 닫기 버튼. 서버 에러
      ★ 같은 모양이면 사용자가 안내를 "무슨 문제가 생겼나" 로 읽는다.

1-3. ★ 전수 점검 — 에러 코드가 사람 화면에 도달하는가

  서버의 sendError 호출 지점을 전부 찾아(27곳) 코드별로 정리했다.

  ┌──────────────────────┬──────────────────────────────┬────────┬────────┐
  │ 코드                  │ 사람이 어떻게 만나는가           │ 수정 전 │ 수정 후 │
  ├──────────────────────┼──────────────────────────────┼────────┼────────┤
  │ NOT_ENOUGH_QUESTIONS │ 문제 수 > 출제 가능 수에서 시작   │ ✗      │ ✅ 자동 │
  │ INVALID_STATE        │ 시작 연타 / 시작 후 설정 변경     │ ✗      │ ✅     │
  │ NOT_HOST             │ 방장 이전 직후 옛 방장이 누름(경합)│ ✗      │ ✅     │
  │ NOT_IN_ROOM          │ 내보내진 직후 조작 (경합)        │ ✗      │ ✅     │
  │ UNAUTHENTICATED      │ 세션 만료된 탭에서 조작          │ ✗      │ ✅     │
  │ INTERNAL             │ 핸들러 예외                    │ ✗ ★전송 │ ✅     │
  │                      │                              │ 자체가  │        │
  │                      │                              │ 없었다  │        │
  │ BAD_REQUEST          │ 방 ID 를 64자 넘게 입력         │ 일부    │ ✅ 자동 │
  │ ROOM_NOT_FOUND       │ 잘못된 초대 링크                │ 일부    │ ✅ 자동 │
  │ ROOM_CLOSED          │ 오래된 초대 링크                │ 일부    │ ✅     │
  │ ROOM_FULL            │ 11번째 사람 입장                │ 일부    │ ✅     │
  │ ALREADY_HAS_ROOM     │ 방을 가진 채 다른 방 입장 시도    │ 일부    │ ✅     │
  └──────────────────────┴──────────────────────────────┴────────┴────────┘

    "일부" = 방이 없는 화면에서는 보였고 로비 화면에서는 보이지 않았다
    "✅ 자동" = ui-check 가 매번 자동으로 확인한다

  ★ 도달할 수 없는 경로가 하나 남아 있고, 그것은 의도적이다

    설정값 범위 위반(BAD_REQUEST)은 클라이언트가 **서버로 보내지 않는다.**
    문제 수를 한 글자 고칠 때마다 에러를 왕복시키면 화면이 에러로 도배된다.
    대신 같은 자리에 검증 메시지를 즉시 보여준다.

    ★ "클라이언트와 서버 판단이 어긋나면 조용히 막힌다" 는 위험이 남는데,
      **두 쪽이 shared/validateRoomSettings 하나를 부르므로 어긋날 수 없다** (D-026).
      즉 이 경로의 안전장치는 에러 전파가 아니라 **코드 공유**다.
      ★ 그리고 서버 쪽 거부는 봇 테스트가 따로 검증한다(문제 수 0/201/소수점 등).

  ★ HTTP(회원가입·로그인) 에러는 이 배너를 쓰지 않는다.
    그쪽은 요청-응답이고 폼 안 인라인 표시가 맞다.
    규칙은 "**서버가 밀어 보내는(push) 에러는 배너 하나로만 표시한다**" 다.

  (3) 자동 확인 항목으로 고정했다 (ui-check [6]). 앞으로 매 게이트에서 확인된다.

3. 로그 소음 처리 — ★ 전제가 실측과 달랐다
═══════════════════════════════════════════════════════════════

3-1. 세 상황을 각각 재현했다

  ┌────────────────────────────────────────────┬───────────────────────────┐
  │ 상황                                        │ 프록시 로그                 │
  ├────────────────────────────────────────────┼───────────────────────────┤
  │ 생 WebSocket 을 열고 terminate (3회)          │ 없음                       │
  │ socket.io 연결을 맺고 밑의 소켓을 강제 종료(3회)│ 없음                       │
  │ ★ 실제 Chrome 에서 프록시 경유 WS 를 맺고       │ ★ **없음**                 │
  │   탭 닫기 (Target.closeTarget)               │                           │
  │ ★ 서버 프로세스가 죽기                        │ ★ ECONNRESET 1건 →         │
  │                                            │   ECONNREFUSED 반복 (14줄)  │
  └────────────────────────────────────────────┴───────────────────────────┘

  ★ 첫 시도는 재현에 실패했고, 그 사실을 근거로 "고쳤다" 고 보고할 수는 없었다.
    (수정 전 설정으로도 0줄이었다 = 테스트가 조건을 만들지 못한 것이다)
    그래서 조건을 바꿔 가며 세 번째에 재현했다.

  ★★ 결론: 이 로그는 "탭을 닫아서 나는 정상 로그" 가 아니다.
    **서버가 사라졌다는 사실을 정확히 알려주고 있었다.**

    ★ 직전 라운드에 내가 낡은 서버 프로세스(포트 3000)를 종료한 적이 있다.
      건우의 클라이언트 창이 그때 떠 있었다면 정확히 이 로그가 난다.
      다만 건우의 화면과 시각을 직접 보지 못했으므로 **추정**이며 확정할 수 없다.

3-2. 그래서 침묵시키지 않았다

  ★ ECONNRESET 을 숨기면 "서버를 안 켰다 / 서버가 죽었다" 를 알 수 없게 된다.
    지시에도 "★ 모든 오류를 숨기지 말 것. 정상적 종료만 걸러라" 가 있었고,
    실측 결과 **걸러야 할 정상적 종료가 존재하지 않았다.**

  대신 신호는 남기고 소음만 줄였다.

    (1) 스택 대신 한 줄로, 무엇을 해야 하는지까지 적는다
        [proxy] ECONNREFUSED — 게임 서버(:3000)에 연결할 수 없습니다.
                다른 터미널에서 npm run dev 가 떠 있는지 확인하세요.
        [proxy] ECONNRESET — 게임 서버와의 연결이 끊겼습니다.
                서버가 재시작되었거나 종료되었습니다.

    (2) 같은 코드가 5초 안에 반복되면 모아 한 번만 알리고 생략 횟수를 적는다
        socket.io 가 재연결을 시도하는 동안 ECONNREFUSED 가 초당 여러 번 나기 때문이다

  결과: 서버 강제 종료 시 **20줄 → 2줄.** 두 줄 모두 원인과 조치를 담고 있다.

  ★ 구현 함정 하나 (실측으로 발견)
    proxy.on('error') 를 달아도 Vite 자신의 로그는 그대로 나온다.
    Vite 가 프록시 오류를 자기 logger 로 직접 찍기 때문이다.
    처음에 그렇게 만들었더니 로그가 오히려 **늘었다(14 → 20줄).**
    → customLogger 로 'proxy error' 계열 한 종류만 가로채 우리 형식으로 바꿨다.
      ★ 다른 로그는 손대지 않는다. 기동 안내와 HMR 로그는 그대로 나와야 한다.

3-3. 문서화

  docs/10-TESTING.md 11장 "개발 중 로그 읽는 법" 을 새로 만들었다.
  ★ "이 로그가 보이면 2번 창(서버)을 확인한다" 로 적었다.
    "무해한 소음" 이라고 적으면 다음에 서버가 죽었을 때 놓친다.
