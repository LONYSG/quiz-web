1-1. 원인 — 추측하지 않고 실측했다

  지시가 "원인을 실제로 확인하고 고칠 것. 추측으로 값만 바꾸지 말 것" 이었다.
  헤드리스 Chrome 을 CDP(DevTools Protocol)로 조작해 실제 레이아웃을 측정했다.

  [측정 방법]
    Range.getClientRects() 로 만들어진 줄 상자의 **top 값 종류를 센다.**
    높이를 line-height 로 나누는 추정이 아니라, 브라우저가 실제로 만든 줄을 센다.

  ★ 도구 자체의 오탐을 먼저 잡았다.
    처음에는 사각형 **개수**를 셌는데, 브라우저는 글자 종류가 바뀌는 경계에서
    텍스트 상자를 쪼갠다. 그래서 "50문제"(숫자+한글)가 한 줄인데도 2개로 나와
    줄바꿈으로 오탐했다. top 값 종류를 세는 방식으로 바꿔 해결했다.
    ★ 이 사실을 밝히는 이유: 도구를 믿고 "문제 없음"을 보고하면 안 되기 때문이다.

  [실측 결과 — 수정 전]

  ┌──────────┬────────────────┬─────────┬──────────────────────────┐
  │ 화면 폭   │ 요소            │ 폭       │ 상태                      │
  ├──────────┼────────────────┼─────────┼──────────────────────────┤
  │ 320px    │ button "전송"   │ 52.2px  │ ★ 2줄로 쪼개짐            │
  │ 360px    │ button "전송"   │ 53.3px  │ ★ 2줄                     │
  │ 390px    │ button "전송"   │ 53.9px  │ ★ 2줄                     │
  │ 480px    │ button "전송"   │ 55.2px  │ ★ 2줄                     │
  │ 720px    │ button "전송"   │ 56.9px  │ ★ 2줄                     │
  │ 320px    │ button "방 나가기"│ 72.6px │ ★ 2줄 (지적받지 않은 것)   │
  │ 360px    │ button "방 나가기"│ 79.5px │ ★ 2줄                     │
  │ 390px    │ button "방 나가기"│ 84.7px │ ★ 2줄                     │
  └──────────┴────────────────┴─────────┴──────────────────────────┘

  ★ 720px 에서도 쪼개졌다. 좁은 화면만의 문제가 아니었다.

  [확정된 원인]

  세 가지가 겹쳤다.

    (1) 버튼이 flex 행의 항목이고, flex 항목의 기본값은
        flex-shrink: 1 / min-width: auto 다 → 눌릴 수 있다
    (2) 같은 행의 입력창이 width: 100% 여서 남는 폭이 없다
        → 버튼이 min-content(한 글자 폭)까지 눌린다
    (3) white-space 기본값이 normal 이다
        → 한글은 글자 사이에서 줄바꿈이 허용되므로 "전" / "송" 으로 쪼개진다

  계산으로 확인: 720px 에서 버튼 폭 56.9px − 패딩 28px − 테두리 2px ≒ 내용 폭 27px.
  15px 글꼴에서 한글 두 글자는 약 30px 이므로 한 글자만 들어간다.

  ★ 건우의 추정("버튼 너비가 부족해 줄바꿈됨, flex 축소로 눌린 것")이 정확했다.
    실측으로 확인했고, 추가로 "왜 복사 버튼은 멀쩡했는가" 까지 규명했다.

  [★ "복사" 버튼만 멀쩡했던 이유]

    .invite-row button { white-space: nowrap; }

  그 하나에만 이 선언이 붙어 있었다. 즉 규칙이 아니라 **우연**이었다.
  ★ 이것이 A-2의 핵심이다. 같은 위험을 가진 요소 중 일부만 우연히 보호되고 있었다.

1-2. 규칙으로 고쳤다 (docs/07-DECISIONS.md D-022)

  개별 요소를 고치지 않았다. 네 가지를 규칙으로 걸었다.

  (1) 라벨성 요소 전체에 줄바꿈 금지
        button, .badge, .seat, .preset, .pill { white-space: nowrap; }

  (2) 모든 버튼이 flex 행에서 눌리지 않게
        button { flex: 0 0 auto; }
      ★ 늘어나야 하는 .tab(로그인/회원가입 탭)은 클래스 선택자가 덮어쓴다.
        클래스가 타입 선택자보다 우선하므로 순서와 무관하게 안전하다.

  (3) ★ "입력 + 버튼 한 줄" 배치를 .field-row 하나로 통일
        .field-row { display: flex; gap: 8px; align-items: stretch; }
        .field-row > input { flex: 1 1 auto; min-width: 0; }
        .field-row > button { margin-top: 0; }

      ★ 이것이 구조적 수정이다.
        .invite-row / .chat-input 처럼 같은 일을 하는 클래스를 여러 개 두는 것이
        "그중 하나에 규칙을 빼먹는" 이번 버그의 원인이었다.
        전용 클래스 두 개를 지우고 공통 클래스 하나로 바꿨다.

      ★ min-width: 0 이 필요한 이유: flex 항목의 기본 min-width 는 auto 라서
        입력창이 자기 내용보다 작아지지 않는다. 그러면 입력창 대신 버튼이 눌린다.

  (4) 제목(h1)과 본문은 규칙에서 **제외**했다.
      방 제목은 30자까지 허용되므로 좁은 화면에서 여러 줄이 되는 것이 정상이고,
      줄바꿈을 막으면 화면을 넘친다.
      ★ 규칙을 무조건 넓히지 않는 것도 규칙의 일부다.

  [Phase 2에서 새로 만든 요소도 자동 적용된다]
    프리셋 버튼(50문제 / 100문제 / 200문제 / 가능한 최대), 즉시 시작, 카운트다운,
    게임 시작, 카운트다운 취소 — 전부 개별 선언 없이 규칙을 받는다.
    ★ Lobby.tsx 상단에 "새로 만드는 버튼과 배지는 styles.css 의 라벨 규칙을
      그대로 받는다. 개별 요소에 white-space 를 다시 쓰지 않는다" 를 주석으로 남겼다.

2-1. 게임 설정 UI (B-1)

  · 문제 수 입력 (1~200, Q-10). 정수만. 소수점은 거부한다
  · ★ 프리셋 50 / 100 / 200 (Q-10 확정) + "가능한 최대 (53)" 하나를 더 넣었다
    → 시드가 53문제인 지금 상태에서 프리셋 3개가 전부 시작 불가라서,
      바로 쓸 수 있는 값을 한 번에 넣을 수 있게 했다. 자체 판단이다
  · 시작 방식: 즉시 시작 / 카운트다운 (버튼 토글)
  · 카운트다운 초 입력 (3~60, Q-11). 시작 방식이 카운트다운일 때만 보인다
  · ★ 방장만 편집 가능. 나머지에게는 값만 보이는 읽기 전용 카드로 바뀐다
  · ★ settingsLocked 가 true 면(COUNTDOWN 이후) 방장도 읽기 전용이 되고,
    "게임이 시작되어 설정을 바꿀 수 없습니다" 를 표시한다

  [★ 서버가 모든 값을 다시 검증한다 — guide 44절]

    검증 함수는 **하나뿐이다**. shared/src/settings.ts 의 validateRoomSettings().
    서버(socket/index.ts)와 클라이언트(GameSettings.tsx)가 같은 함수를 부른다.

    ★ 두 곳에 따로 쓰면 반드시 어긋나고, 어긋나면 양방향으로 버그가 된다.
      · 화면은 통과시키는데 서버가 거부 → 사용자는 이유를 모른다
      · 화면이 막는데 서버는 허용 → 봇이나 조작된 클라이언트가 규칙을 넘는다

    ★ 공유하는 것은 "형식과 범위" 뿐이다. 판정 권한은 서버에만 있다.
      출제 가능 수 검증은 DB를 봐야 하므로 shared 에 두지 않았다. (D-026)

    검증 순서도 서버가 다시 본다.
      guard: 세션 → 방 소속 → 방장 권한 → 방 상태(LOBBY) → 스키마
      핸들러: settingsLocked → validateRoomSettings

2-2. 출제 가능 문제 수 안내 (B-2, Q-21)

  [정의를 확정했다]
    출제 가능 수 = **참가자 중 한 명 이상이 아직 경험하지 않은** 활성 문제의 개수

    근거: Q-20 문제 선정의 1단계 풀(전원 미경험)은 2단계 풀(1명 이상 미경험)의
    부분집합이므로, 합집합은 2단계 조건 하나로 표현된다.
    "전원이 경험한 문제"는 제외된다 — 경험 규칙의 예외를 만들지 않는다는 것이
    guide 25·29절의 강한 금지 규칙이다.

  [화면 안내]
    · 입력 아래에 "지금 출제할 수 있는 문제: 53개" 를 항상 표시한다
    · 입력값이 그보다 크면 같은 자리가 빨간 글씨로 바뀐다
      "★ 지금 출제할 수 있는 문제는 53개입니다. 이대로 시작할 수 없습니다."
    · "가능한 최대 (53)" 프리셋으로 한 번에 맞출 수 있다

  [★ 게임 시작 직전 서버 재검증]
    · 화면에 쓰는 값은 캐시다. 참가자가 바뀔 때만 다시 계산한다
      (설정값과 무관하고 참가자 집합에만 의존하므로 정확하다.
       방장이 숫자를 한 글자 고칠 때마다 DB를 조회하지 않기 위함이다)
    · ★ game.start 에서는 캐시를 믿지 않고 **반드시 다시 조회한다.**
      부족하면 시작을 거부하고 실제 개수를 담아 안내한다.
        code: NOT_ENOUGH_QUESTIONS
        "출제할 수 있는 문제가 53개뿐입니다. 문제 수를 53개 이하로 줄여 주세요. (요청 200개)"
    · 그 값이 games.planned_question_count 에 기록된다

  ★ 에러 코드를 새로 만든 이유: INVALID_STATE("지금은 할 수 없다")와 원인이 다르다.
    이것은 설정값 문제이고 사용자가 문제 수를 줄이면 해결된다. 안내 문구가 달라야 한다.

    ★ 빼먹지 않게 하는 장치 두 개
      (1) tick.ts checkCountdown() 안에 교체할 자리를 주석으로 표시했다

        조회를 기다리는 동안 방장이 취소했거나, 사람이 다 나갔거나,
        다른 경로로 이미 시작되었을 수 있다.

    → rooms/lifecycle.ts 의 closeOpenGame() 하나를 두 경로가 함께 부르게 했다.

- 배경: 이번 라운드에 헤드리스 Chrome 을 CDP로 조작해 라벨 줄바꿈을 실측하는

    · 수정 후 5폭 × 3화면에서 통과를 확인했다
    · 스크립트 자체의 오탐도 실측으로 잡았다

- 왜 tmp/ 에 두었는가: CDP 연결에 쓰는 ws 가 socket.io 의 **전이 의존성**이다.

  판단 기준이었으므로 혼자 결정하지 않는다.

- 선택지
  (A) 현행 유지 — tmp/ 에 두고 필요할 때만 만든다.
      단점: tmp/ 는 gitignore 이므로 사라진다. 라운드마다 다시 만들거나 잊는다
  (B) ws 를 devDependency 로 추가하고 scripts/ui-check.mjs 로 승격.
      npm run verify 에 넣을 수 있어 라벨 규칙(D-022)이 회귀하면 즉시 잡힌다.
      단점: devDependency 1개 증가
  (C) Playwright 도입. 훨씬 강력하다.
      단점: 브라우저 바이너리 수백 MB. "표준에 가깝게, 의존성 최소" 방침과 거리가 있다

- 권장안: (B). 이번 라운드에 이미 값을 증명했고 비용이 devDependency 하나다.
- ★ 확인 불가: (C)로 "한글 IME 조합 이벤트까지 자동 검증할 수 있는가" 는 해 봐야 안다.

- 영향 범위: 낮음. 지금도 사람이 개발자 도구로 같은 것을 확인할 수 있다.

  절차: 참가자 목록을 본다.

  정상이면 보이는 것
    · 닉네임 옆(좁은 화면에서는 아래 줄)에 **"53문제 중 0문제 (0.0%)"**
    · ★ 분모가 53이어야 한다. "0문제 중 0문제" 나 "NaN" 이 보이면 버그다
    · 전원 0문제인 것이 정상이다. 아직 문제를 푼 기록이 없기 때문이다
      (Phase 6에서 실제로 쌓인다)

  ────────────────────────────────────────
  (4) 카운트다운 — 두 창으로 확인
  ────────────────────────────────────────
  준비: 일반 창(방장)과 시크릿 창(다른 계정) 두 개로 같은 방에 들어간다.

  절차
    a. 방장 화면에서 "카운트다운" 을 고르고 초를 30 으로 둔다
    b. 문제 수를 53 이하로 맞춘다
    c. "게임 시작" 을 누른다
    d. 카운트다운이 도는 동안 시크릿 창을 새로고침해 본다
    e. 방장 화면에서 "카운트다운 취소" 를 누른다
    f. 다시 시작하고, 이번에는 초를 3 으로 두고 끝까지 기다린다

  정상이면 보이는 것
    · c: 큰 숫자로 "30.0초" → 0.1초 단위로 줄어든다
    · ★ 시크릿 창에도 **같은 숫자**가 보인다. 서버 시각 기준이므로 두 창이 일치한다
      (완전히 같은 프레임은 아니어도 0.1~0.2초 이내여야 한다)
    · c: 게임 설정 카드가 읽기 전용으로 바뀌고
      "게임이 시작되어 설정을 바꿀 수 없습니다." 가 나온다
    · d: 새로고침해도 카운트다운이 이어진다. 남은 시간이 맞다
      ★ 처음부터 다시 시작하거나 사라지면 버그다
    · e: 즉시 로비로 돌아가고 설정을 다시 바꿀 수 있게 된다.
      ★ 시크릿 창도 같이 돌아간다
    · f: 0.1초까지 줄어든 뒤 "시작 중…" 이 잠깐 보이고,
      곧 점선 테두리 패널로 "게임이 시작되었습니다 — 문제 N개" 가 나온다
      ★ "시작 중…" 은 정상이다. 클라이언트가 0에서 스스로 시작하지 않고
        서버 신호를 기다리는 것이 규칙이다 (guide 45절)
    · 그 패널에 "여기에 문제가 표시되는 것은 Phase 3입니다" 와 games.id 가 보인다

  ★ 게임이 시작된 뒤에는 로비로 돌아가는 버튼이 없다. 정상이다(결과 화면이 Phase 4).
    다시 하려면 "방 나가기" 를 누르고 방을 새로 만든다.

  ────────────────────────────────────────
  (5) ★ 접속 종료자가 있을 때의 배지와 버튼
  ────────────────────────────────────────
  ★ 이 항목만 자동 측정에서 렌더되지 않아 확인하지 못했다. 사람 확인이 필요하다.

  절차: 두 창으로 방에 들어간 뒤 시크릿 창을 닫고 5초 이상 기다린다.

  정상이면 보이는 것
    · 그 사람 줄에 "접속 종료" 배지가 **한 줄로** 나온다
    · 방장 화면에는 그 옆에 "내보내기" 버튼이 **한 줄로** 나온다
    · ★ "접속" / "종료" 나 "내보" / "내기" 로 쪼개지면 버그다 (1장과 같은 유형)
    · 좁은 화면(휴대폰)에서는 배지와 버튼이 닉네임 아래 줄로 내려간다. 정상이다

  ────────────────────────────────────────

    · 프리셋 버튼 4개가 두 줄로 정렬되고 글자가 쪼개지지 않는다
    · 경험률이 닉네임 아래 줄에 보인다
    · 카운트다운 숫자가 화면을 넘치지 않는다
    · 가로 스크롤이 생기지 않는다
