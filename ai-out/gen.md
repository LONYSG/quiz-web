## 1. 조직과 GEN 의 자리

```
찬종(사용자, 운영·기획 결정권자)
  └ 설계·지시 에이전트 (당신)  — 라운드 브리핑을 쓰고, 결과를 읽고, 다음 라운드를 설계
       ├ GEN    — 문제 생성 · 품질 규칙 · 프롬프트 · 문제 데이터 반영(DB 적재 포함, 지시가 있을 때만)
       ├ VERIFY — 생성물 독립 판정 (사실 · 힌트 · 중복 · 노출). 보고서 ai-out/Vnnn.txt
       └ MAIN   — 웹/모바일 풀스택 (server/ client/ shared/). 보고서 ai-out/Rnnn.txt (GEN 과 번호 공유)
```

- 라운드 번호 `Rnnn` 은 **GEN 과 MAIN 이 같이 쓴다** (R038~R046 은 MAIN, R047 은 GEN). VERIFY 는 `Vnnn`.
- 사용자는 브리핑을 GEN 창에 붙여 넣고 "이어서 진행." 정도만 적는다. 브리핑 전체가 곧 지시다.
- ★ **생성자가 자기 산출물을 최종 판정하지 않는다** (Q-75 · [docs/12-SONNET-SESSION.md](../docs/12-SONNET-SESSION.md) 0장). GEN 이 만든 것은 VERIFY 를 거쳐야 "확정" 이다. GEN 의 자기 검사는 기계 게이트와 1차 점검까지다.

## 3. 데이터·도구 지도

### DB
- PostgreSQL, docker 컨테이너 `quiz-web-db`, 포트 5434, user `quiz`, db `quizweb`.
- 분야 7묶음(`categories.game_topic`, 뷰 `category_game_topics`): korea · history · science · arts · sports · life · media. 해외축구 소분류는 sports.

## 4. GEN 의 작업 방식 (실제로 해 온 흐름)

### 4-1. 라운드 한 번의 흐름
1. **브리핑 검증** — 브리핑의 사실 주장(예: "R045·R046 은 문항을 안 건드렸다")을 git log · DB 조회로 먼저 확인한다. 틀리면 보고서에 적는다.
2. **규칙부터** — 사용자 판단이 있으면 기준서(15) → criteria-sync → 새 프롬프트 버전 순으로 반영. 옛 프롬프트는 얼린다.
3. **생성** — 장르/분야별로 서브에이전트에 나눠 맡긴다(프롬프트 + 소분류 + 금지 목록). 각자 `tmp/rNNN/gen-<key>.json` 을 쓴다.
   - 에이전트가 429(사용량 한도) · ENOTFOUND(네트워크)로 죽으면 **결과 파일이 없는 묶음만** 다시 띄운다.
4. **중앙 기계 검사** — 필드 · 소분류 key · 정답 노출 · 빈칸 · 같은 라운드 같은 소재 · 단정어 · 전역(DB) 같은 정답 대조.
5. **사실 확인** — 새 사실은 웹 출처를 단다. 웹 확인 없이 지식으로 쓴 것은 **"지식 근거" 로 표시해 VERIFY 에 넘긴다** (R047: 37건).
6. **채점** — 난이도 · 알 가치 · 접근성 (기준서 5장 외부 기준표). 난이도 3 이상은 일반 힌트 필수.
7. **힌트** — `hint-v3` 기준, `checkHint` 통과. 힌트 → 질문 되풀이 · 뜻풀이 · 해설과 같은 사실이면 다시 쓴다.
8. **게이트** — `pipeline-load` 게이트를 파일 단계에서 미리 돌려 전량 통과 확인.
9. **VERIFY 묶음** — 바뀐 질문은 `questionBefore` 를 같이 넣는다.
10. **적재(지시가 있을 때만)** — 백업 → 반영 스크립트 → 활성 수 · 분포 확인.
11. **문서 · 커밋 · 보고** — 아래 4-3.

### 4-2. 절대 원칙 (매 브리핑에 "(1)~(8) 그대로" 로 들어 있었다)
1. 게임 규칙을 임의로 단순화·변경하지 않는다. 애매하면 Q 항목으로 올린다.
2. 운영·기획 사항을 혼자 결정하지 않는다.
3. 모든 응답은 한국어.
4. 추정을 사실처럼 쓰지 않는다.
5. 비밀값을 절대 커밋하지 않는다.
6. 중단·재개가 가능하게 일하고 상태를 남긴다.
7. ★ 브리핑의 사실 주장은 검증 대상이다.
8. ★ git 에러가 나면 먼저 VPN 을 의심하라.
- 추가로 자주 붙던 것: "사용자에게 확인을 요청하지 마라" · "서버 기동·ui-check 금지" · "server/ client/ shared/ 를 건드리지 마라" · "DB 쓰기 전 백업" · "사용자가 이 라운드 동안 플레이할 수 있다" · "토큰을 아끼고 있다 — 필요한 만큼만".
- GEN 이 혼자 정한 것은 보고서에 **"GEN 판단 (되돌리기 쉽다)"** 로 따로 적어 왔다.

## 5. 지금까지 확정된 핵심 품질 결정 (요약 — 원문은 15 · 07)

- **문제 시간**: 문제 40초, 30초 남았을 때 일반 힌트(15초 동안 혼자), 15초 남았을 때 초성 힌트 추가, 정답 공개 8초 (R034/R035).
- **일반 힌트**: 난이도 3~5 는 반드시 (H0, R036). "도와주기" 여야 하고 "떠먹여 주기" 는 안 된다. H11 = 보이는 시간 고려.
- **읽기 좋은 문제 (R047, 3-1)**: 판정 문장 "한눈에 들어오는가. 두세 줄로 풀면 더 읽기 쉬운가". 배경·단서 문장을 앞에, 묻는 것을 마지막 문장에. 1~3줄. 게임 화면은 문장마다 줄을 바꾼다. ★ 기존 활성 문항은 아직 이 기준으로 고치지 않았다 ("많이 쌓인 뒤 한 번에 점검" — 사용자 확정).
- **미디어 (Q-105~107, R037 · R047)**: 대중 30% / 팬 세부 70%. 미디어만 알 가치 2 허용(레전드 작품의 팬 세부에만), 1 은 제외. 해외축구는 sports 묶음. 소분류 "해외 드라마"(`L3:world-cinema#7`, 마이그레이션 0011).
  - **MD10 작품의 무게**: "그 작품 자체가 세계적이거나 한국에서 레전드로 취급받는가" — 레전드부터 만들고, 소재가 떨어지면 넓힌다. (보아 앨범명 같은 것은 뺀다)
  - **MD11 너무 쉬움**: 줄거리·주연을 다 주는 대히트작 제목 맞히기, 국민 캐릭터·밈.
  - 미디어 난이도 채점표는 바꾸지 않는다. 같은 작품을 다른 사실로 묻는 쌍은 지켜보기만.
- **풀 소진 (R032 측정)**: 50문제 게임 기준 같은 문제 없이 — 상 11판 · 중+상 38판 · 전체 78판. ★ 어려운 문제가 가장 모자라다.
- 알아 둘 실측: "힌트만 보고 정답 맞히기" LLM 블라인드 테스트는 떠먹여 주기를 **구분하지 못한다** (기존 hint-v3 90% vs R036 95%). 힌트 품질 판정을 이 방식에 맡기지 말 것.

## 6. GEN 이 앞으로 할 일 (제안 순서 — 결정은 당신과 사용자 몫)

1. **[대기] C60 VERIFY 결과 반영** — 미디어 200 고침/뺌 반영 + R036 중 힌트 1,328 중 지적분 수정 (활성 문항이므로 DB 백업 후).
2. **[대기] 미디어 200 적재** — VERIFY 통과분만. 적재 후 미디어 묶음 풀 크기 · 분포 보고.
3. **문제 수 늘리기** — 사용자 방침이 "문제 수를 늘리는 데 집중". 특히
   - 난이도 4~5 (상) — 풀 소진이 가장 빠른 층 (5 는 26건뿐).
   - 미디어는 MD10 에 따라 레전드 작품부터 다음 묶음.
   - 묶음마다 같은 흐름: 생성 → 기계 검사 → 사실 확인 → 채점 → 힌트 → 게이트 → VERIFY → 적재.
4. **[나중] 기존 활성 3,943 의 읽기 좋은 문제 일괄 점검** — 사용자가 "많이 쌓인 뒤 한 번에" 라고 했다. 시점은 사용자 결정.
5. **[열림] Q-103** — 출제 로직이 세 점수를 쓸 것인가 (MAIN 몫과 걸침, 급하지 않음).

## 7. ★ 새 에이전트에게 드리는 제안 (구 방식에서 개선할 점)

1. **생성 → 판정 → 적재 사이를 짧게.** 지금은 GEN 이 만든 것이 VERIFY 를 몇 라운드씩 기다린다 (R037 미디어 200 이 R047 까지 적재 안 됨, 그 사이 MAIN 라운드 9개). 생성 묶음마다 바로 VERIFY → 바로 적재 라운드를 이어 붙이면 사용자가 새 문제를 빨리 플레이하고, 피드백도 빨리 돈다.
2. **브리핑을 짧고 구조적으로.** 구 브리핑은 ★ 강조가 많고 사용자 발언 인용 · 설계자 판단 · 할 일이 한 덩어리였다. 권장 틀: `[확정 결정]` / `[할 일 A,B,C — 산출 파일 이름까지]` / `[하지 말 것]` / `[보고 항목]`. 원칙 (1)~(8) 은 이 문서나 docs 에 고정해 두고 "원칙 그대로" 한 줄로 충분하다.
3. **브리핑에 사실을 단정하지 말고 "확인할 것" 으로.** 원칙 (7) 때문에 GEN 은 어차피 다시 확인한다. "R045·R046 은 문항을 안 건드렸다(확인 대상)" 처럼 표시해 주면 좋다 — 구 에이전트가 이미 그렇게 하던 좋은 습관이다.
4. **사용자 검토는 체크박스 문서로.** `docs/*-review.md` 에 ☐ 를 두면 사용자가 표시만 하고 GEN 이 패턴을 읽는 흐름이 잘 작동했다 (R047: 30건 표시 → 200건 전체에 적용). 계속 쓰기를 권한다. 단 그 파일은 GEN 파일이므로 **커밋은 GEN 라운드에서** (MAIN 이 빼 둔 적이 있다).
5. **문서 동시 편집 충돌 주의.** GEN 과 MAIN 이 05 · 06 · 07 · 13 을 같이 고친다. 두 세션을 동시에 돌릴 때는 어느 쪽이 어느 문서를 고치는지 브리핑에 적어 두면 충돌이 줄어든다. 번호(D-nnn · C-nn · Rnnn)도 동시 라운드면 미리 나눠 주는 것이 안전하다.
6. **토큰 예산을 숫자로.** "필요한 만큼만" 대신 "서브에이전트 N개 이내 · 생성 M건" 처럼 주면 GEN 이 규모를 맞추기 쉽다. 대량 생성은 서브에이전트 병렬이 기본이라 비용이 크다.
7. **적재 권한을 명시적으로.** GEN 은 지시 없이는 DB 를 쓰지 않는다. 적재·수정이 필요한 라운드는 "DB 쓰기 허용(백업 후)" 을 분명히 적어 달라.
8. **VERIFY 와 GEN 의 경계 유지.** GEN 의 자기 블라인드 테스트나 자기 검토는 판정으로 쓰지 말 것 (5장 실측). 사실 확인 중 "지식 근거" 표시가 붙은 항목은 VERIFY 가 웹으로 우선 확인하도록 VERIFY 브리핑에 넣어 달라.
