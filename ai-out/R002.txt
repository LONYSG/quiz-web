1-1. 다시 정리한 문제 정의

R001에서 확인된 무료 조합의 실질적 약점은 두 가지였고, 이번 라운드에서 건우의 판단으로
성격이 달라졌다.

  (1) Render Free 15분 슬립 → 콜드 스타트 약 1분
      → 건우 판단으로 수용됨. 방장이 먼저 접속해 대기를 흡수하고, 접속자가 있는 동안은

      → 즉 이제 이것은 "해결해야 할 문제"가 아니라 "이미 처리된 사항"이다.

      → 이쪽이 남은 진짜 위험이다. 한도를 소진하면 컴퓨트가 정지하고 기존 연결이 끊기며

        게임 도중 이것이 발생하면 서비스가 통째로 멈춘다.
      → 따라서 이번 라운드의 재조사는 사실상 "(2)를 5달러 미만으로 없앨 수 있는가"이다.

1-4. 비용 추산 근거 (전부 추정)

  Neon Launch 컴퓨트 비용 = 활성 시간 × CU 크기 × $0.106
  · Neon의 최소 CU 값을 공식 문서에서 확인하지 못했다(확인 불가). 통상 0.25 CU로 알려져 있어
    이를 가정한다.
  · 시나리오 1 — 스케일 투 제로가 정상 동작하는 경우
    친구들이 주 3회 × 2시간 플레이 = 월 약 24시간 활성.
    DB는 5분 유휴 후 정지하므로 실제 활성은 약 30시간으로 잡는다.
    30h × 0.25CU × $0.106 = 약 $0.80
    스토리지 0.5GB × $0.35 = 약 $0.18
    → 월 약 $1
  · 시나리오 2 — ★ 커넥션 풀을 상시 열어두어 스케일 투 제로가 동작하지 않는 경우
    730h × 0.25CU × $0.106 = 약 $19.3 / 월
    → 예산을 20배 초과한다. Free 플랜에서는 "DB가 멈추는" 사고였던 것이,
      Launch에서는 "요금이 20배 나오는" 사고로 형태만 바뀐다.
    → 즉 1-6의 idle timeout 설정은 A안이든 B안이든 반드시 해야 하는 필수 조치다.

  Fly.io(C안) 서버 비용 = $2.02(256MB) 또는 약 $3(512MB, 추정)
  · Node + Socket.IO + 10명 규모라면 256MB로도 동작할 것으로 추정하나, Node의 기본 힙 설정과
    빌드 산출물 크기에 따라 부족할 수 있다. 실측 없이는 확답할 수 없다(확인 필요).
  · 512MB를 택하면 Neon 비용과 합쳐 월 $4~6이 되어 5달러를 넘길 수 있다.

1-5. 권장안

  ★ B안 (Render Free + Neon Launch)을 권장한다. 예상 비용 월 $1~3.

  이유는 세 가지다.
  (1) 남은 유일한 실질 위험이었던 "DB가 월말에 멈춘다"가 완전히 사라진다.
      돈을 쓰는 효과가 가장 큰 지점이 정확히 여기다.
  (2) 콜드 스타트는 이미 건우 판단으로 수용된 사항이므로, 이를 없애기 위해 서버에
      돈을 더 쓰는 것은 비용 대비 효과가 낮다. C안이 추가로 사는 것은 "방장이 첫 접속 시
      1분 기다리지 않는 것" 하나뿐인데, 그 대가로 월 $2~3이 더 들고 배포 플랫폼도 바뀐다.
  (3) Render는 GitHub 연동 후 push만으로 배포되고 render.yaml 한 장으로 설정이 끝나서,
      건우의 1순위 기준(Claude Code가 유지보수하기 쉬울 것)에 가장 잘 맞는다.
      Fly.io는 Dockerfile + fly.toml + flyctl을 다뤄야 해서 한 단계 복잡하다.

  차선은 A안이다. B안과 A안의 애플리케이션 코드는 완전히 동일하고, Neon 대시보드에서
  플랜만 바꾸면 되므로 A안으로 시작해 실제 사용량을 관찰한 뒤 B로 올리는 것도 합리적이다.
  다만 A안으로 시작하면 "언제 100 CU-시간에 도달하는지" 감시가 필요하고,
  도달했을 때는 이미 게임이 멈춘 뒤라 사후 대응이 된다.
  → 처음부터 B안으로 가고, 대신 idle timeout으로 비용을 낮게 유지하는 쪽을 권한다.

  최종 결정은 건우가 한다. Q-39로 올린다.

1-6. ★ Neon 커넥션 풀 idle timeout 방침 (A안·B안 공통 필수)

  목표: 아무도 게임하지 않는 시간에는 DB 커넥션이 0개가 되어 Neon이 스케일 투 제로에
        들어가게 한다. 이것이 지켜지지 않으면 A안은 멈추고 B안은 요금이 20배가 된다.

  구체 방침 (이번 라운드에서 확정 제안, 코드는 R004 이후)
  · 커넥션 풀 최소 유지 연결 수 = 0. (풀이 유휴 연결을 계속 붙들지 않게 한다)
  · 유휴 연결 종료 시간 = 60초. Neon의 스케일 투 제로 기준이 5분이므로 그보다 충분히 짧게 둔다.
  · 풀 최대 연결 수 = 5 정도로 작게. 단일 인스턴스 + 10명 규모에서 그 이상은 불필요하다.
  · ★ 상시 실행되는 주기 쿼리(헬스체크 SELECT 1, 크론성 폴링 등)를 DB에 걸지 않는다.
    이런 쿼리가 하나라도 있으면 스케일 투 제로가 영원히 발동하지 않는다.
    heartbeat(Q-02)는 클라이언트 → 서버 WebSocket 핑이며 DB를 건드리지 않는다.
    이 점을 코드와 문서에 명시적으로 못 박아야 한다.
  · 서버 기동 시 DB에 즉시 연결하지 않고, 첫 쿼리가 필요할 때 연결한다(지연 연결).
  · Neon 대시보드에서 월 사용량(CU-시간)을 주기적으로 확인하는 절차를 docs\11-DEPLOY.md에 남긴다.

1-7. 나중에 갈아탈 수 있게 하려면 설계상 무엇을 지켜야 하는가

  A ↔ B ↔ C ↔ D 사이를 코드 변경 없이 이동할 수 있도록 다음을 지킨다.

  · 접속 정보는 전부 환경 변수로만 받는다. DATABASE_URL, PORT, PUBLIC_BASE_URL,
    SESSION_SECRET, NODE_ENV. 코드에 호스트명이나 플랫폼 이름을 넣지 않는다.
  · 포트는 반드시 process.env.PORT를 사용한다. Render / Fly / 로컬이 모두 다르게 준다.
  · 플랫폼 고유 SDK를 쓰지 않는다. 표준 pg 드라이버와 표준 HTTP/WebSocket만 사용한다.
  · 파일 시스템에 영속 데이터를 쓰지 않는다. Render Free의 디스크는 재시작 시 사라지고,
    Fly도 볼륨을 따로 붙여야 한다. 모든 영속 데이터는 PostgreSQL로만 간다.
  · 프론트엔드 정적 파일은 Node 서버가 직접 서빙한다(R001 3-2 결론 유지).
    오리진이 하나면 CORS·쿠키 SameSite 문제가 사라지고 배포 대상도 하나로 유지된다.
  · 헬스체크 엔드포인트(GET /healthz)는 DB를 건드리지 않고 프로세스 생존만 응답한다.
    1-6의 이유 때문이다.
  · 배포 설정 파일(render.yaml 등)은 저장소 루트에 두되, 애플리케이션 코드가 그것을
    읽지 않게 한다.
  · 로그는 표준 출력으로만 낸다. 플랫폼별 로그 SDK를 쓰지 않는다.

  이 원칙들을 docs\02-ARCHITECTURE.md의 "플랫폼 중립 규칙" 절로 고정한다.

2-1. API 조사

[엔드포인트]
  · 문제 조회        https://opentdb.com/api.php
  · 카테고리 목록    https://opentdb.com/api_category.php
  · 카테고리별 개수  https://opentdb.com/api_count.php?category=N
  · 전체 개수        https://opentdb.com/api_count_global.php
  · 세션 토큰        https://opentdb.com/api_token.php?command=request | reset

[파라미터] (공식 문서 확인, 2026-09-04)
  · amount      1~50 (1회 최대 50건)
  · category    카테고리 ID (미지정 시 전체)
  · difficulty  easy / medium / hard (미지정 시 전체)
  · type        multiple(4지선다) / boolean(True·False) 두 종류
  · encode      기본(HTML 엔티티) / urlLegacy / url3986 / base64
  · token       세션 토큰

  ★ type에 대한 결론: boolean 타입은 True/False 문제이므로 주관식 전환이 원천적으로 불가능하다.
    수집 대상에서 완전히 제외한다. 이번 파일럿의 모든 수집은 type=multiple로만 수행했다.

  ★ encode에 대한 자체 판단: url3986을 사용한다. 기본 인코딩(HTML 엔티티)은
    &quot; &#039; &amp; 가 섞여 나와 후처리가 지저분하고, base64는 디버깅이 어렵다.
    url3986은 decodeURIComponent 한 번으로 원문이 정확히 복원된다. 실측으로 확인했다.

[응답 코드]
  0 성공 / 1 결과 없음(요청 수량만큼 문제가 없음) / 2 파라미터 오류 /
  3 토큰 없음 / 4 토큰 소진(해당 조건의 문제를 전부 받음) / 5 레이트 리밋

[레이트 리밋] 공식 문서 문구: "Each IP can only access the API once every 5 seconds."
  ★ 실측 결과 5.2초 간격으로도 response_code 5(레이트 리밋)가 빈번히 발생했다.
    안정적으로 동작한 간격은 6.5~8초였다. 즉 문서상 5초는 하한이고 실제로는 더 여유가 필요하다.
    이 사실은 배치 설계에 직접 영향을 준다(2-3 참조).

[세션 토큰] 존재한다. 토큰을 붙여 요청하면 이미 받은 문제를 다시 주지 않고,
  해당 조건의 문제를 전부 소진하면 response_code 4를 반환한다.
  ★ 따라서 중복 없는 전량 수확이 가능하다. 이번 파일럿이 실제로 이 방식을 사용했다.

[★ 총 문제 수 — 가장 중요한 발견]
  api_count_global.php 실측 결과 (2026-09-04):
    전체 등록      21,612
    검수 대기      10,906  (pending)
    ★ 검수 완료     5,298  (verified)
    반려            5,425  (rejected)

  ★ API가 실제로 제공하는 것은 verified 5,298건뿐이다.
    카테고리별 api_count.php의 total_question_count를 24개 카테고리 전부 합산한 결과가
    정확히 5,298로 일치했다. pending 10,906건은 API로 받을 수 없다.

  → 즉 OpenTDB는 유한한 코퍼스이며 그 상한은 5,298건이다.
    이 5,298에는 boolean 타입이 포함되어 있으므로, 우리가 쓸 수 있는 multiple 타입은
    그보다 적다. ★ 이번 라운드에서 세션 토큰으로 전량 수확을 완주해 정확한 값을 확정했다.
    type=multiple 문제는 정확히 4,500건이다.
    (토큰이 response_code 4(소진)를 반환할 때까지 훑은 실측값. 따라서 boolean은 798건이다)

  ★ 이 발견이 전략을 바꾼다.
    "매일 랜덤 크롤링해서 문제를 늘린다"는 접근은 성립하지 않는다. 유한 코퍼스이므로
    토큰을 써서 한 번에 전량 수확하면 끝이고, 그 이후에는 OpenTDB 측에 새 문제가
    검수 통과로 추가될 때만 늘어난다(증가 속도는 확인 불가, 매우 느릴 것으로 추정).

[★ 라이선스] 확인일 2026-09-04
  · OpenTDB 메인 페이지에 CC BY-SA 4.0 (Creative Commons Attribution-ShareAlike 4.0
    International) 배지가 표시되어 있다.
  · 이것이 사실이라면 두 가지 의무가 발생한다.
      (a) 출처 표기(Attribution): Open Trivia Database 출처를 명시해야 한다.
      (b) 동일조건변경허락(ShareAlike): 원본을 번역·가공한 파생물(우리의 한국어 문제 DB)도
          동일한 CC BY-SA 4.0으로 배포해야 한다.
  · ★ 저장소가 Public이므로 이 의무는 실제 제약이 된다. 구체적으로는
      - 코드(서버·클라이언트)는 영향을 받지 않는다고 판단한다. ShareAlike는 "각색물"에
        적용되며, 데이터를 사용하는 소프트웨어는 각색물이 아니라고 보는 것이 일반적 해석이다.
      - 반면 OpenTDB에서 파생된 한국어 문제 데이터 자체는 CC BY-SA 4.0으로 공개해야 한다.
      - 다른 출처에서 온 문제와 한 DB에 섞이더라도, 문제별로 출처·라이선스를 기록해 두면
        "여러 저작물의 모음(collection)"으로 취급할 수 있어 다른 문제까지 전염되지는
        않는다고 판단한다.
  · ★ 위 판단은 법률 자문이 아니다. 나는 변호사가 아니며 이 해석은 추정이다.
    실제 대응 방식은 Q-41로 올린다. 최소한 다음은 지켜야 한다고 본다.
      - 문제 테이블에 source / license / source_ref 컬럼을 두고 문제별로 기록 (3장 스키마 반영)
      - README와 서비스 화면 하단에 OpenTDB 출처와 라이선스를 표기
      - 파생 데이터 파일(예: data/questions/*.json)에 라이선스 고지 파일 동봉

[분류 (2) — 보기 참조형, 실제 샘플]

    내려갔다. 즉 필터를 느슨하게 잡으면 멀쩡한 문제 9%를 버린다.

[분류 (3) — 보기를 빼면 정답이 유일하지 않은 것, 실제 샘플]  ★ 가장 위험한 유형
  · "When was Pong released?" → 정답 "November 29, 1972"
    → 주관식이면 "1972", "1972년", "72년 11월 29일" 등 무한한 표기가 나온다.
      guide 16절이 fuzzy matching을 금지하므로 정확 일치만 하는데, 이런 문제는
      정답을 아는 사람이 계속 오답 처리된다.
  · "What day did the Battle of Gettysburg begin?" → "July 1, 1863"  (동일 문제)
  · "Who is one of the co-princes of Andorra?" → "The president of France"
    → "one of"이므로 정답이 실제로 둘이다(프랑스 대통령 / 우르헬 주교).
  · "Who was Hannibal?" → "Carthaginian general"
    → 서술형 정답. "카르타고 장군", "장군", "카르타고의 명장" 전부 맞는 말이다.
  · "What is the average lifespan of a domestic rabbit?" → "8-12 years"
    → 범위형 정답. 주관식 입력으로 재현 불가능하다.
  · "What is the half-life of Uranium-235?" → "703,800,000 years"
    → 자릿수·단위 표기 변형이 무한하다.
  · "What is the approximate value of mathematical constant e?" → "2.72"
    → 2.718, 2.71828 등을 입력한 사람이 오답 처리된다. 정답이 "근사값"인 것도 문제다.
  · "In the 2002 film 'Kung Pow!', why was Wimp Lo purposely trained wrong?" → "As a joke"
    → why 질문의 서술형 정답.
  · "What did the first moving picture depict?" → "A galloping horse"

  ★ 이 유형은 문장만 보면 멀쩡하다. 키워드로는 절반도 못 잡는다. 자동 탐지로 잡은 것은
    2.7%뿐이지만, 수동 라벨링에서는 이 유형이 훨씬 많이 나왔다.
    → 결론: 이 판정은 사람 또는 LLM의 의미 판단이 반드시 필요하다.
      이것이 2-3에서 Gemini 판정 항목에 "정답이 유일하게 결정되는가"를 최우선으로 넣은 이유다.

    · Entertainment: Television — "In 'Breaking Bad', Walter White is diagnosed with which

      자동 카테고리 필터로 버린 39.7% 중 대략 15% 정도는 회수 가능하다고 추정한다.

[분류 (5) — 적절한 한국어 표기 문제]  ★ 자동 판정 불가, 그러나 영향이 매우 크다
  이 항목은 "탈락 사유"라기보다 "복수 정답 배열을 확보하지 못하면 게임이 망가지는 사유"다.

  · 인명 음차 변형: "Justinian I" → 유스티니아누스 1세 / 유스티니아누스 / 유스티니아누스1세
  · 인명 음차 변형: "Nathaniel Hawthorne" → 너새니얼 호손 / 나다니엘 호손 / 호손
  · 인명 음차 변형: "Vincent van Gogh" → 반 고흐 / 빈센트 반 고흐 / 고흐 / 반고흐
  · 제품·고유명사: "Magnavox Odyssey" → 마그나복스 오디세이 / Magnavox Odyssey
  · 작품명: "The Scarlet Letter" → 주홍글씨 / 주홍 글자
  · 국가·지역: "United Kingdom" → 영국 / 잉글랜드(오답) / UK / 그레이트브리튼
  · 일반명사: "Stack" → 스택 / stack
  · 개념어: "Quadratic" → 이차함수 / 2차함수 / 이차 / quadratic
  · 외래어 그대로 통용: 미토콘드리아, 이데올로기, 아이러니 → 한글 표기 그대로 사용 가능
    (건우 지침대로 이런 경우는 (5) 탈락 사유가 아니다)

  ★ 결론: 이 게임은 fuzzy matching이 금지(guide 16절)되어 있으므로,
    표기 변형을 복수 정답 배열로 얼마나 촘촘히 확보하느냐가 게임의 체감 품질을 좌우한다.
    번역 품질보다 이쪽이 더 중요하다.

[★ 수동 라벨링 — 최종 생존율 산출]
  자동 분류만으로는 (3)(4)(5)를 정확히 잡지 못하므로, 무작위 표본을 직접 읽고 라벨링했다.
  두 번 독립적으로 수행했다.

  라벨링 1회차: 구조 필터((2)+장문정답)를 통과한 문항 중 무작위 40건
    → 실제 사용 가능 판정 12건 = 30.0%
  라벨링 2회차: 자동 필터((2)(3)(4)) 전부를 통과한 문항 중 무작위 30건
    → 실제 사용 가능 판정 14건 = 46.7%

  두 경로로 전체 생존율을 계산하면
    경로 A: 구조 통과 81.9% × 30.0% ≈ 24.6%
    경로 B: 자동 잔존 40.7% × 46.7% = 19.0%
            + (4) 버킷 38.2% × 회수율 15%(추정) = 5.7%
            = 24.7%
  두 계산이 24.6~24.7%로 수렴했다.

  ★ 최종 생존율 추정: 약 25% (표본 크기가 작아 실제로는 20~30% 범위로 본다)

  ★ 확보 가능량 계산
    OpenTDB API 제공 상한          5,298건 (verified 전체, boolean 포함)
    그중 multiple 타입              ★ 4,500건 (전량 수확 완주로 확정)
    그중 boolean 타입                 798건 (사용 불가)
    × 생존율 약 25%                 ≈ 1,100건
    ★ 즉 OpenTDB만으로 실제 서비스에 투입 가능한 한국어 주관식 문제는 약 1,100건이다.

  목표가 "수천 건 이상"이므로 OpenTDB 단독으로는 명백히 부족하다.

2-3. 가공 파이프라인 설계

[전체 흐름]

  [0] 소스 어댑터            소스별로 원본을 표준 중간 포맷(RawQuestion)으로 변환
        │                     OpenTDB 어댑터는 그중 하나일 뿐
        ▼
  [1] 원본 적재 (question_raw)  ★ 원본을 절대 버리지 않는다
        │                       가공 규칙이 바뀌면 원본에서 다시 돌린다
        ▼
  [2] 사전 필터 (규칙 기반, 무료)  boolean 제외 / "of the following" 등 구조 패턴 제외
        │                          → 여기서 약 20%를 LLM 호출 없이 걸러 비용을 아낀다
        ▼
  [3] 1차 가공 (Gemini)        판정 + 번역 + 복수 정답 배열 생성
        │                       판정에서 탈락하면 즉시 폐기(rejected)
        ▼
  [4] 역검증 (Gemini)          ★ 번역된 한국어 질문만 주고 정답을 맞히게 함
        │                       원본 정답과 대조 → 불일치면 검수 대기 또는 폐기
        ▼
  [5] 검수 큐 (review_queue)    status=pending_review 로 적재
        │                       ★ 자동으로 서비스 DB에 들어가지 않는다
        ▼
  [6] 사람 검수                 승인 → status=approved, is_active=true
        │                       반려 → status=rejected (원본은 남김)
        ▼
  [7] 서비스 투입              approved + is_active 인 문제만 출제 대상

[★ 1차 가공 Gemini 프롬프트 전문]

  시스템 지시:
  ---------------------------------------------------------------------------
  너는 영어 4지선다 상식 퀴즈를 한국어 주관식 퀴즈로 변환하는 검수관이다.
  변환 결과는 실시간 멀티플레이 퀴즈 게임에서 사용되며, 이 게임은 정답을
  "정확한 문자열 일치"로만 판정한다. 오타 허용이나 유사도 판정을 하지 않는다.
  따라서 조금이라도 정답이 애매한 문제는 반드시 탈락시켜야 한다.
  통과시키는 것보다 탈락시키는 것이 안전하다. 확신이 없으면 탈락시켜라.

  입력으로 문제 배열을 받는다. 각 문제에 대해 아래 순서로 판정하고 결과를 JSON으로 출력한다.

  [판정 1] convertible — 보기 없이 문장이 성립하는가
    다음에 해당하면 false:
    - 질문이 보기 집합을 전제한다 ("다음 중", "이들 중", "~가 아닌 것은")
    - 정답이 문장이거나 서술형이다
    - 정답이 여러 항목의 나열이다

  [판정 2] uniqueAnswer — ★ 가장 중요. 보기를 없앴을 때 정답이 유일하게 결정되는가
    다음에 해당하면 false:
    - 조건을 만족하는 답이 현실에 둘 이상 존재한다
      (예: "국기가 빨강과 흰색인 나라는?" → 일본·캐나다·폴란드·오스트리아 …)
    - 질문에 "~중 하나"가 들어 있다
    - 정답이 날짜이고 연·월·일 표기 방식이 여러 가지다
    - 정답이 숫자인데 단위·정밀도·자릿수 표기가 여러 가지다 (근사값, 범위값 포함)
    - 정답이 이유·방법·현상 설명이라 표현이 사람마다 달라진다
    ★ 정답이 "연도 하나"이거나 "개수 하나"처럼 표기가 사실상 하나뿐이면 true로 둔다.

  [판정 3] krAccessible — 한국의 일반적인 성인이 이 문제를 접했을 때
    "알 수도 있겠다"고 느낄 수준인가. 1~5로 평가한다.
    5 = 한국 교과 과정이나 대중문화에서 널리 알려짐
    3 = 관심 있는 사람은 아는 수준
    1 = 해당 국가·해당 팬덤 밖에서는 사실상 아무도 모름
      (예: 영국 어린이 프로그램 조연의 성, 니치 게임의 내부 수치)
    ★ 카테고리로 판단하지 말고 문항 내용으로 판단하라.
      비디오 게임 문제라도 한국에서 유명하면 높게 평가하고,
      일반상식 문제라도 미국 지역 한정이면 낮게 평가하라.

  [판정 4] koreanTerm — 정답에 대응하는 한국어 표기가 존재하는가
    - 한국어 고유 표기가 있으면 true
    - 한국에서 외래어 표기로 통용되면 true (예: 미토콘드리아, 이데올로기, 아이러니, 스택)
    - 표기가 정착되지 않아 사람마다 다르게 쓸 수밖에 없으면 false

  위 판정 중 convertible=false 또는 uniqueAnswer=false 또는 krAccessible<=2 또는
  koreanTerm=false 이면 verdict="reject"로 하고 나머지 생성 필드는 비운다.

  전부 통과하면 verdict="accept"로 하고 다음을 생성한다.

  [생성 1] question_ko — 한국어 질문.
    원문의 의미를 바꾸지 않는다. 보기 참조 표현을 주관식 어투로 자연스럽게 고친다.
    질문 안에 정답이 드러나지 않게 한다.
    존댓말을 쓰지 않고 "~은?", "~는 무엇인가?" 형태의 간결한 퀴즈 어투로 쓴다.

  [생성 2] displayAnswer — 정답 공개 화면에 보여줄 대표 표기 하나.
    가장 표준적이고 널리 쓰이는 표기를 고른다.

  [생성 3] ★ answers — 정답 판정에 사용할 표기 변형 배열. 이 필드가 가장 중요하다.
    게임은 정확 문자열 일치로만 판정하므로, 실제 사람이 칠 법한 표기를 최대한 넣어라.
    반드시 포함할 것:
      - displayAnswer 자체
      - 원문 영어 표기 (예: Stack)
      - 한글 음차 표기의 흔한 변형 (예: 반 고흐 / 빈센트 반 고흐 / 고흐 / 반고흐)
      - 성만 / 이름 전체 등 인명의 통용 축약형
      - 한자어와 고유어가 함께 쓰이는 경우 양쪽
      - 숫자는 아라비아 숫자와 한글 표기 양쪽 (예: 2 / 둘)
    포함하지 말 것:
      - 명백히 틀린 답
      - 정답보다 범위가 넓은 상위 개념 (예: 정답이 "서울"인데 "한국"을 넣지 않는다)
      - 오타 변형 (게임이 오타를 허용하지 않는 것이 규칙이다)
    ★ 띄어쓰기 차이와 영문 대소문자 차이는 게임 엔진이 알아서 무시하므로
      그 목적만으로 변형을 추가하지 마라.

  [생성 4] category — 다음 중 하나로 매핑한다:
    일반상식 / 역사 / 지리 / 과학 / 수학 / 자연 / 예술 / 음악 / 영화 / 문학 /
    스포츠 / 인물 / 기술 / 신화 / 언어 / 기타

  [생성 5] difficulty — easy / medium / hard.
    ★ 원문 난이도를 그대로 쓰지 말고, 한국인 기준으로 다시 매긴다.

  [생성 6] explanation — 한 문장 해설. 만들 수 없으면 null.

  [생성 7] hintAnswer — 힌트 생성 기준으로 삼을 정답 하나.
    보통 displayAnswer와 같지만, 대표 표기가 지나치게 길면 더 짧고 대표적인 것을 고른다.

  [생성 8] confidence — 위 판정 전체에 대한 self-confidence. 0.0~1.0.

  출력은 아래 JSON 배열만 낸다. 설명 문장을 덧붙이지 마라.
  [
    {
      "sourceRef": "<입력의 sourceRef 그대로>",
      "verdict": "accept" | "reject",
      "rejectReason": "<reject일 때만: convertible|uniqueAnswer|krAccessible|koreanTerm>",
      "convertible": true|false,
      "uniqueAnswer": true|false,
      "krAccessible": 1-5,
      "koreanTerm": true|false,
      "question_ko": "...",
      "displayAnswer": "...",
      "answers": ["...", "..."],
      "category": "...",
      "difficulty": "easy|medium|hard",
      "explanation": "..." | null,
      "hintAnswer": "...",
      "confidence": 0.0-1.0
    }
  ]
  ---------------------------------------------------------------------------

  사용자 메시지(배치 입력) 형식:
    [{"sourceRef":"otdb-000123","question":"...","correct":"...",
      "incorrect":["...","...","..."],"category":"Geography","difficulty":"medium"}, ...]

  ★ 오답 보기(incorrect)를 함께 넣는 이유: 오답 보기를 보면 원문이 어떤 축으로 문제를
    구성했는지 드러나서, uniqueAnswer 판정 정확도가 올라간다.
    예를 들어 오답이 전부 "국가명"이면 그 질문은 국가를 묻는 것이고,
    조건을 만족하는 국가가 여럿인지 판단하기 쉬워진다.
    다만 생성된 한국어 질문에는 보기를 절대 넣지 않는다.

[★ 역검증(back-check) 프롬프트 전문]

  시스템 지시:
  ---------------------------------------------------------------------------
  아래는 한국어 상식 퀴즈 질문이다. 보기는 없다.
  각 질문에 대해 네가 생각하는 정답을 답하라.
  - 정답은 가능한 한 짧은 명사구로 답한다.
  - 확실하지 않으면 confidence를 낮게 준다.
  - 답이 여러 개일 수 있다고 판단되면 ambiguous를 true로 하고
    가능한 답을 alternatives에 전부 나열한다.  ← 이 항목이 핵심이다
  출력은 JSON 배열만 낸다.
  [{"id":"...","answer":"...","alternatives":["..."],"ambiguous":true|false,
    "confidence":0.0-1.0}]
  ---------------------------------------------------------------------------

  판정 규칙 (코드에서 수행, LLM에게 맡기지 않는다):
    · answer가 1차 가공의 answers 배열 중 하나와 정규화 후 일치     → pass
    · ambiguous=true 또는 alternatives 길이 >= 2                      → ★ 즉시 reject
      (보기 없이 정답이 유일하지 않다는 가장 강한 신호다)
    · 불일치하지만 confidence가 낮음                                  → pending_review
    · 불일치하고 confidence가 높음                                    → reject
      (번역이 원문과 다른 것을 묻게 되었을 가능성이 높다)
    · ★ 역검증이 낸 answer가 answers에 없는데 사람이 보기에 맞는 표기라면
      그것을 answers 배열에 추가한다. 즉 역검증은 복수 정답 배열을 늘리는 수단도 된다.

  ★ 이 방식의 실효성 평가
    · 잡을 수 있는 것: 번역 오류, 정답 비유일성, 한국어 표현 애매함, 질문 안에 정답이
      들어가 버린 경우(그러면 역검증이 100% 맞히므로 오히려 통과한다 — 이건 못 잡는다)
    · 못 잡는 것:
      (a) 질문에 정답이 노출된 경우. 역검증은 통과시킨다. → 별도 규칙 검사 필요:
          "question_ko 안에 answers 중 하나가 문자열로 포함되어 있으면 reject"
          이 검사는 코드로 무료로 할 수 있다. 반드시 넣는다.
      (b) 원문 자체가 틀린 경우. OpenTDB는 사용자 투고 기반이라 원문 오류가 존재한다.
          실측 샘플에서 "Which of the following is the world's best-selling book?
          → The Lord of the Rings"가 나왔는데, 이는 통상 성경으로 알려진 것과 다르다.
          역검증에서 LLM이 다른 답을 내면 불일치로 걸러지므로 부분적으로는 잡힌다.
      (c) LLM 자신이 같은 방향으로 틀리는 경우(같은 모델을 두 번 쓰는 데서 오는 상관관계).
          → 완화책: 1차 가공과 역검증에 서로 다른 모델을 쓴다
            (예: 1차 gemini-2.5-flash, 역검증 gemini-2.5-flash-lite).
            완전한 독립은 아니지만 상관관계를 줄인다.
    · 비용: 문제당 LLM 호출이 1회 → 2회로 늘어난다. 배치로 묶으면 요청 수는 늘지 않고
      토큰만 늘어난다. 역검증 입력은 질문 텍스트뿐이라 1차 가공보다 훨씬 짧다.
    → 종합 판단: 비용 대비 효과가 매우 크다. 반드시 넣을 것을 권장한다.

  ★ 더 나은 검증 방법 제안 (역검증에 추가)
    · 규칙 검사 3종 (무료, 반드시 넣는다)
      (a) question_ko에 정답 문자열이 포함되면 reject
      (b) answers 배열에 중복이 있거나, 정규화 후 서로 같아지는 항목만 있으면 경고
      (c) displayAnswer가 answers에 포함되어 있지 않으면 reject (데이터 정합성)
    · 중복 검사 (무료)
      정규화된 question_ko 또는 displayAnswer가 기존 승인 문제와 같으면 중복으로 처리.
      여러 소스를 쓰게 되면 이 검사가 필수가 된다.
    · 샘플 사람 검수 (초기 필수)
      자동 통과분에서 무작위 30건을 뽑아 사람이 확인하고, 오류율이 5% 미만으로 안정되면
      자동 승인 임계값을 낮춘다. 이 절차를 docs\10-TESTING.md에 남긴다.

[검수 방식 제안]
  세 가지를 검토했다.
  (가) SQL 직접 조작
       장점: 만들 것이 없다.  단점: 수백 건을 SQL로 넘기는 것은 현실적으로 고통스럽다.
  (나) CSV 내보내기 → 스프레드시트에서 승인 표시 → 다시 가져오기
       장점: 구현이 거의 없다. 스프레드시트라 대량 편집이 편하다.
       단점: 왕복 과정에서 인코딩·따옴표 사고가 나기 쉽다. 이력 추적이 약하다.
  (다) 최소 관리 페이지 (문제 하나씩 보여주고 승인 / 반려 / 수정)
       장점: 키보드만으로 빠르게 처리 가능. 수정과 승인이 한 화면에서 끝난다.
       단점: 만들어야 한다. 다만 매우 작다(목록 + 폼 하나).

  ★ 권장: (다). 단 Phase 0~4 기간에는 (나)로 버티고, 문제 DB를 본격적으로 채우는 시점에
    (다)를 만든다. 이유는 이 파이프라인이 게임 서버와 별도 트랙이므로(건우 지침),
    게임 핵심 루프 완성보다 뒤에 두는 것이 맞기 때문이다.
    다만 검수 UI를 나중에 만들더라도 review_queue 스키마는 지금 확정한다(3장).
  최종 결정은 Q-45로 올린다.

[★ 소스 무관 설계]
  파이프라인의 [1]단계 이후는 소스를 전혀 모른다. 소스별로 다른 것은 [0] 어댑터뿐이다.

  어댑터가 지켜야 할 계약 (RawQuestion 표준 포맷):
    {
      sourceId:    "opentdb",              // sources 테이블의 키
      sourceRef:   "otdb-000123",          // 소스 내 고유 식별자(중복 수집 방지용)
      lang:        "en",
      question:    "...",
      correct:     "...",
      incorrect:   ["...","...","..."],    // 없으면 빈 배열
      category:    "Geography",            // 소스의 원래 카테고리 문자열
      difficulty:  "medium",               // 없으면 null
      license:     "CC-BY-SA-4.0",
      raw:         { ... }                 // 소스 원본 전체를 그대로 보관
    }

  · 새 소스를 붙이는 작업 = 이 포맷으로 변환하는 함수 하나를 추가하는 것.
  · 파이프라인 [2]~[7]은 손대지 않는다.
  · incorrect가 없는 소스(원래 주관식인 소스)도 그대로 들어올 수 있다.
    그 경우 Gemini 프롬프트의 uniqueAnswer 판정 정확도가 조금 떨어지지만 동작한다.
  · 한국어 소스가 들어오면 lang="ko"가 되고, 번역 단계를 건너뛰고 판정과
    복수 정답 배열 생성만 수행한다. 프롬프트에 분기를 하나 두면 된다.

[GitHub Actions 배치 설계]
  ★ OpenTDB가 유한 코퍼스이므로 "매일 랜덤 수집"은 의미가 없다. 중복만 받는다.
    따라서 수집과 가공을 분리한다.

  · 수집 잡 (harvest) — 수동 실행(workflow_dispatch) + 월 1회 정기
    OpenTDB를 세션 토큰으로 전량 훑어 question_raw에 적재.
    이미 있는 sourceRef는 건너뛴다. 신규 검수 통과분만 늘어난다.
    ★ 실측: 요청 간격 6~8초, 50건씩 90회 요청으로 4,500건 전량 수확에 약 12분이 걸렸다.
      GitHub Actions 무료 러너 한도(공개 저장소는 무제한, 확인 필요) 안에서 충분하다.

  · 가공 잡 (process) — 매일 1회 정기 실행
    question_raw에서 미가공 건을 N개 꺼내 [2]~[5]를 수행하고 검수 큐에 넣는다.
    N은 Gemini 무료 한도에 맞춰 정한다(아래).
    ★ 이 잡이 배치의 본체다. 건우 지시대로 "수확은 1회성, 배치는 원본 처리용"이 맞다.

  · 비밀값은 GitHub Actions Secrets로만 넣는다(GEMINI_API_KEY, DATABASE_URL).
    저장소가 Public이므로 특히 주의한다. guide 55-1절 준수.

[Gemini 무료 한도와 처리량 추산]
  ★ 확인 결과: Google 공식 rate limits 문서는 현재 무료 티어의 구체 수치 표를 게재하지 않고
    "AI Studio에서 본인 한도를 확인하라"고만 안내한다(확인일 2026-09-04). 따라서 공식 확인 불가다.
  제3자 자료 기준(추정, 검증 필요):
    · Gemini 2.5 Flash        약 10 RPM / 250,000 TPM / 500 RPD
    · Gemini 2.5 Flash-Lite   약 15 RPM / 250,000 TPM / 1,500 RPD
    · Pro 계열은 2026년 중 무료 티어에서 제외됨
  → 건우가 AI Studio에서 실제 한도를 확인해 알려주면 이 수치를 확정할 수 있다.

  추산 (RPD 500, 배치 10문제/요청 가정)
    1차 가공: 10문제 × 500요청 = 5,000문제/일 (이론상)
    역검증도 같은 키를 쓰면 절반 → 약 2,500문제/일
    TPM 250,000 제약도 함께 걸리므로 실제로는 그보다 낮을 것으로 본다.
  ★ 결론: OpenTDB 전량(4,500건)을 처리하는 데 무료 한도로 이틀이면 충분하다.
    유료 전환이 필요 없다. 다만 소스를 크게 늘리면(수만 건) 재검토가 필요하다.
  ★ 안전장치: 배치 잡에 일일 처리 상한(예: 1,500건)을 두고, 429 응답이 나오면
    그날 잡을 즉시 중단한다. 무료 한도 초과가 과금으로 이어지는지 여부는 확인 불가이므로
    (결제 수단을 등록하지 않으면 과금되지 않는 것이 일반적이라고 추정하나 확인 필요),
    보수적으로 상한을 두는 것이 안전하다. Q-44로 올린다.

[★ 이 파이프라인의 위치]
  건우 지침대로 이 적재 파이프라인은 게임 서버와 완전히 분리된 별도 서브시스템이다.
  · 디렉터리도 분리한다: pipeline\ (server\ client\ shared\ 와 동급)
  · Phase 1~7과 섞지 않는다. 별도 트랙(Track D — Data)으로 관리한다.
  · 게임 서버는 questions 테이블을 읽기만 한다. 파이프라인은 쓰기만 한다.
    이 단방향 관계를 문서에 명시한다.
  · 유일한 접점은 DB 스키마다. 그래서 3장의 스키마를 지금 확정한다.

2-4. 결론

[OpenTDB를 1차 소스로 계속 쓸 것인가]
  ★ 답: 쓴다. 단 "1차 소스"가 아니라 "초기 시드 소스"로 위치를 낮춘다.

  쓰는 이유
  · 약 1,100건은 결코 적은 양이 아니다. 50문제짜리 게임을 20판 이상 돌릴 수 있고,
    문제 경험 시스템(guide 26절)이 의미를 갖기 시작하는 최소 규모를 넘긴다.
  · 정답·오답 보기가 함께 있어 uniqueAnswer 판정 정확도가 높다. 다른 소스보다 가공이 쉽다.
  · 카테고리와 난이도가 이미 붙어 있다.
  · 수집이 완전히 자동화되고 무료다.
  · 무엇보다 파이프라인 전체를 실제 데이터로 검증할 수 있는 유일한 즉시 가용 소스다.

  위치를 낮추는 이유
  · 코퍼스 상한이 4,500건(multiple 기준)으로 확정적이고, 그중 약 25%만 생존한다.
    전량 수확을 이미 완주했으므로 더 긁어도 나오지 않는다. 성장 여지가 없다.
  · 22%가 비디오 게임이고 전반적으로 서구 대중문화 편중이다.
    한국인 대상 "상식 퀴즈"의 주력 소스가 되기에는 성격이 맞지 않는다.
  · 생존한 1,100건도 카테고리가 고르지 않을 것이다(지리·역사·과학이 상대적으로 많이 살아남고
    음악·TV·게임은 대부분 죽는다). 카테고리 균형이 깨진다.

[수천 건 목표를 채우려면 무엇이 더 필요한가]
  한국어 상식 문제 확보가 핵심 과제다. 이번 라운드에서 조사한 후보를 제시한다.
  ★ 아래는 검색으로 존재를 확인한 수준이며, 실제 데이터 품질·수량·라이선스는
    개별 확인이 필요하다(확인 필요).

  후보 1 — ETRI 엑소브레인 QA 데이터셋
    · 퀴즈 분야 질의응답 데이터. 객관식/주관식/가부형/연상형 4개 유형.
    · 규모는 569건으로 알려져 있어(확인 필요) 그 자체로는 작다.
    · ★ 그러나 "한국어 원본 주관식 퀴즈"라는 점이 매우 크다. 번역·표기 문제가 없다.
    · 회원가입 + 사용허가 협약서 + 담당자 승인이 필요하고 무료.
    · 라이선스 조건 확인 필요. 승인 절차가 있으므로 건우가 직접 신청해야 한다.

  후보 2 — 공공데이터포털(data.go.kr) 및 AI Hub
    · 무료 오픈 API와 데이터셋이 다수 존재. 퀴즈 전용 데이터가 있는지는 확인하지 못했다.
    · 퀴즈가 아니더라도 "한국사 연표", "국가·수도", "문화재 목록" 같은 구조화 데이터로부터
      템플릿 기반으로 문제를 생성하는 방식이 가능하다.
      ★ 이 방식은 정답이 유일하게 결정되도록 우리가 직접 설계할 수 있어서
        (3)번 위험이 원천적으로 없다. 품질이 매우 안정적이다.
      예: "대한민국의 OO번째 대통령은?" / "OOO의 수도는?" / "OO년에 일어난 사건은?"
      단 문제 형태가 단조로워지므로 전체의 일부로만 써야 한다.
    · guide 51절의 AI 문제 생성 금지는 런타임 금지로 해석 확정되었으므로,
      개발 단계의 템플릿 생성은 허용 범위 안이다.

  후보 3 — 위키백과 / 위키데이터 기반 생성
    · CC BY-SA(위키백과) 또는 CC0(위키데이터). 위키데이터는 구조화 트리플이라
      템플릿 생성에 매우 적합하고 CC0라 라이선스 제약이 없다.
    · 규모가 사실상 무한하다. 수천 건 목표를 채울 수 있는 유일한 후보로 본다.
    · 난이도 조절과 "상식 수준" 필터링이 과제다. Gemini 판정을 그대로 재사용할 수 있다.

  후보 4 — 직접 작성 + AI 보조
    · 건우가 카테고리와 주제를 정하고 AI가 초안을 만든 뒤 검수하는 방식.
    · 품질이 가장 높고 게임 성격에 정확히 맞출 수 있다.
    · 속도가 느리지만, 초기 100~200건의 "확실히 재미있는 문제"를 확보하는 데는 최적이다.

  ★ 권장 조합
    단계 1 (지금)      OpenTDB 파이프라인 완성 + 약 1,000건 확보
                       → 파이프라인 자체를 실데이터로 검증하는 것이 진짜 목적
    단계 2             위키데이터 템플릿 생성 어댑터 추가 → 수천 건 확보
    단계 3             ETRI 등 한국어 원본 데이터셋 (건우가 신청·승인 필요)
    단계 4 (상시)      직접 작성으로 품질 높은 문제 보강

    이 순서인 이유는, 단계 1에서 파이프라인·스키마·검수 절차가 검증되면
    단계 2 이후는 어댑터만 추가하면 되기 때문이다. 소스 무관 설계가 여기서 값을 한다.

3-1. 설계 원칙

  · guide 52절이 "향후 확장 대비"와 "MVP 과복잡화 금지"를 동시에 요구한다.
    균형점을 다음 기준으로 잡았다.
      → 컬럼 추가는 싸다(ALTER TABLE ... ADD COLUMN). 나중에 해도 된다.
      → 테이블 분리와 관계 변경은 비싸다(데이터 마이그레이션 + 코드 전면 수정). 지금 정한다.
      → 데이터 소급 입력이 필요한 것은 지금 넣는다. 카테고리가 대표적이다(guide 40절).
    그래서 "테이블 구조와 관계"는 확장을 반영해 지금 확정하고,
    "확장 전용 상세 컬럼"(이미지 URL, 보기 목록 등)은 지금 만들지 않는다.

  · 정답 판정은 서버 메모리에서 동기 코드로 수행한다(R001 3-1, guide 18절).
    따라서 DB 스키마는 조회 성능보다 데이터 정합성과 관리 편의를 우선한다.

3-2. 테이블 확정안

[sources] — 출처와 라이선스
  id             text PK            'opentdb', 'wikidata', 'manual', 'etri'
  name           text               'Open Trivia Database'
  url            text
  license        text               'CC-BY-SA-4.0', 'CC0-1.0', 'proprietary'
  attribution    text               화면·문서에 표기할 출처 문구 전문
  notes          text
  ★ 존재 이유: 2-1의 CC BY-SA 대응. 문제별로 라이선스를 추적할 수 있어야
    여러 소스를 한 DB에 섞어도 share-alike가 다른 문제로 번지지 않는다.

[categories] — 카테고리
  id             smallserial PK
  key            text UNIQUE        'general', 'history', 'geography', ...
  name_ko        text               '일반상식', '역사', '지리', ...
  sort_order     smallint
  is_active      boolean
  ★ 별도 테이블로 두는 이유: guide 40절이 카테고리별 성적 통계를 요구하고,
    52절이 카테고리 선택/제외 기능을 확장 후보로 든다. 문자열로 박아두면 나중에
    이름을 바꿀 때 통계가 깨진다.

[question_raw] — 원본 보관 (파이프라인 전용)
  id             bigserial PK
  source_id      text FK → sources
  source_ref     text               소스 내 고유 식별자
  payload        jsonb              소스 원본 전체
  fetched_at     timestamptz
  processed_at   timestamptz NULL
  process_status text               'pending' | 'filtered_out' | 'processed' | 'error'
  UNIQUE (source_id, source_ref)
  ★ 존재 이유: 가공 규칙이나 프롬프트가 바뀌면 원본에서 다시 돌려야 한다.
    원본을 버리면 그때 소스를 다시 긁어야 하는데, OpenTDB는 레이트 리밋 때문에
    한 번 훑는 데 15분이 걸린다. 반드시 보관한다.

[questions] — 문제 본체
  id              bigserial PK
  question_type   text NOT NULL DEFAULT 'short_answer'
                  ★ 지금은 'short_answer' 하나만 사용. 확장 시 'multiple_choice',
                    'initial_sound', 'ordering' 등이 추가된다. 컬럼만 미리 둔다.
  question_text   text NOT NULL
  display_answer  text NOT NULL     정답 공개 화면에 보여줄 대표 표기
  hint_answer     text NULL         힌트 생성 기준. NULL이면 display_answer 사용 (Q-26)
  answer_lang     text NOT NULL     'ko' | 'en' | 'mixed'
                  ★ 힌트 규칙이 한글/영문으로 분기하므로 필요 (5장)
  category_id     smallint FK → categories
  difficulty      text              'easy' | 'medium' | 'hard'
  explanation     text NULL         guide 21절 해설
  source_id       text FK → sources
  source_ref      text NULL
  license         text NULL         문제 단위 라이선스(소스 기본값을 복사해 고정)
  status          text NOT NULL     'pending_review' | 'approved' | 'rejected'
  is_active       boolean NOT NULL DEFAULT true
                  ★ status와 별개인 이유: 승인된 문제라도 나중에 품질 문제가 발견되면
                    빼야 한다. 그때 status를 rejected로 되돌리면 검수 이력이 오염된다.
                    "승인 여부"와 "현재 서비스 노출 여부"는 다른 축이다.
  created_at      timestamptz
  updated_at      timestamptz
  approved_at     timestamptz NULL
  · 출제 대상 조건: status='approved' AND is_active=true AND question_type='short_answer'
  · 인덱스: (status, is_active, category_id)

[question_answers] — 복수 정답 (guide 17절)
  id              bigserial PK
  question_id     bigint FK → questions ON DELETE CASCADE
  answer_text     text NOT NULL      원문 표기 (사람이 읽는 형태)
  answer_norm     text NOT NULL      ★ 4장 정규화 규칙을 적용한 결과를 미리 저장
  is_primary      boolean            display_answer와 같은 항목 표시
  note            text NULL          왜 이 변형을 넣었는지 (검수 참고)
  UNIQUE (question_id, answer_norm)
  · 인덱스: (question_id), (answer_norm)

  ★ 배열 컬럼(text[]) 대신 별도 테이블로 하는 이유
    (a) answer_norm에 UNIQUE 제약을 걸어 "정규화하면 같아지는 중복 변형"을 DB가 막아준다.
        예: "New York"과 "newyork"을 둘 다 넣으려 하면 삽입이 거부된다.
        배열 컬럼으로는 이 검증을 애플리케이션에서 해야 한다.
    (b) 표기 변형을 나중에 추가·삭제하는 것이 이 프로젝트에서 자주 일어날 작업이다
        (2-2의 (5) 분석 참조). 행 단위 관리가 훨씬 낫다.
    (c) note 컬럼으로 검수 맥락을 남길 수 있다.
    단점은 조인이 하나 늘어나는 것인데, 문제 로딩은 게임 시작 시 한 번뿐이고
    판정은 메모리에서 하므로 성능 영향이 없다.

  ★ display_answer와 question_answers의 관계
    · display_answer는 화면 표시 전용이다. 판정에 쓰지 않는다.
    · 판정은 오직 question_answers.answer_norm 집합과의 비교로만 한다.
    · display_answer에 해당하는 행이 question_answers에 반드시 존재해야 한다
      (is_primary=true). 이 정합성은 삽입 시 검증하고, 2-3의 규칙 검사 (c)로도 확인한다.
    · 이렇게 분리하는 이유: 대표 표기는 "보기 좋은 형태"(예: "빈센트 반 고흐")여야 하고,
      판정 집합은 "실제로 칠 법한 모든 형태"(반 고흐 / 고흐 / 반고흐 / van gogh)여야 해서
      목적이 다르다. 하나로 합치면 둘 중 하나가 반드시 나빠진다.

[review_queue] — 검수 (파이프라인 전용)
  question_id      bigint PK FK → questions
  ai_model         text              가공에 사용한 모델
  ai_confidence    real
  ai_flags         jsonb             convertible/uniqueAnswer/krAccessible/koreanTerm 등 원값
  backcheck_answer text NULL         역검증이 내놓은 답
  backcheck_result text              'pass' | 'mismatch' | 'ambiguous' | 'skipped'
  rule_flags       jsonb             규칙 검사 결과(정답 노출, 중복 등)
  reviewer_note    text NULL
  reviewed_at      timestamptz NULL
  ★ questions와 분리하는 이유: 검수는 파이프라인의 관심사이고 게임 서버는 전혀 읽지 않는다.
    게임 서버가 읽는 테이블을 가볍게 유지한다.

3-3. 확장 대비에 대한 판단과 근거

  지금 넣는 것
  · question_type — 컬럼 하나. 나중에 객관식·초성 퀴즈가 들어와도 기존 데이터가
    'short_answer'로 남아 있어 마이그레이션이 필요 없다. 비용 거의 0.
  · categories 테이블 — guide 40절이 명시적으로 요구. 소급 입력 비용이 매우 크다.
  · sources / license — 2-1의 라이선스 의무 대응. 나중에 소급 불가능하다
    (어느 문제가 어디서 왔는지 잊어버리면 끝이다).
  · question_answers 별도 테이블 — 관계 구조는 나중에 바꾸기 비싸다.
  · answer_lang — 힌트 규칙이 지금 당장 이 정보를 필요로 한다.

  지금 넣지 않는 것
  · question_choices (객관식 보기 테이블) — 객관식은 guide 51절 금지 기능이다.
    필요해지면 테이블 하나를 추가하면 되고 기존 데이터에 영향이 없다.
  · media_url / image_id — 이미지 퀴즈도 51절 금지. ALTER로 충분.
  · tags, difficulty_score(수치형), play_count 등 — 통계는 별도 테이블에서 집계한다
    (R003의 DB 스키마에서 다룬다). questions에 카운터를 두면 매 게임마다 쓰기가 발생해
    Neon CU-시간을 소모한다(1-6과 충돌).
  · i18n(다국어) 구조 — 요구사항에 없다. 과설계.

  ★ 판단 기준 요약: "나중에 컬럼을 추가하면 되는 것"은 넣지 않고,
    "나중에 데이터를 소급 입력해야 하는 것"과 "관계 구조 자체"는 지금 넣는다.


═══════════════════════════════════════════════════════════════
4. 정답 정규화 규칙 명세 + 테스트 케이스
═══════════════════════════════════════════════════════════════

4-1. 위치와 성격

  · shared\ 에 두는 순수 함수. 입력이 같으면 항상 같은 출력을 낸다.
  · 서버가 판정에 사용하고, 파이프라인이 question_answers.answer_norm 생성에 사용한다.
    ★ 두 곳이 반드시 같은 함수를 써야 한다. 다르면 DB에 저장된 정규화 값과
      런타임 판정이 어긋나 정답이 오답 처리된다.
  · 이 함수가 바뀌면 question_answers.answer_norm 전체를 재계산해야 한다.
    따라서 함수에 버전 번호를 두고, 재계산이 필요한 변경인지 문서에 기록한다.
    (docs\07-DECISIONS.md 대상)

4-2. 정규화 단계 (순서 고정)

  단계 0. 입력이 문자열이 아니면 빈 문자열로 취급한다.
          길이 제한(100자, Q-18)은 이 함수의 책임이 아니라 상위 계층에서 처리한다.

  단계 1. 유니코드 NFC 정규화
          목적: macOS / iOS 사파리가 한글을 NFD(자모 분리)로 보내는 경우를 흡수한다.
          이 단계가 없으면 아이폰 사용자가 눈에 똑같은 답을 쳐도 오답 처리된다.
          ★ NFKC를 쓰지 않는 이유: NFKC는 "①"→"1", "㈜"→"(주)", "Ⅳ"→"IV", "㎡"→"m2"처럼
            의미를 바꾸는 변환까지 수행한다. guide 16절이 "특수문자·기호는 무시하지 않는다"고
            했으므로 NFKC는 규칙을 넘어선다. NFC + 명시적 전각 변환만 한다.
            → 이 판단은 자체 기술 판단으로 처리하고 기록한다.

  단계 2. 제로폭 문자 제거
          U+200B(ZWSP), U+200C(ZWNJ), U+200D(ZWJ), U+FEFF(BOM)를 제거한다.
          ★ 이들은 JavaScript의 \s에 포함되지 않아 단계 4에서 걸러지지 않는다.
            복사·붙여넣기로 흔히 섞여 들어오며, 눈에 보이지 않아 디버깅이 매우 어렵다.
          주의: U+200D는 이모지 결합(ZWJ 시퀀스)에도 쓰인다. 이모지가 정답인 경우는
          이 게임에 사실상 없으므로 제거를 택한다. 이 트레이드오프를 기록한다.

  단계 3. 전각 → 반각 변환
          · U+FF01 ~ U+FF5E → 해당 코드포인트에서 0xFEE0을 뺀다 (！→! ａ→a １→1 ＋→+)
          · U+3000(전각 공백) → U+0020 (단계 4에서 어차피 제거된다)
          · ★ 반각 카타카나(U+FF61~U+FF9F)는 대상으로 삼지 않는다. 한국어 상식 퀴즈에서
            의미가 없고, 변환하면 오히려 예상치 못한 동작이 생긴다.

  단계 4. 모든 공백류 제거
          정규식 /\s/g 로 제거한다. JavaScript의 \s는 스페이스, 탭, 개행, 캐리지리턴,
          수직탭, 폼피드, NBSP(U+00A0), U+1680, U+2000~U+200A, U+2028, U+2029,
          U+202F, U+205F, U+3000을 포함한다.
          근거: guide 16절 "띄어쓰기 무시".

  단계 5. 영문 대소문자 통일
          toLowerCase()를 적용한다.
          ★ 로케일 지정 없이 기본 동작을 쓴다. 터키어 로케일의 I/ı 문제는 한국어 서비스에서
            발생하지 않는다. toLocaleLowerCase는 쓰지 않는다(환경에 따라 결과가 달라져
            서버와 파이프라인이 어긋날 수 있다).
          근거: guide 16절 "영문 대소문자 차이 무시".

  단계 6. 결과 반환.

4-3. 하지 않는 것 (명시)

  · 특수문자·기호를 제거하지 않는다. + - . , ! ? ' " ( ) / & % 등 전부 유지한다.
    근거: guide 16절 "A+B와 AB는 다른 문자열이므로 오답".
  · 오타 허용, 편집 거리, 유사도 판정을 하지 않는다. guide 16절 명시적 금지.
  · 조사·어미를 제거하지 않는다. "서울"과 "서울은"은 다른 문자열이다.
    (이 문제는 복수 정답 배열로 해결한다. 정규화의 일이 아니다.)
  · 한자 ↔ 한글 변환을 하지 않는다.
  · 숫자 표기 변환(3 ↔ 삼 ↔ three)을 하지 않는다. 복수 정답 배열의 몫이다.
  · 발음기호 제거(é → e)를 하지 않는다. 다른 글자다.
  · ★ 아포스트로피·하이픈의 유니코드 변형 통일은 현재 규칙에 없다.
    이것이 실사용에서 문제가 될 것으로 보이므로 Q-36으로 올린다(아래).

4-4. ★ 발견된 문제 — 아포스트로피와 하이픈 (Q-36)

  모바일 키보드와 일부 워드프로세서는 작은따옴표를 자동으로 U+2019(’)로 바꾼다.
  하이픈도 U+2010, U+2011, U+2013(–), U+2014(—), U+2212(−) 등 여러 변형이 있다.
  현재 규칙대로면 "don't"(U+0027)와 "don’t"(U+2019)는 서로 다른 문자열이라 오답이 된다.
  이것은 "특수문자를 무시하지 않는다"는 규칙의 취지(A+B ≠ AB)와는 성격이 다르다.
  같은 글자의 다른 표현이지 다른 글자가 아니기 때문이다.
  → Q-36으로 올린다. 권장안은 아포스트로피류와 하이픈류를 ASCII로 통일하는 것이다.

═══════════════════════════════════════════════════════════════
5. 힌트 생성 규칙 명세 + 테스트 케이스
═══════════════════════════════════════════════════════════════

5-1. 위치와 입력

  · shared\ 의 순수 함수. 서버가 문제 시작 시 미리 계산해 메모리에 들고 있는다.
    (guide 18절 판정 블록에 await를 넣지 않기 위해, 힌트도 문제 시작 시점에 미리 만든다)
  · 입력: hint_answer가 있으면 그것, 없으면 display_answer. 그리고 answer_lang.
  · 출력: 힌트 문자열 하나.
  · 표시 시점: 남은 시간 10초 이하일 때만 (guide 11절).

5-2. 복수 정답일 때 어느 것을 쓰는가 (Q-26 확정 제안)

  · 기본: display_answer 하나를 기준으로 힌트를 만든다.
  · 예외: questions.hint_answer가 지정되어 있으면 그것을 쓴다.
  · ★ 모든 정답의 힌트를 나열하지 않는다. 이유는 세 가지다.
    (a) 정답이 여러 개라는 사실 자체가 강한 힌트가 된다.
    (b) 정답 개수가 많으면 화면이 지저분해지고 30초 안에 읽을 수 없다.
    (c) 표기 변형(반 고흐 / 고흐 / 반고흐)까지 전부 나열되면 사실상 정답 공개다.
  · 대신 hint_answer 필드로 출제자가 통제한다. 예를 들어 정답이 "태조 / 이성계"인 문제는
    hint_answer를 "이성계"로 지정해 힌트를 ㅇㅅㄱ로 만들 수 있다.
  · ★ 부작용: 다른 정답을 떠올린 사람은 힌트가 자기 답과 맞지 않아 혼란스러울 수 있다.
    이는 감수한다. 반대로 전부 나열하면 게임이 무너진다.
    이 트레이드오프를 docs\07-DECISIONS.md에 기록한다.

5-3. 문자 단위 변환 규칙

  전처리: 4장의 정규화 중 단계 1~4(NFC, 제로폭 제거, 전각→반각, 공백 제거)만 적용한다.
          ★ 대소문자 통일(단계 5)은 적용하지 않는다. 영문 첫 글자를 원래 대소문자로
            보여줘야 하기 때문이다(guide 11절 Apple → A____).

  변환: 전처리된 문자열을 앞에서부터 한 글자씩 처리한다.
    · 한글 음절 (U+AC00 ~ U+D7A3)
        → 초성으로 바꾼다. 초성 인덱스 = floor((코드 - 0xAC00) / 588)
          초성표: ㄱ ㄲ ㄴ ㄷ ㄸ ㄹ ㅁ ㅂ ㅃ ㅅ ㅆ ㅇ ㅈ ㅉ ㅊ ㅋ ㅌ ㅍ ㅎ
    · 영문자 (A-Z, a-z)
        → 문자열 전체에서 처음 등장하는 영문자 1개만 원래 글자 그대로 노출.
          그 이후의 모든 영문자는 '_'.
    · 숫자 (0-9)
        → '_'.  ★ 숫자를 그대로 노출하면 연도·개수 문제의 정답이 사실상 공개된다.
    · 그 외 (기호, 문장부호, 한자, 가나 등)
        → 그대로 노출한다. guide 16절이 기호를 의미 있는 문자로 취급하므로,
          힌트에서도 문자열의 뼈대를 보여주는 편이 자연스럽다.

  ★ "영문 첫 글자 1개만" 규칙에 대한 판단 (자체 판단, 기록 대상)
    guide 11절 예시는 Apple → A____ 하나뿐이라 다단어 영문에 대한 규정이 없다.
    두 가지가 가능하다.
      (가) 전체에서 첫 글자 1개만:  New York → N______   (공백 제거 후 7글자)
      (나) 단어마다 첫 글자:        New York → N__ Y___
    (나)는 정보량이 훨씬 크다. 단어 수와 각 단어의 첫 글자가 노출되면
    guide 11절의 "정답이 지나치게 노출되지 않도록 한다"에 저촉된다고 판단해 (가)를 택한다.
    다만 이는 해석이므로 Q-38로 올려 건우 확인을 받는다.

5-4. ★ 발견된 문제 (Q-37)

  문제 1 — 매우 짧은 정답
    · 1글자 한글 정답: "달" → 힌트 "ㄷ". 후보가 극히 좁아진다.
    · 1글자 영문 정답: "e" → 규칙상 첫 영문자는 그대로 노출되므로 힌트가 "e" = 정답 그 자체.
      ★ 이건 명백한 결함이다. guide 11절을 정면으로 위반한다.
    · 2글자 한글 정답: "서울" → "ㅅㅇ". 상당히 좁혀진다.

  문제 2 — 기호 노출로 정답이 드러나는 경우
    · "C++" → 첫 영문자 C 노출 + 기호 그대로 → 힌트가 "C++" = 정답 그 자체.
    ★ 이것도 결함이다.

  문제 3 — 글자 수 노출 자체가 과노출인가
    · 초성 힌트는 필연적으로 글자 수를 노출한다. guide 11절이 초성 표시를 명시했으므로
      글자 수 노출은 규칙이 이미 받아들인 것으로 해석한다.
    · 다만 마스킹(6장)에서는 글자 수 노출을 명시적으로 금지했다(Q-35 확정 사항).
      두 규칙이 서로 다른 것은 시점이 다르기 때문이다. 힌트는 마지막 10초에만 나오고,
      마스킹은 문제 시작 직후부터 걸린다. 건우의 판단 근거와 일치한다.
    → 따라서 글자 수 노출 자체는 문제 삼지 않는다.

  권장 보완안 (Q-37)
    · 전처리 후 길이가 1이면 힌트를 생성하지 않고 "힌트 없음"으로 표시한다.
    · 전처리 후 길이가 2 이하이고, 규칙 적용 결과가 원본과 같아지면(즉 아무것도 가려지지
      않으면) 힌트를 생성하지 않는다. C++ 케이스가 여기에 걸린다.
    · 안전장치로, 생성된 힌트가 정규화 후 정답과 같아지면 무조건 힌트를 버린다.
      (규칙이 어떻게 바뀌든 정답이 그대로 노출되는 일은 없게 하는 최종 방어선)
    · 힌트를 만들지 않은 경우 화면에는 "이 문제는 힌트가 없습니다"를 표시한다.
      아무것도 표시하지 않으면 버그로 오인된다.
    · 대안으로 "카테고리를 힌트로 보여준다"도 가능하나, 카테고리는 상시 표시해도 되는
      정보라 힌트 대체물로는 약하다. Q-37에서 함께 검토한다.

6-1. 규칙의 목적과 범위 (Q-35 확정 사항 재확인)

  · 대상: 해당 문제를 이미 경험한 플레이어가 보낸 채팅 메시지.
  · 조건: 현재 문제가 진행 중(QUESTION_ACTIVE)일 때만.
    정답이 이미 공개된 뒤(QUESTION_RESOLVED, 5초 대기 구간)에는 마스킹하지 않는다.
    정답이 이미 모두에게 공개되었으므로 가릴 이유가 없다.
  · 미경험자의 메시지는 마스킹하지 않는다. 그 메시지는 정답 판정 대상이며,
    정답이면 그 순간 문제가 종료된다.
  · ★ 마스킹은 서버에서 수행한다. 클라이언트에 원문을 보내고 CSS로 가리는 방식은
    개발자 도구로 즉시 뚫린다. 서버가 이미 치환된 문자열을 내보낸다.

6-2. 마스킹 표현 3안과 권장

  (안 1) 고정 블록 문자 — "▩▩▩"
    예시:  철수: ▩▩▩인가
    장점: 한 눈에 "가려졌다"가 전달된다. 길이가 항상 3칸으로 고정되어 정답 길이가 새지 않는다.
          구현이 가장 단순하고, 서버가 보낸 문자열을 클라이언트가 그대로 렌더해도 동작한다.
    단점: 채팅 흐름에서 다소 투박하다.

  (안 2) 자물쇠 칩 — "🔒"
    예시:  철수: 🔒인가
    장점: 가장 짧아 채팅 흐름을 거의 해치지 않는다. 의미가 직관적이다.
    단점: 이모지 렌더링이 기기마다 다르다. 사용자가 직접 🔒를 입력하면 혼동이 생긴다.
          (이 경우는 마스킹 토큰과 사용자 입력을 구분할 수 없다)

  (안 3) 서버 치환 + 클라이언트 배지 렌더
    서버는 고정 센티널 문자열로 치환하고, 메시지에 masked=true 플래그를 함께 보낸다.
    클라이언트는 그 센티널을 배경색 있는 작은 칩(예: 옅은 회색 바탕에 "가려짐")으로 렌더한다.
    예시:  철수: [가려짐]인가     ← [가려짐] 부분이 시각적으로 구분되는 칩
    장점: 가장 명확하고 예쁘다. 사용자 입력과 절대 혼동되지 않는다(센티널을 제어문자로
          두면 사용자가 입력할 수 없다).
    단점: 클라이언트 렌더링 코드가 조금 필요하다.

  ★ 권장: (안 3). 근거는 다음과 같다.
    · (안 2)의 사용자 입력 혼동 문제가 실제로 발생한다. 누군가 🔒를 치면
      다른 사람은 그것이 마스킹인지 그냥 이모지인지 알 수 없고, 이 게임에서는
      "저 사람이 정답을 쳤구나"라는 정보가 게임 판단에 영향을 주므로 무해하지 않다.
    · (안 1)은 안전하지만 투박하고, ▩ 문자 자체를 사용자가 입력할 수도 있다.
    · (안 3)은 센티널을 사용자가 입력할 수 없는 문자(예: U+E000 사설 사용 영역)로 두면
      혼동이 원천 차단된다. 클라이언트 렌더링 비용도 작다.
    · 다만 (안 3)을 택하더라도 서버가 내보내는 문자열 자체는 이미 치환되어 있으므로,
      클라이언트가 배지 렌더에 실패해도 정답이 새지 않는다. 안전성이 유지된다.
  Q-42로 올려 건우가 고르게 한다.

  ★ 어느 안을 택하든 지켜야 할 것 (Q-35 확정 사항)
    · 마스크 길이는 정답 길이와 무관하게 항상 고정이다.
      "*****"처럼 길이에 비례하는 마스크는 금지한다.
    · 한 메시지에 정답이 여러 번 나오면 각각을 같은 고정 토큰으로 치환한다.
      (토큰이 2개 보이면 "두 번 썼다"는 것만 드러나며, 이는 무해하다)

6-3. 매칭 기준 (Q-43 관련)

  · ★ 정규화를 적용해 매칭한다. 4장의 정규화 함수를 그대로 쓴다.
    즉 정답이 "New York"일 때 경험자가 "newyork"이라고 쳐도 마스킹된다.
    적용하지 않으면 "고 무 줄"처럼 띄어 쓰는 것만으로 우회되어 규칙이 무력해진다.
  · 구현 방식: 원문을 한 글자씩 순회하면서
      (a) 정규화 결과 문자열과
      (b) 정규화 결과의 각 위치가 원문의 어느 인덱스에서 왔는지의 매핑
    을 동시에 만든다. 정규화 문자열에서 정답을 찾은 뒤, 매핑을 통해 원문의 구간으로
    되돌려 그 구간을 토큰으로 치환한다.
    ★ 이 인덱스 매핑이 이 기능의 유일하게 까다로운 부분이다. R003의 프로토콜 명세와 함께
      구현 지침을 남긴다.

  · 부분 일치 여부 — 권장: 정답 전체가 포함된 경우만 마스킹한다.
    근거: 부분 일치를 허용하면 오탐이 급증한다. 정답이 "고무줄"일 때 "고무"만으로
    마스킹하면 "고무장갑 얘기냐" 같은 정상 대화가 가려진다. 게임이 이상해진다.
    반대로 전체 일치만 잡으면 "고무 줄"처럼 띄어 쓰는 우회는 정규화가 잡아주고,
    "고무-줄"처럼 기호를 끼우는 우회는 못 잡는다.
    ★ 완벽한 차단은 불가능하다는 사실을 문서에 명시한다.
      악의적 우회까지 막으려면 fuzzy matching이 필요한데, 그것은 guide 16절이 금지한
      기술이고 정답 판정과 마스킹에 서로 다른 매칭 기준을 쓰면 규칙이 혼란스러워진다.
      이 게임은 친구들끼리 하는 것이므로 "실수나 무심코 흘리는 것"을 막는 수준이면 충분하다고
      판단한다. 이 판단 근거를 07-DECISIONS.md에 남긴다.

  · ★ 짧은 정답의 오탐 문제 (Q-43)
    정답이 1~2글자면 오탐이 심각해진다.
      정답 "달" → "달라", "달리기", "얼마나 달랐는데" 전부 마스킹된다.
      정답 "말" → "말이야", "무슨 말" 전부 마스킹된다.
    이러면 경험자는 정상적인 대화를 거의 할 수 없게 되어, 28절이 보장한
    "경험자도 채팅은 자유롭게 가능하다"가 사실상 무너진다.
    권장안: 정규화 후 길이가 2 이하인 정답은 "정확히 그 메시지 전체가 정답과 같을 때"만
    마스킹한다(부분 포함으로는 마스킹하지 않는다).
    → Q-43으로 올린다.

  · 복수 정답: question_answers의 모든 항목을 대상으로 검사한다.

[Q-36] 아포스트로피·하이픈 유니코드 변형 통일 여부
──────────────────────────────────────────
- 배경: 4-4 참조. 모바일 키보드가 '를 U+2019(’)로 자동 변환한다. 현재 규칙대로면
  "don't"와 "don’t"가 다른 문자열이라 오답이 된다. 하이픈도 U+2010~U+2015, U+2212 등
  변형이 많다. Q-16 확정 사항에 이 세부가 포함되어 있지 않다.
- 선택지:
  (A) 아포스트로피류(U+2018 U+2019 U+02BC U+00B4)와 하이픈류(U+2010~U+2015 U+2212)를
      각각 ASCII ' 와 - 로 통일한다.
      장점: 실사용 사고를 막는다. "같은 글자의 다른 표현"을 통일하는 것이라
            guide 16절의 취지(A+B ≠ AB)를 위반하지 않는다고 판단한다.
      단점: 규칙이 조금 늘어난다.
  (B) 통일하지 않는다. 표기 변형이 필요하면 복수 정답 배열에 넣는다.
      장점: 규칙이 단순하다.
      단점: 정답에 아포스트로피가 들어가는 모든 문제마다 변형을 넣어야 한다.
            빠뜨리면 조용히 오답이 난다.
  (C) 아포스트로피만 통일하고 하이픈은 두지 않는다.
- 권장안: (A). 한국어 문제가 주력이라 빈도는 낮겠지만, 영문 정답이 섞이는 이상
  반드시 발생한다. 비용이 거의 없고 사고는 확실히 막는다.
- 영향 범위: 중간. 정규화 함수가 바뀌면 question_answers.answer_norm을 전부 재계산해야 한다.

8-1. 자체 판단으로 처리하고 기록만 남긴 항목

  아래는 순수 기술적이고 되돌리기 쉬운 세부사항이라 질문하지 않고 결정했다.
  이견이 있으면 알려주면 즉시 바꾼다.

  · OpenTDB 수집 시 encode=url3986을 사용한다. (HTML 엔티티·base64 대비 후처리가 정확하고 단순)
  · OpenTDB type=boolean은 수집 대상에서 완전히 제외한다. (주관식 전환 원천 불가)
  · OpenTDB 수집 요청 간격을 7초로 둔다. (문서상 5초이나 실측에서 레이트 리밋 빈발)
  · 정규화에 NFKC가 아니라 NFC를 쓴다. (NFKC는 ① → 1 같은 의미 변환까지 수행해
    guide 16절의 기호 보존 원칙을 넘어선다)
  · 정규화 단계에 제로폭 문자(U+200B~U+200D, U+FEFF) 제거를 포함한다.
    (JavaScript \s에 포함되지 않아 별도 처리가 필요하고, 눈에 보이지 않아 디버깅이 어렵다)
  · toLocaleLowerCase가 아니라 toLowerCase를 쓴다. (환경별 결과 차이를 배제)
  · 반각 카타카나는 전각→반각 변환 대상에서 제외한다.
  · 힌트 생성 시 정규화 단계 1~4만 적용하고 대소문자 통일(단계 5)은 적용하지 않는다.
    (영문 첫 글자를 원래 대소문자로 보여줘야 한다)
  · 힌트에서 숫자는 언더스코어로 가린다. (그대로 노출하면 연도·개수 문제의 정답이 공개된다)
  · 생성된 힌트가 정규화 후 정답과 같아지면 힌트를 버린다는 최종 방어선을 항상 적용한다.
  · question_answers를 배열 컬럼이 아니라 별도 테이블로 둔다. (answer_norm UNIQUE 제약으로
    중복 변형을 DB가 막아주고, 변형 추가·삭제가 잦은 작업이라 행 단위 관리가 유리하다)
  · questions.status와 is_active를 분리한다. (승인 여부와 현재 노출 여부는 다른 축)
  · 파이프라인 디렉터리를 pipeline\ 으로 분리하고 게임 서버와 단방향 관계로 둔다.
  · 헬스체크 엔드포인트는 DB를 건드리지 않는다. (Neon 스케일 투 제로를 방해하지 않기 위해)
  · .gitignore에 tmp/ 를 반드시 넣는다. (이번 라운드 조사 스크립트와 수집 데이터가 들어있다)

8-2. 이번 라운드에서 하지 않은 것 (명시)

  · 애플리케이션 코드, git init, 스캐폴딩, 저장소 초기화 — 지시대로 하지 않았다.
  · npm install — 하지 않았다. 조사는 Node 내장 fetch만으로 수행했다.
  · 게임 규칙의 임의 변경 — 없다. 모호한 지점은 전부 Q로 올렸다.
  · Render / Neon / Fly / Google AI Studio 계정 가입 — 하지 않았다.
  · 커밋·푸시 — 이번 라운드는 저장소에 넣을 산출물이 없어 수행하지 않았다.
    (R001.txt와 R002.txt는 Phase 0에서 docs 골격과 함께 첫 커밋에 포함하는 것이 자연스럽다)

8-3. 우려 사항

  · ★ 코퍼스 총량(4,500건)과 자동 분류 비율은 전수 조사 결과라 확정값이다.
    그러나 최종 생존율 25%는 수동 라벨링 표본 70건(40 + 30)에 기반한 추정이다.
    표본이 작아 실제로는 20~30% 범위로 본다. 파이프라인을 실제로 돌려 100건 정도를
    가공해 보면 정확한 수치가 나온다. 그 시점에 이 문서의 추정을 갱신해야 한다.
  · ★ OpenTDB 원본 자체에 오류가 있다. 실측 샘플에서 "세계 최다 판매 도서 → 반지의 제왕"이
    나왔는데 통상 성경으로 알려진 것과 다르다. 사용자 투고 기반이라 이런 것이 섞여 있다.
    역검증이 부분적으로 잡지만 완전하지 않다. 사람 검수를 초기에 반드시 거쳐야 하는 이유다.
  · ★ 마스킹은 완벽한 차단이 불가능하다. "고무-줄"처럼 기호를 끼우거나 초성으로 쓰면
    막을 수 없다. 악의적 우회까지 막으려면 fuzzy matching이 필요한데 guide 16절이 금지한다.
    친구들끼리 하는 게임이므로 "무심코 흘리는 것"을 막는 수준으로 설계했다.
  · ★ 1-4 시나리오 2가 가장 큰 운영 리스크다. 커넥션 풀 설정 하나를 잘못하면
    Neon Free에서는 DB가 멈추고 Launch에서는 요금이 20배가 된다.
    1-6의 방침을 docs\02-ARCHITECTURE.md와 코드 주석 양쪽에 명시한다.
  · Neon의 최소 CU 값을 확인하지 못했다(확인 불가). 0.25 CU를 가정한 비용 추산이므로
    실제 청구액은 다를 수 있다. Q-39에서 B안을 택하면 첫 달 사용량을 반드시 확인해야 한다.
  · Gemini 무료 티어의 정확한 한도를 공식 문서에서 확인하지 못했다(확인 불가).
    건우가 AI Studio에서 확인해 주면 배치 설계를 확정할 수 있다.
  · Render Starter $7과 Fly 512MB 가격은 제3자 자료 기반이라 확인 불가에 준한다.
    권장안(B)은 이 수치에 의존하지 않으므로 결정에 영향은 없다.
