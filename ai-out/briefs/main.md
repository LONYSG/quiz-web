TASK: 난이도를 AI 나 한 사람의 어림으로 매기는 것을 그만두고 **실제 플레이 숫자로 고쳐 나가기로 했다**(찬종 2026-11-17 원문: "실제 정답률, 힌트 의존도, 정답이 나오는 시간 등 디테일한 통계들을 수집해서 보완해 나가는 걸로 해."). 2026-11-17 에 카드 6,160장을 다시 썼고 등급 4 · 5 의 1,012장은 등급을 바꿨다(G100) — 지금부터 쌓이는 숫자가 중요하다. 이 라운드는 ① 지금 무엇이 쌓이고 있는지 확인 ② 모자란 것을 쌓이게 ③ 문항별로 뽑는 스크립트. **플레이 화면 · 규칙은 바꾸지 않는다.**
실행 모델: Opus 5.5 (`claude --model claude-opus-5-5`)

■ 고정 규칙: docs/16 5-1 그대로 · dev(3001 · quizweb_dev)에서 만들고 확인 · 스키마는 **추가만**(칸 · 표 · 색인 — 있는 것을 바꾸거나 지우지 않는다 · 마이그레이션 파일로) · 실 서버 반영은 찬종이 ops 메뉴로 · 보고 `ai-out/R103.txt` · 13 · README · 커밋 · push.

■ 1. 먼저 조사(보고 1절 — 표로): 일반 상식 퀴즈 한 문항이 나갈 때 DB 에 무엇이 남는가. 아래 칸마다 "남는다(어느 표 · 칸) / 안 남는다 / 일부만".
  | 알고 싶은 것 | 뜻 |
  |---|---|
  | 노출 | 그 문항이 어느 판 · 몇 명 방 · 어떤 난이도 설정에서 나갔나 |
  | 사람별 결과 | 방의 각 사람이 맞혔나 · 틀린 답을 몇 번 쳤나 · 아무것도 안 쳤나 |
  | 맞힌 시각 | 문항이 보인 뒤 각 사람이 맞히기까지 걸린 ms |
  | 힌트 단계 | 각 사람이 맞힌 순간 화면에 무엇이 나와 있었나 — 힌트 전 / 일반 힌트 뒤 / 초성 힌트 뒤 |
  | 틀린 답 글자 | 사람들이 친 오답(다른 표기 · 오타 · 흔한 헷갈림을 찾는 데 쓴다 — R102 의 near-miss 기록이 있으면 그것) |
  | 문항 판 | 그때 문항 글이 어떤 판이었나(카드를 다시 쓰면 앞뒤를 가르려고 — `updated_at` 이나 글의 해시) |
  | 평가 | 정답 공개 뒤 👍 · 👎(있는 그대로 · R068) |
  · 사람끼리 한 판과 봇 · 혼자 시험한 판을 가를 수 있는지도(가르는 칸이 없으면 추가).

■ 2. 모자란 것을 쌓이게: 1 에서 "안 남는다 · 일부만"인 것을 **이벤트 한 줄씩**(문항 × 사람) 남기게 한다. 원칙: 판이 느려지지 않게(쓰기는 문항이 끝날 때 한 번에) · 쓰기 실패가 판을 멈추지 않게(try · 로그만) · 개인 식별은 지금 쓰는 사용자 id 그대로(새 개인정보 없음). 미니게임 · 이모지 · 초성 등 다른 놀이는 이번에 넣지 않는다(같은 표에 놀이 종류 칸만 두어 나중에 넣을 수 있게).

■ 3. 뽑는 스크립트 `scripts/question-stats.mjs`(DB 읽기만): 문항별 → `data/stats/question-stats.json` + 터미널에 요약.
  · 문항마다: 노출 수(사람 판만) · 방 정답률(누군가 맞힌 비율) · 사람 정답률 · 힌트 전 정답 비율 / 일반 힌트 뒤 / 초성 뒤 / 끝내 못 맞힘 · 가장 빠른 정답 중앙값(초) · 흔한 오답 다섯 · 👍 · 👎 · 지금 등급.
  · `--since 2026-11-17`(카드 다시 쓴 뒤만 — 기본값) · `--min 3`(노출 3번 이상만).
  · 요약: 등급별 평균 방 정답률 · 노출 3번 이상 문항 수 · **등급과 어긋난 문항 목록**(docs/19 §2 의 띠 — 1: 90%↑ · 2: 70~90 · 3: 45~70 · 4: 20~45 · 5: 20↓ — 에서 두 칸 이상 벗어난 것).
  · 지금 쌓인 것으로 한 번 돌려 숫자를 보고에(적어도 좋다 — 노출 3번 이상인 문항이 몇이나 되는지가 궁금하다).

■ 4. 하지 않는 것: 통계 화면 · 등급 자동 고침 · 플레이 규칙 변경 · 실 DB 직접 쓰기(마이그레이션은 dev 에 적용하고, 실 서버는 찬종이 서버를 바꿀 때 같이 적용되게 — 지금 쓰는 방식 그대로).
