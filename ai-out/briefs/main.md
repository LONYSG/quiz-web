■ 1. 답 반응 속도 — ★ **고치기 전에 재고 까닭부터**(찬종 규칙: 원인을 재서 설명한 뒤 고친다 · 덧대는 보정 층 금지)
  설계가 코드를 읽어 본 것(확인용 · 믿지 말고 직접 잴 것): 서버 `solo.answer` → `soloAnswer` 는 동기 판정 후 곧바로 `solo.wrong` / `resolve` · 화면 `send()` 는 보내고 곧바로 입력칸을 비움 · `solo.wrong` 을 받으면 흔들기 360ms. 코드상 기다리는 곳이 안 보인다 → 늦음은 **그 사이 어딘가**다.
  1-1. 재기: 보내기 누름 → 서버 도착 → 판정 끝 → 화면 도착(`solo.wrong` · `solo.result`) → 화면에 반영(흔들림 · 소리 · 정답 칸)까지를 **구간별 ms** 로. 세 곳에서 각 20번 이상: ① dev 로컬(localhost:3001) ② 실 서버 로컬(localhost:3000) ③ 실 사이트 바깥 주소(quizdojang.com · 터널 거침 — 이 PC 에서 회사 망 때문에 안 되면 그렇게 적는다). 봇(소켓) 숫자 + 브라우저(개발자 도구 Performance · 화면 반영까지) 숫자 둘 다.
  1-2. 의심 목록(설계 생각 · 하나씩 지우며 확인): (a) 웹소켓이 아니라 폴링으로 떨어져 있다(터널 · 프록시) (b) 서버 이벤트 루프가 다른 일로 막힌다(같은 때의 DB 쓰기 `fire(...)` · 로그 · 다른 방) (c) 화면이 매 프레임 큰 컴포넌트(`SoloScreen` 660줄)를 다시 그려서 입력 · 반영이 밀린다(타이머 `now` 갱신) (d) 효과음을 그때 불러와서 소리가 늦게 난다(그래서 늦게 느껴짐) (e) 정답 · 오답 판정이 아니라 **다음 화면으로 넘어가는 연출**(해설 · 점 카운트)이 길어서 늦게 느껴짐 — 찬종이 말한 "틀리면 바로 새 답"은 오답 쪽이다.
  1-3. 보고에 표: 구간 × 곳(①②③) · 중간값 · 가장 늦은 값 + **까닭 한두 줄**. 그다음 뿌리에서 고친다. 목표: 오답 → 입력칸이 다시 칠 수 있게 되기까지 **사람이 늦다고 느끼지 않을 만큼**(보내기부터 흔들림 시작까지 100ms 안 · 로컬 기준) · 정답도 같은 수준. 같이 하기(방) 쪽에도 같은 까닭이 있으면 보고에 적는다(고치는 것은 혼자 하기만 · 방은 다음 판).
  1-4. 하는 김에: 혼자 하기의 다른 동작(시작 · 아이템 · 다음 문제 · 그만하기 · 끝 화면)도 같은 방법으로 재서 표에 한 줄씩. 찬종 원칙 "대단히 복잡한 작업 아닌 이상 로딩이 걸리면 안 된다" — 눈에 띄게 기다리는 곳이 있으면 같이 고친다.

■ 2. 시작 카운트다운
  · [시작]을 누르면 **곧바로** 3 · 2 · 1 카운트다운이 뜨고, 끝나면 첫 문제가 나온다. 시작 준비(아이템 값 빼기 · 판 기록 · 문제 고르기)는 카운트다운 뒤에서 함께 돈다 — 빈 화면 · 로딩 표시가 보이면 안 된다.
  · 문제 시간(타이머)은 **문제가 화면에 보인 뒤부터** 센다(카운트다운 중에 첫 문제 시간이 깎이지 않게 — 서버의 `shownAt` · `endsAt` 기준을 그에 맞게).
  · 모양 · 소리는 같이 하기의 카운트다운(`client/src/Countdown.tsx`)과 같은 것을 쓴다(새로 짓지 않는다).
  · 준비가 실패하면(포인트 모자람 등) 카운트다운을 멈추고 지금처럼 사람 말 안내.
